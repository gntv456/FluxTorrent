## 总根因（一句话）

**上传量（你的做种上传）100% 由客户端自报，全仓没有任何「下载方→上传方」的交叉验证；「是否在种」仅靠 `left==0 && port>0 && conn!=Some(0)` 判定，而 `conn` 只是 TCP 回连（非 BT 握手），且大 swarm 中绝大多数 peer 根本没被探测（`conn=None` 直接放行）。** 这两个点是假种与刷量能成立的总根。

| 级别 | 漏洞 | 直接影响 |
|---|---|---|
| **P0** | 幽灵做种拿做种收益（conn 探测可被 TCP 监听绕过 / 大 swarm 不探测） | 刷 spark 做种收益、seeders 虚高 |

## P0-1 幽灵做种 / 假种拿做种收益（最高危）

**证据**
- `apps/worker/src/jobs/process_event.rs:108`
  ```rust
  let seeding = ev.left == 0 && ev.port > 0 && ev.conn != Some(0);
  ```
- `apps/tracker/src/main.rs:210-234`：回连探测只是 **TCP connect（3s 超时）**，不是 BT 握手。
- `apps/tracker/src/peers/table.rs:222-268` `sample_probes`：**每 5 分钟只抽 50 个 peer**；`out.len() > n` 时才轮转截断，意味着大 swarm 里排名靠后的未测 peer 在 `ceil(total/50)` 轮内才轮到，期间 `conn` 恒为 `None`（未测）。

**利用**
1. 起一个监听 socket（`nc -l -p 6881` 或任意服务）。
2. 对每个目标种子发 `GET /announce/{passkey}?info_hash=...&left=0&port=6881&uploaded=<任意>&peer_id=...`。
3. 判定：`left=0` ✓；`port>0` ✓；`conn` 要么 TCP 可达→`1`（放行），要么根本没被抽中→`None`（放行）。**只要开着一个端口就过**。
4. 后果：`snatches.seeding=true`、`torrents.seeders+1`、`seeded_seconds` 持续累计，`seeding_reward`（`apps/worker/src/jobs/seeding.rs`）每小时按「濒危/独苗」最高稀有度加成发 spark。

**放大**：对成百上千种子各发一次 announce，即可成为每颗的「独家做种」，逐颗吃满稀有度加成 → 做种收益可被大规模刷。即便 `sweep_stale_peers` 会在停报后清标记，只要持续发 announce 就一直领。

  已实现，见「BT 握手验证」章节（68 字节 handshake + info_hash 校验；
  piece 级抽查未做，局限已如实记录）。
- ~~大 swarm 兜底：探测配额按规模线性扩容~~：已实现
  `clamp(len/8, 50, 400)` + `JoinSet` 并发。

## P1-3 伪造 completed（完成度注水）

**证据**
- `apps/worker/src/jobs/process_event.rs:112`
  ```rust
  let completed = ev.event == "completed" && ev.down > 0;
  ```
  只需 `down>0`（1 字节即可），且**不要求 `left==0`**。

**利用**
发 `event=completed&downloaded=1&left=<任意>` → `completed_at` 立即写入，`torrents.times_completed++`、个人「已完成」计数 +1。可刷完成榜、满足「完成 N 颗」类任务/考核；且 `left>0` 也能标记完成，与真实语义不符。

**说明**：H&R 快照创建要求 `downloaded > size×10.4%`（`apps/worker/src/jobs/hr.rs:64`），故 1 字节完成不会触发 H&R 义务——本漏洞主要是**统计/榜单/任务考核诚信**问题，非经济。

**修复**：`completed` 必须 `event=="completed" && ev.down > 0 && ev.left == 0`；并建议要求 `down >= size × 比例`（与 H&R buffer 同口径），杜绝「1 字节完成」。

## P1-4 计数器回退地板过宽（8GiB）可搬动基线

**证据**
- `apps/worker/src/jobs/ledger_guard.rs:45` `COUNTER_RESET_FLOOR = 8 * 1024^3`。
- `:51-76`：下降幅度 ≤8GiB 被视为「正常客户端重置」，锚点（`anchor_up/down`）**跟随下移**。

**利用**：反复把累计 `uploaded` 下调 ≤8GiB（锚点跟着降），再上调吃满速率钳额度，循环把基线往下搬并反复提取额度。

**修复**：任何下降都不更新锚点（credit 直接按 0 计），**仅当上报值严格为 0 才允许锚点归零**；或把地板降到 256MiB 量级。

## P2-6 同用户多发 peer_id 污染实时 seeders

**证据**：announce 用 `peer_id` 入 swarm 表（`apps/tracker/.../announce.rs`），实时 `seeders` 来自 peer 表 count；但权威 `torrents.seeders` 来自 `snatches`（按 `user,torrent` 去重，`apps/worker/src/jobs/announce_main.rs:215-223`）。

**修复**：实时 seeders 也按 `(user,torrent)` 去重，或显式标注「独立用户/IP」。

## P2-7 passkey 内嵌与泄露横向影响

`.torrent` 内置 passkey；泄露后被他人拿来 announce 即「以你身份」刷上传/下载。虽不直接给泄露者比例，但可用于**陷害**（刷下载触发 H&R 禁下载）。属已知 PT 风险。

**修复**：passkey 一键轮换；异常 IP/客户端突变告警（现有 `cheat_events` 框架可接）。

## 交叉上报（P0-2 治本，2026-10-07 已实现）

上传量从「100% 上报者自报」改为「**以 leecher 佐证为上界**」。这是本轮
最大的结构性改动，Gazelle/OPS 业界同款口径。

### 数据流
```
leecher announce ──?xreport=<peer_id_hex>:<bytes>──▶ tracker
   （声明「本轮从该 peer 下载 N 字节」，可多段/逗号分隔）
        │ tracker 侧校验（内存 peer 表，零 DB 开销）：
        │   目标必须是本 swarm「存活 + 在做种 + port>0」的真实 peer
        │   且不能是 leecher 自己（拒绝自报自下载）
        ▼
   flux:xreport 流（独立流，不与 announce 混流）
        ▼
   worker consume_xreport → upload_corroborated(uploader, torrent, bytes)
        （两层幂等：xreport_seen 按流 entry id 去重 + 按维度单调累加）
        ▼
   计费 process_event：credited upload 封顶在
        「已佐证总量 upload_corroborated.bytes − 已入账 snatches.uploaded」
```

### 关键实现点
- **校验放在 tracker**（`peers/table.rs::corroboration_target`）：拒绝
  凭空捏造的 peer_id、指向 leecher/非做种 peer、自报自下载、跨 swarm 解析。
- **封顶而非直接采信**（`process_event.rs`）：`credit_up` 被裁到佐证上界，
  超出部分不入账并记 `cheat_events`（agent `corr:{torrent_id}`，reason 固定
  文案聚合）。`corr:` 已加入 `seeding.rs` 的作弊黑名单——屡次自报超限的账号
  连做种收益一起停发。
- **向后兼容**：客户端还没接 `xreport` 时 `upload_corroborated` 无该用户行，
  维持原自报口径（不会全站瞬间零计费）。等客户端接入后自动收紧为佐证上界。
- **反串通**：单次佐证量 > 10 GiB 判物理不可能，丢弃该笔并记
  `xreport:absurd` 留痕（带 leecher IP，供追查串通）。

### 客户端接入约定
```
GET /announce/{passkey}?info_hash=...&peer_id=...&left=0&uploaded=...&downloaded=...
    &xreport=<peer_id_hex>:<bytes>[&xreport=...]
```
`peer_id_hex` 为**原始 20 字节 peer_id 的小写 hex**（与 announce 响应里
下发的 peer_id 同口径）。同一参数可重复出现，也可用逗号分隔多条。
注意：BEP3 本身没有这个字段，标准 BT 客户端不会自动上报——需要站方客户端
（qBittorrent 补丁版 / 自研客户端）主动携带，才会把上传量切到「佐证口径」。

### 仍存的局限（如实说明）
- 佐证量本身仍来自 leecher 自报，只是**换了个利益方**（leecher 刷上传量对
  自己无直接好处，除非与上传者串通）。已用「>10 GiB 物理不可能」+ 自证
  过滤挡掉低成本串通，但无法杜绝精心构造的串通。
- 这是行业当前能做到的最强手段（无第三方公证时）；要再进一步只能引入
  BT piece 级抽查或第三方见证节点。

## BT 握手验证（P0-1 治本，2026-10-07 已实现）

`conn` 探测此前只做 **TCP 三手**——目标端口有进程 listen 就算「可达」。
于是 `nc -l -p 6881` 这类裸监听即可伪装成做种客户端，TCP 层根本分不出
真假。这是幽灵做种链路上最后一个缺口（端口 >0、`conn` 探测也过不了这关）。

### 手段
`apps/tracker/src/peers/bt_probe.rs`：分三阶段验证，全程同一 timeout 预算内。

```
① 握手    tracker ──TCP connect──▶ peer
          ──68B handshake (pstr"BitTorrent protocol"|reserved8|ih20|pid20)──▶
          ◀──68B handshake 响应（校验 pstrlen=19 且 info_hash 匹配）──
② 有数据  tracker ──interested(msg id 2)──▶ peer
          ◀──bitfield(msg id 5)── 校验位图至少有一位为「我有」
③ 真数据  tracker ──request(index=0, begin=0, len=piece_len)──▶ peer
          ◀──piece(msg id 7)──▶ 算 SHA-1 与 info.pieces[0] 比对
```
- 真做种客户端必然应答握手、被 interested 触发回 bitfield（必然非空）、
  且被 request 后返回**磁盘上的真实数据**——SHA-1 必然匹配；
- 裸 TCP 监听过不了 ①；只回握手不供数据的过不了 ②；
  **临时伪造/注水数据过不了 ③**（SHA-1 对不上）——这是「声称有数据」与
  「真有数据」的分界线；
- 拿到 piece 但哈希不符 = **实锤伪造数据**，直接判 `CONN_DEAD`。
  注意与 `None`（没验成：对方不给/超时/畸形）的区别——后者**不判作弊**，
  只是不算通过抽查，避免误杀加密客户端等合法场景。

### 成本控制（重要）
piece 级抽查要真传数据（每 peer 一个 piece，16 KiB~4 MiB），全量跑会
打爆 tracker 出站带宽。因此：
- `piece_cache`：`piece length` + 首个哈希按 info_hash 缓存 10 分钟
  （数据来自 `torrent_files.raw` 的 bencode——`torrents` 表无此列，
  故新增 `torrent_parse` 最小 bencode 解析器，只认 `info` 子 dict）；
- **小预算抽样**：`FLUX_TRACKER_PIECE_PROBE`（默认 8，0=关闭）限制每轮
  做 piece 校验的 peer 数，且只对「① ② 已通过」的 peer 做——廉价阶段
  先筛一遍，不把带宽浪费在明显不可达的 peer 上。默认 8 × 4 MiB ≈
  32 MB/轮/5min，可控。

### 实现要点
- 探测 peer_id 自报 `"FLUXPROBE000"`，站方可在 peer 端日志里识别探测流量。
- **info_hash 校验不可省**：只验「收到 68 字节」会放过回显型伪服务端。
- 复杂度 `O(1)`：只抽查第 0 号 piece，验证一个即可判定真伪，不做全量。
- 单测 6（bencode 解析，含**真实种子字节回归**）+ 握手/bitfield 5 +
  piece 抽查 3（哈希匹配 / 哈希不符 / 未声明 piece 0 → None）。
- 细节坑：`PSTR` 存 19 字节（长度前缀另写）；BEP3 peer message 帧头
  长度字段固定 4 字节。

判定沿用 connectable 三态：`CONN_OK` = 握手应答且 info_hash 匹配；
其余（超时/拒绝/pstrlen 不符/info_hash 不匹配）= `CONN_DEAD`（视为不可信）；
未抽中 = `CONN_UNTESTED`。

### 实现要点
- 探测 peer_id 自报 `"FLUXPROBE000"`（12 字节 + 8 填充 = 20 字节），站方可在
  peer 端日志里识别探测流量、把它与真实下载流量区分开。
- **info_hash 校验不可省**：只验「收到 68 字节」会放过回显型伪服务端；比对
  info_hash 才能防串台/伪造。单测 `response_validation_matches_and_mismatches`
  覆盖「匹配通过 / info_hash 不匹配拒绝 / pstrlen 不符拒绝」三条分支。
- 复用既有的抽样预算（`clamp(len/8, 50, 400)`）与 `JoinSet` 并发框架，仅替换
  探测函数体；纯探测不阻断任何 announce 响应路径。
- 细节坑：`PSTR` 只能存 19 字节的 `"BitTorrent protocol"`，长度前缀 19 单独
  写在首字节。早期把 `"\x13BitTorrent protocol"`（20 字节，含前缀）整段
  当数据再算一次长度，会构造出 1+20 的越界握手（68 字节装不下）——单测
  当场抓到 3 个 FAILED，改成显式 `PSTR_LEN=19` 后全绿。
- 测试覆盖：5 个纯函数单测（握手布局/peer_id 长度/hex 往返/非法 hex 拒绝/
  响应校验三分支）+ **4 个真实 TCP 集成测试**（起真 listener 验证：真 BT
  握手应答→通过、裸监听不回应→拒、info_hash 造假→拒、非 BT 垃圾应答→拒）。

### 局限（如实说明）
- 哈希匹配证明「对方能交付与 info.pieces 一致的数据」，已是很强的证据。
  但**仍非绝对**：能正确应答 BT 协议并提供合法 piece 的攻击者，理论上可
  用「按需从别处拉数据转发」的方式伪装做种者（relay 挂种）。这需要同时
  掌握真实数据 + 实现 BT 协议，成本远高于收益，属可接受残余风险。
- piece 抽查是**抽样**执行（默认每轮 8 个），不是全量覆盖——带宽约束
  下的必然取舍。可通过 `FLUX_TRACKER_PIECE_PROBE` 调高。

### ⚠️ 通用 PT 站点适配：connectable 第四档 SUSPECT（2026-10-08 补做）

**这是对本节方案的一处重要修正。** 原实现把三类性质完全不同的情况都压成
同一个 `CONN_DEAD(0)`：

| 实际情况 | 原判定 | 通用站是否该罚 |
|---|---|---|
| 端口不通 / 裸监听占位 | DEAD | ✅ 该罚 |
| qBittorrent「仅加密连接」/ MSE-PE | DEAD | ❌ **误伤** |
| peer 白名单限定 / CGNAT / 防火墙 | DEAD | ❌ **误伤** |

**私有站与通用站的本质差异**：私有站客户端基线已知，可以公告要求用户关闭
加密连接；**通用站必须假设用户群里有各种客户端偏好**。把「骗钱的」和
「用加密客户端的好用户」合并成同一个值之后，**事后再也分不出这两种人**，
补救无从下手。

**修正方案**：引入第四档 `-2 = SUSPECT`（无法验证），`probe_one` 改为分档：

```
① 纯 TCP 可达   → 不通         → DEAD    （实锤不可信，唯一无争议的否决条件）
② BT 握手+bitfield → 不响应   → SUSPECT （无法验证，不判不可信）
③ piece SHA-1（抽样）→ 哈希不符 → DEAD （实锤伪造数据）
   通过 / 未验成              → OK
```

**消费口径（重要：本方案不改变任何用户的收益）**
- 只有 `0(DEAD)` 阻断收益与惩罚；`-2(SUSPECT)` 与 `-1(UNTESTED)` **同样放行**。
- 已验算确认现有 SQL `NOT COALESCE(connectable = 0, false)` 天然满足该语义
  （`-2 ≠ 0` → 放行），零行为回归；已在 4 个消费点加注释固化口径，防止后人
  误改成 `IN (0, -2)`。
- 与 0308 的 `connectable_gate=off` 同方向：**宁可放过、不可误伤**。

**可观测（管理端）**：新增 `GET /api/v1/admin/conn/dist` 返回四档分布
（`state / 条数 / 涉及用户数`），并在站点工具「无法连接的用户」页顶部以
带提示的四档徽标展示。运营据此判断：
- `-2` 占比高 → 站内多加密客户端/白名单用户，此时收紧口径就是自伤做种供给；
- `0` 占比高 → 确有实锤作弊面，可考虑把 `connectable_gate` 切 hard。

**已知表达力缺口（如实记录）**：外置 Redis 通道仍是 bool（0225 G30-B12 的
既有契约），SUSPECT 在多副本模式下与 DEAD 同为 false，**无法区分**。
单实例（本项目默认部署）不受影响；多副本要精确分档需把 Redis 侧升成
smallint 后再改。

**回归护栏**：`only_dead_blocks_in_billing_predicate` 断言 SUSPECT 永不阻断，
`conn_state_keeps_dead_and_suspect_distinct` 断言两档不可合并，
`set_conn_state_ignores_untested` 断言「未探测」不被写成「已测」。
