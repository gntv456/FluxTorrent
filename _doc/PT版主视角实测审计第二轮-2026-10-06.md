## 一、对外接口面：私有站的命门在这里

### P0-1 `.torrent` 重建把 `private=1` 写错了位置，等于没有私有化【实测】

`apps/api/src/bencode/torrent.rs` 的 `build_download_torrent` 里，`pairs` 来自
**根字典**，而 `pairs.push((b"private", Int(1)))` 就推在根上。BEP27 规定 `private`
必须在 `info` 字典内 ⇒ 客户端一律忽略 ⇒ **DHT/PEX/LTE 照常开启**，
peer 之间互报地址，资源可以在站外互相拿到，tracker 完全看不到。
私有站最基础的「只能经 tracker 拿 peer」没成立。

为什么不能一行改掉：把 `private` 移进 `info` 会改变 info 字典 ⇒ 改变 info_hash ⇒
客户端 announce 的哈希与库里 `torrents.info_hash` 不一致，tracker 直接判「种子未注册」。
正确做法是**发种时就把 `private=1` 规范进 info 再算 info_hash**，老种子按
`private_in_info` 标记走旧路径。这是一次带迁移的口径变更，需站长拍板（见第四节）。

### P0-2 `url-list` / `httpseeds` / `dht_nodes` 原样进客户端【实测 → 已修】

旧代码只 `retain` 掉 `announce`/`announce-list`。上传者在 `.torrent` 里塞一个
HTTP 种子（BEP19 `url-list`），内容就从站外服务器直接下发：
**announce 计量、比率、H&R、免费时段、下载权限全部失真**，且等于把资源发给非会员。
本轮已把 `url-list`/`httpseeds`/`dht_nodes` 一并剥除（三键都在 info 外，不动 info_hash），
并加单测 `bencode::tests::download_rebuild_strips_offtracker_sources` 断言
「剥离后三键消失 + info_hash 不变」。

### P0-3 详情聚合的共享缓存把待审/被拒种泄漏给普通会员【实测 → 已修】

`torrent_http/aggregate.rs`：缓存键只有 `cache:tdetail:v1:{id}:{reveal}`，
而取数用的是**带视角的放宽查询**（`viewer = (uid, class_id>=90)`，管理视角/作者本人
可见 `approval_status IN (0,4)`）。于是版主或作者打开一条待审种后的 30 秒内，
任何普通会员请求同一 id 都命中缓存，拿到标题/描述/文件/NFO——主详情端点的 404 闸门
在这个聚合口子上不成立。
另一半：`assemble()` 里 `let _ = uid;`，`detail.purchased` / `is_owner` 是**第一个访问者**
的状态被复用给后面所有人（A 买过 → B 看到「已购买」；A 是作者 → B 看到作者态控件）。
本轮修法：① 只有 `approval_status = 1` 才写缓存，② 命中时再判一次可见性，
③ `assemble()` 按当前 uid 重算 `is_owner`/`purchased`。

### P0-4 RSS 把匿名上传者的真名发出去【实测 → 已修】

`rss_http.rs` 的 SELECT 直接 `u.username AS owner_name`，没有 `t.anonymous` 判定
（详情页的权威口径是 `CASE WHEN t.anonymous THEN NULL …`）。
任何订阅源轮询器都能把「匿名发种」的人扒出来——PT 站匿名做种/避嫌的基础失效。
已改为同一 CASE 口径。

### P1-5 API 令牌不受「改密 / 踢出所有会话」约束【实测 → 已修】

`openapi_http.rs::require_token` 只查 `revoked_at IS NULL` + 过期 + `u.status < 2`，
**从不读 `token_revocations.nbf`**；而改密、登出所有设备、管理员重置都只写 nbf。
⇒ 账号被盗后受害者点了「退出所有设备」，攻击者手里的令牌还能跑到 180 天。
已在令牌校验 SQL 里加 `t.created_at > COALESCE(nbf, '-inf')`。

### P1-6 其余接口面条目

- 【实测】`GET /admin/users/{id}` 之外，`/compat/nexusphp/user.json` 会把**本人 passkey**
  回给任何 `read` 域令牌持有者（`nexusphp.rs:89`、`ptpp.rs:95`、`recon.rs:170`）：
  一个只读令牌可以换到永久不可撤销的 tracker 身份。撤销令牌救不回已拿到的 passkey。
  ⇒ 建议：`read` 域不含 passkey 字段，取 passkey 需要独立 `credentials` 域。
- 【实测】RSS 认证用**全局 passkey 拼在 URL 路径里**（`rss_http.rs:42-52`），
  没有独立可撤销的 feed key；enclosure 再拼一次 passkey。
  而访问日志用 `%U`（含路径，`main.rs:232`）、nginx 样例用默认 combined（含 query）
  ⇒ passkey 会进网关/容器日志。⇒ 建议：独立 `rss_key`（可单独撤销）+ 日志脱敏。
- 【实测】客户端 IP 全链路可伪造：`apps/web/app/api/[...path]/route.ts:34-42` 把
  攻击者可控的 `x-real-ip`/XFF 首值转发，api 侧 `auth_infra.rs:63-79` 取**最左**值
  ⇒ `TRUST_PROXY=1` 时 `ip_bans` 与登录 5/min 限流可逐请求绕过。
- 【实测】限流只覆盖 5 个端点（登录×2/注册/邮箱验证/申请）；搜索、magnet、files、
  snatches、peers、评论、附件、NP 别名全部无限流；且 compat/download-key/openapi 的
  令牌桶在 Redis 故障时 `unwrap_or(0)` **fail-open**（与 `limit_passkey` 的 fail-close 相反）。
- 【实测】付费下载先扣款后建文件（`charge.rs:149` → `build_torrent_bytes` 失败）：
  被停下载/挂起的账号**扣了魔力拿不到种子**，且 `torrent_purchases` 已落行，
  之后重下免费但仍被拦。`download_keys.rs:111` 只校验 `expires_at`，不校验 `status<2`。
- 【实测】附件是「登录即可按 sha256 取」，无种子归属/过审判定；上传响应回
  `deduplicated` 字段 ⇒ 全站的**文件存在性 oracle**（「这站里有没有这个文件」）。
- 【线报】未过审种子的 `/files`、`/snatches`、`/peers`、`/comments` 子资源对任意登录用户
  可读（主详情 404、子资源 200）；`details.php?id=` 无判定即重定向，是存在性探针。
  本轮已修聚合口，**子资源口子仍需逐口收**（见第四节）。

## 二、经济玩法防刷

### P0-7 商店同键重放可白拿 99 张卡【实测 → 已修】

`economy_http/shop.rs` 拿到 `spend_spark` 的 `SpendOutcome` 后写 `let _ = outcome;`
（而 `spend.rs:184-189` 自己的文档就把这个枚举写成「重放铸造类缺陷的根因」）。
攻击序列：同一 `idempotency_key` 先 `qty=1` 买 `temp_invite`（付 5000）；
再用同键 `qty=100` 买一次 ⇒ `spend_spark` 返回 `Replayed`（**不扣款、不报错**），
而卡牌分支会插 `idem:2..idem:100` 这些**新订单行**，下面的 CAS 循环按
`= $2 OR LIKE '$2:%'` 把它们全部当作「未发效果」逐行发放
⇒ 0 火花拿 99 张券，券可兑 30 天邀请 ⇒ 批量开小号。
已修：`Replayed` 直接按原单返回，不再插行、不再发效果。

### P0-8 借贷是无抵押火花水龙头，且坏账永远收不回【实测（结构）】

`loans_apply.rs:74-94` 把 `bank_loans.amount` 作为**新火花流水**入账，无对冲分录、
无幂等键（`loan:{uid}:{id}` 每次新 id）；额度门槛只有
`max_loan_amount = hourly*loan_ratio + loan_constant`（`loans.rs:252-260`），
其中 `bank_loan_ratio_constant` 默认 1000 ⇒ **零资产账号也有 1000 的免费额度**。
更糟的是：`bank_overdue_penalty` 把严重逾期行置为 `status='defaulted'`
（`bank_jobs/loan.rs:77-81`），而自动扣款 `bank_auto_deduct` 只选
`status='active'`（`:95-98`）、计息同理（`loan.rs:15`）
⇒ **一旦进入 defaulted，既不涨息也永不追偿**，违约等于免单。
本轮已修：自动扣款候选改为 `status IN ('active','defaulted')`。
未修（需口径）：贷款无对冲/无抵押、`bank_settings` 数值解析 `.parse().ok()` **无 clamp**
（站长一个笔误就把上限变成无限）、以及「同一身份反复借贷」的上限。

### P0-9 银行利息凭空造，且没有总预算【实测（结构）】

固定/活期利息都是新写火花流水（`bank_jobs/deposit.rs:102-120`、`:22-34` 复利计入
`bank_demand_accounts.balance`，再由 `loans.rs:235` 1:1 兑回火花）。
没有任何「Σ利息 ≤ 某池子」的约束；对照：抽卡有 `ratio_worst > 1.0 → 409` 运行时闸
（`gacha_http/draw.rs:50-62`）与奖池 `ev_strictly_below` 整数闸（`games/jgg.rs:181-200`），
**银行两者皆无**。站长在 `_doc/PT游戏-*` 定的「EV 必须 < 1」口径没有覆盖到银行。
本轮已修一条最扎手的：**被封/已注销账号照旧计息**（`deposit.rs` 无 `users.status` join，
已补 `status < 2`）。总预算需站长给数（见第四节）。

### P1-10 幂等与竞态余账

- 【线报】`spark_ledger` 唯一索引是 `(idempotency_key, created_at)`（分区表被迫带分区键，
  `0001_init.sql:221`），实际去重靠 `0080_audit_fix_p0.sql` 的 ±1s/365 天窗口触发器
  ⇒ **一年前的键可重放**；且 `maintain.rs` 按月 DETACH/DROP 分区后，
  应用层「`WHERE NOT EXISTS` 全历史判重」也会失明 ⇒
  `achievement:{code}:{uid}`、`class_promo:{uid}:{class}`、`forum-lottery-win:*`
  这类「一生一次」发放可能被二次兑付。
- 【线报】无幂等键的花钱口：`bank.rs:61`、`loans.rs:122/199`、`medal_buy.rs:81`、
  `medal_gift.rs:68`、`tip.rs:71`（无条件 `Uuid::new_v4()`）、`funding_contribute.rs:110`
  ⇒ 客户端重试/双击即双花双发。
- 【线报】`item_use.rs:267-273` 在 `tx.commit()` **之后**才 `apply_item_effect`
  ⇒ 中途失败会烧掉 `qty` 件物品却只发部分效果，且幂等唯一键挡住重试（不可恢复）。
- 【线报】抽卡幂等键 `gacha:draw:X` **不带 uid** ⇒ 任何人可预注册别人的键，永久否决其抽取。
- 【线报】`shop_effects.rs:53/61`、`increment_bulk.rs:128` 的 `gb * 1024^3` 无上限
  ⇒ 极大值回绕成负上传量。
- 【实测，本轮已修】`user_detail.rs` 的管理员发放键含 `now().timestamp()`/uuid
  ⇒ 双击双发（上一批只补了「走流水」，没补幂等）。

## 三、社区治理：问题最集中的一轴

### P0-11 「禁言」在论坛侧完全空转【实测 → 已修】

论坛/漂流瓶读的是 `users.forumpost`（`forum_perm.rs:69-77`、`shoutbox.rs:60-68`），
而**全仓没有任何一处写 `forumpost`**（只有 0047 的 ALTER）；后台「禁言」写的是
`users.status = 1`，但鉴权层只拦 `status >= 2`（`auth_infra.rs:255`）
⇒ 被"禁言"的人照发帖、照回帖、照刷漂流瓶、照打赏、照投票、照编辑。
版主最常用的处分按钮是个装饰品。
本轮已修：`/admin/users/status` 与批量改状态同时写
`forumpost = (status <> 1)`；并把禁言判定抽成 `community_http::is_muted()`，
接进**种子评论**与**站短**两条此前完全没闸的通道。

### P0-12 站短无人治理，且双方删除即销毁证据【实测】

- 管理侧对 `messages` 唯一的 SQL 是 `count(*)`（`staff_http/stats.rs:28`）；
  `/messages/staff` 只覆盖 staff↔staff 流量（`message.rs:88-107`）
  ⇒ **用户间骚扰私信版主看不见**。
- 举报对象白名单只有 `torrent|comment|user|subtitle|forum`（`http/reports_http.rs:29`）
  ⇒ **私信不可举报**。
- 收发双方各自 `DELETE` 是物理删除（`message_box.rs:84-91`）
  ⇒ 受害者一删，证据同时消失，第二天对方可以说「查无此条」。

### P1-13 其余社区条目（【线报】为主，逐条待复验）

- `forum_access` 在 `class_id >= 90` 直接短路 `can_mod=true`，`forum_mods` 只对 <90 生效
  ⇒ 论坛版主(92)可编辑/删除/置顶/移动**任意区**（含站务区、管理组内部区），
  「这块版面无权管」的边界不存在。
- 敏感词只挡论坛创建/回帖/编辑（`topic_create.rs:73`、`post_write.rs:34`、
  `post_edit.rs:31`）；站短、漂流瓶、种子评论、打赏备注全不查。
- 编辑是万能后门：`post_edit.rs:38-42` 只判 `can_mod || author`，
  不判 `can_write`、不过 flood、不看版块 `minclasswrite`。
- 无编辑历史、无墓碑、无恢复、无「最近删除」视图（`DELETE FROM posts/topics` 物理删）。
- **没有任何版主巡检队列**：`/forums/feed` 是个人关注流，不是新帖流。
- flood 阈值全部硬编码（论坛 10s / 站短 60s / 漂流瓶 10s），不读 `site_settings`，
  且站短与「联系站长」共用同一 `message_flood` 行（发过私信就 60s 内联系不了 staff）。
- 受保护版块两处漏：掩码用**页内相对下标**（`post_read.rs:127-133`，每页首层都漏），
  论坛搜索直接回 `left(body_text, 90)` 摘要（`forums.rs:66-71`）。
- 通知偏好面板 13 个键里只有 4 个有读者；`topic_favorites`（收藏主题）只写不读，
  回复通知走的是 `follows` 而非收藏 ⇒ 「收藏」既不提醒也列不出来。
- 投票/抽奖/悬赏没有管理侧撤销面（`poll_votes` 无删除口、抽奖只能删整个主题、
  悬赏发奖只有楼主，`topic_bounty_awards` 写了没人读）。
- 假开关一批：`enable_forum`、`enable_shoutbox`、`topics_per_page_default`、
  `posts_per_page_default`、`pm_per_page_default`、`max_pm_per_page`、`postsperpage`、
  `topicsperpage`、`protected_forum`、`reportemail`、`forum_video_upload`、
  以及 `forums.min_class`（后台表单能改，读侧用的是 `minclassread/write/create`）。
- `warned_until` 不挡任何事，且到期清理依赖人工点 `/admin/docleanup`——没有到期 job。

## 四、需要站长拍板的四个口径

1. **`private=1` 进 info 的迁移**：新发种规范注入并重算 info_hash，老种子按标记走旧路径。
   代价是全站种子文件的对外哈希会变（新种子之间一致）。不做则私有站名不副实。
2. **银行总预算**：`_doc/PT游戏-*` 的「EV < 1」是否覆盖银行利息与贷款发放？
   给一个「每周期全站最多造多少火花」的硬闸（抽卡已有同类闸）。
3. **私信治理边界**：是否允许 staff 读取用户间私信（合规/隐私口径）？
   至少要做：私信可举报 + 举报后冻结相关会话 + 删除改墓碑。
4. **版主权限粒度**：`forum_mods` 是否真的按版块收口（92 不再是全站 mod）？
   `torrent.manage` 是否拆 review/edit/delete？分类归属表要不要建？

**闸门抓到我自己引入的回归**（记形不记码）：`token_revocations.nbf` 是 **bigint
（unix 秒）**而不是 `timestamptz`，我第一版把 `t.created_at > COALESCE(nbf, '-infinity'::timestamptz)`
写进 SQL——prepare 期类型不符，会让**所有 API 令牌请求 500**。J6 首跑即红，
改成 `to_timestamp(COALESCE(nbf,0))` 后才绿。教训：**给既有列加比较条件前，
