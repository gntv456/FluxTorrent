# 导航挂载与模块开关联动

> 承接 `_doc/前端队伍页面与浏览器验证.md`
> 页面做完了但**导航里没有入口**——玩家只能靠知道 URL 才能访问。本文补上这"最后一公里"，
> 并修正了一处既有的"快照 vs 运行时权威"不一致。

---

## 一、先调研，结果一次查出三个问题

### 问题 1：`contests` 已经是一套现成的"周期 + 状态"机制

```sql
contests (id, title, descr, starts_at, ends_at, is_active)
contest_entries (contest_id, ...)
```

**这和我的 `social_season` 语义高度重叠**（都是"有起止时间的一段周期"）。
按"先调研再动手"的纪律，这提示**赛季不该新建机制，而应基于 `contests` 扩展**
——`social_season` 表目前是空跑状态，后面做赛季时要重新评估它是否多余。

### 问题 2：`menu_items` 挂了也不显示

`menu_items` 是导航配置表（`location` / `label` / `url` / `enabled` / `min_class`），
但当前 `site_settings.nav.custom_enabled = 0` —— **自定义导航没启用**，前台走的是默认导航
（`components/main-menu.tsx` + `layout.tsx` 里硬构造的 `primary` / `groups`）。

所以往 `menu_items` 插记录是无效的，必须改默认导航的构造逻辑。

### 问题 3：站点 profile 的 `modules` 用的是"初始快照"而非"运行时权威"

`/api/v1/site-profile` 返回的 `modules` 直接取自 **`site_type_packs.modules`（JSONB 快照）**：

```rust
"modules": pack.as_ref().map(|p| p.modules.clone()).unwrap_or(json!({})),
```

而项目自己在别处写明（`content_http.rs:636`）：

> `site_type_packs` 只是初始快照，**运行时权威在 `site_settings`**

后果：**站长在后台改了模块开关，导航不会跟着变** —— 因为导航读的是快照。
`textbooks` 正是靠这个字段判断显隐的，所以它也有同样的问题。

## 二、改动

### 2.1 修掉快照 / 权威的不一致（`http.rs::site_profile`）

以快照打底、用 `site_settings.module_*` 覆盖：

```rust
let mut modules = pack.as_ref().map(|p| p.modules.clone()).unwrap_or_else(|| json!({}));
let overrides: Vec<(String, String)> =
    sqlx::query_as("SELECT name, value FROM site_settings WHERE name ~ '^module_'")
        .fetch_all(&state.repo.db).await.map_err(|e| DomainError::Internal(e.into()))?;
if let Some(obj) = modules.as_object_mut() {
    for (name, value) in overrides {
        if let Some(key) = name.strip_prefix("module_") {
            obj.insert(key.to_string(), json!(value == "yes"));
        }
    }
}
```

**这是通用修复**：以后任何新模块（`module_xxx`）都会自动出现在 `profile.modules` 里，
导航只需判断 `profile.modules.xxx === true`，不用各自加查询。

### 2.2 导航挂载（`layout.tsx` 的「发现」组）

沿用仓库里已有的条件展开写法（`textbooksOn` 就是这么做的）：

```tsx
const socialOn = profile.modules.social === true;
...
{ href: "/preserve", label: dict.nav.preserve },
...(socialOn
  ? [
      { href: "/endangered", label: dict.nav.endangered },
      { href: "/teams", label: dict.nav.teams },
    ]
  : []),
```

**位置放在「保种区」之后** —— 保种区 / 濒危预警 / 保种协作 三件套语义相邻，聚在一起最好找。

i18n 补三个语言：`nav.endangered`（濒危预警 / 瀕危預警 / Endangered）、
`nav.teams`（保种协作 / 保種協作 / Seeding crews）。

## 三、验证结果（模块开 / 关两种情况都测）

用 playwright 展开「更多 ▾」并检查导航文本：

| 模块开关 | 濒危预警 | 保种协作 | 期望 |
|---|---|---|---|
| `module_social = no` | ❌ 不出现 | ❌ 不出现 | ✅ 一致 |
| `module_social = yes` | ✅ 出现 | ✅ 出现 | ✅ 一致 |

- 改开关后**页面即时生效**（无缓存问题），测试后已还原为 `no`
- 浏览器控制台 `errors=0`
- 截图：`_shot_nav.png`（可在「发现」组看到两项紧跟在「保种区」之后）

### 测试中踩的一个小坑

`getByRole('button', { name: /更多/ })` **匹配到两个按钮** —— 导航的「更多 ▾」和趣味盒的
「▾ 更多 (1)」，触发 playwright 的 strict mode 报错。改用类名精确定位：
`page.locator('button.mainmenu-link', { hasText: '更多' })`。

### 下一步建议

做赛季之前**先定一件事**：赛季是复用 `contests`（现成的周期 + 参赛机制），
还是在 `social_season` 上独立实现？前者能省掉一整套周期管理，但要看 `contest_entries`
的语义能不能承载"贡献排名"。这个决定没做之前不宜动工——否则容易做出第二个半成品。
