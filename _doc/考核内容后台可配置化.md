# 考核内容与方式的后台可配置化

> 承接 `_doc/新人考核现状与同类项目对比.md`
> 你的判断是对的：**考核内容和考核方式之前只有一半能在后台配**。本文补齐另一半，并把新人考核期限从
> 365 天修正为 45 天。

---

## 一、先说结论：入口在哪，以及一个命名坑

| 后台左侧导航 | 实际管理的东西 | 组件 |
|---|---|---|
| **任务配置** | ✅ **考核引擎**（`tasks` 表 CRUD：新人转正考核 / 周期考核 / 普通任务） | `admin-tasks.tsx` |
| 考核配置 | ⚠️ **绩效考核**（jixiao），与新人考核无关 | `admin-exams.tsx` |

**这是个真实的坑**：叫「考核配置」的其实是绩效考核，而真正配考核的地方叫**「任务配置」**。
名字反了，管理组很容易找错地方。（`admin-exams.tsx` 调的是 `/admin/jixiao-types`，跟 `tasks` 无关。）

---

## 二、补齐的缺口：6 个字段此前只能改库

`tasks` 表有 **18 列**，但后台 `TaskReq` 只能提交其中 **12 列**，剩下 6 列**只能靠 SQL 改**：

| 字段 | 作用 | 此前 |
|---|---|---|
| `duration_days` | **考核期限（天）** —— `claimed_at + duration_days` = 截止时间 | ❌ 不可配 |
| `subtitle` | 副标题（列表里展示，如「注册后自动派发…」） | ❌ 不可配 |
| `tier` | 非空 = 累计口径（基线视为 0，直接报现值） | ❌ 不可配 |
| `fee` | 费用 | ❌ 不可配 |
| `quota_total` | 配额 | ❌ 不可配 |
| `sort` | 排序 | ❌ 不可配 |

**这正是「考核内容和方式也要管理配置」的真实缺口** —— 期限配不了，就只能像之前那样直接改库。

### 改动清单

**后端**（`admin_p3_http.rs`）
1. `TaskRow` 加 6 字段
2. `tasks_list` 的 SELECT 补 6 列，排序改为 `ORDER BY sort, id DESC`（让 `sort` 真正生效）
3. `TaskReq` 加 6 个可选项
4. `task_add` 的 INSERT 补字段（`duration_days` 缺省 30、`quota_total` 缺省 200）
5. `task_update` 的 UPDATE 补字段

**前端**（`admin-tasks.tsx`）
1. `TaskRow` 类型 + `EMPTY` 默认值 + `payload` 各补 6 字段
2. **编辑回填**补 6 字段 —— 这步不能省，否则一进编辑页字段就是空的，保存会把 365 覆盖成默认 30
3. 表单加输入框：副标题 / 费用 / 配额 / 排序（通用区），**考核期限 / 累计口径**（考核区，仅 `kind != task` 时显示）
4. 列表加「期限」列，一眼能看到每个考核给了多少天

> `subtitle` / `tier` 采用**直赋**而非 `COALESCE` 保护 —— 后台表单每次都提交完整对象，传 `None` 即清空意图。
> 其余数值字段用 `COALESCE` 保护「不传就不改」。

## 三、顺带修正：新人考核期限 365 天 → 45 天

改法**走后台接口**（不再手工改库），实测：

```
PUT /api/v1/admin/tasks/28  { ..., "duration_days": 45, "subtitle": "新人转正 · 注册后自动派发：做种满 120 小时即转正" }
→ 200 {"ok": true}
```

回读确认：

| 项 | 结果 |
|---|---|
| 期限 | **45 天**（原 365） |
| 副标题 | 写入成功 |
| reward / kind / period / auto_assign | **未被误改**（2000 / onboard / once / true） |
| 用户侧 `/me/exams` 截止时间 | 派发 2026-09-15 → 截止 **2026-10-30** |

**影响面**：已派发的 13+ 名新人的截止时间会从 2027/9/15 提前到 2026/10/30。
这是本次期望的效果（一年期限对「做种 120 小时」几乎没有约束力），但**属于对存量数据的实时生效**——
若站长觉得这批人应保留原期限，需要单独处理（当前 `duration_days` 不是认领时快照）。

## 五、豁免 / 恢复（0105，已实现）

对标 NexusPHP exam-users 的 `avoid` / `recover`。

### 设计：独立标记列，不动 status 枚举

`task_claims.status` 的状态机是 0（进行中）→ 1（完成）/ 2（失败），`task_settle` 只扫 status=0。
如果用 status=3 表示豁免，会打断这个状态机（恢复时还得迁移回 0）。所以改为**独立标记列**：

```sql
ALTER TABLE task_claims ADD COLUMN exempted_at TIMESTAMPTZ;
ALTER TABLE task_claims ADD COLUMN exempted_by BIGINT REFERENCES users(id) ON DELETE SET NULL;
CREATE INDEX idx_task_claims_open ON task_claims (status) WHERE status = 0 AND exempted_at IS NULL;
```

豁免 = 置 `exempted_at`；恢复 = 清空。结算扫描加 `AND exempted_at IS NULL`，
恢复后原记录**自然回到结算流**——增量口径不受豁免期影响（因为基线没动）。

### 接口与前端

| 接口 | 行为 |
|---|---|
| `POST /admin/exam-users/{claim_id}/exempt` | 豁免（仅 `status=0` 且未豁免；CAS 防重复；记录操作人） |
| `POST /admin/exam-users/{claim_id}/recover` | 恢复 |

后台「任务配置 → 考核记录」每行新增「豁免」列与「豁免 / 恢复」按钮（仅进行中的记录可操作）。

### 端到端测试（6/6 通过）

| # | 用例 | 结果 |
|---|---|---|
| 1 | 列表返回 `exempted_at` | ✅ |
| 2 | 豁免 claim 325 | ✅ 200；DB `exempted_at` 非空、`exempted_by=1` |
| 3 | 重复豁免 | ✅ 404（CAS：`AND exempted_at IS NULL`） |
| 4 | 恢复 | ✅ 200；DB 回到 NULL |
| 5 | 对已结算记录豁免 | ✅ 404（`AND status = 0`） |
| 6 | 收尾核对 | ✅ 豁免中的记录数 = 0（完全还原） |

测试脚本：`_exam_exempt_e2e.py`（可重复执行，自还原）。
