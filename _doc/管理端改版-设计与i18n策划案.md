## 3. i18n 机制

### 3.1 DB 驱动文案（59 条导航）的处理

导航 label/tip 存在 DB（`staff_panel_entries.name` / `info`）。三个方案备选：

1. DB 加 `name_i18n` JSONB，后端按 `Accept-Language` 挑 —— 需要后端引入
   locale 协商（当前后端不读该头），改动面最大。
2. **前端按 `tab_key` 查 i18n，DB 值作 fallback —— 采用此方案。**
3. DB 存 i18n key —— 等价于方案 2，但多一次迁移且后台无法录入。

**采用方案 2** 的理由：与现有 `dict.xxx` 体系零摩擦；不需要后端 locale 感知；
`tab_key` 已验证 59 条全唯一且稳定；**fallback 天然安全**——在 DB 插一行新工具
会立刻显示中文，而不是渲染空白。

落点：`dict.adminNav[tab_key] = { label, tip }`，zh-CN 保留 DB 同名副本便于三语
并排校对，`en` / `zh-TW` 提供译文。

### 3.2a i18n 的验证姿势（必须端到端验，不能只看"字符串搬走了"）

`chk-forums-i18n.js`（B1）与 `chk-admin-i18n-b2.js`（B2）：用 `flux.locale` cookie 分别以
zh-CN / zh-TW / en 打开对应工具页，断言
① 目标语言文案**确实渲染**；
② 改前的硬编码中文在繁体/英文下**彻底消失**；
③ zh-CN 对照组原文案**仍在**（防我把 zh-CN 也误删）；
④ 零 pageerror。
分别期望 `I18N_VERIFY_PASS` / `B2_I18N_PASS`。截图见 `design-system/管理端-i18n-*.png`。

**两条经验：**
- **断言只能挑"无条件渲染"的文案。** 表格行内的按钮（撤销）、依赖加载后才能出现的
  状态值（角色继承）在有数据时才渲染，拿它们做 `want` 断言会假阴性 —— B2 首跑就
  因此报了 3 个假失败，换成表头/空态/表单标签后才真正通过。
- **分区名/版块名/职务名在英文界面仍是中文 —— 那是用户数据（DB 字段），不是
  UI chrome，不该被 i18n 掉**，也别把它当成"漏翻"。

**`.ts` 存量的迁移模式（已用任务域试点验证）**

这些 shared 模块是**非 React 模块**（不能调 `useI18n`），且导出 `[{v,label}]` 形状的
常量、被 3~8 个 tsx 消费。**选型：导出保留原形状的 builder**，消费方只把常量换成
函数调用，`.find((k) => k.v === ...)` 逻辑零改动：

```ts
// admin-tasks-shared.ts
export const KIND_KEYS = ["task", "onboard", "periodic"] as const;
export const kindList = (labels?: Record<string, string>) =>
  KIND_KEYS.map((v) => ({ v, label: labels?.[v] ?? v }));

// 消费方（原本 `import { KINDS }` + `KINDS.map(...)`）
const KINDS = kindList(dict.adminTasks.kinds);   // 形状不变，其余代码不动
```

shared/form/table/exams 四个文件，`chk-tasks-i18n.js` 三语端到端 →
`TASKS_I18N_PASS`。顺带消灭了 `admin-tasks-exams.tsx` 里**第二份重复的本地
KINDS**（同一份三语标签在两处各写一遍，正是漂移温床）。

**试点又验证了一条断言纪律**：`forbid` 不能放可能以**数据**形式出现的词 ——
`tasks` 表里恰有一条任务叫「新人转正考核」（站长输入的 `name`），把该词放进
forbid 会假失败。**数据 ≠ chrome**，这与 §3.2a 的分区名/版块名是同一条纪律。

## 6. 门禁改动（本轮）

| 门禁 | 改动 | 原因 |
|---|---|---|
