# 协作玩法实施深化：可信行为体系与经济模型

> 承接 `_doc/协作玩法引擎与站型适配-深化方案.md`
> v2 解决了「玩法长什么样」，本文解决 v3 的两个命门：**① 行为怎么保证不被伪造 ② 经济怎么保证不通胀**，并给出可开工的数据模型与接口。

---

## 一、先承认 v2 引入的新风险

| | 熊猫的零和系统 | 我们的正和系统 |
|---|---|---|
| 产出锚定 | 玩家之间的魔力值转移 | **站点真实行为** |
| 作弊动机 | 低（产出不挂钩行为，刷了也没用） | **高（刷行为 = 直接印钱）** |
| 需要防伪吗 | 不需要 | **必须，否则整个经济崩盘** |

**这是必须正面回答的问题**：产出锚定真实行为，一旦行为可伪造，正和经济立刻退化成刷子乐园。熊猫那套虽然零和，但它天然免疫这个问题——因为它压根不给真实行为发钱。

**结论：可信行为体系是这个方案的地基，不是可选项。** 它决定了后面所有经济设计能不能成立。

---

## 二、威胁模型：谁在作弊、怎么作弊

先列清楚攻击面：

| # | 攻击方式 | 具体手段 | 危害 |
|---|---|---|---|
| 1 | **客户端谎报** | 魔改 BT 客户端伪造上传量 / 做种时长 | 高（直接刷"摄影"岗位） |
| 2 | **虚假 announce** | 脚本直连 tracker 发 announce 包，模拟做种但无实际数据 | 高 |
| 3 | **小号集群** | 多账号互传，制造流量 | 中（成本高，需要多个 IP/客户端） |
| 4 | **假保种** | 客户端挂着但限速 / 不实际传输，维持 announce | 中（"美术"岗位重灾区） |
| 5 | **自产自销** | 自己发布冷门种子 + 自己保种，刷"冷门保种"分 | **高（专门针对我们的稀缺奖励）** |
| 6 | **发布灌水** | 发大量垃圾种子凑发布数 | 中（"剪辑"岗位） |
| 7 | **发帖灌水** | 论坛刷帖凑社区分 | 低（权重可以压低） |

**注意第 5 条**：我们的设计奖励"保种冷门资源"，这恰好是最容易被自产自销套利的——发布者自己控制资源，自己做种，轻松刷满。**这是本方案最脆弱的一环，必须在设计上封死。**

## 三、核心原则：复用站点已有的反作弊体系，不另建一套

**这是本文最重要的一条设计决策。**

PT 站本来就有成熟的反作弊体系：上传量审查、H&R 考核、作弊者标记（熊猫甚至有个 `cheaterbox.php` 页面）、分享率监控、异常 announce 检测。

我们的做法是：

> **游戏不自己采集和判定行为，只消费站点「已被反作弊体系过滤过」的行为数据。**

| | 自建一套（错） | 复用站点体系（对） |
|---|---|---|
| 实现成本 | 高（要重写检测逻辑） | **低（只读现有字段）** |
| 判定一致性 | 两套标准会打架 | 一套标准 |
| 作弊威慑 | 弱（作弊只是少赚游戏币） | **强（作弊 = 封号）** |
| 维护成本 | 随作弊手段升级要跟进 | 跟着站点反作弊走 |

**关键点：作弊的代价必须是封号，而不是"少赚游戏币"。** 游戏币的损失对刷子毫无威慑力，账号的损失才有。

### 3.1 三条硬性接入规则

1. **只读已审核字段**：消费 `user_uploaded` / `user_downloaded` / 做种记录 / H&R 记录等站点已有字段，不新增采集通道
2. **作弊标记联动**：用户被标记为作弊者（或进入观察名单）→ **游戏进度自动冻结，未结算的贡献作废**
3. **行为可追溯**：每条贡献记录都要能追溯到原始行为来源（哪次 announce / 哪个种子 / 哪个帖子），便于人工复核

### 3.2 封死"自产自销"（针对威胁 #5）

这是最脆弱的一环，需要三条同时生效：

| 规则 | 说明 |
|---|---|
| **发布日门槛** | 只有「发布满 N 天（建议 ≥ 30 天）」的资源才计入冷门保种奖励。自己现发一个冷门种，30 天内不算数 |
| **外部做种者条件** | 该资源必须曾经有过 **≥ K 个不同的外部做种者**（证明它不是自娱自乐）。K 建议 ≥ 3 |
| **发布者剥离** | **资源发布者本人保种该资源，不计入冷门保种奖励**（发布者保自己的种是本分，不是贡献） |

这三条叠加后，刷"冷门保种"就变成：需要发一个资源 → 等 30 天 → 还要找 3 个真人来下过并做种 → 而你自己还不算数。**成本远高于正常做种。**

## 四、行为可信分级：权重与可验证强度正相关

不是所有行为都同等可信。按「伪造成本」分级，**伪造越难的，权重越高**：

| 行为 | 可验证强度 | 建议权重 | 质量门槛 |
|---|---|---|---|
| **长期做种时长** | 高（需持续 announce，脚本常驻易被行为模式检测） | **1.2** | 连续做种 ≥ 7 天 |
| **冷门资源保种** | 高（做种者少，贡献显著且易人工核验） | **1.5** | 见 3.2 三条规则 |
| **有效上传量** | 中（客户端可谎报，依赖 tracker 校验与对等方交叉验证） | 0.8 | 分享率 ≥ 1.0 |
| **发布资源** | 中（可灌水） | 0.6 | 发布后 7 天内 **≥ N 人下载且无投诉** |
| **社区贡献**（答疑/求种应求） | 低 | 0.2 | 被他人标记"有帮助"才算 |
| **纯发帖量** | 极低 | **0** | 不计入产出，只给人气分（纯展示） |

**两条设计意图**：

1. **把权重压在站点真正稀缺的行为上**（冷门保种、长期做种），而不是"量大好刷"的行为（发帖、灌水）
2. **纯发帖不给产出**——直接消灭威胁 #7。想靠刷帖赚钱？一分不给。

## 五、延迟结算：给反作弊留出观察窗

PT 站的反作弊有个特点：**很多作弊是事后才被发现的**（异常模式需要累积样本）。

所以产出**不能即时发放**：

```
行为发生 → 记账（pending）→ 观察窗 T 天 → 复核通过（verified）
        → 赛季结算（settled）→ 发放
                          ↘ 期间被标作弊 → 作废（voided）
```

| 阶段 | 状态 | 说明 |
|---|---|---|
| 记账 | `pending` | 行为已发生，计入预估进度（**展示但不发钱**） |
| 观察 | 持续 T 天（建议 7 天） | 反作弊观察窗口，期间可被推翻 |
| 复核 | `verified` | 通过观察，进入可结算池 |
| 结算 | `settled` | 赛季末发放，写入流水 |
| 作废 | `voided` | 被标作弊 / 触发风控 → 清零 |

**这个思路在 PT 站有先例**：H&R 就是延迟考核（下载后要持续做种 N 小时）。玩家对"延迟确认"的接受度是有的，只要进度条上明确显示"待确认"和"已确认"的区别。

**副产品**：延迟结算还顺带解决了"赛季末冲量"的问题——最后一天刷的行为来不及在窗口内确认。

## 六、参与资格：贡献地板

不是所有人都能参与拿产出。三条地板（任一不满足则不产出，只保留荣誉）：

| 地板 | 阈值 | 理由 |
|---|---|---|
| 分享率 | ≥ 1.0（或站点的及格线） | 防止"只下不传"的用户来薅 |
| H&R 欠账 | 无未清欠账 | 连基础义务都没完成，不该拿游戏产出 |
| 反作弊状态 | 非作弊标记 / 非观察名单 | 见第三节 |

**注意用词**：地板是"不产出"，**不是"禁止参与"**。低于地板的用户仍可以玩、可以看、可以拿荣誉，只是不产生魔力值收益。这比"禁止参与"体验好得多，也避免了把边缘用户推到对立面。

## 七、经济模型：预算池 + 次线性发行

### 7.1 为什么不能"按贡献量线性发钱"

如果按贡献量线性发行，就等于"做得越多印得越多"，结果必然是：

```
贡献总量 ↑ → 发行总量 ↑ → 全站魔力值 ↑ → 通胀 → 魔力值贬值 → 玩家收益感下降
```

这正是熊猫要花大力气建"抽水出口"（槽位/维护费/拍卖手续费）去对冲的问题。**我们不该重蹈覆辙，而应该在发行端就控住。**

### 7.2 两个方案对比

| 方案 | 机制 | 问题 |
|---|---|---|
| A. 固定池 + 按份额分 | 池子固定，按个人CP占比分配 | **零和感**：别人做得多我就拿得少，容易内卷、劝退 |
| B. **次线性发行（推荐）** | 发行总额随贡献增长，但**增速递减** | 兼顾正反馈与通胀控制 |

### 7.3 推荐公式

```
全站发行总额 = k × (全站有效贡献总量) ^ 0.75

个人发行量 = 全站发行总额 × (个人有效贡献 / 全站有效贡献总量)
           = k × (个人贡献 / 全站贡献) × (全站贡献 ^ 0.75)
```

**关键性质**：

| 场景 | 效果 |
|---|---|
| 你自己做得多 | 个人份额上升 → **赚得更多**（正反馈保留） |
| 全站都做得多 | 总额只涨 0.75 次方（贡献翻倍，发行只涨 1.68 倍）→ **人均收益略降，但盘子变大** |
| 没人参与 | 发行趋近于 0 → **不会凭空印钱** |

指数 `0.75` 是调节旋钮：越接近 1 越"卷"，越接近 0 越"平均"。

### 7.4 通胀护栏：反向定标

更稳的做法是**先定通胀目标，反推发行池**：

```
每赛季可发行上限 = (目标年通胀率 × 全站魔力值总量 − 站点原有年产出) / 每年赛季数
```

举例：全站魔力值 10 亿，目标年增 8%，站点做种原有年产出 6000 万，每年 12 个赛季：

```
上限 = (1e9 × 8% − 6000万) / 12 = (8000万 − 6000万) / 12 ≈ 167万/赛季
```

**这样游戏从"通胀源头"变成了"通胀调节器"**：站点产出多的时候，游戏池子自动缩小；产出少的时候可以补一点。这是熊猫完全没做到的事——它只能被动地建出口去堵。

### 7.5 稀缺性奖励（凸函数）

普通贡献线性折算，**稀缺贡献给凸性奖励**：

| 贡献类型 | 折算曲线 |
|---|---|
| 常规上传/做种 | 线性（边际价值稳定） |
| 冷门保种 | **次方加成**：`base × (1 + log(全站同类稀缺度))`，设上限 |
| 断种抢救 | **定额高额奖励**（不是按量算，是按"救活了一个"算） |

理由：保种 1TB 的边际价值递减（大佬再加 1TB 意义不大），而**救活一个濒危资源**的边际价值极高。折算曲线应该反映这个真实差异。

## 八、数据模型（核心表）

```sql
-- ========== 引擎层（与主题无关，只建一次）==========

-- 赛季
social_season (
  id, seq_no, theme_key, status,           -- status: upcoming/active/settling/closed
  started_at, ends_at, settle_at,
  base_pool, pool_formula_snapshot,        -- 赛季池的公式快照（保证可复算）
  total_effective_cp, issued_amount,
  created_at
)

-- 契约（组队关系，一个赛季内有效）
social_contract (
  id, season_id, leader_uid, theme_key,
  status,                                  -- recruiting/active/settled/cancelled/failed
  team_size_limit, role_slots_json,
  offer_price_ratio,                       -- 报价分成比例
  reward_pool, penalty_pool,
  created_at, activated_at, settled_at
)

-- 契约成员与岗位
social_member (
  id, contract_id, uid, role_key,
  offer_ratio, accepted_ratio,
  specialty_level,                         -- 岗位专精等级
  contribute_cp, settled_amount,
  status,                                  -- invited/accepted/rejected/withdrawn/completed
  joined_at, left_at
)

-- 贡献明细（可追溯，一条行为一条记录）
social_contribution (
  id, uid, season_id, contract_id,
  behavior_type,                           -- upload/seeding/seed_rare/publish/community
  source_ref,                              -- 溯源：infohash / announce_id / post_id
  raw_amount,                              -- 原始行为量
  trust_weight,                            -- 可信权重
  quality_pass,                            -- 质量门槛是否通过
  cp_value,                                -- 折算后的有效贡献
  status,                                  -- pending/verified/voided
  occurred_at, verify_due_at, verified_at,
  void_reason,
  idempotency_key UNIQUE
)

-- 信誉
social_reputation (
  uid, score, level,
  fulfilled_count, withdrawn_count, failed_count,
  updated_at
)
social_reputation_log (id, uid, delta, reason, ref_id, created_at)

-- 发行流水（与站点魔力值账本对接）
social_issuance (
  id, season_id, uid, amount, status,      -- pending/settled/reversed
  reason, settlement_id, created_at
)

-- ========== 资源层玩法（全站型通用）==========

rescue_target (
  id, infohash, torrent_id, category_id,
  seeders_at_scan, added_at, days_old,
  status,                                  -- listed/claimed/rescued/expired
  health_threshold, required_days,
  reward_snapshot_json
)

rescue_team (
  id, target_id, leader_uid, status,
  started_at, deadline_at, settled_at,
  progress_json
)
rescue_member (id, team_id, uid, role, joined_at)

-- 永久荣誉（拯救记录，不上限、不重置）
rescue_honor (
  id, target_id, infohash, team_id,
  uids_json, rescued_at, seeders_after
)

-- ========== 主题层（可插拔）==========

social_theme (
  key, name, enabled,
  behaviors_json,                          -- 本主题用到的行为类型（引擎枚举子集）
  role_definitions_json,                   -- 岗位 → 行为绑定
  naming_json,                             -- 文案表（岗位名/产出物名/评级名）
  assets_json,
  created_at
)
```

**三个关键设计点**：

1. `social_contribution.status` 的 **pending → verified → voided 状态机**是防伪的载体，不可省
2. `source_ref` + `idempotency_key` 保证**可追溯 + 不重复计费**
3. `social_theme` 把主题做成**数据行而不是代码**，加主题 = 插一行

## 九、接口设计（对照熊猫的 45 个 action）

| 熊猫 action | 我们的对应设计 | 差异 |
|---|---|---|
| `friendTradeInitOrHome` | `social.home` | 返回赛季进度 + 我的契约 + 预估（未结算）收益，**明确区分"待确认/已确认"** |
| `friendTradeMarketList` | `social.recruit.list` | 从"浏览可买的人"改成"浏览招募中的契约与报名者" |
| `friendTradeSnatch` | `social.recruit.offer` | 从"掠夺"改成"报价"，**双向选择**（对方可拒绝） |
| `friendTradeCommissionStart` | `social.contract.start` | 委托 → 契约启动 |
| — | `social.rescue.list` / `claim` / `progress` | **新增**：资源层玩法（熊猫没有对应物） |
| — | `social.season.current` / `history` | 新增：赛季 |
| — | `social.reputation.get` | 新增：信誉 |
| `friendTradeSetNotificationPreference` | 复用 | 通知开关 |

**接口数量的对比很有说服力**：熊猫 45 个 action，其中一大半是在处理"玩家互转的结算与反套利"（追回资格、包养窗口、批次操作、逐项提示）。

我们的 action 数量**不一定更少**，但**复杂度低得多**——因为没有"玩家之间资金转移"这条最容易出 bug 的链路，所有产出都是"系统单向发行"，不存在双方对账、余额不足逐项跳过、部分成功等一大坨边缘情况。

## 十、观测指标与对照实验

玩法上线前必须定义好"怎么算成功"：

### 10.1 北极星指标（唯一）

> **参与玩家的「周有效做种时长」与「冷门资源保种数」，相比未参与玩家的差值。**

这是整个方案成立的唯一证据。其他指标都是辅助。

### 10.2 必须做的对照实验

- **灰度分组**：随机 10% 用户开启玩法，10% 作为对照（功能全不可见），80% 保持现状
- **观察期**：至少 4 周（覆盖一个完整赛季）
- **判定标准**：
  - 差值显著为正 → 方案成立，进入 P1
  - 差值持平 → 玩法只是"零和搬家"（玩家把原有做种时间挪进了游戏里），需要调整激励方向
  - 差值显著为负 → 玩法分散了注意力，**立即止损**

### 10.3 护栏指标（防止跑偏）

| 指标 | 警戒线 | 含义 |
|---|---|---|
| 赛季发行量 / 全站魔力值总量 | > 目标通胀率 | 通胀失控 |
| 冷门保种的自产自销比例 | > 20% | 威胁 #5 没封住 |
| 参与者的作弊标记率 | 高于全站均值 | 玩法在吸引刷子 |
| 契约违约率 | > 30% | 门槛太高或匹配太差 |
| 未结算贡献作废率 | > 15% | 观察窗设太短或风控过严 |

## 十一、失败预案（诚实面对三种死法）

| 死法 | 征兆 | 降级动作 |
|---|---|---|
| **没人玩** | 灰度 4 周后参与率 < 3% | 关停引擎层，**只保留《抢救断种》**（无门槛、零依赖、产出可量化） |
| **被刷爆** | 作废率飙升 / 作弊率异常 | **立即关闭发行，只保留荣誉**（游戏照常玩，但不再产出魔力值），恢复后再开 |
| **通胀失控** | 发行量超护栏线 | 收紧池子系数 `k`，或临时冻结赛季结算 |

**三条降级动作都必须是"配置项改一下就能生效"**——不能是需要重新部署的硬编码。这也是为什么第七节的池子公式必须存在 `social_season.pool_formula_snapshot` 里。

## 十二、实施拆分

| 模块 | 内容 | 依赖 | 归属 |
|---|---|---|---|
| **A. 贡献采集** | 从站点已有表聚合行为，按可信权重折算 | 只读 tracker/用户表 | 后端 |
| **B. 状态机** | pending → verified → voided 的延迟结算 | A | 后端 + 定时任务 |
| **C. 发行与账本** | 赛季池计算、发行流水、与站点魔力值账本对接 | B | 后端 |
| **D. 引擎玩法** | 契约、岗位、羁绊、专精、信誉 | B/C | 后端 + 前端 |
| **E. 资源层玩法** | 抢救断种（扫描器 + 组队 + 荣誉） | A（不依赖 C，可独立跑） | 后端 + 前端 |
| **F. 主题包** | 数据化配置 + 后台编辑界面 | — | 后端 + 后台 |
| **G. 观测** | 埋点、灰度开关、对照分组、护栏告警 | — | 后端 + 运维 |

**建议实施顺序**：`G（埋点先上）→ A → B → E → C → D → F`

理由：
- **G 先上**：没有对照数据，后面所有决策都是拍脑袋
- **A→B 先于 C**：先有可信的行为数据，再谈发钱
- **E（抢救断种）排在 C 之前**：它不依赖发行体系，可以更早验证核心假设
- **F 最后**：主题包是规模化的东西，验证通过再做

## 十三、一页总结

| 命门 | 解法 |
|---|---|
| 行为会被伪造吗？ | **复用站点已有反作弊，只消费已审核数据**；作弊代价是封号而非少赚币 |
| 自产自销刷冷门保种？ | 发布满 30 天 + 曾有 ≥3 个外部做种者 + 发布者本人不算 |
| 灌水刷分？ | **权重与可验证强度正相关**；纯发帖权重 = 0 |
| 事后才发现作弊？ | **延迟结算**（7 天观察窗），pending → verified → voided |
| 通胀失控？ | **次线性发行 + 反向定标**：先定通胀目标，反推赛季池上限 |
| 保种边际价值递减？ | 稀缺贡献用凸函数（log 加成），抢救类用定额高额奖励 |
| 怎么知道成功了？ | 北极星 = 参与玩家的**周有效做种时长**与未参与者的差值；10% 灰度 + 4 周对照 |
| 失败了怎么办？ | 三条降级：没人玩→只留抢救断种；被刷→只留荣誉；通胀→收紧系数。**全部是配置项** |
