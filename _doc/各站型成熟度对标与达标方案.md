## 0. 总论：我们的"站型"到底是什么

先说清楚现状，否则后面的对标会失真。

**结论（有代码证据）**：FluxTorrent 的 `site_type`（见 `apps/api/migrations/0037_site_type_packs.sql`）目前本质是 **"分类预设 + 模块开关"**，不是"内容模型特化"。

### 0.1 已证实的事实

| 维度 | 现状 | 证据 |
|---|---|---|
| 分类 | 每站型一套预设分类（如 music = 华语/欧美/日韩/单曲/MV/演唱会/无损） | `site_type_packs.categories` JSONB，纯展示用 |
| 模块开关 | 31 个注册模块键（`apps/api/src/modules.rs`），但内容相关的只有 `textbooks`（真实功能）、`showcase`（仅首页展示墙） | `modules.rs` 常量表 |
| `losslessPlayer` | **web 代码零命中**，是声明在 `site_type_packs.modules` 里的空头标志位 | Grep `losslessPlayer` 在 `apps/web` 无结果 |
| 种子结构化元数据 | **六类型字段系统已完整落地**（0195 B1→B2→B3 全闭环，见 §阶段0）：text/number/select/multiselect/date/bool + 必填/多值/启用，写入/详情/筛选/管理端/RSS/种子包全通 | `_doc/B批承重墙-内容字段类型系统设计稿-2026-09-25.md`；`section_kinds.field_type`、`torrent_sections.value` |
| **站型包维度的类型丢失** | **站型包 apply 只落 `(kind,label,sort)`**，`field_type` 等四列回落缺省 ⇒ 六类型系统对站型静默失效。**2026-10-08 已修**（`pack_core.rs` 走 `kind_from_json` 九列） | `staff_http/pack_core.rs`（修前 210-213 行）；修后逻辑在 `pack_types::apply_pack_kinds` |
| 站型包实际内容模型 | music 站原仅 3 个**单选枚举**维度（`media`/`standard`/`source`），无 artist/log_score/haslog/cue。**0313 已补 7 个维度** | `site_type_packs.sections`；迁移 `0313_music_logchecker_dims.sql` |
| 上传表单 / 详情页 / 筛选 | 11 种站型**共用同一套**通用 NP 式表单与页面，仅分类不同 | 代码巡检 |

### 0.2 这意味着什么

切到站型 = 换了分类名 + 开关了几个（大多是空的）模块标志，**种子数据模型、上传字段、详情维度、筛选条件对"音乐/电子书/游戏/动漫/教育"全部一致**。

而成熟站之所以"成熟"，正在于**内容模型特化**——RED 的 `artist/year/releasetype/format/encoding/media/log/cue`、MAM 的 `author/narrator/DRM/format/series`、GGn 的 `platform/DRM-Free/GameDOX`、包子PT 的 `学段/学科/版本/教材`。**没有内容模型，再漂亮的页面也只是换了皮的通用站。**

### 0.3 达标的总原则

> 成熟站型 = **通用 PT 内核（已较强）** + **该内容域的结构化元数据 + 领域专属能力 + 聚合/呈现层**。
> 我们不缺 PT 内核，缺的是"每类型一套内容模型 + 配套能力"。

## 1. 成熟站型的核心分野（所有类型通用）

从 `_doc/种子页面全谱系深度对比.md` §2.3 / §3 / §4.3 提炼，跨内容域都成立：

1. **作品 > 种子（聚合模型）**：Gazelle 的 TGroup、PTP 单电影多版本、BTN show/season/ep、MAM series、GGn 游戏条目。**我们已有 `torrent_groups`（0069）+ 详情页 `GroupVersions`，但仍是"平坦同组"，缺 series / collection 聚合。**
2. **内容元数据与技术信息分栏**：PTP/GGn/AB 把"作品信息"与"技术参数"分区块；我们 MediaInfo/NFO 是通用技术信息，但没有"作品元数据"这一层。
3. **结构化的领域字段**：每个内容域有自己一等公民的字段集（见各节）。
4. **领域专属质量门禁/预览**：Logchecker（音乐）、样章试读（电子书）、截图画廊（影视/游戏）、trumping/duplicates（GGn）。
5. **筛选维度贴合内容域**：Gazelle 音乐有 `haslog/hascue/scene/vanityhouse`；NP 影视有 `处理/标准/音轨/团队`。我们筛选维度是通用的，不随站型变化。
6. **外部资料库打通**：IMDb/TMDB/MAL/AniDB/豆瓣/音乐brainz。我们只有 `imdb_id`，且无自动拉取（详情页 `◐`，待确认）。

## 2. 逐站型对标

> 模板：对标成熟站 → 成熟标准（达标定义）→ 我们现状 → 核心缺口 → 达标改造项。

### 2.1 综合站 general（NexusPHP 默认形态）

- **对标**：NexusPHP 主线 + 华语大站魔改（M-Team/HDSky/柠檬/观众/U2/BYR）。
- **成熟标准**：多级促销（`sp_state` 七态 + 倒计时）、NFO + MediaInfo/BDInfo + PT-Gen + 同 IMDb 副本 + 字幕区 + H&R、DOM 事实契约（`table.torrents`/`.pro_free`/`details.php?id=`）、原生完整 RSS、海报墙、批量下载、实时筛选。
- **我们现状**：**已对标达标（实测）**——三视图（表格/卡片/海报墙）、实时筛选（URL 持久化）、每页可配、磁力、peers、书签、批量多选、语义 DOM 契约、筛选维度超 NP 原生；`/compat/nexusphp/*`兼容层已落地。**这是我们对标最齐的站型。**
- **核心缺口（实测后）**：仅 §3.2 的通用发现层能力——**Collection/Series 策展聚合**、**相似推荐**（PTP/MAM 有、我们无）。促销倒计时列表行 tooltip、H&R 提示进详情页属低成本体验项。
- **达标改造项**：补 Collection/Series + 相似推荐即全面达标。

### 2.2 影视站 movie

- **对标**：M-Team（mTorrent API 侧）、HDSky、UNIT3D、PTP（Cover Flow / Collections / 多版本 SD/HD/UHD）。
- **成熟标准**：海报（TMDB/IMDb 自动拉取）、NFO、MediaInfo 解析到 HDR/音轨、PT-Gen 简介、同 IMDb 副本聚合、字幕区、多版本分组（Web-DL/Remux/BluRay）、H&R 免罪、促销倒计时、Collections 合集。
- **我们现状（实测）**：`imdb_id` 字段已有；MediaInfo/NFO/字幕三位一体已落地；`GroupVersions` 同组版本已支持；截图（`descr_image.rs`）已实现；详情页磁力/peers/书签/批量/多视图均已具备。
- **核心缺口（实测后）**：**Collections 合集层**（PTP 有、我们无）、**多版本语义分组**（我们是"平坦同组"，无 SD/HD/UHD 分组概念）、外部元数据**自动拉取**（仅 `◐` 待确认，imdb_id 需手填）。
- **达标改造项**：① Collections 层（与通用 Collection/Series 共建）② 多版本语义分组（可复用 group 模型加 quality tier）③ 自动拉取+海报回填（接 TMDB/豆瓣）。

### 2.3 音乐站 music

- **对标**：RED / GGn / What.CD（Gazelle 音乐分支）。
- **成熟标准**：**TGroup 聚合**（artist / year / releasetype）、`format/encoding/media` 结构化字段、`haslog`（100%/99%/<100%/无）+ **Logchecker 日志分**、`hascue`、`scene` 检测、真实文件树 + **文件夹冲突检测**、`View log` 详情展示、collage 策展、相似推荐（标签投票）、**无损播放器**（losslessPlayer 模块声明的本意）。
- **我们现状**：`site_type=music` 预设了分类并声明 `losslessPlayer:true`；但**没有任何音乐专属字段、没有 Logchecker、没有文件树冲突检测、losslessPlayer 是空头标志位（零功能）**。详情页仍以通用 NP 形态呈现。
- **核心缺口（最关键，也是用户最先问到的）**：
  1. **Logchecker 完全没有**（EAC/CUETools/WHipper 解析 + 100% 打分），见前序对话确认。
  2. 缺 `artist/releasetype/format/encoding/media/log_score/cue/scene` 结构化字段。
  3. 缺 TGroup 聚合（音乐是 Group 模型最典型的受益者）。
  4. losslessPlayer 未实现（声明了却无功能）。
  5. 缺 collage / 相似推荐（标签投票）。
- **达标改造项**（按依赖排序）：
  - M0：扩展元数据框架，加 `torrent_music` 扩展字段（artist/year/releasetype/format/encoding/media）。
  - M1：**Logchecker**（上传解析 + 日志分存储 + 详情 `View log` + 列表 `haslog` 筛选）。最小可跑版先支持 EAC log 的 100%/非100% 判定，再扩展完整打分。
  - M2：文件树冲突检测（Gazelle 真实文件树能力）。
  - M3：TGroup 音乐聚合 + collage + 标签投票相似推荐。
  - M4：losslessPlayer 真正实现（在线试听，挂载 `losslessPlayer` 模块键）。

### 2.4 无损音乐站 lossless（Gazelle 口径）

- **对标**：RED（Gazelle lossless 主线）、GGn 音乐分支。
- **成熟标准**：在 music 基础上强化——Hi-Res / SACD / 黑胶转制 / 采样率结构化字段、log 100% 为硬门槛、无损播放器、高保真试听。
- **我们现状**：`site_type=lossless` 预设分类（无损专辑/Hi-Res/黑胶转制/SACD/采样/单曲/Live）+ 声明 `losslessPlayer:true`，**其余与 music 同为空壳**。
- **核心缺口**：与 music 完全一致（Logchecker、结构化字段、losslessPlayer 全缺），另缺采样率/位深/Hi-Res 标识字段。
- **达标改造项**：复用 music 的全部改造（M0–M4），额外加 `samplerate/bitdepth/hi_res` 字段与"log 100% 才允许上传/标红"的校验规则。

### 2.5 动漫站 anime

- **对标**：AnimeBytes（Gazelle 变体）、U2（动漫花园）、Bangumi。
- **成熟标准**：`studio/字幕组` 维度、MAL/AniDB 关联元数据、季度番/剧场版/生肉熟肉分类、多版本（BD/DVD/Web）、制作组维度、单集/合集聚合。
- **我们现状**：`site_type=anime` 仅分类预设（动画/季度番剧/剧场版/漫画/同人/音乐/周边）；无 `studio/字幕组/MAL_id` 字段；无动漫向筛选维度。
- **核心缺口**：缺 `studio/字幕组(team)/MAL_id/AniDB_id` 字段、缺外部元数据拉取（MAL/AniDB）、缺"字幕组"这一动漫站标志性的上传者/组维度（我们通用有 `official` 但非语义化字幕组）。
- **达标改造项**：① 动漫扩展字段（studio/team/mal_id）② 外部元数据接 MAL/AniDB ③ 字幕组维度提升为上传/筛选一等公民（可复用现有字幕区能力，但需语义化）。

### 2.6 电子书站 ebook

- **对标**：MAM（闭源，业界最强电子书站）。
- **成熟标准**：`author/narrator/DRM/format/series` 结构化字段、`DRM` 显式标签、样章试读/在线试听、series 聚合、图书评分 + 书评、类型（文学/社科/杂志/有声书/漫画）细化。
- **我们现状**：`site_type=ebook` 仅分类预设；**无 author/ISBN/narrator/DRM/series 字段**；无样章试读能力（缺附件预览/试读端点）。
- **核心缺口**：结构化书目字段全缺、无 DRM 标签、无样章试读、无 series 聚合。
- **达标改造项**：① 书目扩展字段（author/isbn/narrator/drm/series/format）② 样章试读端点（复用 attachment 体系，加"试读页/试听片段"语义）③ series 聚合。

### 2.7 教育站 education

- **对标**：包子PT（已知教育 PT）、各类教材/网课 PT。
- **成熟标准** `[推断/业内]`：学段/学科/教材版本（人教版/北师大版…）分类、**教材/课件/试卷/真题/网课/大纲**资源类型维度、年级/学期、考纲关联、求种/教材互助、考核（我们已有 `exams`/`tasks` 模块）。
- **我们现状**：`site_type=education` 是**唯一有真实专属功能的非通用站型**——`textbooks` 模块 + `/textbooks` 板块 + `textbook-link-button` 真实落地 `[实证]`。但教材/课件/试卷等"资源类型"仍以通用分类表达，无结构化字段。
- **核心缺口**：缺 `学段/学科/教材版本/资源类型/年级` 结构化字段；`textbooks` 板块与种子元数据未打通（教材条目 ↔ 对应种子未关联）。
- **达标改造项**：① 教育扩展字段（subject/grade/edition/resource_type）② 让 `textbooks` 板块与种子双向关联（教材条目下挂相关种子）③ 资源类型成为上传一等字段。

### 2.8 游戏站 game

- **对标**：GGn（Gazelle 游戏分支，业界标杆）。
- **成熟标准**：`platform`（PC/主机/掌机/Switch/Mac/移动）结构化字段、`DRM-Free` 显式标签、GameDOX/OST/更新多版本聚合、平台覆盖 NES→Switch、**trumping + duplicates 合并规则**、评测外链。
- **我们现状**：`site_type=game` 仅分类预设（PC/主机/掌机/汉化/MOD/游戏音乐/攻略）；无 platform/DRM 字段；无 GameDOX/版本聚合；trumping 缺。
- **核心缺口**：结构化游戏字段全缺、无 DRM-Free 标签、无 GameDOX/更新版本聚合、无 trumping/duplicates 质量门禁。
- **达标改造项**：① 游戏扩展字段（platform/drm_free/region）② GameDOX/OST/更新版本聚合（复用 GroupVersions 升级）③ trumping + duplicates 合并规则（GGn 实证能力）。

### 2.9 软件站 software

- **对标**：成熟软件 PT（普遍较朴素，多为分类 + 平台维度，`[推断]`）。
- **成熟标准** `[推断]`：平台（Windows/macOS/Linux/Android/iOS）维度、版本/激活方式、教程配套、素材分类。
- **我们现状**：`site_type=software` 仅分类预设；无 platform/version 字段。
- **核心缺口**：缺 platform 结构化字段、缺版本维度。
- **达标改造项**：软件扩展字段（platform/version/license_type）；改造量小，可作为"内容模型框架"的验证样板（低成本立标杆）。

### 2.10 体育站 sports

- **对标**：BTN 的 show/season/episode 模型（赛季维度）`[业内]`；纯体育 PT 较少，`[推断]`。
- **成熟标准** `[推断]`：联赛/赛事维度、赛季/轮次、集锦分类、新赛事订阅通知（对标 BTN 新集通知）。
- **我们现状**：`site_type=sports` 仅分类预设（足球/篮球/网球/格斗/赛车/综合赛事/集锦）；无 league/season 字段；无订阅通知基建。
- **核心缺口**：缺 league/season 结构化字段、缺追更/通知（全站级能力，见 §3 P3）。
- **达标改造项**：体育扩展字段（league/season/round）；追更通知依赖全站订阅基建（P3，优先级低）。

### 2.11 纪录片站 documentary

- **对标**：影视站轻量版（自然/历史/科技纪录片，`[推断]`）。
- **成熟标准** `[推断]`：对标 movie 但更轻——海报/简介/分类（自然/历史/科技/军事/人文）即可；无需复杂多版本。
- **我们现状**：`site_type=documentary` 仅分类预设；复用 movie 的全部通用能力（MediaInfo/NFO 等已支持），但不强制影视专属增强。
- **核心缺口**：几乎无专属缺口，主要是"复用 movie 的达标项"。
- **达标改造项**：达标 movie 即自动达标；纪录片可视为 movie 站型的"轻配置档"。

## 6. 风险与纪律

1. **不要每种站型各建一套独立表**：用阶段0的统一扩展框架，避免 schema 爆炸与维护债（参考 XBTIT hack 生态死因）。
2. **Logchecker 是不可绕过的核心**：音乐/无损站若无 Logchecker，等于"挂着音乐站名号的通用站"，用户一眼能看出不专业。
3. **losslessPlayer 空头标志位必须落地或移除**：当前声明了却无功能，是"假成熟"的典型，对外展示会翻车。
4. **保持种子为独立聚合根**：绝不把种子绑到帖子/教材条目上（TorrentPier/Discuz-PT 反例）。
5. **筛选维度动态化，而非写死**：阶段0框架让筛选随 `site_type` schema 生成，避免每加一种站型改一遍前端。
6. **增量交付**：每个站型独立可上线，不阻塞其它站型；任一站型未达标不影响其它站型可用。
