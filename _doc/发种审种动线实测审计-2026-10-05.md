# 发种员 · 审种员视角实测审计（2026-10-05）

审计身份：PT 站资深发种员 + 审种员。口径：只报**当场跑出来的**行为，每条附复现证据与 `file:line`；推断一律标注。

环境：本地栈 `flux-api :8080` / `flux-web :3000` / `flux-tracker :7070` / `flux-postgres`。
探针：`.workbuddy/_pt_upload_probe{,2,3,4,5}.py`、`_pt_leak_probe6.py`、`_pt_descr_size.py`、`_pt_dl_isolation.py`（均在 gitignored 目录，探针数据跑完即清，收尾回读 `残留: 0`）。
本轮**未改动任何仓库文件**。与 `_doc/PT版主视角实测审计-2026-10-05.md`（经济/权限线）不重叠。

---

## 0. 一句话结论

发种动线有 **四处会把人当场卡死**（校验后置死锁、被拒种无法自助、描述超长无信息、队列 200 条截断），
审种动线本质是**盲审**（看不到 NFO、下不到原文件、点不进详情），
治理面**零粒度**（发布员可审任何人、包括自己），
入库校验**只认格式不认有效性**（没有 `pieces` 的 .torrent 也能发出去）。
好消息是主闸门与 passkey 隔离这一层做得扎实——问题集中在**子资源、旁路和末端可达性**。

## 1. P0（六条，按修复性价比排序）

### P0-1 审核结果通知 100% 静默失败，发种员永远收不到「过审/被拒」

- 实测：以用户 39 发种 → 站长 `POST /admin/reviews/decide approve=true` 返回 `200 ok`，
  但 `messages` 表该用户条数 **审核前 1 → 审核后 1**（零新增）；库内 `subject LIKE '种子过审%'` **0 条**，
  而 `torrent_operation_logs` 里 `action=approve` 有记录 —— 裁决成功、通知蒸发。
- 根因：`apps/api/src/admin_http/review.rs:207` 的通知查询
  `SELECT t.owner_id, t.title, d.label, t.deny_note FROM torrents t LEFT JOIN torrent_deny_reasons d ...`
  里 **`torrents.title` 和 `torrent_deny_reasons.label` 两个列都不存在**
  （实测原样执行：`ERROR: column t.title does not exist`；`torrent_deny_reasons` 实际列为 `reason`）。
  调用处 `.await.ok().flatten()`（`:209`）把 prepare 期错误吞成 `None` → 站内信 + 邮件两条通道同时哑火且无日志。
- 影响：PT 站的发种员动线全靠这条通知驱动（过审→开始做种、被拒→改后重提）。通知不发 = 做种启动延迟 + 被拒无人善后 + 审核积压看起来「没人管」。
- 修法：把列名改对（`t.name` / `d.reason`），并且**这条通知路径必须有会红的守卫**——`let _ =`/`.ok()` 吞错的写口在这个仓库已第二次出事（Round9 的 `let _ = sqlx::query(...)` 站名/announce 未落库同族）。建议 `.map_err` 上抛或至少 `tracing::warn!` 落 `runtime_logs`。
- **注意**：站长此刻正在改这个文件（工作树 `review.rs` +48 行给队列补字段），但 `:207` 这两列**在最新的树里仍然是错的**，本轮在制批次没覆盖到。

### P0-2 待审队列硬顶 200 条且按 id 升序 → 积压后新提交的种对审核员永久不可见

- 实测：一次性造出 207 条待审 → `GET /admin/reviews` 返回 **200 条**，区间 `40049..40320`，
  **最新那条待审（40327）不在返回里**；`?limit=500&offset=0` 参数被完全忽略（仍 200 条）。
- 根因：`review.rs` 队列 SQL `... WHERE t.approval_status = 0 ORDER BY t.id LIMIT 200`（工作树同 HEAD，`:70-71`），无分页、无排序参数、无筛选。
- 影响：这是审核吞吐的硬天花板。只要老的 200 条没被处理完，**新种在审核员的眼睛里不存在**，而且不报错、不提示——外部看起来就是「这站没人审种」。
- 修法：分页（`limit/offset` 或 keyset）+ 默认排序改 `ORDER BY created_at ASC`（等价的 FIFO，但能配合筛选）+ 至少给 `total` 计数；`LIMIT` 放宽到 500 不是解药，分页才是。

### P0-3 被拒种子对作者和审核员都不可达 → 无人能自助，`resubmit` 端点成死码

- 实测（种子 #x 被拒 `approval_status=2`，作者 = 用户 39）：

  | 谁 | 动作 | 结果 |
  |---|---|---|
  | 作者 | `GET /torrents/{id}` | **404 资源不存在** |
  | 作者 | `GET /torrents/{id}/detail` | **404** |
  | 作者 | `GET /torrents/{id}/download` | **404** |
  | 站长(99) | 同上 | **404** |
  | 作者 | `PUT /torrents/{id}`（编辑） | 200，且状态自动回到 0 |
  | 作者 | `POST /torrents/{id}/resubmit` | 400「仅被拒种子可重提」 |

- 根因：`apps/api/src/torrents/detail.rs:27` 可见性谓词
  `(t.approval_status = 1 OR ((t.approval_status = 4 OR t.approval_status = 0) AND (is_staff OR owner_id = uid)))`
  —— **状态 2 不在放宽集合里**，于是被拒种谁都进不去。
  而唯一的编辑入口（`TorrentManage`）在详情页上，详情页 404 ⇒ 作者能改但**没有 UI 能改**；
  `POST /torrents/{id}/resubmit`（`torrent_http/manage.rs:280-313`）在 `apps/web` **零调用方**（全量 grep 只命中 `i18n/audit-labels.ts` 的标签串）。
  再加 P0-1（没有通知），被拒这件事的唯一可见面是 `/my/torrentlist?kind=uploads` 上的一枚红徽标。
- 修法：把 2 纳入 owner/staff 放宽集（`approval_status IN (0,2,4)`），前端在「我的上传」的 uploads 视图加「查看/编辑/重新送审」按钮，或直接接线 `resubmit`。

### P0-4 校验后置 → 报错时种子已入库，同一 .torrent 从此永久报「重复」，删都解不开

- 实测：普通用户（class 1）带管理组专属参数发种，**四个入口三种错**：

  | 场景 | 返回 | 种子是否已入库 | 同一 .torrent 重试 |
  |---|---|---|---|
  | 官方标签 `tags=[3]` | 403 无权限 | **是**（status=0 进待审队列） | **400 种子重复** |
  | 不存在标签 `tags=[999999]` | 400 标签不存在 | **是** | **400 种子重复** |
  | 推荐位 `pos_state=1` | 403 无权限 | **是** | **400 种子重复** |
  | 非法分类 `category_id=9999` | 400 分类不存在 | 否（已前置，正确） | 400 分类不存在（可自愈） |

- 进一步：作者把残种 `DELETE /torrents/{id}`（软删 → `approval_status=3`，实测 200 成功）之后，**重发同一枚 .torrent 仍然 400 种子重复**。
- 根因：`publish_http/upload.rs` 的判重 `SELECT EXISTS(SELECT 1 FROM torrents WHERE info_hash=$1 OR raw_info_hash=$2)`（`:120-128`）**不排除 3=软删/2=被拒**；
  而标签校验在 `store_sections_tags`（`:289`，INSERT 之后）、推荐位校验在 `upload_files_promo.rs:72-116`（也是 INSERT 之后）。
  `sections` 已在 Round 批次前置到 INSERT 之前（`:224-230`），**这两处是同一课没补完**。
- 影响：PT 站最常见的两个死锁场景 —— ① 手滑带了越权参数 → 这条内容在本站永久发不了，只能开 ticket 让管理员清库；② 种子被下架/删掉后想重新发（换源、补字幕、修描述），**永久不可**，而 `.torrent` 文件本身**没有任何替换端点**（全仓 `torrent_files` 无 UPDATE/DELETE），所以只能发一枚重打包的新 hash，等于制造重复种。
- 修法：(a) 标签/推荐位/权限类校验一律前置到 INSERT 之前；(b) 判重加 `AND approval_status <> 3`（或对同一 owner 放行重发）；(c) 补一个「换 .torrent 文件」端点并强制回待审。

### P0-5 审核权限零粒度 + 无利益冲突校验：发布员可审任何人，包括自己

- 实测：
  - `POST /admin/reviews/decide` 的门槛只有 `guard::staff()` = `require_perm(STAFF_PANEL)`（`admin_http/review.rs:98`、`admin_http/guard.rs:11-19`）。
  - `permissions` 表里**不存在 `torrent.review` 之类的审核专用键**（实测 `COUNT(*)=0`；种子域只有 `torrent.upload / manage / repost / set_price / see_banned / view_anonymous / approval.auto`）。
  - class 91 发布员 `user_can(39,'staff.panel') = t` → **实测成功过审了他人提交的种子**。
  - **自审**：用户 39 先以普通身份发种（status=0），再取得 staff 身份调 `decide` → 200，status=1。**没有任何 owner==operator 检查**（工作树 `review.rs` 里 grep `owner_id == auth.id` 零命中）。
- 影响：①「审核员」这个 PT 站必然存在的职务无法建模——要么给整个后台面板（能改用户、读 passkey，见经济线 P0-3），要么完全不给；② 版主/发布员可自审自助上架，绕开全部审核价值；③ 队列里也不显示「是否本人上传」（前端 `admin-queue-panels.tsx` 无此列），利益冲突对同事不可见。
- 修法：新增 `torrent.review` 权限键（接进 `authz/perm.rs` 与 `module_keys_guard` 那套三方一致校验），decide 用它替换 `staff()`；被拒种/待审种的裁决加 `if owner_id == auth.id && !can_override { Forbidden }`；队列输出 `is_self` 供前端高亮。

### P0-6 .torrent 只解不验：没有 `pieces` 的种子也能发出去

- 实测（全部 `http=200` 入库并进待审）：

  | 畸形 | 结果 |
  |---|---|
  | 无 `pieces` 字段 | **接受**，`pieces_hash=''` |
  | `pieces` 长度非 20 的整数倍（25 字节） | **接受** |
  | `piece length = 0` | **接受** |
  | 所有文件 `length = 0`（总大小 0 字节） | **接受**，`size=0` |
  | `info.name` 为空且表单名也为空 | **接受**，`length(name)=0`，队列里是一条**空白标题** |
  | 文件数 5000 | **接受**（逐行 INSERT 5000 次） |

- 根因：`apps/api/src/bencode/torrent.rs:31-111` 的 `parse_torrent` 只做「能不能解析」，
  字段缺失一律 `unwrap_or(0)` / `unwrap_or_default()`；`piece_length` 解析出来后**全链路无人使用**
  （结构体上还挂着 `#[allow(dead_code)]`，`:9`）。
- 影响：这类种子在客户端**必然 hash 校验失败** → 0 做种死种、误伤下载者、举报与工单都回到审核员面前；`size=0` 还会污染按大小排序/比例计算/付费定价；空标题种子进队列是让审核员白看一条。
- 修法：入库前最小结构校验（`pieces` 存在且 `len%20==0`、`piece_length>0`、`size>0`、`name` 非空、`numfiles<=上限`），错因写进 `TorrentInvalid` 文案（哪个字段、期望什么）。

## 2. P1（九条）

**P1-1 未过审种子的子资源端点绕过主闸门**（实测，身份=无关的 class 1 用户）

| 端点 | 待审(0) | 被拒(2) | 内容 |
|---|---|---|---|
| `/torrents/{id}/files` | **200** | **200** | 完整文件清单（`泄漏探针-待审`、实测另一枚返回 `私密目录/未过审文件.bin`） |
| `/torrents/{id}/snatches` | **200** | **200** | **下载者名单**（`user_id/username/agent/progress/completed_at`） |
| `/torrents/{id}/peers` | 200 | 200 | `masked:true`、空列表（风险低但口径不一致） |
| `/torrents/{id}/comments`、`/tags`、`/collections` | 200 | 200 | — |
| `/nfo`、`/download`、`/magnet`、`/detail`、`/aggregate` | 404 | 404 | 正确 |

- 根因：主详情走 `torrents/detail.rs` 的谓词，而 `/files`（`torrent_http/detail.rs:61-71` + `torrents/detail.rs:209-220`）、`/snatches`（`torrents/manage.rs:31-35`）等只 `require_auth` 后直查表，**approval 闸门在各 handler 里各写各的**。
- 影响：一部待审/已被拒的资源，其**内容身份**（文件目录结构）与**谁下载过它**对全站任意登录用户可查——PT 站这是隐私与合规双重事故。
- 注：`?approval=2` 走列表那条我按子代理静态推断验过一次，**实测未泄漏**（无 `see_banned` 权限者返回不含未审种），故不列为缺陷。
- 修法：抽一个 `load_visible_torrent(db, id, viewer)`（把 detail 的谓词收口成唯一入口），所有子资源端点先过它。

**P1-2 下载重建不剥离 `url-list`（HTTP seed）**
- 实测：上传一枚带 `url-list=[http://evil.example.com/movie.iso]` 的种子，过审后 `GET /torrents/{id}/download` 返回的文件里 **该外链原样保留**；外站 `announce` 已正确剥离、`private` 已置 1、BEP12 fallback 正常。
- 根因：`bencode/torrent.rs:127` `pairs.retain(|(k,_)| k != b"announce-list" && k != b"announce")` —— 白名单只覆盖 announce，`url-list`/`httpseed`/`webseed` 变体全部漏网。
- 影响：下载者可从站外拿到数据 → 完全绕过 tracker 计量，**上传量/下载量与 ratio 失真**，且站方可被第三方源投喂篡改内容。PT 站惯例是发种即拒绝、下载时必剥。
- 修法：发种时拒收含 `url-list` 的 .torrent（给出明确原因），下载重建时无论历史数据一律 `retain` 掉。

**P1-3 发种元数据走 query string，描述长度上限由 HTTP 层决定，且失败无信息**
- 实测（同一枚合法 .torrent，只变 descr 长度）：

  | descr | URL 长度 | 结果 |
  |---|---|---|
  | 6144 字（≈12KB） | 55KB | 200 |
  | 8192 字（≈16KB） | 74KB | **400，响应体为空** |
  | 16384 字（≈32KB） | 148KB | **431** |
  | 32768 字（≈64KB） | 295KB | **431** |

- 现状：前端把所有字段拼进 `?qs`（`upload-form.tsx:223`，后端 `web::Query<UploadForm>`，`upload.rs:32`），描述 textarea `maxLength=30000`（`upload-form-descr.tsx:261`）——**前端允许的长度约为后端能收的 2.5 倍**，超了只落到 `catch { setMsg(networkError) }`（`upload-form.tsx:250`），发种员看到「网络错误」，重试无用。
- 影响：PT 站的描述正文普遍 5–30KB（截图 BBCode + MediaInfo 文本），这是**真实用户会日常撞上的发种失败**；顺带副作用：描述进 access log / 代理 URL 日志。
- 修法：把元数据改成 multipart 字段或 JSON part（保持 query 兼容一条版本周期即可），后端对 `descr/name/small_descr` 定显式上限并可配；错误必须带「哪一项超了多少」。

**P1-4 审核员手里只有文字，审不了内容**
- 实测：待审种子对站长 `GET /nfo` → **404**（`torrents/manage.rs:51` 写死 `AND approval_status = 1`）、`/download` → 404；审核队列面板无详情链接（`admin-queue-panels.tsx` 全为 `div/button`，无 `<a>`）；后台种子表的名称链接指向 `/torrents?id=…`，而 `/torrents` 页不解析 `id` 参数 ⇒ **死链**（`admin-torrents-table.tsx:111`）。
- 已有的一半：站长在制的队列改造会补 `owner_name/category/dup_hash/dup_name/过审比/descr_excerpt`（工作树 `review.rs:46-75`），方向对。
- 影响：审核员只能凭标题+800 字摘要裁决 → 内容真伪、是否盗版源、文件与标题是否相符，全都审不到。
- 修法：给 staff（或 `torrent.review`）开「审核视图」：待审种的 NFO、文件清单、原 .torrent 下载（不注入本人 passkey，只作核验）、完整描述。

**P1-5 服务端零内容质量闸门；`screenshots` 列全仓无人写**
- 实测：`无 descr/无 small_descr` 可发（200）；空名可发；截图走图床后只把 `[img]URL[/img]` 拼进 descr，`torrents.screenshots` **没有任何 INSERT/UPDATE 路径** ⇒ 在制队列里那个「截图数」列恒为 0（`review.rs:51-52` 读它）。
- 影响：审种员日常拒的三类（描述不完整 / 无截图 / 名不符实），站点没有任何一道前置门，全部堆到人审；而审核面板即将展示的「截图数」会是**一列假数据**。
- 修法：按站型/分类做**可配最低标准表**（例：必填 descr 最小长度、最少截图数、必须 MediaInfo/NFO 之一、标题命名正则），发种时服务端强制，并顺带把 screenshots 真正落库或删掉这个列。

**P1-6 危险/非法文件名原样入库并回显**
- 实测：`../../etc/passwd`、`/etc/passwd`、`..\..\win.ini` 均 200 入库，`files.path` 原样保存，`GET /torrents/{id}/files` 原样回显（叠加 P1-1 即对外泄漏）；非法 UTF-8 文件名被 `from_utf8_lossy` 替换成 `` 后入库（与原始种不一致，不可逆）。
- 修法：发种时拒绝含 `..`/绝对路径/盘符的路径段（NP 口径），或入库前清洗为安全显示形式；非法编码应拒收而不是静默替换。

**P1-7 重复发布只提示不拦，且不自动并组**
- 实测：同内容改 `piece length` 重发 → 新建成功，返回 `group_suggest:{same_source:true,torrent_id:40112}`，但两行 `group_id` 都为 NULL（**没并组、没提示审核员、也没拦**）；同名不同内容 → 直接建。
- 现状评价：`pieces_hash` 同源识别（`bencode/torrent.rs:91-99`）与 trgm 名称候选（`upload.rs:335-345`）机制是**建对了的**，缺的是把它升级成「审核可见 + 站长可配拦」。
- 修法：站长开关（默认：命中即要求并组，或进待审并给审核员高亮 dup）；队列里的 `dup_hash/dup_name` 正好是落点。

**P1-8 免审连击自我强化**
- 实测：class 92 / class 91 / `approve_streak>=5` 三条通道均 `auto_approved=true, status=1`（免审后**立刻对外可读**，符合设计）。
- 但 `upload.rs:368-376` 免审也 `approve_streak + 1`，只有被拒才清零；而免审等级用户自己的种**不需要别人审**，几乎不可能被拒 ⇒ 一旦过 5 就事实永久免审。
- 修法：连击免审加封顶（例如只在前 N 条有效，或要求「近 30 天有人审记录」），并把连击数显示在队列里给审核员参考。

**P1-9 通知与拒因是「成品中文」入库**
- `review.rs:220-240` 的 `subject/body` 用 `format!` 拼中文字面量后写进 `messages`，`deny_note` 是审核员手打的自由文本。en / zh-TW 站收到的是中文站内信，且**事后不可翻译**（这正是本项目 09-27 抽卡样张定下的口径：凡是「先存下来、以后再展示」的文本一律存 key + 参数）。

**P1-7 的机制批注（写闸门时才发现，诚实记下）**：`pieces_hash` 是 `SHA1(info.pieces)`，
只有当 `info` 字典被**逐字节复制**时才与另一枚种子相同 —— 而那种情况下 `info_hash` 也相同，

### 7.8 复验中挖出的两件事（都不属于本批改动，但影响判断）

1. **我自己的缺陷，已由闸门抓到并修**：`assert_visible` 初版写 `SELECT 1` 按 `i64` 解，
   Postgres 回 INT4 ⇒ 六个子资源端点对**所有**种子 500。
   教训与本仓既有口径一致：**闸门本身必须过一遍行为验证**——静态编译通过、单测全绿都拦不住它。
2. **站长在制的 `torrent_http/aggregate.rs` 缓存闸门在工作树里消失了**：
   该文件曾出现过 `hit 侧 approval_status==1 才用缓存` + `cacheable 才写缓存`（+51 行），
   现在两处都没有 ⇒ `e2e_surface_economy_invariants.py` 的 **J2a 待审种不进共享缓存** 回红。
   复现：把 40079 置待审 → 站长读 `/torrents/40079/aggregate` → Redis 立刻出现
   `cache:tdetail:v1:40079:1`，30 秒内任何普通会员都能拿到未过审种的标题/描述/文件清单。
   本批已按原写法把它补回（命中侧 + 写入侧各一处）。
   同一现象还发生在 `torrent_http/detail.rs` 上——我改完后被编辑器旧缓冲整文件覆写，需重新应用；
   **结论：这台机器上「编辑器保存旧缓冲」会静默吞掉磁盘上的新改动**，
   多个文件并行改时，收尾务必 `git diff` 对一遍清单，别只看有没有报错。

### 7.9 刻意没做的三件（不是遗漏，是判断）

1. **`private` 标记位置**：`build_download_torrent` 把 `private=1` 写在**根字典**，
   BT 规范里它是 `info` 的键 ⇒ 客户端不会据此关 DHT。

   `raw_info_hash` 匹配 announce ⇒ 移动后所有做种计量当场失配。
   正确做法要配套：入库时另存「分发态 info_hash」并让 worker/tracker 按它匹配。
   这是一个需要与 tracker 联动的独立改造，不该混在这批里悄悄做。
2. **非法 UTF-8 文件名不拒收**：CP1251/Shift-JIS 命名的真实种子很多，拒了等于赶客；
   只拒结构危险的（`..`、绝对路径、`\`、`:`）。
