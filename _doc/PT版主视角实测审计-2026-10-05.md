## 一、站点经济层：三处 P0，两处已实测复现

### P0-1 announce 计数器回放＝无限铸造上传量【本机实测】

`apps/worker/src/jobs/process_event.rs:109-110` 用「客户端累计总量 − 上次上报值」算增量，负数按 0 处理；
但 `:176-177,202-203` 把**本次客户端上报的原始总量**直接写回 `snatches.last_up/last_down`。
于是「报大数 → 报 0 → 再报同一个大数」每轮回一圈就多算一次全额。

实测（root / torrent 40，种子实际 15 MB）：5 次 announce 只上报了同一个 `uploaded=500GB` 计数，

```
traffic_ledger 新增 3 条，每条 delta_up = 500,000,000,000
users.uploaded  1,075,838,976 → 1,501,075,838,976   （2.5 TB 凭空产生，零字节传输）
```

放大面：任何持有 passkey 的用户 5 个 HTTP 请求＝无上限上传量。连带失效的东西——
分享率（ratio）、按比率降级、H&R 判定、等级晋升、魔力/火花经济、付费下载，
因为它们全部建立在这个数字之上。

同族两处配套缺陷：
- **无增量上限**：`apps/tracker/src/http_track/announce.rs:43-44` 原样接收 `uploaded/downloaded`，
  全程不与 `torrents.size` 比对（15 MB 的种可以报 500 GB）。
- **速度审计有 30s 盲区且不扣回**：`process_event.rs:129` 要求间隔 `secs >= 30` 才均速判定；
  实测两次 500 GB 落在同一秒（13:48:03.033 / .073）＝检查被跳过；
  而判定命中时（`speed_anomaly 8333333333B/s over 60s`）**流量照记不误**（`:243-254` 无条件 INSERT ledger）。
  即 cheat_events 是纯留痕，不是闸门。
- **重投双计**：`traffic_ledger` 无事件 id／幂等约束（`0001_init.sql:193-202`），
  而 consume 用 `reclaim_stale(360_000)` 回收 PEL（`announce_main.rs:147-148`），同一事件可被计两次。

建议（口径＝把「上传量」当账本货币，而不是当计数器）：
1. `last_up/last_down` 改 `GREATEST(snatches.last_up, EXCLUDED.last_up)`（一行改动，堵死回放）。
2. 单事件增量钳制：`delta > torrents.size × K`（K 取 2~4，站点设定可调）时**不计入**，
   改为进 cheat_events ＋ 管理组待核队列；速度判定去掉 `secs >= 30` 门槛，改按
   「累计增量 / 自上次入账的真实秒数」，并在窗口内累计（同秒多次也要能算出均速）。
3. `traffic_ledger` 加 `event_id`（announce 事件 UUID）＋ 唯一索引，XADD 时带上，落账 `ON CONFLICT DO NOTHING`。
4. 回归闸门：新增 `scripts/e2e_announce_economy.py`，把这 4 条写成断言（回放不双计／超限不计／重投幂等／补量持久）。

### P0-2 管理端「补流量」会被用户下一次 announce 抹掉【本机实测】

`apps/api/src/admin_http/user_ops.rs:56-68` 直接 `UPDATE users SET uploaded=…`，
既不写 `traffic_ledger`，也不抬 `balance_baseline`；
而 `apps/worker/src/jobs/announce_main.rs:174-190` 每次消费后对「本轮有事件的用户」重算
`uploaded = COALESCE(base_up,0) + SUM(delta_up)`。

实测（探针号 39）：

```
T0 uploaded = 0
T1 POST /admin/users/adjust uploaded_delta=1073741824 -> HTTP 200，uploaded = 1,073,741,824
   （traffic_ledger 行数 = 0，balance_baseline 行数 = 0）
T2 用户客户端一次普通 announce（零流量，只报进度）
T3 uploaded = 0        ← 站长补的 1 GB 静默消失
```

运营后果：版主给被误判的用户补量、捐赠/商店发放的上传券、活动奖励，
只要用户客户端还活着（默认 1800s 内必发生一次 announce），这笔补偿就蒸发；
用户看到「说好了补给我，怎么没到账」，版主无法自查是哪儿吃掉的。
同形状的写入口还有 `admin_http/user_detail.rs:180`（upload_credit）。

建议：凡改 `users.uploaded/downloaded` 的路径一律**改走 traffic_ledger**（新增 kind=`admin_adjust`），
或同事务抬 `balance_baseline`；并在 `reconcile` 里加一条不变式断言
「`users.uploaded == base_up + sum(delta_up)`」，不等即 WARN 进 runtime_logs。
`UserAdjustReq.note` 目前是「声明了但从不绑定」（`:24` vs `:81-95`），要一并落进流水原因列。

### P0-3 版主要哪个用户的 passkey 就能拿哪个，且不留痕【本机实测】

`apps/api/src/admin_http/user_detail.rs:49-56`：路由门槛只有 `staff()`（＝`staff.panel` 权限），
SELECT 里直接带 `u.passkey`，返回体还含 email、last_ip；**该 handler 不写 audit_log**。

实测（把探针号临时设为 class 92 论坛版主）：

```
GET /admin/users/1 -> HTTP 200，data.passkey = 771ffcb4…（与库中站长真值一致）
                       data.email / data.last_ip 均在
之后 30s 内 audit_log 相关条目：0
```

`/me/passkey/rotate` 的自服务改密路径也印证了 passkey 的价值：拿到它就能以受害者身份
announce、计流量、下载，等于接管其做种身份。
组合风险：P0-1 的铸币 ＋ 无审计的批量读取 ＋ 轮换后 60s 才失效（见 P1-4）＝
一个被收买或被盗的版主账号可以把全站用户的上传量任意改写而不被发现。

建议：`/admin/users/{id}` 返回掩码（`771f****`）；查看/重置明文 passkey 拆成独立
`POST /admin/users/{id}/passkey/reveal`，要求 `user.passkey.reveal`（新权限，缺省仅站长/主管）
＋ `ensure_outranks` ＋ 强制写审计（含目标 id、理由）。后台列表页一律不出现 passkey 列。

## 二、凭证与封禁级联：处置动作「点了但没断」

### P1-4 passkey 轮换后的失效延迟：**实测 ≤3s，原报「60s」为误判【本报告已更正】**

我最初据 `helpers.rs` 的 60s TTL 判定「旧 key 可用 60s」，实测也只抓到「轮换后 0s 仍 ACCEPTED」。
但漏看了 `apps/tracker/src/main.rs:193-197`：guard 版本轮询（每 3s）命中变化时会
`st.guard_write().passkeys.clear()`，且 `auth_http/me_security.rs:25` 的轮换确实调了
`bump_guard_ver`。所以真实窗口是 **≤3s**，不是 60s。
教训（记形不记码）：**「缓存 TTL = 失效延迟」只在没有主动失效通道时成立**；下结论前要把
失效触发链（写侧 bump → 轮询 → clear）跑一遍，我的探针只测了 t=0s 与 t=65s 两点，
中间的 3s 窗口没采到就顺手接受了代码注释里的 TTL 值。
本批只改文案口径（`me_security.rs` 注释已改为「随 guard 版本轮询 ≤3s 失效」）。

### P1-5 封禁对 Web 会话是立刻生效，对 tracker 是 60s 后生效；且凭证不轮换【本机实测】

```
POST /admin/users/status status=2 -> 200，库里 status=2
封禁后 0s：  受害者已签 JWT GET /me = 403，GET /torrents = 403   ← 这块做对了
            该用户 passkey announce = ACCEPTED                    ← 60s 缓存窗口
封禁后 65s： passkey announce = REJECTED
passkey 是否随封禁轮换：False；api_tokens / RSS key / user_passkeys 不回收
```

建议：guard 缓存里 passkey→user 的映射在「轮换／封禁／删号」三种事件下**按 key 主动 DEL**，
不要等 TTL；封禁时顺带轮换 passkey 并写 `token_revocations`（`nbf=now()`），
解封时提示「旧下载工具配置需重新导入」。PT 场景里「封了但客户端还在跑」是版主最常被质问的一条。

### P1-6 11 个 PT 风控设置是假开关（填了没用）【代码实测：grep 零消费者】

`apps/api/src`＋`apps/web` 全域 grep，命中文件数＝0：
`ratiolimit` `dlamountlimit` `enable_hr` `maxip` `securetracker` `cheaterdet`
`maxseeding` `perseeding` `deldeadtorrent` `expirefree` `enable_freeleech`。
另有 `user_classes.min_ratio` 是**死列**（全仓零引用），下载闸门
（`publish_http/download.rs:16-31` ＋ `torrents/charge.rs`）只判「过审＋付费余额」，
**没有任何比率/等级下载门槛**。

按项目既定口径「要么真生效要么删」处理。其中值得真接的三条（版主日常真的要用）：
`ratiolimit`＋`min_ratio` → 下载闸门按等级下限拦（现在只有 `ratio_watch_*` 的 14 天观察期，滞后且软）；
`maxseeding/perseeding` → 做种数上限（现在是纯摆设）；
`maxip` → 同 passkey 并发 IP 数（`snatches`/peers 表有数据，判定不存在）。
真正在跑的只有：`announce_interval`、`speed_alarm_bps`、`hr_hours/hr_violation_limit`、`ratio_watch_*`、`agent_rules`。

## 三、版主动线：能审、但审得又瞎又险

### P1-7 审核队列不下发内容【本机实测＋代码】

`GET /admin/reviews` 的 SQL 只取 `id,name,owner_id,size,created_at`（`admin_http/review.rs:27-33`），
面板 `_parts/admin-queue-panels.tsx:27-51` 也就只渲染这 5 个字段。
版主看不到 descr／文件清单／NFO／截图／上传者历史／查重命中，
却要按「过/不过」决定一条种子的生死——实际等于逼着版主只看标题审。
（本条为接口层证据；面板截图未做，不作为视觉结论。）

配套：批量端点 `admin_p3_http/torrent_batch.rs:69-293` 的动作清单里**没有 approve/reject**，
只能一条条点（`review.rs:48`）；拒绝原因字典 `torrent_deny_reasons` 有 CRUD、有种子数据、
也真会发给上传者，但审核队列自己的 reject 只发自由文本（`admin/page.tsx:160-170`），
工作台还要求手输数字 id（`components/admin-torrents-list-parts.ts:30-36`），
而维护字典需要 `settings.manage`＝class 95，版主连「改个措辞」都做不到。

### P1-8 权限粒度不支撑「造一个只审某区的版主」【本机实测】

`user_can(uid,perm)`（`0056_user_can_fn.sql`）是「等级阈值 ∪ 职务」，方向对，但：

```
class 91 发布员     staff.panel user.warn bans.manage plugins.manage audit.view offers.promote
class 92 论坛版主   同上（且 torrent.manage 已在 >=90 授予 ⇒ 能审/能删任意种子）
class 93 总版主     + user.adjust
class 99 站长       + roles.manage settings.manage
```

三个问题：① 审、删、改种全挤在 `torrent.manage` 一个键，无法拆分；
② 论坛版主天生可审全站种子（`forum_mods` 只作用于论坛，无 `category_mods` 表，
`review.rs:26-34` 零 actor 过滤）；③ `role_permissions` 里 class 90 一次性 INSERT 25 键
（含 `bans.manage`/`plugins.manage`/`audit.view`）——`plugins.manage` 能改站点行为，
不该是「论坛版主」的默认赠品。

### P1-9 缺少等级护栏的具体写口【本机实测】

```
class 92（论坛版主） POST /admin/users/1 {"weeks":1} -> HTTP 200
                     root.warned_reason 实际写入 "AUDIT-PROBE"
```

`staff_http/warned.rs:38-52` 只判 `user.warn` 权限，没有 `ensure_outranks`
（对照 `admin_http/user_status.rs:105` 是有的）⇒ 版主可以给站长挂警告。
`gaps_http/appeals.rs:265-275` 申诉通过解封同样没有护栏 ⇒ 版主可解开被删档/被封的管理员。
`admin_http/roles.rs:87-104` 有 outranks 但没有 `roles.manage` ⇒ 版主可给任意低等级用户
发 `uploader` 职务（＝`torrent.approval.auto`，等于给熟人开后门绕过审核队列）。
建议：把 `ensure_outranks` 从「各 handler 自觉调用」改成中间件级——凡 body 带 `user_id`
的管理写口统一先判，漏判即 403，并在 e2e 里对每个写口跑一条「低等级打高等级必 403」。

### P1-10 审计链「有形式、无内容」【本机实测】

写口 `repo/mod.rs:229-245` 只把 `ref` 存成 `{"id": <目标id>}`，
读模型 `admin_http/audit.rs:30-33` 又只 SELECT `id,actor_id,action,created_at`（连 `ref` 都不取）。
实测刚做完一批操作后：

```
GET /admin/audit 返回行： {id, actor_id, action, created_at}
库中真实 ref： warn_user | {"id": 1}      shop_buy | {"id": 12}
```

0266 的哈希链让审计**不可篡改**，但审计**不可读**——
「谁改了这名用户的余额、改成多少、为什么改」目前无法回答，
而这三问是版主交接和纠纷仲裁的全部依据。
建议：`audit(actor_id, action, target_type, target_id, detail jsonb, reason text)`，
读模型显示 target＋detail 摘要＋reason；敏感读取（`/admin/users/{id}`、`/snatches`、
`/admin/spark-logs`、`/admin/login-logs`、`/admin/reports`）也要各写一条 `*.view` 审计——
它们现在一条都不写（`user_detail.rs:53`、`records.rs:42,87,121` 等）。

### P1-11 举报与内容处置链半闭环

- 可举报对象＝种子/评论/用户/字幕/论坛（`http/misc_handlers.rs:219`），**没有站短/PM**，
  也没有任何 admin 路由读 `messages` ⇒ 站内信骚扰对版主不可见。
- `POST /reports` 无条件 INSERT（`misc_handlers.rs:250-258`），
  `(ref_type,ref_id,reporter)` 无唯一约束、无去重、无限流 ⇒ 同一目标被举报 50 次＝队列 50 行。
- 处置只有 act/dismiss（`admin_http/reports.rs:92-95`），不能顺手警告/封禁/删内容；
  claim/release 有，但 resolve 不校验 `claimed_by`（`:109-111`）⇒ 别人能关你手上的工单。
- 内容删除是物理删除：`DELETE FROM posts`（`community_http/post_edit.rs:115`）、
  `topics`（`:262`）、`comments`（`torrent_http/interact.rs:65`）⇒ 无墓碑、不可恢复、
  版主误删无法自证清白（这与 P1-10 是同一个病根）。
- 没有「版主主动巡检队列」：无 `/admin/comments`、`/admin/posts` 路由，
  版主只能处理被举报到的内容；PT 站实际需要的正是主动巡查（热帖/新评论/新做种包）。

### P2-12 其他版主力所缺

- **无跨站/改名查重**：查重只比 `info_hash` 完全一致（`publish_http/upload.rs:120-140`），
  `files` 表只有 `path,size`，没有文件级 hash ⇒ 换名重打包/重制包检不出来，
  上传者也不会被告知「已有同类源」。
- **复活（resurrection）没有管理侧**：`ops_http/resurrections.rs:12,60` 只有用户申请与领取，
  奖励硬编码 5000（`:92`），无后台队列/指派/改奖励；`/admin/docleanup` 不碰死种。
- **发种者信誉只有 approve_streak/deny_count**（`review.rs:107-115`），
  `/admin/uploaders`（`staff_http/site.rs:199-215`）是裸计数，版主挑「可信做种包」时无从判断。
- **通知缺口**：封禁/停下载/删种/批量改种/职务授予/权限覆盖**零通知**
  （`user_status.rs:34-70`、`torrents/interact.rs:115`、`torrent_batch.rs`、`roles.rs`、`perms.rs:239`）；
  Web Push 只在站短触发（`push_notify.rs:41`）。被处置用户只看到「突然不能用了」，
  这是版主工单量的直接来源。
- **邮箱域名策略入口不全**：`email_policy.rs:47-51` 只接在 `/auth/register` 与 `invite_http/email.rs`，
  申请入口 `/apply`、后台 `adduser`、找回密码都没过策略；空列表时 fail-open；
  且只比对最后一个 `@` 段 ⇒ 封 `qq.com` 挡不住 `mail.qq.com`。

## 四、作为版主，我要先承认这些是真能用的

- **H&R 链路是真的**：`worker/src/jobs/hr.rs` 会按 `hr_hours/hr_violation_limit` 判定，
  命中后 PM＋push＋`download_enabled=false`，不是留痕而已。预警邮件通道（c4337e）也已装配。
- **ratio_watch 观察期是真机制**：跌破 `ratio_watch_threshold` → 进观察期 ＋ 一次性警告信 ＋
  到期未恢复自动停下载（`worker/src/jobs/audit.rs:136-256`）。缺的是「即时硬门槛」，不是全盘空白。
- **announce 侧防护是真的**：passkey→用户、IP 黑名单、每 IP/每用户频率、UA/peer_id 黑名单、
  info_hash 未注册拒（`torrent_registered`，DB 异常 fail-open 需注意）、
  畸形 `left` 不再被当做种（ZT81）。`.torrent` 生成注入 private=1 ＋ 用户 passkey。
- **封禁对 Web 会话即时生效**（实测 403），装机/迁移/门禁闸门齐全。

## 五、建议的动手顺序（若按一个批次做）

**Round A（止血，改动小、收益大）**
1. `last_up/last_down` 改 `GREATEST(...)` ＋ 单事件增量钳制 ＋ ledger 事件 id 幂等 → 附 e2e。
2. 管理补量走 ledger（`user_ops.rs`／`user_detail.rs`），`reconcile` 加对账断言。
3. `/admin/users/{id}` 去 passkey 明文，reveal 拆端点＋权限＋审计；passkey 轮换/封禁主动 DEL guard 缓存。
4. `warned.rs`／`appeals.rs` 补 `ensure_outranks`；`roles.rs` 补 `roles.manage`。

**Round B（版主可用）**
5. 审核队列补内容字段＋批量审批＋拒绝字典下拉＋查重命中；`torrent.manage` 拆 review/edit/delete；新增分类归属表。
6. 审计读写两侧补 detail/target/reason ＋ 敏感读取留痕；帖子/评论删除改墓碑。
7. 举报去重唯一约束＋SLA＋`claimed_by` 校验；处置动作补通知（封禁/停下载/删种/批改）。
8. 假开关按「要么接上要么删」清一遍（优先接 `ratiolimit`/`min_ratio`/`maxip`/`maxseeding`）。
