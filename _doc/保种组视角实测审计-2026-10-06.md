# 保种组视角实测审计（2026-10-06）

> 角色：资深 PT 站保种组（负责种子活着、分享率经济可信、做种考核可执行）。
> 轴：与一/二/三/四轮（经济、对外接口面、发审种动线、读路径）不重叠。
> 方法：读码 + 在册账号末端实测（真打下载口、真解 `.torrent` 字节）+ 全站库内体检。

## 二、P0-A：零分享率账号可以整库下载（实测）

现造在册账号，落库 `uploaded=0, downloaded=10 GiB`、`ratio_watch_until=NULL`，
站点设置 `ratiolimit=6`、`ratio_watch_threshold=0.4`、`ratio_watch_action=limit_download`，
然后直接打下载口：

```
探针 uid=4214 torrent=42237
ratio=0 watch=NULL download_enabled=t ratiolimit=6
下载响应 HTTP=200 前 200 字节=b'd8:announce63:http://127.0.0.1:7070/announce/…4:infod5:files…'
```

拿到的是带本人 passkey announce 的合法 `.torrent`。链条上没有任何一环判比率：

1. `charge_for_download`（付费种子才扣魔力）——不看比率；
2. `build_torrent_bytes` 的闸门只有 `suspended` / `download_enabled`（`download.rs:80-95`）；
3. 唯一的比率处置是 `ratio_watch`（`worker/src/jobs/audit.rs:136-200`）：跌破 0.4 →
   发一封警告信 + 14 天观察期，到期仍跌破才 `download_enabled=false`；
   且 `class_id >= 90` 与 `downloaded = 0` 一律豁免。
4. 等级晋升（`class_adj.rs:67,179`）判据是 `min_uploaded` + `min_download_count`，
   **不含比率**；`user_classes.min_ratio` 这列自 0001 建表起零消费。

对被停下载的账号，tracker 只在 `left > 0` 时拒 announce（`apps/tracker/src/http_track/announce.rs:108`），
所以「停下载」之后**照样能靠 announce 刷上传量、照样领做种魔力**——惩罚打在错误的那一侧。

**这为什么是保种组的命门**：分享率是保种考核唯一的全站杠杆。杠杆不存在时，
做种时长榜、H&R、等级晋升全都建立在可以被「只下不做」白嫖的账本上。

**建议（按性价比）**

1. 把 `ratiolimit` 变成真闸门：`build_torrent_bytes` 之前加一道
   `ratio_gate(db, uid, torrent)`——全局阈值 ∪ 等级阈值（复用 `user_can` 那种
   SQL 函数口径，别让规则再有两份），豁免位显式列出：
   保种区/复活任务在做的种、`price=0` 且在观察期内的新注册用户、H&R 已豁免者。
2. `psratioone..five` 与 `user_classes.min_ratio` 二选一：要么接到
   `class_adj` 的**降**级支路（现在降级只看 demotable 的绝对量，不看比率），
   要么从后台摘掉。假开关比没有开关更坏——它会误导站长的运营决策。
3. `download_enabled=false` 之后应当**同时停掉上传记账资格**（或改成
   「只许做种不许领 seeding 魔力」），否则惩罚可被 announce 抵消。

## 三、P1-B：保种区收不到「有人在等」的死种

`preserve_seed` 每 300s 跑一次，谓词是
`t.seeders = 0 AND t.leechers = 0 AND t.approval_status = 1 AND created_at < now() - preserve_dead_days`。
`leechers = 0` 这一条把「0 保种但有 N 个下载者在等同伴」——**保种价值最高、
用户感知最痛**的一类——永久排除在保种区外；而复活任务
（`resurrections.rs:12-41`，谓词 `seeders=0 AND 30 天无 snatch`）反倒不看 leechers。
两套「死种」定义不一致，界面上却都叫保种。

濒危雷达（`social_http/endangered.rs:112-137`，`seeders<=1 AND times_completed>=3`）
**模块默认关闭**，新站开箱即无。

建议：① 保种区谓词改 `seeders = 0 AND (leechers > 0 OR times_completed > 0)`，
并把 `leechers` 作为排序权重的第一键；② 两个「死种」口径合并成一个 SQL 视图，
保种区/复活任务/濒危雷达各自引用它——与本轮商城「两份规则时界面那份必是被改漏那份」同型；
③ 保种类工具**现在没有一个读 `pick_type` / `official_tag` / 精选**，
建议给它们一个权重入参（精选种优先出奖金、优先派任务）。

## 四、P2-D 全站 hash 体检（脚本已留）

`.workbuddy/_probe_hash_inventory.py`：对每个种子取 `torrent_files.raw`，
按 bencode 边界切出 `info` 原始字节，`SHA1` 后与 `torrents.info_hash` 比对。

```
总数=38 一致=37 异常=1
  torrent 40079  approval=1  info_hash 分叉 库=7f3989e3… raw=f1dd9a3e…
```

#40079 是 10-03 的「对接自测种子 (demo)」（size 96B / raw 213B），大概率是旁路 SQL 直插
`torrents` 行而没走发种链。**定性还没做**：需要用真实发种路径复现一次，
若真实链上也分叉，那才是产品缺陷（当前发种链是好的——今天新发的 42237/40360 都一致）。

顺带一个正面结论值得记：**BEP27 的 `private` 已经在 `info` 内**（40360/42237 实测），
且写进 info 之后 info_hash 仍与库里一致 ⇒ 上一轮那条「私有站命门」在**新发的种**上已闭合；
但**老种**（40/40049/40079 实测）info 内仍无 private ⇒ DHT/PEX 对存量种依然开着，
这正是审计报告里留待拍板的「要不要给存量种做带迁移的口径变更」——**这条仍未拍板**。

## 五、口径闭环、本轮无缺陷的部分

- 流量增量不信客户端累计值：`(ev.up - last_up).max(0)` + `FOR UPDATE` 串行化
  + 物理上限 `credit_ceiling × secs`（`process_event.rs:120-147`）；上限夹
  `[1 MiB/s, 1 TiB/s]`，设定填 0/非数字既不清零也不放开。
- 事件幂等：`announce_seen(event_id)` 主键 + `ON CONFLICT DO NOTHING`（0285），
  3 天清理。
- `users.uploaded/downloaded` 单一真值是 `traffic_ledger`（基线 + SUM），
  每轮 announce 点刷 + 每 6h 全站重算 + 漂移 >10 GiB 告警。
- 做种魔力有渐近上限（arctan，150/h）、稀有度加权、donor ×2，
  且排除「不可达且零上传」与陈旧行；`seeded_seconds` 受 `seed_cap` 容忍窗夹取。

## 六、过程性发现（不是产品缺陷，但会骗过验收）

上一批（商城审计）的 **P0-2 / P1-1 / P1-2 / P2-2 / P2-3 只在源码里，没进线上镜像**：
api 镜像 18:17 构建，而 `admin_p3_http/shop.rs` 18:20、`economy_http/shop.rs` 18:47 才改完。
二进制内标识符核对（带阳性对照）：

```
未知商品类型      0     ← 新代码的护栏文案
价格须在 1 - 1,000 0
stock_left        0
admin/shop-items  2     ← 阳性对照，证明 grep 方法有效
发放未生效         1     ← 同批的发放侧修复确已在镜像里
```

实测在 :8080 上真建成了 `price=-100` 与 `kind=free_money_forever` 两个 SKU（已删，
`shop_items` 回到 29 行）。**现有 pt_audit 闸门家族没有任何一条覆盖商店护栏**
（`b_billing` 全是计费/announce 断言），所以「五套门禁全绿」不等于商城 P0 已上线。
建议把负价/kind 白名单/PUT 库存/重放不占库存/空幂等键/`stock_left` 六条收进
`pt_audit_f_shop.py` 挂 `ci_local.sh --with-pt`，并在闸门里保留一条
「只有新代码才可能通过」的部署对照。

## 七、优先级建议

1. **立即**：P0-A 第 1 条（即时比率闸门 + 豁免位）——它是保种考核的地基；
   商店护栏只需重建 api 镜像 + 一条闸门即可闭环。
2. **本周**：P1-B 两个死种口径合一 + 保种区收「有 leecher 的 0 保种种」；
   `download_enabled=false` 与上传记账的关系拍板。
3. **需拍板**：存量种 `private` 是否随迁移进 info（改 info_hash 的代价 = 全部
   历史 announce/做种归属要重挂）；`ratiolimit` 的默认值（NP 口径 0.5 vs 现值 6，
   6 意味着「比率低于 6 才限制」= 实际上永不限）。
