## TL;DR

防线比一般开源 PT 站厚（双口径哈希、幂等键、物理速率钳制、白名单、回连抽样、差额对账都有），
但**每条防线的默认参数都开在最宽松档**，且存在一个可无限复用的基线重置漏洞。实测结论：

## 一、防线现状盘点（哪些已做对）

- ✅ announce 双协议：passkey 鉴权 + 60s 缓存（含负缓存）、IP/用户/全局三级限流、
  IP 封禁、客户端黑白名单（UA+peer_id 交叉）、种子白名单（双口径 info_hash）、
  `stopped` 归属校验（不能踢别人下线）、每账号每 swarm 10 peer 上限、空桶 GC。
- ✅ 计费：`announce_seen` 幂等键（0285）防重投双计；增量按 `last_up/last_down` 差值；
  物理速率钳制 `credit_ceiling × secs`；促销按事件时点裁决；券核销同事务。
- ✅ 余额：流水权威 + `balance_baseline` 基线 + 6h 对账告警，`users.uploaded` 只是快照。
- ✅ 做种收益：`last_seen_at` 新鲜度过滤（僵尸不发钱）、`connectable=0 AND uploaded=0` 幽灵过滤、
  幂等键 `seeding:{user}:{hour}`。
- ✅ H&R：快照口径、免费窗口豁免、buffer 10% 豁免、hr.exempt 权限豁免、prewarn、自动处罚/恢复。
- ✅ 回连抽样：5min/50 个、未测优先+轮转（含 retriable 轮转）、结果随事件流回写。
- ✅ 事后审计：torrent_gap 差额对账、multi_ip_check、speed/ghost cheat_events、DLQ 告警。

## 二、实测漏洞详情

### P0-1 基线重置套利（process_event.rs 计费核心缺陷）

**位置**：`apps/worker/src/jobs/process_event.rs:132-133` + snatches upsert `last_up = EXCLUDED.last_up`。

**机理**：`raw_up = (ev.up - last_up).max(0)` 本意是「计数器回绕按 0 处理」，但 `last_up` 的写入
是无条件的——announce 报什么，基线就变成什么。于是：

1. 报 `uploaded = 9223372036854775807`（i64MAX）→ 增量被钳制不人账，但 **`last_up` 被写成 i64MAX**；
2. 再报 `uploaded = 0` → `raw_up = max(0 - i64MAX, 0) = 0` 不入账，但 **`last_up` 归零**；
3. 此时 `last.is_some()` 基线存在、但 `last_up=0` → 下一次报 300 GiB，`raw_up = 300 GiB`，
   秒差口径 → 又被钳制；**但如果先等 60s 再报**，`allowance = 2GiB/s × 60s = 120 GiB` 全额入账。

实测（用户 4149 / 种子 42514）：i64MAX → 0 → 300GiB 三连后，`snatches.last_up=0 → 322122547200`，
累计刷入 **1.32 TiB**，中间仅产生一行 `over_ceiling hits=1`（无任何阻断）。

**变体（更隐蔽）**：报 i64MAX 后正常使用（报真实值）→ `raw_up = max(真实值 - i64MAX, 0) = 0`
**真实上传也不入账**（反向作弊：只刷时长不刷量，H&R 义务最小化）；或报 0 把基线永远钉死在 0
→ 每颗种子都能反复吃首报额度。

**根因**：`last_up/last_down` 是「客户端上次的累计读数」基线，但它同时被用作增量换算的锚点，
而**写入它时没有任何有效性校验**（回绕检测、与上一基线的单调性检查都没有）。

**修法**（三选一，推荐 A+B 组合）：
- **A. 单调性守卫**：`raw_up` 只有在 `ev.up >= last_up` 时才换算增量；`ev.up < last_up`（回绕/重置）
  时**不更新 `last_up`**（保持旧基线），增量记 0，并把该 peer 记入 cheat_events（counter_reset）。
  回绕是真实存在的（32 位客户端），但真实回绕幅度极小（从 2^32 附近回 0），可以用
  `last_up - ev.up > 2^33` 判定为「恶意重置」，小幅回退才按回绕容错。
- **B. 基线只进不退**：DB 层 `last_up = GREATEST(snatches.last_up, EXCLUDED.last_up)`（i64MAX
  会钉死基线，需配 A 的上限校验：`ev.up > 某物理上限（如站点总流量+种子大小×倍数）` 直接拒）。
- **C. per-torrent 天花板**：`snatches.uploaded` 累计不得超过 `种子大小 × 站点系数（如 1000×）`，
  正常做种几十年也到不了，伪造者一碰就 clip。

### P0-2 幽灵做种（假保种）全链路可刷

**实测**：对 5 颗种子各发一条 `left=0, port=0, numwant=0` 的 announce（纯 HTTP GET，无客户端、
无文件、无监听端口），worker 消费后：

- 5 行 `snatches.seeding=true`（`port=0` 在 tracker 内存表被剔除、但 **DB 侧照写**）；
- `torrents.seeders` 4 颗从 0 → 1（**在线做种数被抬高**，其它客户端看到「有人保种」）；
- `seeded_seconds` 持续累计（实测 120s → 180s → 780s，每 announce 周期都在涨）。

**发钱面**（每一条都是真实利益）：
1. **做种收益**（seeding_reward）：唯一幽灵过滤是 `connectable=0 AND uploaded=0`。实测里
   connectable=1（tracker 回连结果未及时覆盖/历史值），过滤不生效 → 火花照发。
   绕过方式极多：偶发上传 1 字节（uploaded>0）、让端口短暂可达一次（connectable=1 之后
   5min 轮转复测周期内一直有效）、或干脆 NAT 后端口巧合开放。
2. **保种区认领**（preserve_settle）：认领后「结算时点在种」即发 `preserve_bonus_per_day`——
   「在种」的判定就是 `snatches.seeding`，幽灵挂种即满足，无需真实文件。
3. **复活任务**（resurrection_settle）：`seeded_seconds >= required_hours AND seeding`——
   ghost 挂种 240 小时即领 5000 魔力+免费券+7 天免费（无需下载过文件，实测 completed 事件
   可伪造，snatches 行直接 seeding=true 连 completed_at 都不需要）。
4. **任务系统**（task_settle）：`seed_points_delta` / `seed_seconds_delta` 指标全部来自
   `sum(snatches.seeded_seconds)`，无独立校验。
5. **等级晋升**（class_auto_adjust）：`min_seed_hours` 来自同一 `seeded_seconds`。
6. **每日做种满 6h 发口粮券**（games_coupon_seed_hours）：复用 seeding_reward 流水判定。

**修法**：
- **A. seeding 有效性三条件**（推荐落到 process_event / snatches 写入处）：
  `seeding = ev.left==0 AND port>0 AND connectable!=0`。port=0 明确不可连接——正常客户端
  做种必带监听端口；connectable=0（回连不可达）时先降级为 `seeding_suspect` 而非直接发钱。
- **B. 上传量与做种时长的交叉校验**：长期（如 ≥7 天）`uploaded == 0` 且 swarm 内有 leecher
  的 seeder，做种收益打折/暂停（真实做种者对热门种必有零星上传；对 0 leecher 的冷种豁免，
  否则误伤保种员——保种场景多数时间无人下载，这也是为什么不能简单一刀切）。
- **C. completed 事件需要「下载侧证据」**：`event=completed` 时校验该用户该种子存在
  `downloaded ≥ size×4%` 的历史（券核销/H&R buffer 都用 10.4% 口径，这里可用 4%），
  否则 completed_at 不落、times_completed 不 +1。
- **D. 保存 & 复活领取资格**：认领/领取前要求 `snatches.completed_at IS NOT NULL` 或
  管理组白名单（保种员常常有站外备份、重新下载即可，正常路径不受影响）。

### P1-3 物理速率上限缺省 2 GiB/s

`traffic_credit_max_bps` 缺省 2147483648（`process_event.rs:286`，站点当前值也是 2 GiB/s，
clamp 下限 1 MiB/s 上限 1 TiB/s）。2 GiB/s = 16 Gbps——现实中不存在 household 线路，
NVMe 本地盘间传输也才 ~3.5 GB/s。实测稳定刷 120 GiB/分钟（每 60s 报一次恰好贴额度）。

**修法**：缺省降到 125 MiB/s（1 Gbps 线路的合理上限，万兆站长可自行上调）；或按用户等级/
做种时长动态给额度（新号 32 MiB/s，老保种员放宽）；超出额度部分当前只是 held——建议
`held` 累计达阈值（如 10 GiB/周）自动降级 `seeding_reward` 并 PM 警告。

### P1-4 首报额度按「有 snatch 行」判定而非「真首报」

`process_event.rs:142-145`：`secs = last.and_then(...).unwrap_or((seed_cap/2).max(60).min(300))`。
首报额度 300s × 2GiB/s = **600 GiB/颗种子**。10-06 审计把它从 900s 收紧到 300s，方向对，
但没堵「换种子无限首报」：站内种数 = 首报次数上限。实测单种首报 600 GiB 秒到账。

**修法**：首报额度改成「窗口内全站首报总额度」——`users` 上的新列 `first_report_budget`
（如每日 50 GiB，随等级增长），或简单粗暴：首报增量上限 = `min(300s×速率, 种子大小×2)`
（下载都没开始就报 600 GiB 上传，物理上不可能——**上传量不可能超过已下载/已有的数据量**）。

### P1-5 cheat_events 无执法闭环

实测全程只产生 3 行 cheat_events（over_ceiling×2 / suspect_ghost_seed×1），hits 各=1，
无 PM、无限制、无人工介入入口提示。`agent_hit_action` 只作用于客户端黑白名单，对
speed/ghost/torrent_gap 类事件没有任何分级处置（连累进阈值都没有）。

**修法**：
- 给 cheat_events 加 `severity` 与累进处置链：如 over_ceiling hits≥3 → 自动 PM 警告；
  hits≥10 → 该种子做种收益暂停 + 管理组信箱置顶；suspect_ghost_seed hits≥5 → 自动把
  该用户全部 `snatches.connectable` 复测一轮。
- 后台「作弊探测」页加待办视图（未处置的 first_hits 排序），而不是只能翻 200 条列表。

### P2-6 稀有度加成可被 swarm 计数污染

seeding 公式的稀有度项 `(1 + rarity_k × seeders^-rarity_exp)`、濒危档 `seeders<=1 AND
completed>=3` 都吃 `torrents.seeders` 快照。实测 ghost announce 能把 seeders 0→1；再多几个
小号就能把种子钉在「濒危」档（2.0 分）+ 独苗加成（×1.6），配合 P0-2 幽灵挂种吃高额收益。
快照口径 `count(snatches.seeding)` 修掉 port=0 后此路即断（与 P0-2 同修）。

### P2-7 UDP 事件 agent 恒空

`udp/announce.rs:190`：UDP 事件 `agent=""`。BEP15 无 UA 头是协议限制，但 agent_rules 若
只配 UA 侧正则，UDP 通道就是豁免通道；且 snatches.agent 被空串覆盖（`agent = EXCLUDED.agent`
每次 announce 覆盖），HTTP 侧记录的 UA 会被 UDP announce 冲掉。**修法**：空 agent 不覆盖
（`agent = COALESCE(NULLIF(EXCLUDED.agent,''), snatches.agent)`），并把「同一用户 HTTP/UDP
双通道混用」记入 cheat_events 供人工研判。

### P2-8 cheat_audit 的双用户门槛与免费豁免窗口

`HAVING ... AND COUNT(DISTINCT user_id) >= 2`（audit.rs:61）：单账号刷量不触发。
设计意图是「虚报上传者没有对应真实下载方」需要对价用户，但攻击者挂 ghost seeder 等
真实用户来下载时，差额又恰好对冲不齐——**先下载完再伪造上传的攻击者全程隐身**
（实测 723 GiB 差额零告警）。免费豁免判定用 `now()` 而非事件时点，促销刚结束的 7 天窗口
内刷的量会被误豁免。**修法**：`COUNT(DISTINCT user_id) >= 1` + 按事件时点判促销
（ledger 里已存 promotion_kind，直接用它豁免更准）；差额阈值从绝对 GiB 改为
`gap / max(1, Σdown)` 相对比率（up/down > 5 且 Σup > 50GiB 即报）。

### P2-9 其它确认过的次级问题

- **XFF 右值信任**：TRUST_PROXY=1 时 `client_ip` 取 XFF 最右段——多层代理/自建代理场景
  攻击者可控自己 proxy hop 数伪造 ip 进事件流（取证污染+限流绕过），文档已声明单层假设，
  但建议增加 `TRUST_PROXY_DEPTH` 配置显式对齐部署拓扑。
- **snatches.agent 被 announce 覆盖**（0098 口径）：做种榜单/peers 面板的客户端列可被任意
  伪造（实测 `User-Agent: qBittorrent/5.0.0` + 伪 peer_id 前缀即过），仅取证参考价值，
  不能作为白名单执法依据——UA 侧 agent_rules 只能当旁路信号，主判定必须在 peer_id 侧。
- **回连抽样 50/5min**：大站（>10 万 peer）全量复测周期 >33 小时，伪造者有充足窗口在两次
  复测间保持 connectable 历史值。建议按 swarm 热度加权抽样（有 leecher 的 swarm 优先）。
- **`port=0` peer 不下发但 DB 计数照收**：内存侧已防（table.rs:162 count 排除 port=0），
  但 worker 快照点刷 `count(snatches.seeding)` 无 port 概念——P0-2A 修掉后自然对齐。

## 三、已验证无需整改项（防误报）

- 计费速率钳制本身工作正常：秒级 8 GiB 增量被正确 held 且只入账 2 GiB；
- `announce_seen` 幂等键防住了同事件重投（ghost 多 peer 实验中每事件恰好入账一次）；
- 负数 uploaded/downloaded、left 非法、peer_id 长度非法均在 tracker 侧拒绝；
- stopped 事件无法伪造他人下线（remove_owned 归属校验）；
- 未知 info_hash 被种子白名单拦截；
- 促销/券倍率在事件时点裁决，DLQ 积压重放不会按过期价补计费；
- 保种区结算的「天数=已发次数+1」口径已堵住「反复上下线刷首档」（三轮遗留修复确认）；
- H&R 的免费窗口豁免/buffer 豁免/hr.exempt 语义正确（保种员视角无压迫感）。

## 四、修复优先级建议

1. **立即**（P0）：P0-1 基线重置守卫（改动集中在 process_event.rs 一个文件 + snatches upsert
   SQL，约 30 行）；P0-2A `seeding` 三条件（port>0 且 connectable!=0，改动两处）。
2. **本周**（P1）：速率缺省降档、首报额度加上传量物理上限、cheat_events 累进处置、
   completed 事件下载侧证据。
3. **择期**（P2）：cheat_audit 口径、UDP agent 不覆盖、稀有度污染（随 P0-2 收口）、
   回连热度加权、XFF 深度配置。
