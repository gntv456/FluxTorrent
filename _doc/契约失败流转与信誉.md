# 契约失败流转与信誉体系

> 承接 `_doc/组队结算job与单人隔离.md`
> 到上一轮为止，契约只有「成功结算」一条路。本文补齐**失败流转**与**信誉读写**，
> 让 `social_reputation` 这张空表真正落地。

---

## 一、动手前的调研（两个发现）

**发现 1：`expired` 是个"声明了但没实现"的状态。**

`resurrections.status` 的枚举里写着 `open | done | expired`，但全仓库搜不到任何代码把状态置为
`expired` —— 和 `social_reputation` 一样，属于建表时预留、逻辑从未落地。

**发现 2：`social_team` 漏了 `deadline_at`。**

我在 0102 建 `social_team` 时只留了 `settled_at` / `fail_reason`，**没有期限字段**——没有期限就无法判定超时。

### 处置：新增 0103 迁移，而不是改 0102

0102 已在库中执行并有 `_sqlx_migrations` 记录。**sqlx 会校验迁移文件 checksum**，
改动已执行的迁移会直接导致启动失败：

```
migration 102 was previously applied but has been modified
```

所以新增 `0103_social_deadline.sql`：补 `deadline_at` 列 + 回填存量数据 + 建部分索引 +
写入信誉参数。`deadline_at` 的回填口径是 `created_at + 14 days`。

## 二、设计口径

### 2.1 不连坐（这是最重要的一条）

契约失败时**不额外惩罚个别成员**。理由在方案阶段就论证过：

> 团队连坐会让**新人不敢加入**（"我万一拖累别人怎么办"），而新人恰恰是最需要参与的人。

所以失败只做两件事：**记一次失败事实**（信誉 −5）+ 通知成员。不罚款、不追责、不公开点名。

### 2.2 「逃跑」与「尽力」必须区分

| 行为 | 信誉变化 | 理由 |
|---|---|---|
| 契约完成 | **+20** | 事实驱动，系统判定 |
| 到期未达标（尽力了） | **−5** | 只记失败事实，不重罚 |
| 中途主动退出（逃跑） | **−15** | 这才是真正该罚的 |
| 队友评价 | 不参与主流程 | 防互刷（见方案 v5：事实驱动 ≥ 90%） |

「未达标但坚持到期」和「半路跑掉」性质完全不同，惩罚必须拉开差距——否则等于逼人在快失败时提前跑。

### 2.3 信誉只影响准入资格，不剥夺已得收益

信誉分的作用是决定「能不能发起契约 / 能不能接高级契约」，**不会回收已到手的火花或荣誉**。
信誉区间 `[0, 2000]`，初始 1000。

### 2.4 惩罚的方向是"收益"而不是"羞辱"

失败通知的文案刻意写得平实：

> 资源 #N 的协作保种未在期限内达标，契约已结束。**你已产生的做种时长仍计入做种收益，不受影响。**

重点在于告诉玩家「你没有损失已得的东西」——协作失败本身就令人沮丧，不该再加一层羞辱。

## 三、实现

### 3.1 新增接口：`POST /social/team/leave`

| 校验 | 行为 |
|---|---|
| 不在队伍中 | 400「你不在该队伍中」 |
| 队伍已结束 | 400「该队伍已结束」 |
| **队长退出** | 400「队长不能直接退出」（避免队伍失去发起人） |
| 正常退出 | `join_status = 3`、`left_at = now()`、信誉 −15 |

退出后该成员**不再参与结算**（结算只取 `join_status IN (0,1)`，已产生的做种时长照常计入其个人做种收益）。

### 3.2 新增 job：`social_team_expire`

挂在 hourly tick，**排在成功结算之后**——恰好卡在期限内达标的队伍应该算成功。

```rust
with_lock(&db, "job:social_team_settle", social_team_settle(&db)).await;
// 失败判定必须排在成功结算之后：恰好在期限内达标的队伍应算成功
with_lock(&db, "job:social_team_expire", social_team_expire(&db)).await;
```

处理流程（每个队伍一个事务）：

```
CAS: UPDATE social_team SET status=3, fail_reason='deadline_exceeded', settled_at=now()
     WHERE id=? AND status IN (0,1) AND settled_at IS NULL     ← 与成功结算互斥
  → resurrections.status = 'expired'
  → 每个成员：信誉 −5（failed_count +1）
  → 站内信
```

### 3.3 成功结算补上信誉加分

`social_team_settle` 里给每个成员 `fulfilled_count +1`、信誉 `+20`。

### 3.4 一个有意为之的设计点

**worker job 不检查 `module_social` 开关**（只有 API 检查）。因为模块被关闭时，
**已经存在的契约必须能收尾**——否则那些队伍会永远悬在"进行中"，成员的信誉与奖励都拿不到。
这与 `resurrection_settle` 的现有行为一致。

## 四、端到端测试结果（三个场景全通过）

| 场景 | 造数 | 结果 |
|---|---|---|
| **1. 超时失败** | deadline 已过期、增量 300s « 阈值 864000s | ✅ `status=3` / `fail_reason=deadline_exceeded`；`resurrection=expired`；两人信誉 `995,0,0,1`（−5，failed+1）；站内信 2 条 |
| **2. 中途退出** | 正常期限的队伍 | ✅ 队长退出 400「队长不能直接退出」；队员退出 200（`reputation_delta: -15`）；`join_status` 2=1 / 3=3；重复退出 400 |
| **3. 成功结算** | 增量达标的队伍 | ✅ `status=2`；分账 **2777 + 2223**；信誉 `fulfilled_count=1`、`+20` |

**信誉累计验证**（user2 一路走完三个场景）：

```
1000 − 5（场景1失败） − 15（场景2退出，user3） + 20（场景3完成）
```

user2：`995 → 1015`（−5 +20）✅
user3：`995 → 980（−15，退出） → 1000（+20，完成）`✅

三者串起来正好闭环，说明信誉的加减、上下限、`UPSERT` 都正确。

### 测试环境已完全恢复

`module_social=no`、`social_team=0`、`social_team_member=0`、`resurrections=0`、
`social_reputation=0`、`rescue_honor=0`。

### 测试过程中踩的两个坑（都是脚本层）

1. **`team_id` 传成字符串**：`psql` 返回的是 `str`，直接塞进 JSON 变成 `"team_id": "7"`
   → 报 `invalid type: string "7", expected i64`。要 `int()` 转换。
2. **三个场景共用一个种子**：`resurrections.torrent_id` 有唯一约束，第二个场景插入直接失败
   → 后续队伍没有关联任务、永远不会被结算。**每个场景必须用不同种子。**
3. **`rescue_honor` 漏清理**：它的 `team_id` 是 `ON DELETE SET NULL`（刻意设计，为了荣誉能留存），
   所以删队伍不会带走荣誉行，必须显式清理。
