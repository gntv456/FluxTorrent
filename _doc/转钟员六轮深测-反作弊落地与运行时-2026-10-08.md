## 二、问题清单（按严重度）

### P0-1 「近零重置」把基线守卫的钥匙还给了攻击者（实测复现）

**位置**：`apps/worker/src/jobs/ledger_guard.rs` `anchor_for()` + `process_event.rs` upsert 的 `$18/$19` CASE 豁免。

前五轮把锚点改成「只进不退 + GREATEST 兜底」，堵死了搬基线。六轮为修「NAS 重启
流量冻结」加了例外：**上报值 ≤ 1 GiB（RESET_ACCEPT）的下降被认可为真实重启，
锚点跟随下调**，且 SQL 侧 CASE 让 GREATEST 让路。

**攻击链（本地实测，用户 4307 / 种子 42821，实验后已清理）**：

| 步骤 | 操作 | 结果 |
|---|---|---|
| A | 首报 up=5GiB | 只立基线（首报恒 0，正确） |
| B | 报 up=**1 MiB** | 锚点 5GiB→1MiB 下调成功（近零重置被认可），入账 1MiB |
| C | 120s 后报 up=144MiB | **增量 143MiB 全额入账**（≤ 128MiB/s × 120s 钳制窗） |

即：**每个「报小值重置 → 等窗 → 报增量」循环可再铸 ≤15.6 GiB**（ RESET_ACCEPT
1GiB × 128MiB/s 速率窗）。速率钳、终身上限（size×1000）、佐证上界全部以「从
锚点起的增量」为基准——锚点能被拉回近零，所有下游防线每循环重置一次。该循环
无次数限制、无 cheat_events 留痕（1GiB 内的重置是「合法」路径）。

**与前几轮的对照**：一轮审计 P0-1 的原始变体「i64MAX→0→重吃首报」被堵死后，
六轮为了真实重启用户重新开了个 1GiB 的口子——但真实客户端重启后从 **0** 起算，
而口子开在 1GiB。这正是审计自己写过的教训（RESET_ACCEPT 注释：「换 peer_id /
换种子无限首报」），换了个方向复发。

**修法（推荐 ①+②）**：
1. **重置认可收窄到「严格近零」**：`RESET_ACCEPT` 从 1GiB 降到 **16MiB**（真实
   重启的已传量量级是 0~几 MiB，1GiB 的「重启」不存在）。更稳的是只在
   `ev.up == 0 || ev.up < 1MiB` 时认可，并要求**两侧同时近零**（真实重启 up/down
   计数器一起归零；攻击场景往往只想重置 up 侧）。
2. **重置频率限制**：真实用户一年重启几次；同一 (user, torrent) 24h 内认可超过
   1 次近零重置 → 第二次起锚点钉死 + `cheat_events(reset:)`。可以用
   `snatches.reset_count`（新列）或 Redis 键实现。
3. 重置后首个窗口给**收紧的速率额度**（如 ×0.25），让循环收益低于正常做种。

### P1-A `collusion_check` 每 10 分钟必炸：NUMERIC 解码 + 自连接膨胀（实锤）

两处独立缺陷，都在 `apps/worker/src/jobs/collusion.rs`：

1. **down_under_check 的 NUMERIC 坑（sqlx 老坑第三次出现）**：
   `SELECT ... COALESCE(sum(s.downloaded),0)` 返回 NUMERIC，却按 `(i64,i64,i64)`
   解码 → `Rust type i64 is not compatible with SQL type NUMERIC`。job 每 10 分钟
   报错一次（日志实锤，04:54 / 05:04 / 05:14 各一次），**谎报下载检测自上线起
   从未跑通过**。修法：`sum(s.downloaded)::bigint`（或查询里 cast）。
   注：GROUP BY 里引用 `l.corr_total`（非聚合列依赖函数依赖关系）也是坏味道。
2. **self_deal_check 的 O(n²) 自连接 + 常驻防抖表缺位**：56 行实测数据
   EXPLAIN 显示 Nested Loop 400 行过滤；按 30 分钟窗口的
   `COUNT(DISTINCT)²` 外推，2 万活跃 peer 站点 ≈ 1.6~6.9 亿中间行。配合
   with_lock 的 900s 超时，一次慢查询就能把 tick10 分支占满（见 P1-C）。
   修法：改为先 `GROUP BY ip, info_hash` 聚出 ≥2 账号的组再在组内（组很小）找
   方向对；以及 `cheat_events` 对 deal 命中按 (user,hash) 有天然幂等，风险只在
   查询本身——聚合下推后即可控。

### P1-B 单测红了：断言写错暴露判据边界没定义（cargo test FAILED）

`ledger_guard::tests::near_zero_reset_is_accepted_and_lowers_anchor` 用例输入
`anchor_for(12KiB, 0, Some((500GiB, 20GiB)))` —— **up 侧 500GiB→12KiB 是近零重置，
down 侧 20GiB→0 也是近零重置**（0 ≤ RESET_ACCEPT），而断言要求
`!got.reset_down`。测试失败是断言错，但它暴露真正的产品问题：
**「只重启了一侧计数器」没有定义**。真实客户端重启两侧一起归零；只归零一侧
（尤其只归零 up 侧）恰恰是 P0-1 攻击的最小动作。修法与 P0-1-① 一致：
要么要求两侧同时近零才认可，要么把断言改成两侧独立、并明示单侧重置进
cheat_events。

### P1-C worker 调度架构：collusion_check 与消费共享同一个 select 循环（实测饿死）

实测 04:54–05:14 的 **20 分钟里 flux:announce lag 持续 >0、consume_announce
零执行**——计费消费被 tick10 分支的 `cheat_enforce + collusion_check` 阻塞
（shard_lock! 宏在 select 分支内 **同步 await**，与 ZT81 已修复的 60s 分支
「重型任务分离到后台」纪律相悖）。collusion_check 必炸（P1-A）+ 超时 900s，
每次触发都可能让整站计费停摆到超时。修法：tick10/tick30 分支照抄 60s 分支的
`tokio::spawn(JoinSet)` 模式；根因修复后此项自然缓解，但结构性风险建议一并消除
（计费消费是 revenue path，不该和任何 O(n²) 检测共享调度量子）。

### P1-D 部署漂移：0305 未应用 + worker/tracker 跑旧镜像（上线即炸链）

- dev 库 `_sqlx_migrations` 停在 **0304**：`xreport_credited` 不存在、
  `leecher_xreports.over_bytes` 不存在。
- 运行中 worker 二进制不含 `xreport_credited` 字符串（旧构建）。
- 工作区 `xreport.rs` 已改写为「corr_room 物理上界」版（0305 配套）——
  **谁先把这份代码 build 进镜像、谁就让自己的 xreport 消费 100% 事务回滚**：
  `SELECT credited FROM xreport_credited` 直接 relation not exist。
  按仓库惯例（迁移先 drill 库验证再动开发库；上线=迁移先行），0305 必须
  先应用再随镜像发布，否则交叉佐证链路整体哑火且无告警（消费错误只进
  日志，事件被反复重投 360s 后进 DLQ）。
- tracker 同理：piece probe / BT 握手代码全在工作区但运行镜像没有——
  「已上线验证」的说法（假种审计文档「上线验证」节）与当前运行态不符，
  应以镜像内字符串/行为验证为准。

### P2-E cheat_enforce L1 是无阈值短信机（实测已刷 77 条）

判据 `hits >= 1` + 每轮（10 分钟）重发去重键文档写的是 Redis 7d NX，但实现里
L1 分支 **没有任何去重**（L2 的 staffmessages 靠 `NOT EXISTS resolved` 挡重）。
实测：用户 39 已收 **50 条**同文「流量记录异常提醒」，全站 77 条。修法：
- L1 加与 L2 同源的 (user, agent) 去重（resolved_at IS NULL 存在即不发）；
- 阈值从 hits>=1 提到 hits>=3，且把 `xreport_over`/`nearcap`/`deal` 这类
  「只记录不处罚」的低置信信号排除在自动发信外（collusion 注释明说这些
  留人工裁量，cheat_enforce 却已经把它们发给了用户）。

### P2-F 保种区（preserve_seed）洪水面：阈值默认把「健康种子」也灌进保种区

`uploader_seed_enabled=on, uploader_seed_min=3` 下，任何 seeders<3 的种子
（大部分正常冷种）dead_days 后进 `seed_preserve`。与 `preserve_exit` 的
`seeders > 3` 移出构成 **进多出少的棘轮**：seeders=3 的种子既进不去也出不来，
而 seeders=2 的常见冷种全部长驻。保种区从「死种坟场」变成「大半个站点」，
认领结算面（preserve_bonus_per_day）被放大到所有冷种。dev 库目前只有 1 行，
但那是数据少，不是逻辑防住了。建议：入区阈值语义改为「**发布者自己不在种**
且 seeders<min」（发布者义务的本意），而不是「seeders<min 就入区」。

### P2-G 其余静态发现（择要）

1. **`anchor_for` 未消费 `acc_up/acc_down`**：`FOR UPDATE` 取了 5 列只用 3 列，
   终身天花板在 `ledger_guard` 内另算——不算错，但 lifetime cap 与锚点判定
   分离，后续维护容易漏改（建议把 lifetime cap 也移进 anchor 判定或删掉冗余取列）。
2. **seeding 判定的 `conn != Some(0)` 一票否决 vs 探测抽样**：BT 三阶段探测
   （握手+bitfield+piece）上线后，`CONN_DEAD` 将包含「MSE 加密客户端不回明文
   握手」的合法用户——六轮文档自己列了这个局限，但 `seeding` 判定没有对应
   降级路径（探到 DEAD 直接停发收益）。建议：piece 实锤伪造（probe 返回
   Some(false)）才一票否决；仅握手失败标 suspect，不进 seeding 否决。
3. **`piece_cache` 全量清空策略**：容量满 `m.clear()` 会把热种子缓存一起丢，
   造成下一轮 400 个 peer 同时打 DB——改成 LRU 或按 TTL 淘汰即可。
4. **`near_cap_check` 无 peer 维度**：total/near_cap 计数按 snatches 行累计，
   用户换 peer_id 不清零（好）；但用户删种重下（snatches 行保留）也不清零，
   长期做种者的历史贴边占比永远洗不掉——建议加时间衰减或只看近 7 天增量。
   （当前计数从 0304 迁移起才有，存量行为空，暂无实害。）
5. **`emit.rs` `payload["ip"]` 判空但 `ip` 参数无注释**：`xreport` 流的 ip 直写
   不判空（announce 判了）——空 ip 会进 `cheat_events.peer_ip` 的 NOT NULL？实测
   未触发，列为观察项。
