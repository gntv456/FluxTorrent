# 站型成熟度对标与补齐方案（2026-10-08）

> 问题：我们支持 11 个站型，切过去之后**到底像不像一个该类型的成熟站**？
> 本文给出事实底稿、机制层缺口、逐站型缺口（四路独立对标汇总）、以及分批方案。
> 判定标准一章是可执行的验收清单——「达到成熟站型标准」必须能被脚本或页面证伪，
> 不能停留在「看起来像个音乐站」。
>
> **配套文档**（两文分工，勿混用）：
> - `_doc/各站型成熟度对标与达标方案.md` = **总纲**：通用层对标结论
>   （列表/详情页形态已达 UNIT3D 级、通用缺口 2026-10-08 清零）+ 逐站型
>   达标判据总表 + 分阶段路线图（阶段 0 框架已完成 → 阶段 2 逐站型领域能力）。
> - 本文 = **机制层深化**：站型包 apply 链路的安全性缺口（H1–H10）+
>   四路对标证据 + 素材补齐/切换安全/垂直能力三批方案。
>   总纲的「阶段 2」落地前，先做本文批次 0/1（素材与切换安全），
>   顺序口径：**批次 0（纯数据）→ 批次 1（切换安全）→ 总纲阶段 2（逐型垂直能力）**
>   → 本文批次 3（对外契约）。

## 1. 结论先给

1. **机制骨架是完整的，垂直能力是空的。** 站型包的物化链路（事务 + 全量快照 +
   变更台账 + restore 回滚 + 在用维度保护 + 模块缓存即时失效）比多数自建 PT 程序
   讲究；但 11 个包随站型真正变化的只有三样：**分类名、维度词表、5 个模块开关**。
   没有任何一类的**垂直能力**（数据层 / 发种校验 / 详情页形态 / 审核口径 / 对外契约）
   随站型落地。所以当前「切站型」= 换词表，不等于换站点类型。
2. **切站型在有种子的站点上会偷换语义**（H1）：全部分类包共用 `id = 1..7` 这一段
   主键，而 `merge` 模式的语义就是「同 id 覆盖改名」。实测本站 `general` 的
   `id=1 电影` 下挂着 **55 枚种子**；切到 `education` 会把这一行原地改名成
   「学前教育」，**55 枚电影种子的分类名当场变了**，而 `category_id` 不动。
   `replace` 模式在有种子的站上直接拒绝（这是对的），于是现实路径只剩会污染的那条。
3. **变更预览里看不到这条最危险的改动**（H2）：`diff_preview` 只算
   `site_type / site_name / module_*` 三类键，分类改名不在其中；站长点「应用」前
   看到的 diff 是干净的。
4. **站长的手工定制会被 apply 无声回滚**（H4/H3）：`apply` 无条件把包里 31 个
   `module_*` 键全部写一遍，也无条件把 `site_name` 写成 `pack.brand`——而
   **11 个包的 brand 全是空串**。同一个函数里 `tagline` 却有「站长自定义值保留」
   的守卫（0145 语义），这是同一文件内的双口径。
5. **包载荷只有 `{id, name}`**（H6）：分类表其实早就支持 `parent_id / sort /
   icon_key / bg_color / legacy_id / newznab_id`，apply 也真会写它们——但没有一个
   包声明过。实测线上 10 个分类 `bg_color` **10/10 为空**、`parent_id` 全空、
   `sort` 全是默认 100。层级分类、分类色、图标、对外分类号这些能力是
   「代码已就位、素材未填」，补齐成本是纯数据改动。
6. **两类站型有真垂直分支，其余没有**（H7）：全仓按 `site_type` 分支的行为只有两处
   ——`sitetype.rs:52` 的 `edu_like` 决定 grades/editions 词表给不给，
   `apply_subtitle_kind` 决定字幕区叫「字幕」还是「歌词」。除此之外，
   music/lossless 的 `losslessPlayer` 是死声明（不在模块键表、前后端零消费者），
   `music`/`lossless` 的元数据源配的是 douban + mediainfo（音频站的正确源应是
   Discogs / MusicBrainz + 抓轨日志），`game`/`software`/`sports`/`ebook`
   元数据源为 None，`general`/`sports`/`software` 连标签词表都是空的。

7. **两把尺子量出来的结论**（详见 §7.0）：
   - 筛选面其实**是通的**——`TorrentFilter`（`torrents/types.rs:150`）已含
     `sections` 维度值 + 30 余个字段，维度可筛这一点达标；
   - **实体层几乎为零**——`torrents` 32 列里能承载类型语义的只有
     `textbook_id`（教育）与 `imdb_id`（影视），库里**不存在** artist/album/
     author/isbn/season/episode/version/checksum/match 任何一张表，
     `technical_info` 是全仓零读写的死列。
   ⇒ 缺的不是「能不能筛」，而是**榜单、订阅、去重、聚合页、外部库对齐、
   审核口径这六件事没有实体可挂**。这是 11 个站型共同的天花板。

一句话：**先别加新站型，先把「切过去像不像」这件事做成可验收的。**

## 2. 方法、参照系与置信度口径

- 我们的现状一律读代码/查库给证据（`file:line` 或 SQL 结果），不采信旧文档。
- 参照系按类型取**公开可核**的那一个：影视/综合 = UNIT3D 与 Gazelle 系代码；
  音乐/无损 = OPS-Gazelle + heybrochecklog(RED 口径打分器) + What.CD 规则镜像；
  动漫 = Gazelle 动漫分支持 + 公开字幕站惯例；电子书 = ZVDD/本城类公开形态；
  游戏/软件/体育/教育 = 无公开源码，**只能标「业内惯例·待核」**，本文照此标注，
  不假装有出处。
- 每条竞品能力标：【代码核实】/【公开文档】/【业内惯例·待核】。
- 优先级口径：**P0 = 不补这个，切过去就不是那类站**；P1 = 同类站有而我们没有，
  站长会在第一个月撞上；P2 = 拉开体验差距，可排后。

三张表读数：

- **分类一律扁平、一律 7 个**（general 10 个），没有任何包用 `parent_id`。
  成熟同类站的分类通常是两级并且**第二轴正交**（音乐站：语种 × 格式 × 音质；

  `magic_pool`/`attendance`/`resurrections` 对任何站型都开——
  教育站和无损站的玩法面一模一样。

## 4. 机制层缺口（H1–H10，跨所有站型）

| # | 缺口 | 证据 | 站长会遇到的痛 | 补齐改动面 | 优先级 |
|---|---|---|---|---|---|
| H1 | 分类 id 跨包重叠，`merge` 原地改名，老种子语义被偷换 | 全部包 `ids=[1..7]`（general 1..10）；`pack_core.rs:44-82` `ON CONFLICT (id) DO UPDATE SET name`；**已实测**（`.workbuddy/_h1_probe.sql`，只回滚事务里复刻同一条 SQL）：`id=1 电影 种子数=55` → `id=1 学前教育 种子数=55`，种子行本身没动 | 切一次站型，首页分类名与种子内容大面积对不上；`replace` 在有种子的站上直接拒绝，于是现实路径只剩会污染的那条 | 分类改为**按 key 匹配**而非 id（新增 `categories.key`，包载荷与物化两侧都用它，id 退化为内部主键）；apply 时输出「将被改名的在用分类 + 种子数」并要求确认 | **P0** |
| H2 | 变更预览不含分类改名 | `pack_snapshot.rs:180-212` 只 push `site_type/site_name/module_*` | 点「应用」前看不到风险；出问题才知道是这一步 | 在 diff_preview 里加 categories 段（旧名/新名/在用种子数/新增/失活） | **P0** |
| H3 | `site_name` 被无条件写成 `pack.brand`，而 11 个预置包 brand 全空 | `pack_core.rs:90-94`；`brand 分布: 11/11 为空`；对照：自定义包在另存时会把当时的 `site_name` 烤进 brand（`pack_save.rs:97-104`），所以只有预置包会踩 | 切一次站型，站名变空串——`site_name` 是站名的权威键（`sitetype.rs:72` 注释），丢的是整站的抬头 | brand 为空则**不写**；预置包补 brand；与 H4 同一守卫口径 | **P0** |
| H4 | apply 无条件覆盖站长手工调过的 `module_*` | `pack_core.rs:96-113`；对比 `pack_apply.rs:47-58` tagline 的 0145 保留语义 | 「我只想做音乐站，不要把我关掉的游戏区又打开」 | 模块开关引入「站长显式覆盖」标记（`module_*` 写 manual 位），apply 只填未被覆盖的；或提供「仅切分类/仅切模块/全量」三档 | **P1** |
| H5 | 分类写入吞错 + 计数用载荷长度而非实际写入 | `pack_core.rs:60-82` `let _ = sqlx::query(...)`；`added = cats.len()`（第 26 行） | 应用返回 `categories: 7` 但库里其实没写全（假成功）。这是本仓已定性过的缺陷族（`let _ =` 吞 SQL 错） | 改为 `?` 上抛或累计 `rows_affected()`；失败即回滚 | **P1** |
| H6 | 包只声明 `{id,name}`，层级/排序/图标/分类色/对外分类号全不声明 | 载荷键集实测 = `['id','name']`；线上 `categories`：`parent_id` 全空、`sort=100` 全同、`bg_color` 10/10 空；而 apply 支持写这些（`pack_core.rs:57-82`），并有 `pick_category_icon()` 兜底 | 列表类型色块没颜色、图标回落首字、RSS/Torznab 的 Newznab 号不随站型语义、切站型后新分类无对外号 | **纯数据改动**：11 包的 categories 载荷补 `parent_id/sort/icon_key/bg_color/legacy_id/newznab_id`；配一条迁移重放（走 restore 语义避免覆盖站长改过的值） | **P0**（性价比最高的一批） |
| H7 | 站型间垂直能力为零：全仓只有两处按 `site_type` 分支 | `sitetype.rs:52` `edu_like`；`apply_subtitle_kind`（0146/0178）。其余「差异」都是词表 | 切到任何站型，发种表单/筛选面/详情页/审核台的字段与校验**完全相同** | 见 §6「批次 2」：按类型引入 `pack.features`（结构化声明 + 消费点），而不是继续散 `match site_type` | **P0** |
| H8 | 类型专属字段无处安放 | `torrents` 列（0001_init.sql:86-112）只有影视/教育语义；`media_info` 键只有 poster/imdb/mediainfo（`ptgen.rs:243`）；`technical_info` 列**全仓零读写** | 音乐要 artist/album/release/log score、影视要 season/episode、书要 author/ISBN/press、软件要 version/校验和、体育要 赛事/赛季/对阵——现在只能塞进 sections 的字符串值 | 见 §6：区分「进 schema 的实体」与「进 section 的标签」两类，逐型明确 | **P0/P1 混合** |
| H9 | 死声明与错配源 | `losslessPlayer` 只在包 JSON 里（`modules.rs` key::ALL / 0107 modules 表 / `MODULE_KEYS` 三处都没有，前端零消费者）；music/lossless 元数据源 = douban+mediainfo | 站长以为无损播放器已存在；音频站拿豆瓣+MediaInfo 当元数据源，真正需要的 Discogs/MusicBrainz/日志分没有 | 要么补实现并入模块键表（受 `module_keys_guard.mjs` 约束），要么从包里删掉并在文档写明；元数据源按类型重配 | **P1** |
| H10 | 首页区块与对外可见面完全不随站型变 | `http/home_layout.rs:36` 的 `HOME_SECTIONS` 是**一份全局清单**（news/attendance/shoutbox…带 `in_default`），无站型维度；除包机制自身外，全仓按 `site_type` 分支的行为只有两处（`staff_http/sitetype.rs:52` 的 `edu_like`、SQL 函数 `apply_subtitle_kind`），`admin_http/site.rs:351` 只是拦住直改 | 切到无损音乐站，首页仍是「签到 + 喇叭 + 教育资讯」那套；音乐站最该有的「新专辑 / 艺人榜 / 待补日志」无处放 | 包载荷增加 `home_sections` 段（该型默认区块集合与顺序），`home_layout` 读包默认再被站长覆盖——与 `view_layout` 现范式一致，改动集中在一处 | **P1** |

**机制层结论**：包机制的「写」已经足够健壮（事务/快照/台账/回滚/在用保护），
缺的是三件事——**身份匹配（H1/H2）**、**素材填充（H6/H9）**、
**能力声明（H7/H8）**。前两件是低风险改动，可以在一个批次内做完；
第三件决定「站型」这个词是否成立，必须逐类做。

已有的缓解措施要写清楚，免得方案被当成救火：**全量快照 + 回滚面板确实存在**
（`pack_applies.rs:113-136` 用 `restore` 模式重放快照，前端
`staff-tools-pack-applies.tsx` 有入口），快照里 `site / modules / categories /
sections / tags / classes / economy / terms` 九段都在。但它是**事后救火**：
H2 让站长在点「应用」之前看不到分类会被改名，H4/H5 让失败的 apply 仍然报成功——
于是要么没人知道需要救火，要么救火的时机已经脏了。补齐方向不是再加一层回滚，
而是把危险变更挪到 apply **之前**去见光。

## 5. 「算达到成熟站型」的可验收清单

每个站型给出**可执行判据**（接口断言 / DOM 读数 / 截图三选一，禁止"看起来对"）。
后续任何补齐批次，验收就是把这些格子从 ☹ 变成 ✅。

通用（所有站型，5 条）：

1. 切到该站型后，`GET /api/v1/categories` 返回的是**两级或带 sort/色/图标**的分类树，
   且不与已有种子的语义冲突（脚本断言：切前后 `category_id` 对应内容的标题关键词一致率）。
2. `POST /admin/site-type-packs/apply` 的响应 diff 里**含分类改名与在用种子数**；
   `site_name` 不被写成空串（psql 回读）。
3. 站长手工关闭的模块在再次 apply 后仍为关闭（psql 回读 `module_*`）。
4. 发种表单出现**至少 3 个该类型专属字段**，且这些字段在详情页可读、在列表可筛。
5. 该类型的核心检索分面在 `/torrents` 上可用（HTTP 200 + 结果集非空且语义正确）。

分类型（每型 5–8 条硬指标，随 §6 批次落地时逐条建脚本）：见纵向各表末列。

## 6. 分批方案

### 批次 0 · 素材补齐（纯数据，零业务代码）
- 内容：H6 + H9 + §7.5 里所有「改包 JSON 就能生效」的行——
  11 包 categories 载荷补 `parent_id/sort/icon_key/bg_color/legacy_id/newznab_id`；
  6 个挂着 `team` 维度却空词表的包补出厂项（anime 字幕组 / sports 球队 /
  software·documentary·general·lossless 各自的制作组口径）；
  `general/sports/software` 补标签词表；
  **`music`/`lossless` 的元数据源从 douban+mediainfo 改为按音频口径配**；
  `brand` 给默认或明确删列；`losslessPlayer` 二选一（删声明 / 补实现）。
- 改动面：1 条迁移（新增号；按 restore 语义「包声明才覆盖」，不动站长改过的值）+
  1 个只读校验脚本（`scripts/pack_material_check.py`：逐包断言载荷键集完整、
  词表非空、id 不重叠、元数据源与该型匹配）。
- 为什么先做它：这批**不动一行 Rust/TS**，切站型后前台与筛选立刻可见地变像；
  同时把 H6 的「能力已在、素材未填」一次性兑现，是整份方案里性价比最高的一批。
- 风险：迁移只重写 `site_type_packs`，不影响已物化的 `categories`；
  要 `apply` 才生效，所以老站点零感知。

### 批次 1 · 切换安全性（H1/H2/H3/H4/H5）
- 内容：分类匹配从 id 改为 `key`（新列 `categories.key`，包载荷与物化两侧都用它，
  id 退化为纯内部主键）；`diff_preview` 增加分类段与在用种子数；`brand` 空不写；
  `module_*` 引入站长覆盖位；`let _ =` 全部改成 `?`；apply 前必须传
  `confirm: true` 才允许改住在用分类名。
- 改动面：1 迁移 + `pack_core.rs`/`pack_snapshot.rs`/`pack_apply.rs` + 后台
  「应用站型包」弹窗（预览表 + 确认勾选）。

## 7. 逐站型缺口

### 7.0 先给两条统摄性事实（决定了 11 个站型的天花板）

**事实 A：只有两类站型在 schema 里有专属承载面。**
`torrents` 实测 32 列，能承担「类型语义」的只有
`category_id / medium_id / grade_id / edition_id / textbook_id / imdb_id /
media_info / nfo / screenshots`。也就是说：

- **教育**有 `textbook_id` + `textbooks` 表（真实体）；
- **影视/纪录片**有 `imdb_id` 专属列；
- 其余 9 类**一列都没有**。`technical_info` 列至今全仓零读零写（死列）。

库里 `information_schema` 实测不存在
`artist / album / release / track / author / book / press / isbn / season /
episode / series / version / checksum / match` 任何一张表
（`social_team / social_season` 是社交战队与赛季，与体育无关）。

**事实 B：筛选面反而是通的。** `TorrentFilter`（`torrents/types.rs:150`）
除 `sections`（维度值可筛）外已有 category/medium/grade/edition/tags/size/
date/seeders/leechers/completed/rating/owner 等 30 余个字段。
所以问题不是「筛不出来」，而是**没有实体 ⇒ 榜单、订阅、去重、聚合页、
外部库对齐、审核口径这五类功能无处安放**。§7.1–7.4 的每一行都落到这条上。

置信度标注：`我们现状` 一律本会话实测或代码引用；
`成熟参照` 中标【待核】者 = 业内惯例印象，**四路独立对标（影视/音乐/动漫电子书/
游戏软件体育教育）正在用公开代码与文档逐条核实**，回来后替换本列并补出处。
