## 1. 方法与口径

**闭环定义**：站长从「起服务」到「日常运营」的每一层都能**自己走完、不写代码、不进数据库**。任何一处必须改代码/改 SQL/改环境才能继续 = 断点。

**判定标准**（站长视角，非接口视角）：
- **闭环** = 该层所有主线动作均可在后台/前台完成，且「配置项改了真的生效」；
- **半闭环** = 主线可用，但有必须绕道的支路（缺 UI、缺出口、只写不收）；
- **不闭环** = 存在必须进数据库/改代码才能过的硬断点。

**证据规则**：
- 每条「已修」必须有真实消费点（grep 读取方，不只看控件存在）；
- 每条「假开关」均经全仓 grep 复核零消费方（api src + web components/lib）；
- 本文所有结论带 file:line，主代理逐条抽查过承重项（SMTP 装配、字幕注入、权限端点、字段值写口）。

**与既有文档的关系**：本方案合并并取代 09-25/09-26 各轮审查的**缺口清单部分**——四审报告（09-25）、闭环审查 20 项（09-26）、五路方案与复核附记（09-26）。编号统一为 G#，映射表见附录 A。各文档中的「已修」结论一律以代码现状复核为准。

**批次基线**：0208（闭环 P0/P1）→ 0209（面板权限 CRUD）→ 0210（公告中性化）→ 0211（复检二轮）→ 0212（Round3 三缺口）→ 0213（促销档位外置）→ **0214（Round4，工作区未提交）**。
