## 阶段 S1：核心 PT MVP（M01–M10）

**交付**：Monorepo 骨架（Turborepo + pnpm workspace + Cargo workspace）、认证体系（Argon2id + JWT）、种子发布/下载/列表/详情、自研 Tracker（BEP3 二进制安全）、评论/感谢/收藏、管理后台基础（审核/举报/用户管理）、RSS。

**关键决策**：
- Tracker 字节层 percent-decode 解析 info_hash/peer_id，compact 响应返回 `Vec<u8>`（不经 String 避免 UTF-8 lossy 破坏哈希）。
- 不信任客户端自报 IP，仅 `TRUST_PROXY_IP=1` 时信任 X-Forwarded-For。

## tracker 高频请求防护（2026-09-11）

背景审查结论：tracker 此前对高频/异常请求**零防护**（既有限流全在 API 层、不覆盖 announce；ip_bans 表存在但无任何请求入口强制；announce_interval 设置项为死配置）。

### announce/scrape 防护链路（apps/tracker/src/main.rs）
按 cheap → expensive 排序，全部 fail-open 设计（Redis/PG 故障不阻断正常 announce）：
1. **ip_bans 封禁**：内存缓存 60s 刷新，命中即拒（`ip_banned()`）——ip_bans 表首次接入请求路径。
2. **每 IP 限流**：Redis INCR 60s 窗口（`ANN_RATE_IP_PER_MIN`，默认 300/min），置于 passkey 之前拦截垃圾流量。
3. **passkey 内存缓存**：60s TTL（`resolve_passkey_cached()`），命中免查 PG；上限 5 万条防膨胀。挂起/禁下载最迟 60s 生效（折衷）。
4. **每用户限流**：Redis INCR 60s 窗口（`ANN_RATE_USER_PER_MIN`，默认 120/min）——按 user_id 而非 IP，NAT 场景不误伤。
5. **agent_rules 黑白名单**：改为内存缓存 60s 刷新，不再逐请求全表扫描。
- DB 连接池 3 → 8（高频路径 DB 压力已由缓存削掉，池宽是兜底）。

### BEP3 interval 下发（apps/tracker/src/peers.rs）
- `bencode_announce()` 补上 BEP3 强制的 `interval` / `min interval` 字段——此前缺失，客户端拿不到汇报间隔，是高频重发的诱因之一。
- interval 读 `site_settings.announce_interval`（clamp 60–86400，缺失回退 `ANN_INTERVAL_DEFAULT`=1800）；min interval 取一半（clamp 30–3600）。
- 阈值均可经 compose 环境变量调整（tracker 服务已注入默认值）。

### 保种影响评估与阈值调整（同日，两轮上调后终值）
- **计费链路对被拒 announce 容忍**：worker `process_event` 按客户端累计量与 `snatches.last_up/last_down` 差值计费（jobs.rs:218-232），被拒 announce 只延迟到下次成功 announce 补齐，**不丢流量**；`seeding` 标记为粘性 OR（jobs.rs:245），被拒不会摘掉做种标记 → 保种区/H&R 快照口径不受限流影响。
- **正常用户数学边界**：interval 1800s 下每分钟 announce ≈ 挂种数/30。
- **阈值终值（用户反馈 1.8 万挂种覆盖不够，两轮上调）**：每用户 120→600→**1800/min**（覆盖 5.4 万挂种）、每 IP 300→1800→**3600/min**（60r/s/IP）；Nginx 边缘 10r/s→30r/s→**60r/s**、burst→**120**、conn→**120**（边缘必须 ≥ 应用层每用户速率，否则先卡住鲸鱼）。垃圾洪水仍有界（60r/s/IP），有凭据的滥用走挂起账号（passkey 缓存 60s 生效），分布式洪水属边缘网关/WAF 职责。
- **顺带发现的既有缺陷（同日已修）**：`snatches.seeded_seconds` 全仓**无写入点**——H&R 追责（hr_snapshots 同步 jobs.rs:329）、等级做种小时（jobs.rs:369/391）、保种认领基线（ops_http.rs:526）、/me/hr（community_http.rs:473）等十余处读取，但 worker/api 均不更新它 → 做种时长恒为 0（除 demo 数据），H&R 将全部误判 violated、等级做种小时不增长。

### seeded_seconds 断链修复（同日）
- **迁移 `0043_snatches_last_seen.sql`**：`snatches` 加 `last_seen_at TIMESTAMPTZ NOT NULL DEFAULT now()`。
- **worker `process_event`**（jobs.rs）：announce 计费 upsert 内累计保种时长 —— 本次为做种 announce（left=0）且与上次 announce 间隔未超容忍窗时，记入 `now() - last_seen_at` 真实时间差；超窗（离线/故障/挂机）不记；`last_seen_at = now()` 随每次 announce 刷新。以**本次事件**的 left 为准，不受 seeding 粘性 OR 影响。
- **容忍窗** = 2 × announce_interval（consume_announce 每轮从 site_settings 读一次，clamp [3600, 172800]，与 tracker 下发口径一致）。
- **hr_flag 运行时刷新**：0029 只在迁移里置过一次，运行时无人刷新；hr_enforce 追加第 5 步 —— 完成超 14 天且做种 < 120h 置 hr_flag=TRUE（幂等，NOT hr_flag 守卫）。
- 生效后闭环：H&R（hr_snapshots 329 行同步）、等级做种小时、保种认领时长增量（ops_http seed_time_delta）、/me/hr 视图全部拿到真实数据。
- 验证：`cargo check/test -p flux-worker` 通过（3/3）。注意 demo 库已有 snatches 行的 last_seen_at 默认为迁移时刻，首轮累计从迁移后开始，无回溯。

**发现并修复两个缺陷**：

1. **P1 · 改密输入框是摆设**：安全 tab 一直有「修改密码/确认新密码」两个输入框，但全后端不存在任何自助改密接口（只有忘记密码的邮件重置与管理员重置）——填了也没地方提交。修复：新增 `POST /me/password/change`（验旧密码→Argon2id 新哈希→抬撤销线→审计；旧密码错/新旧相同/短密码三重拒绝），前端补「当前密码」输入与提交按钮（三语文案），成功后其他设备全部下线。
2. **P1 · 令牌撤销线时序误杀**：改密后撤销线若取 `now()`，会把「改密前一刻刚登录」的合法新 token 一并作废（用户改完密立刻被踹且无法自救的极端窗口）。定稿口径：**登出 nbf=凭证 iat（登出所用凭证自身也死）；改密 nbf=iat−1（同秒重登的新凭证不误杀）**——`require_auth` 维持 `iat<=nbf` 判死。权衡说明：同秒签发的多张 token 无 jti 不可区分，改密路径放过同秒旧凭证（1 秒窗口）换取不误杀新登录，语义可接受。
**E2E 踩坑记录**（写进脚本注释，防后人复踩）：
- 同用户名登录限流 5 次/分钟（code=1015）——E2E 改密链路会耗尽预算，脚本必须带整窗口重试，且密码可能停在中间态需手工复原；
- 撤销线验证顺序必须「先拿早凭证→再改密→再验早凭证」，改密后登录的新凭证 iat 必然 > nbf，验证无意义；
- `regression.py` 的 RSS 断言原为硬编码 passkey，usercp E2E 轮换 passkey 后即失效——改为 `/me/overview` 动态取当前值。

**验证**：usercp E2E 20/20、cargo test 32/32、Vitest 16/16、回归 60/60、sweep 42/42。
