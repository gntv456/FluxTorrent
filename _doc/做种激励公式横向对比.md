## 0. 一页结论

| 维度 | 我们 | NP | Gazelle | U3D |
|---|---|---|---|---|
| 体积因子 | ❌ **无**（只有 25/100GiB 两个离散档） | ✅ 线性 `×Si(GB)` | ✅ 线性 `(size/scale)/1024³` | ✅ 规则档（1-25/25-100/≥100GiB） |
| 种龄因子 | ✅ 档位（>365天 1.5 / >180天 1.0） | ✅ 连续 `1-10^(-T/4周)`，4 周达 90% | ❌ | ✅ 规则档（>12月 1.5 / 6-12月 1.0） |
| **个人做种时长** | ⚠️ **反向衰减** `1/(1+h/2160)` | ❌（不含） | ✅ 对数递增 `ln(1+h/24)` | ✅ 4 档加分（1月→1年） |
| 稀有度 | ✅ 衰减 `seeders^-0.35`（同 Gazelle） | ✅ 加成 `1+√2·10^(-(N-1)/6)` **最大 ×2.414** | ✅ 衰减 `seeders^-0.35` | ✅ 规则档 |
| 封顶 | ✅ arctan，渐近 +200（总 210） | ✅ arctan，渐近 B0（50~100） | ❌ 无（靠系数小） | ⚠️ 靠单种上限 ~4.5/h |
| 可读性 | ✅ 规则名 + 收益构成页 | ⚠️ 只有公式图片 | ❌ 只有一个数 | ✅ 规则名（最好的） |
| 参数化 | ✅ 全 `site_settings` | ⚠️ 部分硬编码（等级阈值） | ✅ | ✅ 全 DB 表 |
| 反假保种 | ✅ 排除 `connectable=0 且 uploaded=0` | ⚠️ 「零魔种子」权重 0.2 | ❌ | ✅ `connectable` 变量 |
| 幂等重跑 | ✅ `seeding:{uid}:{HH}` | ❌ cron 重跑会重复发 | ⚠️ 去重表 | ⚠️ |

**一句话**：结构上我们最接近「Gazelle 的稀有度衰减 + NP 的 arctan 封顶 + U3D 的规则可读性」的混合体，工程健壮性（幂等/反假/参数化）优于三家；
但**缺体积因子**导致「堆小种」可套利（见 §3.1，这是必须修的），且**个人做种时长是惩罚而非奖励**（见 §3.2，与三家方向相反）。

## 1. 四家公式原文

### 1.1 我们（FluxTorrent）

```
每颗种子  s_i = 规则分(档) ÷ seeders^0.35 ÷ (1 + 个人累计做种小时 / 2160)
用户总和  Σ   = Σ s_i
每小时魔力     = ( base + ⌊(400/π)·atan(Σ × 6/50)⌋ ) × (donor ? 2 : 1)
```
- 规则分：濒危 2.0（`seeders≤1 且 完成≥3`）/ 高龄 1.5（>365天）/ 老 1.0（>180天）/ 大体积 0.75（≥100GiB）/ 中体积 0.5（≥25GiB）/ 日常 0.25
- `base` = `site_settings.seeding_base_hourly`，缺省 **10**
- 幂等键 `seeding:{uid}:{YYYYMMDDHH}`；底薪不进压缩曲线；渐近上限 `base+200`

### 1.2 NexusPHP

```
A = Σ_i (1 - 10^(-Ti/T0)) × Si × (1 + √2 × 10^(-(Ni-1)/(N0-1)))
每小时 B = B0 × (2/π) × arctan(A / L)          + 1 × min(做种数, 7)

T0 = 4 周（种子生存时间参数）  N0 = 7（做种人数参数）
L  = 300                       B0 = 50（部分站 100）
```
- 时长项 `1-10^(-Ti/4)`：**Ti 越大越大**（0 周→0，4 周→0.9，8 周→0.99）→ **奖励老种**
- 稀有度项 `1+√2·10^(-(Ni-1)/6)`：`Ni=1 → 2.414`，`Ni=7 → 1.141`，`Ni≥10 → ≈1` → **独苗最多 ×2.414，人多只降到 1（不归零）**
- 体积 `Si` **线性且无上限** → 大种迅速把 A 顶到封顶区（`A/300` 在 A=1000GB 时已是 0.81B0）
- 另有：零魔种子权重 0.2、捐赠者 ×2、官方标签 ×0.5、勋章系数、后宫加成

### 1.3 Gazelle（What.CD 系）

```
每小时每种子 = (size / 分类scale) / 1024³ × (0.0433 + 0.07 × ln(1 + seedtime_h/24) / max(seeders,1)^0.35)
```
- 体积**线性除以分类 scale**（不同分类不同权重）
- 时长走**对数递增**（长期做种的边际收益递减，但方向是奖励）
- 稀有度 `seeders^-0.35` —— **我们这一项就是照抄它的**

### 1.4 UNIT3D BON 规则引擎 v2

`bon_earnings` 表驱动（position/variable/multiplier/operation/condition 全是行），变量集含 `age / size / seeders / leechers / times_completed / seedtime / connectable / internal`，默认 11 条规则：
Dying +2.0 / Legendary(种龄>12月) +1.5 / Old(6-12月) +1.0 / Huge 0.75 / Large 0.5 / Everyday 0.25 /
**Legendary Seeder（个人做种该种 ≥1 年）+2.0 / MVP(6-12月) +1.0 / Committed(3-6月) +0.75 / Team Player(2-3月) +0.5 / Participant(1-2月) +0.25**

## 2. 逐因子优劣

### 2.1 体积因子 —— 我们缺失（最大短板）

| | 形态 | 后果 |
|---|---|---|
| NP | 线性 `×Si(GB)`，无上限 | 大种优势极大（但被 arctan 封顶吸收）；小种天然几乎零收益 |
| Gazelle | 线性 ÷ 分类 scale | 同上，且能按分类调节权重 |
| U3D | 三档（1-25 / 25-100 / ≥100GiB） | 与我们同款，但它的**基准是规则加分叠加**，仍有体积档 |
| **我们** | **无体积项**，只有 25/100GiB 两个离散档 | ① 小种（1MB~24GiB）与 25GiB 种子同分；② 边界跳变（24.9 vs 25.1 GiB 差 2 倍）③ **可堆小种套利**（§3.1） |

### 2.2 种龄因子 —— 我们与 NP/U3D 齐平（档位 vs 连续）

我们和 U3D 用「离散档位」（>180 天 1.0、>365 天 1.5），NP 用连续曲线 `1-10^(-T/4)`（4 周即达 90%）。
- 我们的**优点**：档位可读（玩家能一眼看懂"熬过 180 天就翻倍"），且不会像 NP 那样 4 周就到顶（NP 的 T0=4 让"老种激励"很快饱和，8 周后基本无差别）。
- 我们的**缺点**：跳变（179 天 vs 181 天收益差 4 倍？不，是 0.75→1.0，差 33%）；且我们最老的档也只到 1.5，NP 的老种在体积加权下系数接近 1.0（无惩罚）——但 NP 的"新鲜种"系数趋 0，**惩罚新种**，这在逻辑上更激进（新种刚发布时几乎不给分，等 4 周）→ 对新种保种不利。**这一点我们比 NP 更好**。

### 2.3 个人做种时长 —— 我们方向与三家相反（第二大短板）

| | 项 | 方向 |
|---|---|---|
| NP | 不含（只看种龄） | — |
| Gazelle | `0.07·ln(1+个人做种小时/24)` | **递增**（挂越久越多，边际递减） |
| U3D | 4 档：1月/2-3月/3-6月/6-12月/≥1年 | **递增**（最高 +2.0，与濒危种同权） |
| **我们** | `1/(1+个人做种小时/2160)` | **递减**（90 天半衰，挂得越久单位收益越低） |

PT 的核心 KPI 是**种子的长期可用性**（seed retention）。三家都奖励"长期做种"，只有我们反向衰减。
我们的设计意图可能是"鼓励轮换新种"，但这与"保种"目标冲突：一个把老种挂了两年的人，单位收益只剩 1/(1+17520/2160)=11%。

> 注意区分两个"时长"：**种龄**（种子发布多久）我们奖励 ✅；**个人做种时长**（我挂它多久）我们惩罚 ❌。三家对前者一致（部分奖励），对后者（Gazelle/U3D）奖励。

### 2.4 稀有度 —— 我们只有"惩罚"，NP 有"加成"

| | seeders=1 | seeders=7 | seeders=10 | seeders=100 |
|---|---|---|---|---|
| NP | **2.414** | 1.141 | ≈1.03 | ≈1.00 |
| Gazelle / 我们 | **1.0** | 0.51 | 0.447 | 0.20 |

- NP：独苗给 **+141%** 额外奖励，人多只回到 1（不惩罚）。语义是"**奖励稀有保种**"。
- 我们/Gazelle：独苗只是"不被惩罚"，人多则惩罚到 20%。语义是"**惩罚热门**"。
- 后果：**热门大种在我们这儿几乎零收益**（0.75×0.447 = 0.335，比一枚独苗日常种 0.25 还低不了多少），用户容易觉得"我挂了 50 个热门种，时魔 12，白挂"。而我们唯一的"稀有奖励"是离散的**濒危保种 2.0**，但它要求 `times_completed ≥ 3` —— **刚发布的独苗新种拿不到**（这是最需要鼓励的场景）。

### 2.5 封顶与通胀

| | 封顶 | 渐近上限 |
|---|---|---|
| NP | `B0·2/π·arctan(A/L)` | B0（默认 50，部分站 100）+ 做种数×7 |
| 我们 | `400/π·atan(Σ·6/50)` | base + 200 = **210**（donor 420） |
| Gazelle | 无显式封顶 | 靠系数小（每 GB 每小时 ~0.04BP） |
| U3D | 单种上限 ~4.5 BON/h × 种子数 | 无全局封顶 |

结构上我们**明显借鉴了 NP 的 arctan**（同样 `2/π·arctan` 形式），且把"底薪"放在曲线之外（NP 是 `+1×min(做种数,7)` 的线性补贴，同样在线性区）。
差异：我们的渐近值是 NP 的 2~4 倍。结合我们另有 4 个**回收**玩法（刮刮乐/猜大小/九宫格/农场，EV 0.66/0.951/0.725/0.90），产出侧宽松一点是设计选择，但**净产出仍需按月对账**（v4 §79 的运营数据：真实产出大头其实是 `increment_bulk` 87%，不是公式结算 —— 说明公式额度不是通胀主因）。

### 2.6 工程健壮性 —— 我们最强

| 项 | 我们 | NP | Gazelle | U3D |
|---|---|---|---|---|
| 幂等重跑 | ✅ `seeding:{uid}:{HH}` 唯一键，worker 停机/重跑不重复发 | ❌ cron 直接写，重跑会重复 | ⚠️ 去重表 | ⚠️ |
| 反假保种 | ✅ 排除 `connectable=0 AND uploaded=0` | ⚠️ 零魔种子权重 0.2 | ❌ | ✅ connectable 变量 |
| 参数化 | ✅ 全 `site_settings`，热改 | ⚠️ 等级阈值硬编码 | ✅ | ✅ 全 DB |
| 可读性 | ✅ 规则名 + 收益构成页 + 公式说明 | ⚠️ 只有公式图片 | ❌ | ✅ 最好 |
| 明细可审计 | ✅ `spark_ledger` 幂等流水 + 按规则名聚合 | ⚠️ | ⚠️ | ✅ |

## 3. 两个结构性问题（建议修）

### 3.1 「堆小种」可套利 —— 因为没有体积因子

我们用缺省参数实算三家的同场景收益（`base=10`，`B0=50`，`L=300`，`T0=4周`）：

| 场景 | 我们 | NexusPHP | Gazelle |
|---|---|---|---|
| A. 6 颗 100GiB 老种（seeders=1，做种 24h） | **89/h** | 87/h（B0=100 时） | ~0.6/h |
| B. **1000 颗 1MB 小种**（seeders=1，做种 1h） | **205/h**（≈满额） | **0.26/h** | ≈0 |
| C. 1 颗 100GiB 大种（seeders=1，做种 1h） | 21/h | 8/h | 0.4/h |

我们 s_i 的算法（场景 B）：`0.25 ÷ 1 ÷ (1+1/2160) ≈ 0.2499`，× 1000 → `Σ≈250` → `400/π·atan(250×0.12=30) ≈ 196` → 每小时 **206**。

**这比保 6 颗濒危大种（89/h）还高 2.3 倍**，而成本是 1GB 磁盘 + 1000 条做种连接（还会给 tracker/客户端添负担）。
根因：`ELSE 0.25` 对**任意体积**生效，没有下限过滤，也没有体积权重。
→ 老实说，这与我上一轮「堆数量收效极低」的判断相反，**以本数字为准**。

**修复提案（三选一，推荐 A）**
- **A. 体积对数饱和因子**：`v(size) = min(1, log10(1+size_GB) / log10(1+50))` —— 1MB→0.11、1GiB→0.25、25GiB→0.85、50GiB→1.0、100GiB+→1.0。连续无跳变，小种收益极低，大种不超额。
- B. 最小有效体积：`size < 100MB 不计`（简单粗暴，但仍有 100MB~1GB 的中间地带）。
- C. 直接引入 NP 式线性 `×Si(GB)`（会把"挂一个巨种躺赚"放大，与我们的封顶设计冲突，**不推荐**）。

### 3.2 个人做种时长处罚 → 改为与 U3D 对齐的分档加分

**修复提案**：删除 `1/(1+h/2160)` 乘数，改为**加分档**（与 U3D 的 Legendary Seeder 系列对齐，也与我们已有的规则名体系一致）：

| 档 | 条件（个人做种该种时长） | 规则分 |
|---|---|---|
| 传奇做种者 | ≥ 1 年 | +2.0 |
| 资深做种者 | 6-12 月 | +1.0 |
| 稳定做种者 | 3-6 月 | +0.75 |
| 新晋做种者 | 1-3 月 | +0.5 |

好处：① 奖励长期保种（对齐三家）；② 玩家看得懂"我差 2 周升级到资深"；③ 与"濒危/高龄/老种"档并列，构成统一的规则命名体系（前端 `reward_rules` 直接多几行）。
代价：全站时魔会**上升**（去掉衰减因子），需要同时**下调封顶或规则分**以保持回收口径 —— 建议把 arctan 的渐近值从 `+200` 降到 `+150`，或把系数 `6/50` 调到更保守的值，用一次性标定验证（脚本见 §4）。

### 3.3 附带建议：稀有度补一个"加成"通道

把 `seeders^-0.35` 改为 `(1 + k × seeders^-0.35)`（k 缺省 0.6）或直接对齐 NP 的 `1+√2·10^(-(N-1)/6)`：
- 独苗：×1.6（我们）/ ×2.414（NP）
- seeders=10：×1.05 / ×1.03
- seeders=100：×1.006 / ×1.0
让"保独苗"从"不被惩罚"变成"被奖励"，同时不给热门种加钱（seeders 大时趋 1）。这一条与 §3.1 的体积因子配合，能把"堆小种"彻底堵死（小种 × 体积因子 ≈ 0）。

## 5. 结论

- **不要照抄任何一家**：NP 的 `Si` 线性 + `B0=50` 是为"大站 + 大文件"设计的；Gazelle 的 BP 单位与物价体系绑定；U3D 的规则表驱动最灵活但要 11 条规则维护成本。
- **我们的方向是对的**：规则名化 + 参数化 + arctan 封顶 + 幂等流水，工程上比三家都干净；缺的是"体积"这一根支柱，以及"个人做种时长"的方向性错误。
- **优先级**：§3.1 体积因子（堵套利，P0）> §3.2 时长分档（纠方向，P1）> §3.3 稀有度加成（调平衡，P1）。
- 三项都要先算账再上线，改的是**全站产出**，不是单个玩法。

## 6. 实施记录（2026-09-19，已落地并验证）

三项已全部实施（迁移 `0133_seeding_formula.sql`）。

### 6.1 新公式与实现形态

```
每颗种子 s_i = ( 种子档位分 + 个人做种时长档位分 )
             × min(1, log10(1+size_GB)/log10(1+vol_base))   -- 体积对数饱和
             × (1 + rarity_k × seeders^-rarity_exp)         -- 稀有度加成
             × scale                                        -- 总标定
时魔 = ( base + floor( (2/π)·cap·atan(Σ × curve_k) ) ) × (donor ? donor_mult : 1)

个人做种时长档位分：≥1年 +2.0 / 6-12月 +1.0 / 3-6月 +0.75 / 1-3月 +0.5 / 不足1月 0
```

**实现形态：公式落在 DB 里（单一真相源）**，不再散在 Rust：

| 对象 | 作用 |
|---|---|
| `seeding_params()` | 参数行（从 `site_settings` 读一次；worker 用 CROSS JOIN 复用同一行，避免每行读表） |
| `seeding_torrent_bonus(size, seeders, age_days, completed, personal_hours, vol_base, rarity_k, rarity_exp, scale)` | **纯函数**：单颗种子系数（参数全部显式传入 → 可直接做性质断言） |
| `seeding_hourly(sum_bonus, base, cap, curve_k, donor_mult, is_donor)` | Σ → 每小时魔力 |

worker 的 `seeding_reward` 与 API 的 `hourly_estimate`（`/me/spark`）**都调用这两个函数** —— 顺带把此前 `10 + 颗数×2` 的粗估预估换成了真实公式（预估与实发不再打架）。

### 6.2 参数（全部 `site_settings` 可调，含后台中文标签/说明）

| 键 | 缺省 | 含义 |
|---|---|---|
| `seeding_base_hourly` | 10 | 底薪（不参与压缩曲线） |
| `seeding_cap_hourly` | **150** | arctan 渐近上限（原硬编码 200，下调以对冲时长加分带来的抬升） |
| `seeding_curve_k` | 0.12 | 曲线系数（= 原 6/50） |
| `seeding_vol_log_base_gb` | 50 | 体积满分基准（1GB≈0.17、5GB≈0.46、30GB≈0.87、≥50GB=1.0） |
| `seeding_rarity_k` | 0.6 | 稀有度加成（独苗 ×1.6） |
| `seeding_rarity_exp` | 0.35 | 稀有度指数（Gazelle 口径） |
| `seeding_bonus_scale` | **0.4** | 总标定系数（见 6.3） |

### 6.4 验证（`_v_seeding.py`，21/21 全绿）

- 性质：体积单调 + 饱和（100G == 1T）、1MB 系数 3.97e-5、稀有度同档位下独苗>热门且加成比 = 1.2618、热门衰减温和（0.8346，旧公式 0.35）、时长档位单调递增、时魔渐近 base+cap（159/160，atan 开区间不可达）、零加成只拿底薪、极端输入不报错
- **双实现对账**：`seeding_torrent_bonus` 与 Python 独立实现 **180 组参数逐组一致**（1e-9 容差）
- **账本对账**：三个测试用户（含 donor）账本金额 == Python 期望（90 / 22 / 29）
- 幂等键每小时 1 行；`scale` 改动生效且可回退
- 核心结论：**堆 1000×1MB 只剩底薪 10/h，而保 6 颗濒危老种 112/h（11 倍）**

### 6.5 顺带加固的两处

1. **结算的数据新鲜度过滤**：`seeding_reward` 原本只按 `seeding=TRUE` 取行，而僵尸清理（`sweep_stale_peers`）跑在**另一个 tick**（分钟级）—— 意味着客户端崩溃的行在"被清理前的窗口"里仍会领钱。现结算侧独立过滤 `last_seen_at > now() - max(2h, 2×announce_interval)`，阈值算法抽成 `stale_peer_threshold_secs()` 供两处共用（**发钱动作不该依赖另一个 job 恰好跑过**）。API 估算同步加同一过滤。
2. **收益构成页补维度**：`/me/spark` 的 `reward_rules` 现在同时给出「种子档位」与「做种时长档位」两类（如"传奇做种者（≥1年）×3"），玩家能看懂为什么拿这么多 —— 这是相对 NP（只有一张公式图）的体验优势。

### 6.6 未做 / 后续

- **不做追溯补发**：只对新小时生效（旧流水不动）。
- 若站长想微调总量：只改 `seeding_bonus_scale`（0.1~2.0，step 0.05）即可，无需动公式。
- 体积满分基准 `seeding_vol_log_base_gb` 可按站点资源体量调（小资源站可下调到 10~20GB）。
