## 一、高危：web 代理 XFF 重组方向与 api 右值取信相反（已修）

**位置**：`apps/web/app/api/[...path]/route.ts:34-42` + `apps/api/src/http/auth_infra.rs:69-94`（动态验证 + 子代理推演双重确认）

web 代理把 `clientIp = x-real-ip ?? XFF首值 ?? "unknown"` 放进重组 XFF 的**首位**追加原链；而 api（二轮改的）取 XFF **右值**。两者语义相反：
- **本地/直连 web 形态 + TRUST_PROXY=1**：攻击者 `curl -H "x-forwarded-for: 1.2.3.4"` 打 web 代理 → 代理重组 `XFF: 1.2.3.4, 1.2.3.4`（clientIp 来自攻击者可设的头）→ api 取右值 = **假 IP**。登录/注册/申请/验证码限流、ip_bans、login_events 风控全部记到攻击者任意指定的 IP——换一个头就绕过 5/min 限速爆破登录、伪造他人 IP 的登录失败记录嫁祸。
- 宝塔标准形态（nginx→web→api）下若 nginx 正确设置 `$proxy_add_x_forwarded_for` 则右值=真 IP（安全）；漏配 X-Real-IP 时右值模型反而兜底正确。
- **修复**：web 代理不再从请求头猜 clientIp——XFF 原样透传（外层可信代理的追加语义生效）；`x-real-ip` 原样透传备用。同源/跨站/伪造 XFF 三形态线上复测通过。
- 附带：`pt_audit_f_entitlement.py` 的 G1-G3 只测 Origin 不测 IP——XFF 链是闸门盲区（记入建议）。
