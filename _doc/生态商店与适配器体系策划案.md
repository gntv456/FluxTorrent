# 生态商店与适配器体系策划案（Marketplace & Adapter Framework）

> 状态：**策划定稿，未排期实施**。本文是「通用 PT 建站系统」的生态层总纲，
> 继承并取代《通用PT建站系统策划案》§1.4 中「插件市场维持非目标」的临时表述——
> 非目标收窄为「**代码级动态加载插件**」，生态建设以「内容包 + 受信适配器」的形态立项。
>
> 结论速览（TL;DR）：**不做 NP 式插件商店，做「信任商店」。**
> 货架分三层——内容包（复用既有基建，零新增架构）、适配器（WASM 进程内沙箱，打 NP 生态最痛的软肋）、
> 自营深度能力（Hook 面加厚但不出租）。分期 M1→M5，M1 可完全搭现行路线图便车。
>
> 撰写日期：2026-09-24。前置讨论三轮：技术可行性 → 零成本推演 → 站长维护性视角。

---

## 0. 本案要解决的问题

通用建站系统卖出去之后，站长的需求分三类，前两类已覆盖，第三类是本案对象：

1. **「功能开关」**——29 键模块注册表（0107）：开箱内置的功能，toggle 控制。✅ 已交付。
2. **「形态选择」**——11 站型包（0037/0092）：分类/品牌/模块默认值矩阵。✅ 已交付。
3. **「生态供给」**——分类学补齐、外观皮肤、经济数值、元数据源、支付渠道等**持续会过期的运营资产**。
   现状是「出厂时有一份静态快照」，没有更新通道。❌ 本案补齐。

NP 圈对此类需求的解法是论坛帖 + 拷文件 + 加密付费插件——结果是：
生态繁荣与工程腐烂并存，插件断裂拖死核心升级，站长排障无门。
我们要做的是**用工程化手段吃下同一块需求**：把「插件商店」重新定义为「信任商店」。

### 0.1 非目标（明确不做，与总纲 §1.4 的关系）

| 不做项 | 理由（详见 §9） |
| :--- | :--- |
| 第三方任意代码动态加载（NP 模式） | Rust 无稳定 ABI；同进程全权限与资金安全冲突；维护责任无法转嫁 |
| dylib/.so 运行时加载 | 无稳定 ABI + segfault 不可拦，直接排除 |
| 边车容器插件（面向站长侧） | 部署面变大 = 归因灾难；仅保留为未来 B 端托管形态备选 |
| 第三方深度插件（改结算/权限/流程） | 违反 A6「禁用即还原」，维护责任在构造上就无法转嫁 |
| 多租户单实例 | 总纲非目标，本案不重开 |

总纲原表述「运行时动态加载插件 / 第三方插件市场：不立项」修正为：
**「代码级动态加载不立项（永久）；生态商店以内容包 + 受信适配器形态立项（本案）」。**

## 1. 立项逻辑：三轮探讨的结论沉淀

### 1.1 为什么不是「插件商店」

市面实现方式逐一流派评测后的共同结论：

| 流派 | 代表 | 对我们的致命问题 |
| :--- | :--- | :--- |
| 文件级动态加载 | NexusPHP / WordPress | PHP 解释型的物理优势我们没有；NP 的「安装易」是行为经济学陷阱——安装痛可见、维护痛递延 |
| Composer 包目录 | Unit3D / Flarum | 要站长兼职系统管理员，受众错配 |
| 重建镜像 | Discourse / Gazelle(fork) | 每次插件变更 = 停机重建；Gazelle fork 模式恰是我们要消灭的 |
| 官方目录 + 签名 | WP/Grafana/Jellyfin | 好东西，但其货品本质仍是同进程代码，继承无隔离问题 |
| 沙箱 guest 运行时 | VSCode / wasmtime | 工程最正统；成本集中在「宿主 API 面设计」，仅对窄能力品类划算 |
| 边车 + 事件总线 | （PT 圈无人做） | 隔离最强但部署面 +1，站长归因灾难 |

且 PT 圈的盘子本身薄：站点总量有限、插件作者池 ≈ 站长池 ≈ 极客池，
U3D 有 composer 目录仍然小众——**双边市场冷启动无解，空货架的商店是负资产**。

### 1.2 三个与预算无关的结构约束（零成本推演后存活）

即使开发成本归零，以下四条依然成立，它们是本案权衡的骨架：

1. **双边市场冷启动**：钱能建店，不能进货，更不能雇人来逛。破解只能靠自营种子内容 + 悬赏，
   属于持续社区运营投入，不属于开发成本。
2. **沙箱能力悖论**：越安全，插件越弱。NP 插件的强大源于不安全。运行时越 engineered，
   第三方插件相对 NP 生态越「玩具化」——接受它，把深度能力收回自营。
3. **契约治理税是永续的**：每暴露一个宿主 API 就是永久冻结面。我们正处在追平 NP/U3D/KG
   功能清单的冲刺期，核心迭代速度此刻就是唯一的产品。
4. **资金安全与审查责任**：魔法值池/银行/支付在站内，开店即成为审查主体，插件事故的品牌损失由核心背书。

### 1.3 站长维护性视角（决定形态的最终裁判）

站长的信任资产有二，插件生态天然腐蚀两者：

- **单一责任方**：出问题 = 我们的 bug，单一仓库可复现修复。第三方物每引入一个，责任面碎一分，
  但站长心理上仍只找我们。
- **「后台即全站真相」**：29 键注册表承诺面板描述站点全部行为、契约测试锁死。第三方物结构上
  不可能纳入我们的契约测试——装了它，面板就开始说谎。

由此推出本案的六条硬规则（A1–A6），它们是**准入门槛而非功能清单**——
任何第三方分发物不满足即不上架：

- **A1 核心升级永不被插件阻塞**：兼容矩阵由商店侧强制执行；核心升级时发现不兼容 →
  货品自动禁用 + 面板通知，核心照升（反 NP「插件拖死核心升级」宿命）；
- **A2 禁用即回到已知好态**：安装的单位是「装 + 一键还原」，禁用后核心行为与
  从未安装过不可区分；
- **A3 第三方不得做 schema 迁移**：持久化只能在自身命名空间内（数据残留是
  卸载不干净的总根源，与 0145「禁止单路径物化」同源）；
- **A4 熔断自愈**：连续 panic/trap/超时自动停用并亮灯（M28 catch_unwind 语义的
  计数化升级）；
- **A5 后台卡片心智延续**：货品在站长眼里与 29 个模块开关联构，多一枚
  来源/版本/健康度角标，不新增心智模型；
- **A6 在册维护人**：弃养即下架标灰，维护责任不得默认塌到核心项目头上。

**核心命题**：站长的维护性把「插件商店」的定义从「能力平台」改成了「信任平台」——
产品不是「第三方能给你的站加什么」，而是「你按下去的每一键，倒回去时还是不是你的站」。

## 2. 总体架构：三层货架 + 一条边界

```
┌──────────────────────────────────────────────────────┐
│                  FluxTorrent Marketplace               │
│          （站点后台内的一个 tab，中央索引 + 一键导入）      │
├──────────────┬───────────────────┬────────────────────┤
│  Tier 1 内容包 │   Tier 2 规则包    │   Tier 3 适配器     │
│  分类学/主题/  │   经济数值/反作弊/  │   元数据源/支付网关/ │
│  素材/汉化     │   防灌水          │   Indexer          │
├──────────────┴───────────────────┴────────────────────┤
│  内容包/规则包：无代码/受限表达式 → 无沙箱需求             │
│  适配器：WASM 进程内沙箱（wasmtime），manifest 能力制      │
├───────────────────────────────────────────────────────┤
│  Tier 4 深度能力：Hook 面加厚，自营，不出租（§6）          │
└───────────────────────────────────────────────────────┘
```

三层的能力/审查/失败模式对照：

| 层 | 货品 | 执行形态 | 审查强度 | 失败模式 |
| :--- | :--- | :--- | :--- | :--- |
| T1 内容包 | 分类学/主题/素材/汉化 | 纯数据 | 内容审 | 无聊：导入失败，站点原样 |
| T2 规则包 | 经济数值/反灌水/风控规则 | 受限表达式（AST 白名单求值） | 轻校验（lint + 数值域） | 无聊：规则拒绝加载 |
| T3 适配器 | 元数据源/支付网关/Indexer | WASM 沙箱，仅出网+回调 | 中等 + 自动更新 | 受控：熔断停用，功能降级手填 |
| T4 深度能力 | 结算规则/权限联动/流程改写 | 编译期 Hook（不出租） | 自营代码评审 | 不适用 |

**边界即产品**：T1/T2/T3 是「店」，T4 永远是「厂」。对外的商店叙事刻意模糊这个边界
（一个 Marketplace，三个 tab），对内的工程纪律严格维持这个边界。

## 3. Tier 1：内容包商店（M2）

### 3.1 货品与现状对接

| 货品 | 现有基建 | 缺口 |
| :--- | :--- | :--- |
| 站型包 | 0037/0092 种子，settings 导入导出（0039/0053） | 导入导出对 site_type_packs 快照的覆盖核对；店侧索引 |
| 分类学包 | categories 表、icon_key 全链路（f49041d） | 打包格式（含图标键+质量维度 sections）与导入冲突策略 |
| 主题包 | CSS 变量层（globals.css/layout.css）、品牌设置 | 变量清单脱敏 + 打包格式 |
| 素材包 | 勋章图鉴/头像框四季度双形态 | 素材包格式 + run 盐沿用 0146 教训 |
| 汉化包 | zh-CN/zh-TW/en + 后端 task-local i18n | 术语库导出格式；**不开放文案覆盖**（保三语一致性门禁） |

### 3.2 包格式与生命周期

- 格式：带 manifest 的 zip（或直接 JSON，素材包为 zip），manifest 含 `pack_id / version /
  core_compat / depends（如分类学包可依赖某站型包）/ checksum`。
- 生命周期四步，全部走后台 UI：
  1. **浏览**：店内按站型/类别过滤，展示预览（分类学包渲染出树预览，主题包渲染截图）。
  2. **导入**：一键拉取 + checksum 校验 + 冲突策略（纯覆盖语义）。
  3. **回滚**：一键恢复到导入前快照（复用设置历史基建）。
  4. **更新**：店内新版本提示，diff 预览后确认。
- **审计**：每次导入/回滚写 audit_log（沿用站型派生值排查口径——先看 audit_log 写入路径）。

### 3.3 硬性纪律（继承 0145 教训）

**所有内容包必须走「纯覆盖 + 动态合并」，禁止单路径物化。**
分类学包导入后，导航/列表页/上传表单/搜索聚合全部从同一份注册数据派生，
不允许任何页面在导入时把分类「抄」进自己的配置——否则就是把 site_type 派生值漂移
那类 bug 打包批发。包导入器的集成测试必须覆盖「导入 → 四处一致」断言。

## 4. Tier 2：规则包（M3）

### 4.1 货品

- **经济数值包**：银行利率表、定期档位、魔法值池系数、绩效公式参数、促销定价梯度。
- **反灌水规则包**：发帖间隔/新用户限制/敏感词表。
- **反作弊基线包**：做种量突变阈值、幽灵客户端特征、命中率区间。

### 4.2 受限表达式引擎

规则包里的「公式」不是代码，是 AST 白名单表达式（参考 expr-eval 类库的 Rust 实现）：

- 白名单节点：算术/比较/逻辑/条件 + 显式注册的变量名（如 `seed_time_hours`、`downloaded_gb`）；
- 编译期 lint：未知变量、除零风险、数值域检查（利率 ∈ [0, 1] 之类按规则类声明）；
- 求值超时熔断：表达式求值加硬性毫秒上限，超时按默认值降级并告警。

**不开放**：函数调用、循环、赋值、任意属性访问。这套引擎同时反哺自营功能
（绩效公式后台可配置化的底层就是它）。

## 5. Tier 3：适配器体系（M4）——本案的技术重心

### 5.1 为什么适配器值得一个沙箱

适配器是「上游一改就断」的品类——豆瓣改版、TMDB 换 API、支付渠道换签名方式。
NP 生态里这类东西散落论坛帖、断了没人修，**是 NP 生态工程化最差、站长痛最真的一块软肋**。
「带自动更新的受信商店」相对论坛帖分发是碾压级体验，这是打 NP 的正面一击。

现状对接：PT-Gen 源白名单已按站启（`metadata_sources` 设置 ∩ 源校验），
说明「元数据源是站级可配物」的口径已通——本案把它从「内置白名单」升级为「可装载适配器」。

### 5.2 运行时选型：进程内 WASM（wasmtime）

| 候选 | 裁决 | 理由 |
| :--- | :--- | :--- |
| **进程内 WASM** | ✅ 采纳 | 部署面恒定（docker compose 不长新东西）+ trap 不 segfault + 崩溃圈在沙箱内 + 后台可做一键安装 |
| 边车容器 | ⏸ B 端备选 | 隔离更强但站长部署面 +1；留给未来托管站群（有专职运维的场景） |
| 编译进核心 | ❌ | 每个站要的源不同，按站编译不可行 |

**关键决策**：适配器只需要「出网 + 回调」能力，**不需要深库权能、不需要 veto、不需要改写响应**。
这恰好绕开 WASM 在重 DB 操作上的全部短板（沙箱能力悖论在窄品类上不成立）。
宿主 API 面从第一天就刻意做小（见 5.3），冻结面越小，契约治理税越轻。

### 5.3 宿主 API（冻结面，v1 极小）

适配器 manifest 声明能力，安装时站长看到的是权限清单而非代码：

```yaml
adapter_id: metadata.douban.v2
version: 2.3.1
core_compat: ">=1.4"
kind: metadata            # metadata | payment | indexer
capabilities:
  http_out:               # 出网白名单
    - "https://*.douban.com/**"
  secrets_read: [ptgen_key]   # 仅可读声明过的命名空间
rate_limit: 30/min
cache_ttl: 6h
```

宿主函数（guest 可调用）初始仅四个，全部显式同步、可审计：

1. `http_fetch(url, headers) -> response`（强制走出网白名单 + 代理配置 + 限流）
2. `cache_get / cache_set`（适配器命名空间 KV）
3. `secret(name)`（仅 manifest 声明过的键）
4. `log(level, msg)`

guest 导出函数（宿主调用）：`fetch_metadata(kind, ids) -> result`、
`health_check() -> result`、`migrate(from_version) -> result`。

**明确不提供**：SQL、任意文件、环境变量、进程、响应改写、请求 veto。
将来真需要更强能力时按品类逐个评审扩面，而不是给一个万能 escape hatch。

### 5.4 可靠性机制（A4/A5 的落地）

- **熔断**：连续 N 次 trap/超时 → 自动停用 + 后台亮灯 + 降级（元数据手填，站不倒）。
- **健康度**：`health_check` 定时跑，失败率入面板。
- **自动更新**：店内新版本 → 兼容矩阵通过 → 灰度替换 → 失败自动回退上一版本。
- **资源限额**：wasmtime store 设 fuel/epoch 上限，防死循环。
- 语言 SDK：先 TypeScript（受众最广）+ Rust；插件作者不需要懂我们的核心代码。

### 5.5 支付网关适配器的特别纪律

支付品类即使沙箱化也要追加：

- 适配器**只做协议适配**（签名/回调验签/格式转换），**不碰账务**——扣款入账仍走核心
  payment 域的既有幂等结算路径（0148 双结算教训）；
- 回调验签在宿主侧二次校验金额与订单号，适配器返回的「已支付」只是主张，不是事实。

## 6. Tier 4：自营深度能力——Hook 面加厚（M5，低强度持续）

M28 插件系统（3 个 fire-and-forget Hook）保持编译期装配，但按内部需要加厚：

- **Hook 面扩展**（按需，不预制）：新内部功能优先走 Hook 而非直插领域层，
  维持「领域层不知道插件存在」的现行纪律；
- **可选引入同步 veto 语义**（仅极少量咽喉点，如发布审核拦截）：仅自营插件可用，
  第三方永远拿不到——这个不对称是刻意的；
- **动机**：为「将来若开放边车/B 端」预留事件面，成本极低；日常收益是内部功能解耦。

**对外口径**：不宣传「插件系统」。「后台模块开关 + 商店内容包 + 适配器」就是全部故事。
吸 NP 插件生态的作者没有意义——他们的插件在我们的货架上没有对应的品类。

## 7. 中央仓库与商店产品（随 M2 起，持续运营）

### 7.1 仓库职责

- 索引：货品清单、版本、对核心版本的兼容矩阵（core_compat）；
- 分发：HTTPS 下载 + checksum；
- 信任链：货品签名（T1/T2 由我方直接签发；T3 适配器我方审核后签发，**无社区直传代码**）；
- kill switch：恶性问题一键全网停用（适配器自动更新通道天然支持）；
- 弃养治理：维护人必须在我方在册（A6），失联即下架标灰。

### 7.2 商店 UI（站点后台内嵌）

- 入口：后台「生态」tab，与「模块开关」卡片区同构——不新增站长心智模型；
- 适配器卡片：来源/版本/健康度/最近事件角标；内容包卡片：版本/diff 预览/回滚按钮；
- 离线模式：仓库不可达时商店只读降级，不影响站点任何功能（商店是增强，不是依赖）。

### 7.3 冷启动策略（承认 §1.2 约束 1）

- **自营铺货先行**：11 站型包、按站型预置分类学包（教育/影视/无损音乐…）、
  常用经济数值档位包（温和/通胀/紧缩）、主流元数据适配器（douban/bangumi/TMDB）——
  目标是开店当天货架不是空的；
- 悬赏征集：分类学包与主题包按「被导入站数」给积分激励（复用站内积分基建发外部贡献者奖励的口径另议）；
- 不追求数量指标：货品宁缺毋滥，每件过审。

## 8. 分期路线图

| 期 | 交付 | 量级 | 依赖 |
| :--- | :--- | :--- | :--- |
| **M1 目录化（搭便车）** | 分类学包/主题包格式定稿（复用 0039/0053 导入导出 + 0107 纪律）；站点后台「导入导出」页升级为包管理页（本地导入/回滚，无中央仓库） | 1–2 周 | 无新架构，可完全并行于标签重构 P2 |
| **M2 内容包商店** | 中央索引站 + 后台商店 tab（浏览/一键导入/更新提示）；素材包/汉化术语包格式；audit_log 全覆盖 | 2–3 周 | M1 |
| **M3 规则包** | 受限表达式引擎 + 经济/反灌水/反作弊规则品类 + lint；同步反哺「绩效公式后台可配置化」 | 2–3 周 | 独立，可与 M2 并行 |
| **M4 适配器体系** | wasmtime 集成、宿主 API v1、manifest/签名/自动更新、TS+Rust SDK、首个自营适配器（douban 或 TMDB）迁移 | 4–6 周 | M2（复用仓库/签名/更新通道） |
| **M5 Hook 加厚** | 按内部功能需要逐个加，无专项排期 | 持续 | — |

**排期原则**：M1–M3 不碰运行时、不立沙箱、不加部署面——全部是现行架构的自然延伸；
M4 是唯一的新架构决策点，且已被「窄能力面」约束框死。任何一期都可以独立止损。

### 8.1 验收基准（每期通用）

- **M1**：干净库导入「影视分类学包」→ 导航/列表/上传表单/搜索聚合四处一致（继承 0107 契约自检思路）；一键回滚后与导入前 bit 级等价（素材 run 盐不变）；
- **M2**：断网状态下商店页只读、站点全功能正常；导入/回滚全量审计可查；
- **M3**：表达式 lint 拒绝未知变量与越域数值；求值超时降级为默认值且告警；绩效面板数值与公式预览一致；
- **M4**：适配器内 panic/死循环/出网越权 → 熔断停用 + 面板亮灯 + 元数据降级手填，核心 API 全程无感；自动更新失败自动回退；支付适配器回调金额在宿主侧二次校验（伪造「已支付」主张不生效）。

## 附：本案不变式（评审清单，违例即打回）

1. 站长的 docker compose 文件**永远不因商店而改变**；
2. 任何第三方分发物**永不获得** SQL / 文件系统 / 环境变量 / 响应改写 / 请求 veto；
3. 任何货品**必须**满足 §1.3 六条硬规则 A1–A6；
4. 仓库不可达 = 商店只读，**永不**影响站点功能；
5. 深度能力（结算/权限/流程改写）**永不出租**给第三方。
