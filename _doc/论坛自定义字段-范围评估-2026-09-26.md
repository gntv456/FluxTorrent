# 论坛自定义字段——范围评估结论（2026-09-26，闭环审查 P2-20）

## 结论：本轮不做全量实现，给出分层替代路径

「自定义字段」当前覆盖两类实体：用户（`user_field_defs`，0186，六类型全套）与
种子（`section_kinds.field_type`，0195，六类型 + 发布表单六控件 + 内容包四处同
形状导出/导入）。论坛话题/板块、合集没有等价能力。

## 为什么不建议直接照搬

1. **话题字段的消费面远大于用户/种子字段**：用户字段只需「注册页 + usercp +
   管理端」三处渲染；种子字段有统一的 sections 聚合出口。而论坛话题字段需要
   进：发帖表单（forum-composer 弹窗）、帖子渲染（post-row 的 LATERAL 聚合）、
   主题列表列、搜索/筛选、举报上下文、RSS/视频内嵌规则联动——每一处都要
   按字段类型分支，工作量约等于 0186+0195 两批之和。
2. **数据模型要么宽表要么 JSONB**：话题无 `torrent_sections` 那样的从表先例；
   JSONB 一把梭会绕过现有词表/维度体系（B 批刚把种子侧收编进同一谓词）。
3. **用户价值密度低**：审查排序时该项列为 P2 末位——没有站长反馈卡在这，
   而卡在面板/订单/通知的已全部修掉。

## 分层替代（站长当下可用的近似能力）

| 需求 | 现有能力 |
|---|---|
| 版块级结构化信息 | 版块描述支持富文本 + 版块分类（分区）树 |
| 话题打标 | 论坛 tags（0159 标签体系：受控词表 + 三入口校验） |
| 话题结构化分类 | 主题类型（normal/bounty/poll/lottery）+ 版块归属 |
| 跨实体自定义展示 | 自定义页面（0187）+ 术语表（0205）改写文案 |

## 若后续要做（建议排期口径）

- 迁移：`topic_field_defs`（对齐 user_field_defs 六列）+ `topics.fields JSONB`
  （V8 后再normalize 成从表）；
- 出口：发帖弹窗按类型渲染（复用 upload-form-quality 的六控件）、
  `topics/{id}` 聚合带回、列表可选列；
- 管理端：`staff-http` 加 defs CRUD（对齐 user_fields 面板交互）；
- 门槛信号：两个以上站长反馈「论坛要结构化字段」再启动。
