## 1. 背景与目标

娱乐玩法的痛点是「纯娱乐」与「PT 站核心行为（做种 / 上传 / 活跃）」两层皮。
完善玩法的核心，是把**活跃行为变成游戏资源**，让「玩」反哺「站」。

本模块实现《玩法完善与数值平衡》文档中优先级 **① 核心行为联动轻量版**，包含两条联动链：

1. **口粮券（养成侧联动）**：每日做种满 6h → 送 1 张口粮券，抵宠物喂养 / 鱼竿升级的消耗。
   让喂养不纯靠氪魔力，形成「做种 → 养宠 / 钓鱼」正循环。
2. **渔汛做种门槛（钓鱼侧联动）**：周末「渔汛」活动鱼仅对「本周做种达标」用户开放，
   把活跃行为变成限定产出门槛。

> **经济纪律**：口粮券是**纯行为联动资源**，本身不返魔力、不进入火花交易管线，
> 结构上杜绝通胀源（见 §7）。

## 2. 总体设计

### 2.1 行为联动模型

```
        每小时做种结算 (seeding_reward)
                     │  写 spark_ledger
                     │  idem = seeding:{user}:{yyyymmddhh}
                     ▼
   行为信号（已存在，零新增）          游戏资源（本模块新增）
   ┌───────────────────────┐      ┌──────────────────────────┐
   │ spark_ledger           │      │ users.food_coupons       │
   │  kind='seeding_reward' │ ──►  │ food_coupon_grants       │
   │  idempotency_key       │ 计数  │ coupon_uses             │
   └───────────────────────┘      └──────────────────────────┘
       当日不同段数 = 做种小时          口粮券余额 / 发放幂等 / 核销幂等
```

### 2.2 关键设计决策：复用 `seeding_reward` 流水

判定「当日做种满 N 小时」**不新建任何做种时长累计表**，而是直接统计
`spark_ledger` 中 `kind='seeding_reward'` 且属于当日的记录条数：

- 做种结算 job（`apps/worker/src/jobs/seeding.rs`）的幂等键格式为
  `seeding:{user}:{yyyymmddhh}`，即**每用户每自然小时至多 1 条**；
- 用 `split_part(idempotency_key, ':', 3)` 取出第 3 段（10 位 `yyyymmddhh`）；
- `count(DISTINCT 第3段)` 当日 = 当日做种小时数。

**为什么这么做**：

- 零新增累计表，不引入新的数据一致性负担；
- 零改动资金管线（`spark_ledger` 是既有真相源，本模块只**读**它）；
- `seeding_reward` 本身幂等（`idem` 唯一），统计天然去重；
- 阈值走 `site_settings`，运维可热调，无需改代码重发。

**已知近似**：若某小时结算 job 因故障未跑，该小时不计。属可接受的「轻量」口径；
如未来要求严格，可改为扫 `snatches.seeded_seconds` 日增量，但成本更高。

### 2.3 范围边界（轻量版做了 / 没做）

| 做 | 没做（留给后续优先级） |
|---|---|
| 口粮券发放 + 余额 + 状态查询 | 宠物喂养 / 鱼竿升级实际消耗点（需宠物、钓鱼模块） |
| 渔汛做种门槛「判定」 | 渔汛活动鱼的实际发放（属钓鱼模块） |
| 口粮券核销接口（防双花） | 前端页面 / 后台面板 |

## 3. 数据模型

### 3.1 DDL（迁移 `0239_linkage_coupons.sql`）

```sql
-- 口粮券余额（挂在 users 上，单字段轻量）
ALTER TABLE users ADD COLUMN food_coupons integer NOT NULL DEFAULT 0;

-- 每日发放幂等：每用户每自然日（站点 UTC+8）至多 1 张
CREATE TABLE food_coupon_grants (
    user_id bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    day date NOT NULL,
    granted_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, day)
);

-- 核销幂等（防同键重放白嫖）
CREATE TABLE coupon_uses (
    idem text NOT NULL PRIMARY KEY,
    user_id bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    used_at timestamptz NOT NULL DEFAULT now()
);

-- 行为联动查询加速：按 kind + 时间范围扫 seeding_reward 流水
CREATE INDEX idx_spark_seeding_day
    ON spark_ledger (created_at, user_id)
    WHERE kind = 'seeding_reward';
```

### 3.2 字段说明

| 表 / 列 | 类型 | 说明 |
|---|---|---|
| `users.food_coupons` | integer | 口粮券余额，缺省 0；只增（发放）只减（核销） |
| `food_coupon_grants.user_id` | bigint | 领取人 |
| `food_coupon_grants.day` | date | 站点自然日（`now() AT TIME ZONE 'UTC' + 8h`）；PK 一半 |
| `food_coupon_grants.granted_at` | timestamptz | 发放时刻（审计用） |
| `coupon_uses.idem` | text | 客户端幂等键（带 `use_coupon:` 前缀），PK |
| `coupon_uses.user_id` | bigint | 核销人 |
| `coupon_uses.used_at` | timestamptz | 核销时刻 |

### 3.3 部分索引

`idx_spark_seeding_day` 是**部分索引**（`WHERE kind='seeding_reward'`），
只覆盖做种流水，体积小、对 §4 / §5 的日/周统计有效。若后续 `seeding_reward`
流水进入旧分区，索引随分区继承（Postgres 分区表索引为每分区独立）。

## 4. 配置项（双源，运维可热调）

| 设置键 | 类型 | 缺省 | 含义 |
|---|---|---|---|
| `games_coupon_seed_hours` | integer | 6 | 每日做种满该小时数才发券 |

读取方式：

> 运维写入时务必是整数。

## 5. Worker 定时任务

### 5.1 文件

- 新增：`apps/worker/src/jobs/game_coupons.rs` → `pub async fn grant_food_coupons(db: &PgPool) -> anyhow::Result<u64>`
- 注册：`jobs/mod.rs`（模块声明 + `pub(crate) use game_coupons::*`）
- 调度：`jobs/run.rs` 的 **hour_tick** 分支
- 目录：`jobs/catalog.rs` 的 `JOBS` 数组（`cadence: "1h"`）
- 手动：`jobs/manual.rs` 的 `run_named` 分派

### 5.2 逻辑

```sql
WITH cfg AS ( SELECT COALESCE((SELECT value::bigint FROM site_settings
                  WHERE name='games_coupon_seed_hours'), 6) AS thr ),
     today AS ( SELECT date_trunc('day', now() AT TIME ZONE 'UTC' + interval '8 hours') AS start,
                       (now() AT TIME ZONE 'UTC' + interval '8 hours')::date AS d ),
     seed_hours AS (
        SELECT l.user_id,
               count(DISTINCT split_part(l.idempotency_key, ':', 3)) AS hrs
        FROM spark_ledger l, today t
        WHERE l.kind='seeding_reward'
          AND l.created_at >= t.start
          AND l.created_at <  t.start + interval '1 day'
        GROUP BY l.user_id
        HAVING count(DISTINCT split_part(l.idempotency_key, ':', 3)) >= (SELECT thr FROM cfg)
     )
INSERT INTO food_coupon_grants (user_id, day)
SELECT s.user_id, t.d FROM seed_hours s, today t
WHERE NOT EXISTS ( SELECT 1 FROM food_coupon_grants g
                   WHERE g.user_id = s.user_id AND g.day = t.d )
ON CONFLICT (user_id, day) DO NOTHING
RETURNING user_id;
```

第二步：把 `RETURNING` 回的新晋达标用户 id 批量 `+1` 口粮券：

```sql
UPDATE users SET food_coupons = food_coupons + 1 WHERE id = ANY($1);
```

### 5.3 调度与幂等

- **节奏**：挂 `hour_tick`（每小时）。用户做种满 6h 后最迟 1h 内到账，体验可接受。
- **分片**：`shard_lock!(&db, "job:game_coupons", ...)` —— 多实例部署时仅认领该 job 的实例执行。
- **锁**：内部 `with_lock("job:game_coupons", ...)` advisory 锁，多实例互斥、900s 超时。
- **幂等**：`food_coupon_grants(user_id, day)` 主键 + `ON CONFLICT DO NOTHING`，
  job 重跑 / 跨日补跑 / 手动重触发均**零副作用**（至多 1 张/日）。
- **手动触发**：后台面板「执行 `game_coupons`」→ 入队 `job_triggers` → 60s tick 认领，
  与定时同一函数、同一把锁（口径永不漂移）。

### 5.4 失败与重跑

- 若某小时 job 中途失败：已写入 `food_coupon_grants` 的部分不重复；下一轮重新评估未发卡用户。
- 余额 `+1` 在 `INSERT...RETURNING` 之后批量执行；若 job 在「写幂等表」与「+1 余额」之间崩溃，
  下一轮会因主键存在而跳过该用户 → **该用户当日漏发 1 张**（保守、不上溢，符合安全优先）。
- 返回值：实际 `+1` 的用户数（`rows_affected`）。

## 6. API 接口

全部挂在 `v1_scope()` 下，完整路径前缀为 **`/api/v1`**；且受 `games` 模块门控
（`requireModule("games")`），站型可整体关闭。响应统一信封：

```json
{ "code": 0, "message": "ok", "data": { ... }, "request_id": "..." }
```

错误：`Validation` → `code: 1002`；`Internal` → `code: 1000`（见 `apps/api/src/errors.rs`）。

### 6.1 `GET /api/v1/games/linkage/status`

**鉴权**：必须登录（`require_auth`）。

**行为**：现算当前用户的行为联动进度（只读，不改动任何数据）。

**响应 `data`**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `food_coupons` | int | 口粮券余额 |
| `daily_seed_hours` | int | 今日（UTC+8 自然日）做种小时数 |
| `weekly_seed_hours` | int | 本周（周一为周首，UTC+8）做种小时数 |
| `coupon_granted_today` | bool | 今日口粮券是否已发放 |
| `fishing_event_threshold` | int | 渔汛期解锁所需周做种小时（= `games_fishing_event_seed_hours`） |
| `fishing_event_unlocked` | bool | `weekly_seed_hours >= threshold` |

**实现要点**（见 `games_http/linkage.rs::linkage_status`）：

- 三处统计 + 一处 `EXISTS` 合并为单条 `query_as`；
- 当日窗口：`date_trunc('day', now() AT TIME ZONE 'UTC' + interval '8 hours')`；
- 本周窗口：`date_trunc('week', now() AT TIME ZONE 'UTC' + interval '8 hours')`（Postgres `week` 以周一为周首）；
- 做种小时同样用 `split_part(idempotency_key, ':', 3)` 取 `yyyymmddhh` 后 `count(DISTINCT)`。

### 6.2 `POST /api/v1/games/coupons/use`

**鉴权**：必须登录。

**请求体**（可选）：

```json
{ "idempotency_key": "客户端生成的唯一串，可选" }
```

不传则服务端回落随机键（兼容无幂等场景）。

**行为**：核销 1 张口粮券，返回剩余余额。当前是消耗侧的**独立入口**，
供未来养成喂养 / 鱼竿升级调用（这些模块尚未落地，故先以独立接口形式提供）。

**响应 `data`**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `consumed` | bool | 是否实际核销 |
| `food_coupons` | int | 核销后余额 |

**特殊返回**：同键重放时 `consumed=false, reason="duplicate"`，余额不变。

**实现要点**（见 `games_http/linkage.rs::use_coupon`）——防双花双保险：

1. 开启事务，`SELECT ... FOR UPDATE` 锁用户行（防并发两笔各扣一次）；
2. 余额 ≤ 0 → 直接回滚报错「口粮券不足」（`code: 1002`）；
3. `SELECT EXISTS(SELECT 1 FROM coupon_uses WHERE idem=$1)`：
   - 已存在 → 回滚，返回 `consumed=false, reason="duplicate"`（防同键重放白嫖）；
4. 否则 `INSERT coupon_uses` + `UPDATE users SET food_coupons = food_coupons - 1 ... RETURNING`，
   同事务原子提交。

> 行锁 + 幂等键二者缺一不可：行锁堵「两笔不同键并发双花」，幂等键堵「同键重放」。

## 7. 风控与边界

| 风险 | 处置 |
|---|---|
| 并发双花 | `FOR UPDATE` 锁用户行 + 单条事务原子扣减 |
| 同键重放白嫖 | `coupon_uses.idem` 主键去重，二次返回 `duplicate` |
| 通胀 | 口粮券**不返魔力**、不进火花管线；纯消耗侧资源 |
| 脚本刷券 | 发放完全由既有 `seeding_reward` 流水驱动（已有反假保种过滤：回连不可达且无上传的不计） |
| 阈值越权 | 走 `site_settings`，写入需整数；非整数 `::bigint` 转换即报错 |
| 合规 | 界面不出现「赌」字；纯虚拟货币（与既有娱乐玩法一致） |

