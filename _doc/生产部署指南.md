# FluxTorrent 生产部署指南

> 适用：单机 Docker Compose 部署（方案 §8.4）。目标读者：运维 / 站长。

## 1. 前置要求

- Docker 24+ 与 docker compose 插件
- 2C4G 起步（实测基线见 §6：debug 构建下 announce ~1100 RPS，release 构建预计 3-5 倍）
- 域名与 TLS 证书（经 Nginx/Caddy 反代，应用端口默认只绑 127.0.0.1）

## 2. 配置

```bash
cp docker/.env.example docker/.env
# 必填项：
#   DB_PASSWORD     强密码（PG）
#   REDIS_PASSWORD  强密码（Redis；compose 会强制 requirepass + 256mb LRU）
#   JWT_SECRET      ≥32 字节随机串；含 "change_me" 的值在非 FLUX_DEV 态会被启动检查直接拒绝
#   CORS_ORIGINS    https://你的站点域名（逗号分隔白名单；留空=宽松模式并打警告，仅开发）
openssl rand -hex 32   # 生成 JWT_SECRET 的便捷方式
```

## 3. 启动

```bash
cd docker
docker compose up -d --build
docker compose ps          # 五个服务 healthy：postgres redis api worker tracker web
```

迁移自动执行（api 启动时跑 sqlx migrate）。种子数据（商品/勋章/作物等）在迁移内幂等写入。

## 4. 反向代理要点

| 上游 | 说明 |
|---|---|
| `127.0.0.1:3000` | web（页面与静态资源） |
| `127.0.0.1:8080/api/` | api（`/api/v1` 前缀） |
| `:7070/announce/` | tracker **必须公网直通**（BT 客户端不携带站点 Cookie；compose 里 tracker 保持 `0.0.0.0`） |

Nginx 示例（片段）：

```nginx
server {
    listen 443 ssl http2;
    server_name pt.example.com;
    # ssl_certificate ...;

    location /api/      { proxy_pass http://127.0.0.1:8080; }
    location /_next/    { proxy_pass http://127.0.0.1:3000; }
    location /          { proxy_pass http://127.0.0.1:3000; }
    client_max_body_size 32m;   # 种子上传（multipart .torrent）
}
server {
    listen 7070;
    location / { proxy_pass http://127.0.0.1:7070; }   # 或直通容器
}
```

## 5. 安全基线（已内置，勿在部署时关闭）

- JWT：HS256 ≥32B 启动校验；登出走 Redis not-before 撤销（旧 token 立即失效）。
- 限流：登录 5 次/分/用户名；注册 5 次/分/IP；游戏 60 局/时/人；开放 API 按 token 独立 rpm。
- CORS：生产必配 `CORS_ORIGINS` 白名单（未配置打 WARN 并宽松——仅限开发态）。
- Tracker：不信任自报 IP（`TRUST_PROXY_IP=1` 才信 X-Forwarded-For）。
- 审计：管理操作、商店购买、token 签发/撤销、审核/举报处理全部落 `audit_log`。

## 6. 性能基线（2026-09-09，开发机 release 构建，10s/8 并发；括号内为 debug 构建对照）

| 场景 | RPS | P50 | P95 | P99 |
|---|---|---|---|---|
| announce（tracker） | 1383（1108） | 4.7ms | 16.5ms | 26.5ms |
| torrents 列表（api） | 1158（897） | 6.0ms | 12.5ms | 26.6ms |
| login 成功请求 | ~0.4 | 46ms | — | — |

> login 场景中 2 万+ 次请求被 5 次/分/用户名限流拦截——这是防护生效的证据；
> 成功请求本身的 Argon2 校验成本约 46ms（release）。压测窗口内首次成功后的连续尝试
> 均计入被拦截数，属预期行为。

复测方式：`python scripts/bench.py 10 8`。

## 9. 本地部署验证记录（2026-09-09，Windows + Docker Desktop）

全栈 `docker compose up -d` 从零验证通过：

- **六容器全 healthy**：postgres/redis（healthcheck 通过）、api（healthy）、worker、tracker、web。
- **空库引导**：迁移 0017 自动创建站长 root（class 99，初始密码 password123，生产首登必改）。
- **19 项容器环境断言全 PASS**：root 登录 → 15 个核心接口（含 farm/dressup/fun polls/admin 三件套/openapi/vapid）→ 邀请发放 → 邀请码注册新用户 → 新用户登录 → 登出后旧 token 撤销。
- **Web 页面**：`/`、`/torrents`、`/admin` 均 200；PWA 资产（manifest/sw.js/icon/offline）200。
- **tracker**：容器内 12 worker 监听 7070，announce 直连可用。

构建期网络适配（国内网络环境，已固化进 Dockerfile）：
- 基础镜像走 `docker.1ms.run` 镜像源（docker.io 直连 EOF）；
- apt 换清华 TUNA 源（deb.debian.org 502）；
- cargo 换 rsproxy.cn sparse 源（crates.io 间歇 SSL 断连），配置经 `docker/cargo-config.toml` 静态拷贝；
- pnpm 走 npmmirror，**Corepack 下载 pnpm 二进制也要设 `COREPACK_NPM_REGISTRY`**；
- **根因级修复**：新增 `.dockerignore` 排除宿主机 `node_modules`——Windows 下 Docker COPY 会把 pnpm 的符号链接变成坏链，覆盖容器内安装产物导致 `next` 模块找不到；
- web runner 阶段补 `COPY public`（Next standalone 不打包静态资源）。
- **静态资源路径（UI 全裸的真因）**：standalone 的 `server.js` 位于 `apps/web/` 下，`.next/static` 与 `public` 必须拷到 `/app/apps/web/` 下（而非 `/app/`），否则 CSS 404、整站无样式。
- 空库演示数据（0018 幂等迁移）：12 名各等级用户（密码 password123）、24 枚覆盖全分类的种子、评论/论坛帖/做种记录/火花流水。生产环境可跳过该迁移。
