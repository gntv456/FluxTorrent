# FluxTorrent 生产部署指南

> 适用：单机 Docker Compose 部署（方案 §8.4）。目标读者：运维 / 站长。

## 1. 前置要求

- Docker 24+ 与 docker compose 插件
- 2C4G 起步（实测基线见 §6：debug 构建下 announce ~1100 RPS，release 构建预计 3-5 倍）
- 域名与 TLS 证书（经 Nginx/Caddy 反代，应用端口默认只绑 127.0.0.1）

## 2. 配置

```bash
cp docker/.env.example docker/.env
# 必填项：
#   DB_PASSWORD     强密码（PG）
#   REDIS_PASSWORD  强密码（Redis；compose 会强制 requirepass + 256mb LRU）
#   JWT_SECRET      ≥32 字节随机串；含 "change_me" 的值在非 FLUX_DEV 态会被启动检查直接拒绝
#   CORS_ORIGINS    https://你的站点域名（逗号分隔白名单；留空=宽松模式并打警告，仅开发）
openssl rand -hex 32   # 生成 JWT_SECRET 的便捷方式
```

## 3. 启动

```bash
cd docker
docker compose up -d --build
docker compose ps          # 五个服务 healthy：postgres redis api worker tracker web
```

迁移自动执行（api 启动时跑 sqlx migrate）。种子数据（商品/勋章/作物等）在迁移内幂等写入。

## 4. 反向代理要点

| 上游 | 说明 |
|---|---|
| `127.0.0.1:3000` | web（页面与静态资源） |
| `127.0.0.1:8080/api/` | api（`/api/v1` 前缀） |
| `:7070/announce/` | tracker **必须公网直通**（BT 客户端不携带站点 Cookie；compose 里 tracker 保持 `0.0.0.0`） |

Nginx 示例（片段）：

```nginx
# ↓ 置于 http {} 层（tracker 边缘限流：应用层限流之外的纵深防御）
# 阈值需高于保种大户的启动风暴：数万挂种的客户端启动时会集中 announce（libtorrent 内部队列约 5/s）
limit_req_zone  $binary_remote_addr zone=ann_perip:10m rate=60r/s;
limit_conn_zone $binary_remote_addr zone=ann_conn:10m;

server {
    listen 443 ssl http2;
    server_name pt.example.com;
    # ssl_certificate ...;

    location /api/      { proxy_pass http://127.0.0.1:8080; }
    location /_next/    { proxy_pass http://127.0.0.1:3000; }
    location /          { proxy_pass http://127.0.0.1:3000; }
    client_max_body_size 32m;   # 种子上传（multipart .torrent）
}
# tracker：BT 客户端不携带站点 Cookie，必须公网直通；
# 正常客户端按 announce interval（默认 1800s）汇报，10r/s 每 IP 已远超正常流量
server {
    listen 7070;
    location / {
        limit_req  zone=ann_perip burst=120 nodelay;   # 每 IP 60r/s，启动风暴容忍 120 瞬发
        limit_conn ann_conn 120;                       # 每 IP 并发连接 ≤120（NAT/做多盒余量）
        limit_req_status 429;
        proxy_pass http://127.0.0.1:7070;              # 或直通容器
    }
    # 指标端点：仅监控网段可抓取（/metrics 自带 token 校验，双重防护）
    location = /metrics {
        allow 127.0.0.1;
        # allow <监控机IP>;
        deny all;
        proxy_pass http://127.0.0.1:7070;
    }
}
```

## 5. 安全基线（已内置，勿在部署时关闭）

- JWT：HS256 ≥32B 启动校验；登出走 Redis not-before 撤销（旧 token 立即失效）。
- 限流：登录 5 次/分/用户名；注册 5 次/分/IP；游戏 60 局/时/人；开放 API 按 token 独立 rpm；tracker announce 每用户 1800 次/分、每 IP 3600 次/分（`ANN_RATE_*` 可调，按保种大户口径设定，被限只延迟计费不丢失）+ 登录/注册入口 ip_bans 强制校验。
- CORS：生产必配 `CORS_ORIGINS` 白名单（未配置打 WARN 并宽松——仅限开发态）。
- Tracker IP 取信（**两个开关不是一回事，2026-10-07 纠正本文旧口径**）：
  - `TRUST_PROXY=1` —— 采信 `X-Forwarded-For` 的**右数第 `TRUST_PROXY_DEPTH` 段**（缺省 1 = 单层反代）。反代必须用 `$proxy_add_x_forwarded_for` 追加语义，配成透传 `$http_x_forwarded_for` 就等于把来源 IP 交给客户端。
  - `TRUST_PROXY_IP=1` —— 采信 announce 查询串里的 **`?ip=`**，即**完全由客户端自报**。这一档比 XFF 更危险，仅用于调试；生产请保持关闭（本文旧版把它写成「信 XFF 的开关」，照着配会正好打开最宽的口子）。
  - 两个开关取到的值都必须是合法地址且不属于本环/链路本地/组播/文档段，默认还拒绝 RFC1918/CGNAT/ULA（纯内网部署才用 `ALLOW_PRIVATE_PEER_IP=1` 放行）；不合法就回落到 socket 对端并计数 `flux_tracker_ip_inject_rejected_total`。tracker 每 5min 的 connectable 回连抽样也**不会**连本环/链路本地/组播这类地址。
- Tracker 其他基线：announce 响应下发 `interval`/`min interval`（读 `announce_interval`，BEP3）；ip_bans 缓存 60s 生效，且**支持段封禁**（后台可直接填 `10.9.8.0/24`、`2001:db8:abcd::/48`；`/0` 被拒）。scrape 侧独立限流 `SCR_RATE_IP_PER_MIN`（缺省 600/分/IP）与单次条数上限 `SCR_MAX_HASHES`（缺省 64）。
- passkey 生命周期：改密或后台重置密钥后，**旧密钥默认仍可用 7 天**（`PASSKEY_GRACE_HOURS`，0 = 立即失效）——passkey 烤在用户已下载的每个 .torrent 里，即刻失效等于集体停种。判据收在视图 `user_by_passkey`（tracker/兼容层/RSS 共用一份）。
- 汇报加密：下载注入的 announce 地址以站点设定 `announce_url` / `https_announce_url` 优先（`PUBLIC_TRACKER_URL` 环境变量兜底）。`https_announce_url` 配置后（tracker 域名需有证书并在反代终结 TLS），种子经 BEP12 `announce-list` 同时下发 https 首选 + http 回退，passkey 加密传输。
- 审计：管理操作、商店购买、token 签发/撤销、审核/举报处理全部落 `audit_log`。

## 6. 性能基线（2026-09-09，开发机 release 构建，10s/8 并发；括号内为 debug 构建对照）

| 场景 | RPS | P50 | P95 | P99 |
|---|---|---|---|---|
| announce（tracker） | 1383（1108） | 4.7ms | 16.5ms | 26.5ms |
| torrents 列表（api） | 1158（897） | 6.0ms | 12.5ms | 26.6ms |
| login 成功请求 | ~0.4 | 46ms | — | — |

> login 场景中 2 万+ 次请求被 5 次/分/用户名限流拦截——这是防护生效的证据；
> 成功请求本身的 Argon2 校验成本约 46ms（release）。压测窗口内首次成功后的连续尝试
> 均计入被拦截数，属预期行为。

复测方式：`python scripts/bench.py 10 8`。

### 6.1 announce 压测基线（2026-09-14，0079 批次，announce_bench.py，容器 tracker + 真实 passkey）

| 并发 | 吞吐 | p50 | p95 | p99 | max | 失败 |
|---|---|---|---|---|---|---|
| 32（20s） | **2138 req/s** | 7.15ms | 10.00ms | 13.45ms | 73.2ms | 0 |
| 128（20s，双 passkey） | ~2100 req/s（同量级） | 7.05ms | 9.84ms | 12.84ms | 31.7ms | 0 |

> 2138 req/s 是压测端（Python 线程）饱和值，tracker 侧未现降级；延迟平稳（p99<15ms）零失败。
> 对照：U3D PHP announce ~250 req/s/核、Rust 外挂 50k req/s——我们处于"远超 PHP 世代、
> 量级低于极限优化"的实用区间，教育站规模（千级 peer）余量 >100 倍。
> 复测：`python scripts/announce_bench.py --url http://127.0.0.1:7070 --passkeys <pk> --concurrency 32 --duration 20`（脚本已兼容 Python 3.8）。

## 8.5 监控与告警（tracker 防护观测）

tracker 暴露 Prometheus 指标端点 `GET /metrics`：
- 需在 compose 设置 `ANN_METRICS_TOKEN`（非空才启用），抓取端带 `X-Metrics-Token` 头；未配置时端点返回 404，不对外暴露；
- 若 7070 经 Nginx 反代，在 server 块加 `location = /metrics { allow <监控机IP>; deny all; proxy_pass http://127.0.0.1:7070; }`。

| 指标 | 含义 | 建议告警（Prometheus 语义） |
|---|---|---|
| `flux_tracker_announce_total` | announce 总量 | `rate(...[5m])` 突增数倍 → 疑似攻击/风暴 |
| `flux_tracker_announce_limited_ip_total` | 每 IP 限流拦截数 | `rate(...[5m]) > 10` 持续 10m → 单点滥用 |
| `flux_tracker_announce_limited_user_total` | 每用户限流拦截数 | `rate(...[5m]) > 5` 持续 10m → 阈值失配或滥用 |
| `flux_tracker_announce_auth_fail_total` | 无效 passkey | `rate(...[5m]) > 50` → passkey 喷洒 |
| `flux_tracker_announce_ip_banned_total` | 封禁 IP 拦截数 | 突增 → 封禁名单正在生效 |
| `flux_tracker_announce_global_shed_total` | 全局熔断触发数 | `> 0` 即需人工介入（已开总闸） |
| `flux_tracker_redis_fallback_total` | Redis 故障→本地降级次数 | `rate(...[5m]) > 0` → Redis 健康告警 |
| `flux_tracker_peers_active` / `flux_tracker_guard_cache` | 活跃 peer / 缓存规模 | 容量观测 |

全局限流应急熔断：`ANN_RATE_GLOBAL_PER_MIN`（默认 0=关闭）。遭分布式洪水打垮后端时临时设为
总量上限（如 120000 ≈ 2000r/s 总闸），事后务必恢复 0。

### H&R 存量误判清理（部署 0043 修复后一次性执行）

`snatches.seeded_seconds` 修复（0043）前的历史数据不可信：`hr_snapshots.seeded_seconds` 恒 0，
所有到期的 open 快照都会被误判 violated。部署后由 sysop 执行：

```sql
-- 1) 核对误判规模
SELECT count(*) FROM hr_violations WHERE resolved_at IS NULL;
-- 2) 确认无误后，将部署前产生的未处置违规整体 pardoned（resolved_by 填执行人 user id）
UPDATE hr_violations SET resolved_at = now(), resolved_by = <sysop_id> WHERE resolved_at IS NULL AND detected_at < '<部署时间>';
UPDATE hr_snapshots  SET status = 'pardoned', pardoned_by = <sysop_id>  WHERE status = 'violated';
```

此后 H&R 口径（`seeded_seconds` 真实累计）才可信；新产生的违规均为有效判罚。

## 9. 本地部署验证记录（2026-09-09，Windows + Docker Desktop）

全栈 `docker compose up -d` 从零验证通过：

- **六容器全 healthy**：postgres/redis（healthcheck 通过）、api（healthy）、worker、tracker、web。
- **空库引导**：迁移 0017 自动创建站长 root（class 99，初始密码 password123，生产首登必改）。
- **19 项容器环境断言全 PASS**：root 登录 → 15 个核心接口（含 farm/dressup/fun polls/admin 三件套/openapi/vapid）→ 邀请发放 → 邀请码注册新用户 → 新用户登录 → 登出后旧 token 撤销。
- **Web 页面**：`/`、`/torrents`、`/admin` 均 200；PWA 资产（manifest/sw.js/icon/offline）200。
- **tracker**：容器内 12 worker 监听 7070，announce 直连可用。

构建期网络适配（国内网络环境，已固化进 Dockerfile）：
- 基础镜像走 `docker.1ms.run` 镜像源（docker.io 直连 EOF）；
- apt 换清华 TUNA 源（deb.debian.org 502）；
- cargo 换 rsproxy.cn sparse 源（crates.io 间歇 SSL 断连），配置经 `docker/cargo-config.toml` 静态拷贝；
- pnpm 走 npmmirror，**Corepack 下载 pnpm 二进制也要设 `COREPACK_NPM_REGISTRY`**；
- **根因级修复**：新增 `.dockerignore` 排除宿主机 `node_modules`——Windows 下 Docker COPY 会把 pnpm 的符号链接变成坏链，覆盖容器内安装产物导致 `next` 模块找不到；
- web runner 阶段补 `COPY public`（Next standalone 不打包静态资源）。
- **静态资源路径（UI 全裸的真因）**：standalone 的 `server.js` 位于 `apps/web/` 下，`.next/static` 与 `public` 必须拷到 `/app/apps/web/` 下（而非 `/app/`），否则 CSS 404、整站无样式。
- 空库演示数据（0018 幂等迁移）：12 名各等级用户（密码 password123）、24 枚覆盖全分类的种子、评论/论坛帖/做种记录/火花流水。生产环境可跳过该迁移。
