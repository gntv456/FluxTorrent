## 二、二次修正之一：v7 的贡献反查方案已废弃（本轮已验证）

v7 写"契约期内 seeding 流水自动归属契约"。核对 `jobs.rs::seeding_reward` 落库语句：

```sql
INSERT INTO spark_ledger (id, user_id, amount, kind, idempotency_key) VALUES (...)
```

**没有 `ref_type` / `ref_id`**。因为它是**每用户每小时聚合一条**（覆盖当时所有做种），本就不对应单个种子。

→ 改为 **`snatches` 基线/delta 法**（与 `seed_preserve` 同款），已在 `0102` 的 `social_team_member` 表落地（`seed_seconds_begin` / `uploaded_begin` / `contributed_sec`）。

### 3.1 修正后的做法：不另起炉灶，给 `resurrections` 加一列

组队 = 给已有的单人复活任务加一个 `team_id`：

```sql
ALTER TABLE resurrections ADD COLUMN IF NOT EXISTS team_id BIGINT
    REFERENCES social_team(id) ON DELETE SET NULL;
```

`team_id IS NULL` 就是现有的单人任务，**行为完全不变，向后兼容**。

## 四、本模块的真实定位：错位竞争，而非重复

修正后，`social_http.rs` 提供的不是"抢救"，而是**现有体系缺的前置环节**：

| | 现有 `resurrections` | 本模块 `endangered` |
|---|---|---|
| 对象 | **已死**的资源（`seeders = 0`） | **濒危但有救**的资源（`seeders <= 阈值`） |
| 定位 | 死种复活（后置抢救） | **预警雷达（前置保种）** |
| 动作 | 认领并做种 `required_hours` | 只读展示 + 引导保种 |
| 依赖 | worker 验收、奖励发放 | 无（纯查询） |

**为什么"前置"有价值**：资源一旦死到 0 做种者，能否救活**取决于还有没有人留着完整数据**——很多死种是救不回来的。所以"还没死的时候提醒"比"死了再救"便宜得多。

而且它顺带展示了"这个濒危资源是否已经有人在救"（`LEFT JOIN resurrections`），避免重复认领。

**这是错位互补，不是重复建设。**
