# FluxTorrent 反作弊·安全·性能加固方案（v1）

> 2026-09-13 · 承接《主流PT架构横向对比与借鉴》v2 §5.8 与反吸血讨论。
> 每项标注：**现状代码证据 → 具体改法 → 验收标准**。按 P0（上线前必做）/ P1（上线后一个月）/ P2（观察后决定）排期。

## 一、性能（三个已被代码证实的隐患 + 两个防御性工程）

### P0-1 worker 每分钟全表重算快照 —— 最大的确定性性能债

**现状**：`apps/worker/src/jobs.rs` `consume_announce()` 尾部每 60s 执行两条全表重算：
```sql
UPDATE users SET uploaded = (SELECT sum(delta_up) FROM traffic_ledger WHERE user_id = users.id) ...  -- 整张 users
UPDATE torrents t SET seeders = (SELECT count(*) FROM snatches ...) ...                              -- 整张 torrents
```
用户 1 万、种子 5 万时，每分钟对两张大表全量子查询聚合——这在 10 万种子级会成为 worker 的固定开销顶点，且全部更新行造成 WAL 放大。

**改法**：
1. users 快照改为**只刷本轮有事件的用户**：`consume_announce` 收集本轮 `user_id` 集合，`UPDATE ... WHERE id = ANY($1)`；
2. torrents 计数改为**只刷本轮涉及 torrent**，且 `seeders/leechers` 改为从 snatches 的 `seeding/leeching` 标志位增量维护（announce 时 process_event 已知方向），`times_completed` 保持事件驱动；
3. 追加一个**低频对账 job**（每 6h，`CONCURRENTLY` 语义用 `WHERE updated_at 窗口` 圈定），纠偏增量漂移。

**验收**：`EXPLAIN` 确认两条 UPDATE 走索引点查；1 万种子下 worker 周期耗时 < 1s（当前为全表聚合）。

### P0-2 流水表"分区"目前是摆设 —— 时间炸弹

**现状**：`traffic_ledger` / `spark_ledger` / `posts` 三表按月 RANGE 分区，但**全库 69 个迁移里没有任何一条预建未来分区的语句**，所有数据都在 `*_default` 分区里（`0001_init.sql:204/223/305`）。数据量上来后想拆分区要线上 DDL；DEFAULT 分区膨胀后查询裁剪（partition pruning）完全失效。

**改法**：worker 新增 `ensure_partitions` job：每日检查，用动态 SQL `CREATE TABLE IF NOT EXISTS ... PARTITION OF ... FOR VALUES FROM ('2026-10-01') TO ('2026-11-01')` 预建未来 2 个月分区；并提供 `detach + 全量重灌` 的一次性迁移脚本把存量从 DEFAULT 拆出。

**验收**：`pg_partition_tree` 显示每月分区存在；`EXPLAIN` 对带时间条件的流水查询命中具体分区。

### P0-3 tracker snapshot 是 O(全体在线 peer) 遍历

**现状**：`apps/tracker/src/peers.rs` `snapshot()` 对整个 DashMap `iter()` 再按 info_hash 过滤——swarm 冷热极不均（热门种 1 万 peer × 数千种）时，一次热门 announce 要扫全表。当前单机 30 万 announce/s 目标下这是第一瓶颈（比 DashMap 锁竞争更早出现）。

**改法**：PeerTable 增加二级索引 `DashMap<String /*info_hash*/, HashMap<peer_id, Peer>>`（按 info_hash 分桶后每桶独立小表）；`counts_*` 同样走桶。GC 从全表 retain 改为按桶惰性清理。

**验收**：基准测试（inject 10 万 peer 混合 500 种子）announce p99 < 1ms；`/metrics` 增加 per-swarm 大小 Top10。

### P1-4 读缓存从 stats 扩到列表首屏与详情主体

0069 已做 `/stats`（60s TTL）。扩展顺序：站点首页聚合块 → 种子列表第 1 页（无筛选）→ 详情页 sections。键带 `v{N}` 版本，写路径（编辑/促销/审核）`INCR flux:cachever:torrent:{id}` 精确失效；TTL 兜底 30s。**原则：只缓存匿名等价视图，凡带当前用户视角的字段（collect/userTorrentInfo）留在缓存外拼接。**

### P1-5 压测基线先于调参

上线前用 `qBittorrent` WebAPI 脚本或自写 Go announce 压测器打三组数字进文档：announce p50/p99（1k / 10k / 50k 在线 peer）、列表页 RPS、worker 周期耗时。没有基线的"性能更好"无法验收。

## 二、反作弊（对照 NP/GZ/U3D 的缺口，四件套）

### P0-6 种子级 up/down 全站对账（抄 NP cheaterbox，我们有流水表成本更低）

**原理**：虚报上传者没有对应真实下载方，同种子 `Σ上传 − Σ下载` 会长期为正且巨大。
**改法**：worker 新增 `cheat_audit` job（每 10min）：
```sql
SELECT torrent_id, sum(delta_up) - sum(delta_down) AS gap, count(DISTINCT user_id)
FROM traffic_ledger WHERE window_start > now() - interval '7 days'
GROUP BY torrent_id HAVING gap > 50GiB AND count(*) >= 2
```
命中 → 写 `cheat_events`（reason='torrent_gap_audit'）+ 首次进管理组信箱。白名单来源：官种/促销种（free 造成天然 gap）按 promotions 表豁免。

### P0-7 peer_id ↔ User-Agent 交叉验证（抄 NP `agent_allowed_family` 三层模型）

**现状**：`agent_rules` 只做 `agent.contains(pattern)` 子串匹配；`peers.rs` 存了 peer_id 但从不校验。
**改法**：迁移给 `agent_rules` 加列（只增不改）：`peer_id_pattern TEXT`（regex）、`match_version INT`（最低版本号）、`family TEXT`。tracker `agent_blocked()` 升级为：① UA 正则匹配 → ② peer_id 正则匹配 → ③ 两边版本号比较 → ④ exception 放行。迅雷系典型特征是 peer_id 与 UA 声称的客户端不一致，此招专杀伪装。

### P1-8 Ratio Watch 柔性观察期（抄 GZ）

H&R 目前是硬处罚（快照到期即 violated）。新增观察层：分享率跌破阈值 → `users` 标记 `ratio_watch`（警告 + 14 天期限 + 站内信），期内仍跌破才进入现有 H&R/禁下载链路。教育网 NAT 场景误伤率主要靠这层兜底。

### P1-9 connectable 主动回连校验（抄 NP，防假保种刷做种收益）

tracker 已有内存 peer 表。worker 新增抽样 job：每 5min 对"高做种收益低流量"嫌疑 peer（`seeded_seconds` 增长快、`delta_up` 长期 0）发起 TCP 连接验证 `ip:port` 可达性，连续 N 次不可达 → 停发做种收益 + 记 `cheat_events`。

### P2-10 蜜罐 peer（业内极少实现，留观察位）

对已命中的可疑用户在 snapshot 里插入虚构 peer，若其后续上报了"对蜜罐的上传量"即实锤。实现成本不高，但误报治理复杂，等 P0-6 对账运行一个月有数据后再决定。

### P2-11 同账号 IP 跳变检测

`maxminddb` 依赖已在 `Cargo.toml`（`geo.rs` 已存在）。announce 事件里已带 IP，worker 对账时顺带检查：单账号 24h 内跨 ASN/跨大洲跳变 → 记录 + 提示改密。

## 三、安全基线（一次核对清单，多数已有，补三件）

已有 ✅：Argon2id、TOTP、JWT 撤销线、API Token 时效/吊销、临时下载凭证、audit_log 哈希链、SQL 全参数化、CORS 白名单、安全响应头、登录事件 90 天留存。

待补：
1. **JWT HS256 → RS256**（`auth.rs` 注释已自认生产应换）：HS256 意味着任何能读 `JWT_SECRET` 的组件（web 容器日志、CI）都能伪造任意用户 token。改 RS256 后私钥只在 api，公钥可下发校验。
2. **下载路径穿越复核**：`build_download_torrent` 与 `torrent_files.raw` 均为 DB 字节流，无文件系统路径拼接 ✅；但字幕/头像未来的对象存储接入（`file_ref` 占位）落地时必须走「UUID 键 + 拒绝 `..`」白名单，写进 TODO 注释。
3. **backup 恢复演练**：`backups/*.dump` 已有，缺「从 dump 恢复到干净环境跑通登录+下载」的演练脚本，上线前做一次并记录 RTO。
