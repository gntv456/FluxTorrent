> 承接 `_doc/落地修正-基于现有代码的增量方案.md`（v6）
> 本文做三件事：**① 修正 v6 的一个关键错误 ② 补掉 10 个设计漏洞 ③ 给出可直接执行的 P0 实现**

---

## 一、v6 的一个关键错误（必须先修）

### 1.1 错在哪

v6 我写了：

> 契约期内的所有 `seeding` 流水自动归属该契约。

**这条不成立。** 我去核对了 `jobs.rs::seeding_reward` 的落库语句：

```sql
INSERT INTO spark_ledger (id, user_id, amount, kind, idempotency_key)
SELECT nextval('spark_ledger_id_seq'), id, amount, 'seeding_reward', idem
```

**没有 `ref_type`，没有 `ref_id`。**

原因是设计使然：`seeding_reward` 是**每用户每小时聚合一条**（覆盖该用户当时的所有做种），本来就不对应单个种子。所以：

- ❌ 无法从 `spark_ledger` 反查到"某个种子的贡献"
- ❌ 即使按时间窗过滤，也只会得到"该用户契约期内的全部做种收益"，会把无关种子一起算进来

### 1.2 正确方案：从 `snatches` 算增量

`snatches` 表是 `(user_id, torrent_id)` 粒度，天然带每人对每个种子的累计数据：

```
snatches (user_id, torrent_id, uploaded, downloaded, seeded_seconds, seeding, ...)
```

**做法和现有的 `seed_preserve` 完全一致**（它就是记 `seed_time_begin` / `uploaded_begin` 基线，结算时算 delta）：

```
成员加入契约时 → 记录基线
  seed_seconds_begin = snatches.seeded_seconds  (该成员对该契约目标资源)
  uploaded_begin     = snatches.uploaded

结算时 → 算增量
  契约贡献 = seeded_seconds - seed_seconds_begin
           + (uploaded - uploaded_begin) × 权重
```

**好处**：
- 精度到单个资源，**无关种子的做种不会被算进来**（根治刷分）
- 复用现有 `snatches` 表，零新增写入
- 与 `seed_preserve` 的口径完全一致，运维直觉统一

**代价**：`social_member` 表要加两个基线字段。

## 二、10 个设计漏洞与修补

### 漏洞 1：契约贡献的归属范围（严重）

**问题**：如果按"契约期内该成员的全部做种"算，成员只要挂一堆无关种子就能刷贡献——契约针对的是资源 X，他却在给 Y 做种。

**修补**：**只算契约目标资源**（`contract.target_ref`）的 `snatches` 增量。见 1.2。

### 漏洞 2：信誉互评可以互刷

**问题**：2 人小队互相好评，等于协议刷分。

**修补**：**信誉必须由"不可伪造的事实"主导**。

| 来源 | 权重 | 可伪造性 |
|---|---|---|
| 契约按期完成 / 未完成 / 中途退出 | **90%** | ❌ 不可伪造（系统判定） |
| 队友评价 | **≤10%** | ⚠️ 可互刷 |

好评权重压到 10% 以下，互刷的收益低于成本，问题自然消解。另外限制：每人每季 **5 次**评价配额，同一对用户每季只能互评 1 次。

### 漏洞 3：赛季末发起契约必然失败

**问题**：赛季剩 1 天时发起 7 天契约，注定失败——这是设计缺陷，不是玩家的错。

**修补**：`赛季结束前 7 天内不允许发起新契约`。已有的契约不受影响。

### 漏洞 4：同一资源被多个契约同时认领

**问题**：两队抢同一个濒危资源，重复发放奖励。

**修补**：部分唯一索引（只约束活跃契约）：

```sql
CREATE UNIQUE INDEX uq_social_contract_active_target
  ON social_contract (target_type, target_ref)
  WHERE status IN (0, 1);   -- 0招募 1进行
```

### 漏洞 5：资格校验的时机

**问题**：v4 提了"贡献地板"（分享率/H&R/非作弊），但没说在哪校验。如果等结算时才发现不合格，玩家白做了。

**修补**：**加入契约时就校验**，不满足则不允许加入（而不是加入了不算）。校验项：`users.status < 2`（非封禁）、分享率达标、无 H&R 欠账、无 `cheat_events` 记录。

### 漏洞 6：系统托底队友（NPC）与荣誉归属冲突

**问题**：v5 我设计了"系统托底队友"解决招不到人。但 NPC 不产生真实贡献，且不该出现在荣誉名单里——**这是我自己给自己挖的坑**。

**修补：直接取消 NPC，改成"允许 1 人契约"。**

- 人数下限 = **1**，上限由主题/等级决定
- 人数不是**门槛**，而是**加成**（人多有协作加成）
- 这样根本不需要 NPC，冷启动问题也被"单人可玩"自然解决

**这比 NPC 方案简单得多，也更符合 v5 的冷启动思路。**

### 漏洞 7：资源被"自然救活"了算谁的

**问题**：契约进行中，非契约成员的做种让资源健康了。契约算成功吗？

**修补**：**算成功。** 契约的目标是"资源恢复健康"，不是"证明是我的功劳"。但荣誉文案要诚实：

```
「2026-09 由 小李 等人推动资源恢复健康（契约期做种 320 小时）」
```

而不是「小李拯救了这个资源」。**把契约成员的贡献如实写出来，不夸大。**

### 漏洞 8：结算的事务一致性

**问题**：契约结算要同时改契约状态、写荣誉、写 `spark_ledger`。中途失败会造成状态不一致。

**修补**：整个结算在**单个数据库事务**内完成（`preserve_settle` 是纯 SQL 单语句所以不需要，但契约结算跨多表，必须显式事务）。

### 漏洞 9：幂等

**问题**：结算 job 重跑或补跑。

**修补**：沿用现有风格：

```
social:rescue:{contract_id}        -- 契约结算
social:season:{season_id}:{uid}    -- 赛季发行
```

写 `spark_ledger` 前先查（分区表无全局唯一约束，现有代码也是应用层保证）。

### 漏洞 10：契约目标资源被删除

**问题**：种子被删了，契约还在。

**修补**：结算时检查 `torrents` 是否存在。不存在 → 契约进入**独立状态 `5 = 作废`**（不是失败），**不扣信誉**（不是玩家的错）。

## 三、修正后的迁移脚本（0102）

```sql
-- 0102_social_contract.sql
-- 社交经营玩法：契约组队 + 信誉 + 赛季 + 拯救荣誉
-- 复用：spark_ledger / seed_preserve / snatches / torrents / site_type_packs / cheat_events
-- 前置核对（已完成）：site_settings(name, value, updated_at) ；
--                    seed_preserve 已有 seed_time_begin / uploaded_begin / last_settle_at

CREATE TABLE IF NOT EXISTS social_season (
  id             BIGSERIAL PRIMARY KEY,
  seq_no         INT NOT NULL UNIQUE,
  theme_code     TEXT NOT NULL,                  -- 复用 site_type_packs.code
  name           TEXT NOT NULL,
  status         SMALLINT NOT NULL DEFAULT 0,    -- 0预告 1进行 2结算中 3已结算
  starts_at      TIMESTAMPTZ NOT NULL,
  ends_at        TIMESTAMPTZ NOT NULL,
  readonly_until TIMESTAMPTZ,                    -- 结算后只读期
  pool_cap       BIGINT NOT NULL DEFAULT 0,      -- 发行硬顶（0=按通胀公式自动算）
  pool_coef      NUMERIC(6,3) NOT NULL DEFAULT 1.000,
  issued_amount  BIGINT NOT NULL DEFAULT 0,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS social_contract (
  id                BIGSERIAL PRIMARY KEY,
  season_id         BIGINT NOT NULL REFERENCES social_season(id) ON DELETE CASCADE,
  leader_uid        BIGINT NOT NULL REFERENCES users(id),
  title             TEXT NOT NULL DEFAULT '',
  status            SMALLINT NOT NULL DEFAULT 0, -- 0招募 1进行 2已完成 3失败 4取消 5作废
  team_size_max     INT NOT NULL DEFAULT 5,      -- 下限恒为 1，人数是加成不是门槛
  target_type       TEXT NOT NULL DEFAULT 'torrent',
  target_ref        BIGINT,                      -- torrents.id
  required_seeders  INT NOT NULL DEFAULT 3,      -- 目标做种数（对齐 preserve_exit 的 7 为"健康"）
  started_at        TIMESTAMPTZ,
  deadline_at       TIMESTAMPTZ,
  settled_at        TIMESTAMPTZ,
  seeders_before    INT NOT NULL DEFAULT 0,
  seeders_after     INT NOT NULL DEFAULT 0,
  fail_reason       TEXT,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_social_contract_season ON social_contract (season_id, status);
CREATE INDEX IF NOT EXISTS idx_social_contract_leader ON social_contract (leader_uid, status);
-- 漏洞 4：一个资源同时只允许一个活跃契约
CREATE UNIQUE INDEX IF NOT EXISTS uq_social_contract_active_target
  ON social_contract (target_type, target_ref) WHERE status IN (0, 1);

CREATE TABLE IF NOT EXISTS social_member (
  contract_id        BIGINT NOT NULL REFERENCES social_contract(id) ON DELETE CASCADE,
  uid                BIGINT NOT NULL REFERENCES users(id),
  role_key           TEXT NOT NULL DEFAULT 'keeper',
  is_leader          BOOLEAN NOT NULL DEFAULT FALSE,
  join_status        SMALLINT NOT NULL DEFAULT 0, -- 0邀请 1接受 2拒绝 3退出 4完成
  specialty_lv       INT NOT NULL DEFAULT 0,
  -- 漏洞 1 修正：贡献基线取自 snatches，与 seed_preserve 同款口径
  seed_seconds_begin BIGINT NOT NULL DEFAULT 0,
  uploaded_begin     BIGINT NOT NULL DEFAULT 0,
  contributed_sec    BIGINT NOT NULL DEFAULT 0,   -- 结算时回填的增量
  settled_amount     BIGINT NOT NULL DEFAULT 0,
  joined_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  left_at            TIMESTAMPTZ,
  PRIMARY KEY (contract_id, uid)
);
CREATE INDEX IF NOT EXISTS idx_social_member_uid ON social_member (uid, join_status);

CREATE TABLE IF NOT EXISTS social_reputation (
  uid             BIGINT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  score           BIGINT NOT NULL DEFAULT 1000,
  fulfilled_count INT NOT NULL DEFAULT 0,
  withdrawn_count INT NOT NULL DEFAULT 0,
  failed_count    INT NOT NULL DEFAULT 0,
  review_quota    INT NOT NULL DEFAULT 5,      -- 漏洞 2：每季评价配额
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS rescue_honor (
  id             BIGSERIAL PRIMARY KEY,
  torrent_id     BIGINT NOT NULL,              -- 不加 FK：种子可能被删，荣誉要留
  info_hash      CHAR(40),
  contract_id    BIGINT REFERENCES social_contract(id) ON DELETE SET NULL,
  season_id      BIGINT REFERENCES social_season(id) ON DELETE SET NULL,
  uids           BIGINT[] NOT NULL,            -- 漏洞 6：只记真实用户，无 NPC
  total_sec      BIGINT NOT NULL DEFAULT 0,    -- 契约期团队做种总时长（文案用，如实展示）
  seeders_before INT NOT NULL DEFAULT 0,
  seeders_after  INT NOT NULL DEFAULT 0,
  rescued_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_rescue_honor_torrent ON rescue_honor (torrent_id);
CREATE INDEX IF NOT EXISTS idx_rescue_honor_uids ON rescue_honor USING GIN (uids);

INSERT INTO site_settings (name, value) VALUES
  ('social_enabled', '0'),
  ('social_pool_coef', '1.0'),
  ('social_pool_cap', '0'),
  ('social_income_ratio_cap', '0.30'),
  ('social_readonly_hours', '24'),
  ('social_reputation_keep_ratio', '0.70'),
  ('social_min_days_to_season_end', '7'),
  ('social_health_seeders', '7')
ON CONFLICT (name) DO NOTHING;
```

> `site_settings` 字段名已核对无误（`name` 主键 / `value` / `updated_at`），`ON CONFLICT (name)` 可用。

## 四、P0 实现细节（可直接开工）

P0 目标：**濒危资源清单公开化 + 只读页面 + 埋点**。不写任何数据，风险极低。

### 4.1 濒危清单查询（`rescue_scan` 的读模型）

**这里有个重要判断：P0 不需要建清单表。**

清单是 `torrents` 的一个实时查询结果——因为"濒危"是动态状态（今天濒危、明天可能就有人保种了），落表反而要处理时效性。直接查：

```sql
-- 濒危资源清单（对齐 seeding_reward 的「濒危保种」口径）
SELECT t.id, t.info_hash, t.name, t.seeders, t.leechers,
       t.times_completed, t.size, t.category_id, t.owner_id,
       t.created_at,
       EXTRACT(EPOCH FROM (now() - t.created_at)) / 86400 AS age_days,
       -- 是否已被契约认领
       c.id AS contract_id
FROM torrents t
LEFT JOIN social_contract c
       ON c.target_type = 'torrent' AND c.target_ref = t.id AND c.status IN (0, 1)
WHERE t.approval_status = 1
  AND t.seeders <= 1
  AND t.times_completed >= 3
  AND t.seeders > 0                 -- 还有人挂着（彻底没人做种的另作一类）
ORDER BY t.seeders ASC, t.times_completed DESC, t.size DESC
LIMIT 50 OFFSET $1;
```

**注意**：口径直接抄 `seeding_reward` 的"濒危保种"判定（`seeders <= 1 AND times_completed >= 3`），保持全站一致。

「健康」阈值用现有的 `seeders > 7`（`preserve_exit` 口径），配置项 `social_health_seeders = 7`。

### 4.3 页面（web）

一个只读列表页 `/rescue`：

| 区域 | 内容 |
|---|---|
| 顶部 | 一句话说明："以下资源只剩 1 个做种者，随时可能消失" + 当前总数 |
| 列表 | 资源名 / 分类 / 大小 / 做种数 / 完成数 / 已发布天数 / 操作按钮 |
| 操作 | P0 阶段是 **只读**（按钮显示"认领"但点击提示"即将开放"）——先收集兴趣数据 |
| 排序 | 默认按"做种数升序 + 完成数降序"（越濒危越靠前） |

**P0 的埋点**（这是 P0 的真正目的）：

| 事件 | 用途 |
|---|---|
| `rescue_list_view` | 有多少人看到这个页面 |
| `rescue_claim_intent_click` | **多少人点了"认领"** ← 关键指标 |
| `rescue_item_expand` | 多少人展开了资源详情 |
| `rescue_sort_change` | 排序偏好 |

**判定**：如果 `rescue_claim_intent_click / rescue_list_view > 15%`，说明需求真实存在，进 P1；低于 5% 就要重新考虑钩子设计。

## 七、一页总结

| 问题 | 答案 |
|---|---|
| v6 哪里错了？ | **`spark_ledger` 反查贡献不成立**（`seeding_reward` 不写 `ref_id`）；改用 `snatches` 增量法 |
| 为什么要改？ | 一是技术上做不到，二是即使能查也会把无关种子的做种算进来（刷分漏洞） |
| 新方案复杂吗？ | 不复杂——**和现有 `seed_preserve` 的基线/delta 做法完全一样**，运维直觉统一 |
| NPC 托底队友还要吗？ | **取消**。改成"允许 1 人契约"，人数是加成不是门槛，比 NPC 简单得多 |
| 信誉怎么防互刷？ | **事实驱动 90%（不可伪造），好评 ≤10%**，外加每季配额 |
| 表要改吗？ | 同上 5 张表，新增 2 个基线字段 + 1 个部分唯一索引 |
| P0 要建清单表吗？ | **不要**。濒危是动态状态，实时查询即可，落表反而要处理时效性 |
| P0 的真实目的是什么？ | **不是为了功能，是为了拿到"多少人真的想认领"这个数字**（>15% 才进 P1） |
