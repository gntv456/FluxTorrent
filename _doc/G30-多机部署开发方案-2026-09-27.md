## 1. 目标与非目标

**目标**（验收口径）：
1. 单台 api/web 实例故障或重启，站点不中断（LB 摘流 + 滚动更新可操作）；
2. 站长能照官方配方把一套站拆到 2–3 台机器（web+api / worker+tracker / 数据层）；
3. 多副本下机制不撒谎：配置变更跨进程可见（≤5s）、任务认领不互踩、日志可分实例；
4. 容量边界进入部署文档（定性），何时必须升级到 B 轨有明确触发条件。

**非目标**（本期明确不做，防止范围蔓延）：
- worker 调度重写（分片/角色/并发化/水位入库）——B 轨长期；
- tracker peer 外置与多副本——B 轨长期（接口契约本方案只记录、不实现）；
- k8s/swarm chart——部署主体是站长自建单机/少量 VPS，配方文档比编排系统贴定位；
- tracker announce 走 LB——配方让 tracker 直连公网端口绕开 LB，从而绕开其无 XFF 的缺口（`announce.rs:45-55` 仅 BEP3 `?ip=`）；LB 后挂 tracker 触发 B 轨再补 XFF。

## 4. 批次二 G30-A2：代码小改批（六件）

### A2-1 worker SIGTERM 优雅停机（承重件）

- 现状：`apps/worker/src/main.rs:10-43` 为裸 `#[tokio::main]` + `jobs::run_all` 永续循环，`apps/worker/src/jobs/run.rs:30` 的 `select!` 无信号分支；任务 spawn 后句柄弃置（`manual.rs:80` 注释「spawn 而非 await」）。
- 改动：`select!` 增加 SIGTERM/SIGINT 分支（`tokio::signal::unix`）→ 置停机位：停止取新 tick、`poll_manual_triggers` 不再认领；手动任务 spawn 句柄收进 `JoinSet`，停机时 `join`（上限 60s）；超时强退。advisory 锁随连接关闭自动释放，被中断任务走既有 30 分钟回收（`manual.rs:84-89`）+ 各 job 幂等。
- 边界（写进配方）：长结算任务（银行结息等，上限 900s）不等待强杀——恢复路径既有且幂等，**发布窗口避开每日结息时刻**。
- 验收：`docker stop flux-worker` 期间不再认领新任务、在跑短任务收尾、进程 <90s 退出；再启动后回收+重跑无重复计费（流水表幂等键断言）。

### A2-2 任务认领 `SKIP LOCKED` + 认领者记录

- 现状（本次亲验 `apps/worker/src/jobs/manual.rs:91-96`）：认领语句
  `UPDATE job_triggers SET status='running', started_at=now() WHERE id IN (SELECT id … WHERE status='pending' ORDER BY id LIMIT 3) RETURNING id, job`
  **无 `FOR UPDATE SKIP LOCKED`**——两实例认领同一批，输家在 advisory 锁上拿「另一实例正在跑」假失败。入队侧连点合并注释自述「多实例部署下也不重复排队」（`admin_p3_http/ops.rs:205`），但不重复排队 ≠ 不重复认领。
- 改动：子查询加 `FOR UPDATE SKIP LOCKED`（单实例无竞争时语义等价，零回归）；`job_triggers` 加 `claimed_by` 列（迁移 0224，见 A2-4）记录认领实例；中断回收语句（`manual.rs:84-89`）保持全局超时判失败的面板语义不变。
- 已知边界（如实记录，不掩盖）：A 实例长任务超 30 分钟后仍会被 B 的回收标 failed（中间态误报，A 结束时覆盖回真实状态）；租约/心跳机制列 B 轨。
- 验收：双 worker 并发手动触发同 job ×1000 次脚本断言无同一行双认领、无假失败行。

### A2-3 跨进程失效统一通道（吸收 G22 机制部分）

- 现状：进程内快照/缓存只认本地失效——术语快照 `static RwLock` 写侧仅本进程 `reload()`（`terms.rs:18`；写点 `staff_http/terms.rs:123/151/181`、`pack_terms.rs:69`）；模块/插件缓存 TTL 30s 且 `invalidate()` 只清本地（`modules.rs:165`、`plugins.rs:71`；写点 `setup_http.rs:260`、`pack_apply.rs:97`、`pack_applies.rs:204`）；`settings:changed` **全仓零订阅者**（`settings_http/groups.rs:97`）。真跨进程通道现成范式只有两条：`flux:guard:ver` 版本键 + 3s 轮询（`auth_infra.rs:51`；tracker `main.rs:145-166`），首页缓存 Redis DEL（`http/home.rs:26`）。
- 设计：新增共享模块（api/worker/tracker 同用）读写 Redis hash `flux:cfg:ver`，field 按 `terms`/`modules`/`plugins`/`settings` 等域；写侧在上述所有 reload 失效点同步 `HINCRBY`；订阅侧每 3s `HGETALL` 与本地版本比对，命中才 reload 对应域。**选轮询不选 pub/sub**：继承 guard:ver 已验证范式，消息不丢、断线自愈、无新依赖语义；3s 陈旧度满足验收。tracker 把既有 3s 轮询任务并入同一 HGETALL（少一条轮询连接）。
- 降级语义：Redis 不可达或通道故障 → 退回现状 TTL 行为（只增不减）。
- 验收（D5 实证转绿）：A 改术语 → B 错误信封 ≤5s 跟随（修复前：永不跟随）；A 关模块 → B 导航 ≤5s 收敛（修复前 ≤30s）；`settings:changed` 语义由 bump 替代并删除死发布点。

### A2-4 运行日志与任务面板的实例维度（迁移 0224）

- 现状：`runtime_logs` 列 `(id, ts, level, source, target, message, repeat)`，`source` 仅 `'api'/'worker'` 字面值（`0218_ops_runtime_and_jobs.sql:16-27`）；写入侧列清单固定（api `runtime_log.rs:184-196`、worker `runtime_log.rs:82-89`）→ 多副本下日志分不开机器；`job_status` 主键 `job` 单行覆盖写，「最近运行」被随机一台盖掉。
- 改动：迁移 `0224_ops_multi_instance.sql`（顺延现最新 0223）——`runtime_logs` 加 `instance text NOT NULL DEFAULT ''`；`job_triggers` 加 `claimed_by text NOT NULL DEFAULT ''`（供 A2-2）；写入侧取 `FLUX_INSTANCE_ID`（默认容器 hostname）；后台 syslog 页加实例列与筛选（i18n 三语，走既有门禁）。`job_status` 历史化列 B 轨，本期仅加 instance 注记列。
- 验收：双副本跑一段负载后，syslog 按实例筛选各行归属正确（D5-5 转绿）。

### A2-5 rs256 密钥自生成 fail-fast（净修复，附破坏性变更标注）

- 现状（继承 G30 已复核 `auth.rs:100-138`）：`JWT_ALG=rs256` 且未注入 PEM 时，**每副本各自生成 2048 位密钥对写本地 `data/`（未挂卷）**——多副本互不认（A 签 B 拒），单机容器重建也全员登出。
- 改动：rs256 启动时必须显式提供 PEM 路径（env 指向挂卷文件），缺失即拒绝启动并给明确报错；删除静默自生成路径。**CHANGELOG 标破坏性**：依赖"自动生成"的现网部署（本就受密钥漂移之苦）需改挂卷注入。
- 验收：rs256 无 PEM 启动即退且报错可读；挂卷后双副本互认（并入 B3-1 实证第 1 条）。

### A2-6 迁移/种子单飞开关（G26 最小形态）

- 现状：每个 api 实例启动都 `Migrator::run`（`apps/api/src/main.rs:123-127`）；演示账号防线（141）与 `adapter_seed`（178-181）随启动幂等重跑。
- 改动：新增 `FLUX_BOOT_MIGRATIONS`（默认 `1` 兼容现状）；配方中第二副本起置 `0`（跳过迁移+种子，仅起 HTTP）。sqlx 内部 advisory lock 保留为兜底。
- 验收：双 api 同时冷启无迁移争用报错；`0` 值实例正常服务。

### B3-2 三机配方文档（`_doc/` 新篇或并入《生产部署指南》加章）

- 机器分工：**M1** LB(nginx)+web+api×2 ｜ **M2** worker+tracker（announce 直连不走 LB）｜ **M3** PG+Redis（或托管服务）。web 与 api **必须同机**——`API_SERVER_URL` 构建期烘焙（`docker/web.Dockerfile:18-20`、`next.config.ts:10-13`），跨机触发 B 轨，此为配方硬约束。

## 7. 对附录 D 的证据勘误（建议回写，本方案不代改）

附录 D 档一「零停机发布不成立：api/worker 无任何 shutdown 信号处理（main.rs:26 / main.rs:22）」**半错**：

- api：`apps/api/src/main.rs:184-238` 走 actix `HttpServer::new(...).bind(...).run()`，依赖 `actix-web = "4"`（根 `Cargo.toml:16`，默认 feature 含 actix-server 的信号处理）——**SIGTERM/SIGINT 优雅停机默认存在**（停止接新连接、drain 在途请求，默认上限 30s）。原文 grep 无 `signal/shutdown` 找到的是"无自定义处理"，不等于"无停机处理"。
- worker：结论成立（`apps/worker/src/main.rs:10-43` 裸 tokio 循环，亲验无信号分支）。
- 真正的缺口因此改写为三件：① worker 无停机处理（A2-1）；② compose 全文无 `stop_grace_period`（亲验），docker stop 默认 10s SIGKILL 早于 actix 30s drain（A1-3）；③ LB 摘流时序无配方（A1-8/B3-2）。

建议：附录 D 该行加一行勘误注并同步 D3-A 路线描述（"滚动更新需先补 SIGTERM"改为"api 已有，需补 worker 停机 + stop_grace_period"）；由总纲会话拍板后回写。
