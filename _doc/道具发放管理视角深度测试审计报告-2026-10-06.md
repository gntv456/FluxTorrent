## 二、P0 详述与实测证据

**P0-1 发出去是空的。** `gnt_target` 余额 0 → `POST /admin/users/4181/grant-item/10`
（item 10 = 赠送魔力，`config={"spark":1000}`）→ HTTP 200，
`{"item_id":10,"kind":"gift_spark","name":"赠送魔力"}`，回读余额仍是 0。
商店购买路径 `shop_effects.rs:160` 读 `config.spark`，发放路径读 `config.amount`，
两把尺各量各的。同一 SKU 在商店能生效、在后台发放就是空转——而后台发放是站长
认为「我已经补给他了」的动作，这是发放面最贵的一类缺陷。修法：三个取值器
（`spark_amount`/`credit_gb`/`voucher_kind`）收进 `economy_http`，购买与发放共用；
取不到正数一律 400 并说明缺哪个键，不再 `unwrap_or(0)`。
（A4：把 config 改成 `{}` 再发 → 现在 400 且余额不动；旧版 200 空转。）

**P0-2/3 券作废。** 发 2 张 admin 券 + 插 1 张 `source='shop'` 自购券 →
`POST /admin/user-vouchers/void {"user_id":…,"limit":2}` → HTTP 500「内部错误」，
回读：admin 券 **0 张**（已删干净）、`stock_used` 仍是 2、`audit_log` 无本次
`voucher.void`。psql 侧证明形状：`PREPARE v(bigint) AS … $2 …` →
`ERROR: wrong number of parameters … Expected 2 parameters but got 1`。
修后：单条 CTE 在一个事务里「挑(仅 source='admin')→删→按 free/neutral 归位退配额→
报数」，实测 voided=2 / admin 剩 0 / 自购剩 1 / 两张 SKU 配额各回落。

**P0-5 双击双发。** 同参数 `{"kind":"spark","amount":100,"user_ids":[t]}` 连发两次
→ 两次都 200，余额 0→200。界面上「试运行」旁边就是「提交」，`disabled={busy}`
挡不住 React 提交前的第二次点击，而服务端当时完全没有跨请求概念。
修后（界面上真点两次「提交」）：余额 +5，`grant_batches` 只 1 行。

**P0-6 界面回收删付费单。** 给 99 级探针插一张 `price=100000` 的改名卡单，
用 93 级探针 `DELETE /admin/user-props/{id}` → HTTP 200，行被删（用户花魔力买的东西
没了、没退款、没留证、也没过等级护栏），而 `stock_used` 一点没退。
同一时刻带校验的 `revoke-item`（0 价 + 未生效 + 退配额 + outranks）前端零调用。
**同一件事有两份规则时，界面在用的那份必然是被改漏的那份。** 现在两条共用
`reclaim_order` 一份实现。

## 五、闸门自身的问题（这条和上面同等重要）

本轮 4 条「产品缺陷」其实是**闸门写错**——`pt_audit_b_billing.py`：

1. 促销传 `kind`/`hours`，接口收 `promo_kind`/`promo_until` ⇒ serde 认不到就
   静默缺省，库里三行促销全成了 `free`，于是「x2free 上传翻倍」「p30 按 30%」
   永远不成立（产品是对的，闸门一直红）。
2. 只 `sleep(12)` 就查库，而 announce 由 worker 按 **60s 一批** flush
   （实测流水在 announce 后约 90s 才落库）⇒ 集体假红。改成轮询到目标值或 150s。
3. 「对照组」在**同一时刻连读两次**去证明「涨了 10MB」，且基线取在 announce 之后
   ⇒ 这条断言逻辑上不可能成立，是恒红噪声。
4. 付费种子只认 402/403，而「余额不足」按设计回 400 ⇒ 拆成
   无余额拦下 / 有余额真扣全价 / 卖家净得税后款 / 站税进资金池 四条。

我自己这轮新写的闸门也暴露了两个自身缺陷并已修：台账自清按 `actor_id` 删会漏
（操作者是 root，受众才是锚点）；建探针号在 `try/finally` 之外，一次限流 abort
就留下 4 个未删探针号。另把 `login()` 的 429 退避收进公共层 `pt_audit_lib`
（否则放在 finally 的兜底会一起失败，脏数据留在原地）。

## 八、这轮最贵的一条经验：镜像 = 工作区快照，会替别人把半成品上线

部署二轮镜像后，**后台所有工具面板都卡在「正在打开页面…」**（勋章面板一小时前还实测正常）。已证实的事实：

- SSR 出的 HTML 里**有**「勋章管理」与「有效期」两列（我这批的改动都在），但客户端把 `<main>` 换成了骨架屏 ⇒ 问题不在数据层、也不在我的面板，而在路由级 loading 边界。

**我自己判错过的两步（比缺陷本身更值得记）**：

1. *假阴性*：我第一次 grep 镜像只搜了 `.next/static`，而那句话在
   `.next/server/chunks/2974.js` 里 ⇒ 我据此断定"镜像里没有这句话"，方向整个错了。
   验镜像内容必须搜 **整个 `/app`**，且中文要走 `-r`+全路径，别只挑产物目录。
2. *干净树重建其实是有效的*：`--no-cache` 从 `git archive HEAD` 的导出目录构建后，

## 十、部署口径（改成"先验镜像、再验行为"）

- 部署 web 前先 `git status --short apps/web`：出现未跟踪的 `.tsx` / `loading.tsx`，就意味着这一构建会把别人的半成品一起上线——**先跟对方确认或等对方提交**，别直接 build。
- 上线后先验**镜像内容**再看行为，而且要搜整个 `/app`（中文串可能在 server chunk 里）：
  `docker exec flux-web sh -c 'grep -rl "<只有未提交才有的字符串>" /app | head'`。
- **共享机器上不要只认 tag**：`web:latest` 会被并行构建随时改指向。部署动作要做两步——
  给自己构建的镜像打**提交号 tag**（`web:$(git rev-parse --short HEAD)`），
  部署后回读 `docker inspect -f '{{.Image}}' flux-web` 与自己的 image id 比对；
  不一致就是被人抢过，别再往下判断。
- 恢复手段现在是零：`docker images` 里 web 只有一个 `latest`，每次构建都覆盖它，
  出问题时无镜像可回滚。建议构建时**同时打提交号 tag**
  （`FLUX_VERSION=$(git rev-parse --short HEAD)`），回滚才是可能动作。
- 本轮接口侧不受影响：`pt_audit_e_grant` 34/34、`pt_audit_a/b/c/d` 全绿、
  `admin_e2e` 97/97、`cargo test` 191 全过——所以这是**部署问题，不是代码缺陷**。
