## 二、FluxTorrent 已有的做种激励体系（详细）

`apps/worker/src/jobs.rs::seeding_reward`（0074 改造）的完整口径：

```
每种子加成 = 规则分 × 稀有度因子 × 时长饱和因子

规则分：  濒危保种 2.0（seeders≤1 且 times_completed≥3）
          高龄种   1.5（>365 天）
          老种     1.0（>180 天）
          大体积   0.75（≥100GiB）
          中体积   0.5（25-100GiB）
          日常种   0.25

稀有度因子：seeders^(-0.35)        ← 人多衰减，防大户垄断热门种
时长饱和：  1/(1 + seed_hours/2160) ← 90 天半衰

每小时收益 = base + 400/π·atan(Σ加成 × 6/50)   ← arctan 软封顶，渐近 +200/h
                                                ← 底薪不进压缩曲线
反假保种：  回连不可达（connectable=0）且从无上传（uploaded=0）的做种行不计
幂等键：    seeding:{user}:{yyyymmddhh}
```

**这套设计与前四轮方案的对比**：

| 前四轮我的设计 | 现有实现 | 谁更好 |
|---|---|---|
| "稀缺贡献用凸函数（log 加成）" | 规则分档位 + `seeders^-0.35` | **现有更好**：我的 log 加成没有解决"热门种大户垄断"问题 |
| "保种 1TB 边际价值递减" | 时长饱和因子 `1/(1+h/2160)` | **现有更好**：有明确的半衰常数 |
| "反假保种" | connectable + uploaded 双校验 | **现有更严**：我没想到用"回连不可达" |
| "次线性发行防通胀" | arctan 软封顶 | **现有更优雅**：数学上自然渐近 |
| "延迟结算观察窗" | 整天边界结算 | **现有更实用**：和保种时长天然对齐 |

**结论：不要重写激励层，前四轮 v4 文档里的"经济模型"章节应当作废。**

## 五、修正后的数据模型（只新增 4 张表）

前四轮我设计了 9 张表（`social_season` / `contract` / `member` / `contribution` / `reputation` / `issuance` + `rescue_*`）。**现在收敛到 4 张，理由如下**：

| 原设计表 | 处理 | 理由 |
|---|---|---|
| `social_contribution` | ❌ **删掉** | 贡献明细直接用 `spark_ledger` 反查（`kind='seeding_reward'` + `ref_id` + 时间窗），不必重复存储 |
| `social_issuance` | ❌ **删掉** | 发行直接写入 `spark_ledger`（`kind='social_season_reward'`），不另建账本 |
| `social_theme` | ❌ **删掉** | 挂到已有的 `site_type_packs.modules` JSONB 字段 |
| `social_reputation` | ✅ 保留 | 全新概念 |
| `social_contract` / `social_member` | ✅ 保留 | 社交层核心 |
| `social_season` | ✅ 保留 | 赛季循环 |
| `rescue_honor` | ✅ 保留 | 拯救荣誉（永久，不随赛季重置） |

### 5.1 关键设计：契约贡献用"时间窗归属"，不建关联表

```
契约期内的所有 seeding 流水，自动归属该契约。

归属查询：
  SELECT sum(amount) FROM spark_ledger
  WHERE user_id = ? AND kind = 'seeding_reward'
    AND created_at BETWEEN contract.started_at AND contract.settled_at
```

好处：**零额外写入**（现有 `seeding_reward` 一行不改），归属关系可随时重算，不会出现"流水与关联表对不上"的数据不一致。

### 5.2 迁移脚本（0102）

```sql
-- 0102_social_contract.sql
-- 社交经营玩法：契约组队 + 信誉 + 赛季 + 拯救荣誉
-- 复用：spark_ledger（账本）/ seed_preserve（认领）/ site_type_packs（主题）
--       cheat_events（反作弊）/ snatches（做种时长）/ torrents（seeders, owner_id）

-- 赛季
CREATE TABLE social_season (
  id            BIGSERIAL PRIMARY KEY,
  seq_no        INT NOT NULL UNIQUE,           -- 第几季
  theme_code    TEXT NOT NULL,                 -- 复用 site_type_packs.code
  name          TEXT NOT NULL,
  status        SMALLINT NOT NULL DEFAULT 0,   -- 0预告 1进行 2结算中 3已结算
  starts_at     TIMESTAMPTZ NOT NULL,
  ends_at       TIMESTAMPTZ NOT NULL,
  readonly_until TIMESTAMPTZ,                  -- 结算后 24h 只读期
  pool_cap      BIGINT NOT NULL,               -- 本季发行硬顶（通胀护栏）
  pool_coef     NUMERIC NOT NULL DEFAULT 1.0,  -- k，每季按上季数据重算
  issued_amount BIGINT NOT NULL DEFAULT 0,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 契约（组队）
CREATE TABLE social_contract (
  id            BIGSERIAL PRIMARY KEY,
  season_id     BIGINT NOT NULL REFERENCES social_season(id) ON DELETE CASCADE,
  leader_uid    BIGINT NOT NULL REFERENCES users(id),
  title         TEXT NOT NULL DEFAULT '',
  status        SMALLINT NOT NULL DEFAULT 0,   -- 0招募 1进行 2已完成 3失败 4取消
  team_size     INT NOT NULL DEFAULT 1,
  team_size_max INT NOT NULL DEFAULT 5,
  target_type   TEXT NOT NULL,                 -- torrent 抢救 / relay 接力
  target_ref    BIGINT,                        -- 关联 torrents.id
  required_seeders INT NOT NULL DEFAULT 3,     -- 目标：恢复到几个做种
  required_days INT NOT NULL DEFAULT 7,
  started_at    TIMESTAMPTZ,
  deadline_at   TIMESTAMPTZ,
  settled_at    TIMESTAMPTZ,
  fail_reason   TEXT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_social_contract_season ON social_contract (season_id, status);
CREATE INDEX idx_social_contract_leader ON social_contract (leader_uid, status);

-- 契约成员
CREATE TABLE social_member (
  contract_id   BIGINT NOT NULL REFERENCES social_contract(id) ON DELETE CASCADE,
  uid           BIGINT NOT NULL REFERENCES users(id),
  role_key      TEXT NOT NULL DEFAULT 'keeper', -- 岗位，取值由主题包定义
  is_leader     BOOLEAN NOT NULL DEFAULT FALSE,
  join_status   SMALLINT NOT NULL DEFAULT 0,   -- 0邀请 1接受 2拒绝 3退出 4完成
  specialty_lv  INT NOT NULL DEFAULT 0,        -- 专精等级（赛季内重置）
  contributed   BIGINT NOT NULL DEFAULT 0,     -- 契约期内贡献缓存（可从 spark_ledger 重算）
  settled_amount BIGINT NOT NULL DEFAULT 0,    -- 本契约分账（写入 spark_ledger 后回填）
  joined_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  left_at       TIMESTAMPTZ,
  PRIMARY KEY (contract_id, uid)
);
CREATE INDEX idx_social_member_uid ON social_member (uid, join_status);

-- 信誉（不随赛季重置，跨季保留 70%）
CREATE TABLE social_reputation (
  uid             BIGINT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  score           BIGINT NOT NULL DEFAULT 1000,
  fulfilled_count INT NOT NULL DEFAULT 0,
  withdrawn_count INT NOT NULL DEFAULT 0,
  failed_count    INT NOT NULL DEFAULT 0,
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 拯救荣誉（永久，不随赛季重置）
CREATE TABLE rescue_honor (
  id            BIGSERIAL PRIMARY KEY,
  torrent_id    BIGINT NOT NULL,               -- 不加 FK：种子可能被删，荣誉要留
  info_hash     CHAR(40),
  contract_id   BIGINT REFERENCES social_contract(id) ON DELETE SET NULL,
  season_id     BIGINT REFERENCES social_season(id) ON DELETE SET NULL,
  uids          BIGINT[] NOT NULL,
  seeders_before INT NOT NULL DEFAULT 0,
  seeders_after  INT NOT NULL DEFAULT 0,
  rescued_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_rescue_honor_torrent ON rescue_honor (torrent_id);
CREATE INDEX idx_rescue_honor_uids ON rescue_honor USING GIN (uids);

-- site_settings 补充项（沿用现有 site_settings 机制，不建新表）
INSERT INTO site_settings (name, value) VALUES
  ('social_enabled', '0'),                     -- 总开关，默认关闭
  ('social_pool_coef', '1.0'),                 -- k
  ('social_pool_cap', '0'),                    -- 0 = 自动按通胀公式计算
  ('social_income_ratio_cap', '0.30'),         -- 社交加成 ≤ 基础做种收益的 30%
  ('social_readonly_hours', '24'),
  ('social_reputation_keep_ratio', '0.70')
ON CONFLICT (name) DO NOTHING;
```

**注意**：`site_settings` 的字段名我按现有用法（`name` / `value`）推测，落地前需核对该表实际列名。

## 六、worker 新增任务（照抄现有写法）

新增 4 个 job，全部按 `preserve_exit` / `preserve_settle` 的风格写（单条 SQL + 幂等键 + `rows_affected` 返回）：

| job | 频率 | 职责 | 参考现有实现 |
|---|---|---|---|
| `rescue_scan` | 每日 1 次 | 扫 `seeders <= 1 AND times_completed >= 3` 的资源，写入待抢救清单（可用一张视图或直接查 `torrents`，不必新建表） | `preserve_exit` |
| `rescue_settle` | 每小时 | 契约到期检查：达标则完成并写荣誉；未达标则失败（**不连坐**，只失败不罚） | `preserve_settle` |
| `social_season_settle` | 每季末 | 汇总各契约的贡献（从 `spark_ledger` 时间窗反查）→ 按 `pool_cap` 与 `pool_coef` 计算发行 → 写 `spark_ledger`（`kind='social_season_reward'`） | `seeding_reward` |
| `social_reputation_decay` | 每季初 | 信誉跨季保留 70%，专精等级归零 | — |

**幂等键命名建议**（与现有风格一致）：

```
social:rescue:{contract_id}          -- 抢救契约结算
social:season:{season_id}:{uid}      -- 赛季发行（每用户每季一条）
```

**重要**：`social_season_settle` 写账本时**必须复用 `spark_ledger` 的 `idempotency_key` 先查后插**（该表是分区表，无法建全局唯一约束，现有代码也是应用层保证）。

## 七、API 设计（沿用现有组织方式）

现有 API 按域分文件（`economy_http.rs` / `games_http.rs` / `community_http.rs` …）。新增一个文件：

```
apps/api/src/social_http.rs
```

| 路由 | 方法 | 说明 |
|---|---|---|
| `/api/v1/social/overview` | GET | 赛季进度、我的契约、信誉、荣誉摘要 |
| `/api/v1/social/rescue/list` | GET | 濒危资源公开清单（分页） |
| `/api/v1/social/contract` | POST | 发起契约（指定 target / 人数 / 期限） |
| `/api/v1/social/contract/join` | POST | 报名加入（**自愿**，非邀请即入） |
| `/api/v1/social/contract/leave` | POST | 中途退出（**只扣信誉，不清零已有收益**） |
| `/api/v1/social/contract/detail` | GET | 契约详情、成员进度、贡献明细（可点进 `spark_ledger` 溯源） |
| `/api/v1/social/honor` | GET | 我的拯救记录与赛季历程 |
| `/api/v1/social/reputation` | GET | 信誉分与加减明细 |

**收敛效果**：前四轮设想的动作面（对标熊猫 45 个 action）在这里只有 8 个——因为**激励、结算、账本、反作弊全在 worker 和现有表里，API 只暴露社交关系本身**。

## 八、路线修正

前四轮的 P0~P5 现在可以压缩：

| 阶段 | 周期 | 内容 | 验收 |
|---|---|---|---|
| **P0 · 濒危清单公开化** | 1 周 | `rescue_scan` + `/social/rescue/list` 只读页面 + 埋点 | 清单准确；用户能点进去看到濒危资源 |
| **P1 · 单人认领 + 荣誉** | 1~2 周 | 复用 `seed_preserve` 认领流程，**加上荣誉归属**（`rescue_honor`） | ≥5% 活跃用户完成过 1 次抢救 |
| **P2 · 契约组队** | 2 周 | `social_contract` + 报名/退出 + 契约期贡献归属 | 50 个契约完成；违约率 < 30% |
| **P3 · 赛季与发行** | 2 周 | `social_season` + 结算 job + 发行入账 | 发行 ≤ 硬顶；社交加成 ≤ 基础做种收益 30% |
| **P4 · 主题包挂载** | 1 周 | 在 `site_type_packs.modules` 加社交模块标记 + 文案表 | 换主题 = 改一行 JSONB |

**总周期约 7~8 周**（前四轮估算是这个的两倍以上，因为当时假设要从零建激励层）。
