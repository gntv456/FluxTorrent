# 审种员视角深测审计报告

**日期**：2026-10-08
**方法**：静态全链路梳理（发种→审核→裁决→重提→tracker 闸门）+ 本地容器动态实测（铸 JWT 模拟审核员 94 级/普通上传者，构造真实 .torrent 走完整发种-审核-拒绝-重提循环，对 tracker 发三态 announce 探针）
**范围**：`apps/api`（review/review_batch/upload/manage/interact/offers）、`apps/tracker`（gate/guard）、`apps/web`（审核台 UI）、`apps/worker`（approved_at 消费面）
**结论**：无 P0；**P1×2、P2×8**。状态机主干（守卫、自审拦截、通知、被拒禁发）实测健康，两处 P1 都是「字段/配置键没人写对」型的静默失效——不炸、不报错、但功能等于没有。

---

## 一、P1（应尽快修）

### P1-1 `approved_at` 审核链路从不写入——泄露检测与社交队窗口对全部常规过审种恒空转

- **证据**：
  - `apps/api/src/admin_http/review.rs:191-211`：decide 的 UPDATE 只写 `approval_status/deny_reason_id/deny_note`，无 `approved_at`；`review_batch.rs:122-142` 同样。
  - 全仓唯一写点：`apps/api/src/content_http/offers.rs:172-173`（offers 转正）。
  - **实证**：本地库 60/60 条 `approval_status=1` 的种子 `approved_at` 全部 NULL——包括本审计刚通过审核的 42815。
  - 消费者全部因此空转：worker 泄露检测 `apps/worker/src/jobs/settle.rs:170-172`（`approved_at IS NOT NULL AND s.completed_at < t.approved_at + 10min`）、社交队小时窗 `social_team_expire.rs:141-142, 199-200`。
- **影响**：「过审后 10 分钟内完成下载」这一泄露信号（资源在外部渠道先行泄露、秒下完成）对所有走审核台的种子（即绝大多数）**从不触发**；社交组队窗口同理。防作弊面静默失明。
- **修法**：
  1. decide 与 batch 的 UPDATE 增加 `approved_at = CASE WHEN approve THEN now() ELSE NULL END`；
  2. 存量回填：`UPDATE torrents SET approved_at = created_at WHERE approval_status = 1 AND approved_at IS NULL`（created_at 近似过审时间，总比 NULL 强）；
  3. 顺手给 `resubmit`（回 0）加 `approved_at = NULL`，防重提旧种带旧时间戳。

### P1-2 被拒阈值配置键漂移——站长在设置页改的阈值不生效

- **证据**：
  - 代码读：`upload.rs:131-137` → `site_settings.name = 'upload_deny_limit'`（缺省 2）。
  - 设置页种的数据：`migrations/0039_settings_meta.sql:68` → `upload_deny_approval_deny_count`（值 3），且 0039:345 在设置页注册了后者。
  - **实证**：把设置页键值改成 5 后，`deny_count=2` 的用户发种仍被拦（代码键不存在→缺省 2 生效）。站长把阈值调到 5 的意图完全落空。
- **影响**：与 P2-1（deny_count 永不重置）叠加后变成刚性惩罚：阈值按缺省 2 拦，且没有线上重置路径。
- **修法**：统一键名——建议代码改读 `upload_deny_approval_deny_count`（设置页已有 UI），或迁移补种 `upload_deny_limit` 并改设置页写它。二选一，保持一处真相。

## 二、P2（真问题，按优先排序）

### P2-1 resubmit 无改动校验 + deny_count 永不重置
`manage.rs:280-324`：被拒种不要求任何实际修改即可重提。实测循环「拒绝→原样重提」两轮全部通过，审核队列被同一条反复占用；唯一代价是 deny_count+1，但该计数**没有任何清零路径**（过审不动、申诉纯线下），叠加 P1-2 后等于「两次被拒→账号永久禁发」。建议：① resubmit 前置「descr/标题等字段必须变化」或冷却期（如 10 分钟）；② approve 时对作者清零 deny_count（给改过自新的用户留活路）。

### P2-2 tracker gate 对 guard 缓存 miss 的兜底是放行——被拒/删除种的 announce 在刷新窗内仍拿得到 peers
`apps/tracker/src/http_track/gate.rs:87-106`：`meta_of(info_hash)` 查不到（guard 只载 status 0/1，被拒种拒绝后从缓存消失）时落到 106 行 `Ok(false)` = 正常 announce + 下发 peer 列表。**实证**：拒绝 42819 后立刻 announce，返回 200 且带 peers；数秒后 guard 刷新才回「torrent unregistered」。同理非作者对待审种 announce 被收进 swarm（complete 计数+1）只是不下发 peers。建议：guard miss 且站点开启审核制时，至少剥离 peers 下发（与 pending 的 `Ok(true)` 同口径），或对「曾经存在过的 info_hash」做负缓存。

### P2-3 审核队列权限只查 staff.panel
`review.rs:61`：`GET /admin/reviews` 不校验 `torrent.review`。当前默认授权（0285：90 级同给两者）无实际越权，但站点用权限矩阵单独收窄 review 权后，队列内容（descr 摘要、发布者过审/被拒历史）仍对全体 90+ 可见。一行 `require_perm` 的事。

### P2-4 postpone/resume 与 decide 口径漂移
`v4_http.rs:87-157`：用 `torrent.manage` 而非 `torrent.review`；无自审拦截（可把自己的种暂缓——影响小但口径不一致）；不写 `torrent_operation_logs`；不通知发布者（暂缓往往意味着「等作者补充证据」，作者却收不到任何信号）。

### P2-5 offers promote 是第二条「过审」入口
`offers.rs:150-200`：持 `offers.promote` 直接 `approval_status=1`，绕过 decide 的自审拦截与连击/计数副作用。讽刺的是它是唯一写 `approved_at` 的地方。若 offers 候选本身已经过人工把关可接受，但至少应补：自审拦截 + 过审副作用（`apply_approval_side_effects`）+ 操作日志。

### P2-6 审核台 dup_hash 指标恒 0
`review.rs:87-89`：info_hash 有唯一索引，子查询除 raw 变体外恒空，「DUP×n」提示一半是死的（dup_name 有效）。建议改为按 `pieces_hash`（同内容不同打包）或 raw_info_hash 变体查重，这个指标才有信息量。

### P2-7 异主墓碑判重锁死内容再上架
`upload.rs:91-104`：只有**同作者**的墓碑（status=3）走复活；他人软删后的同 info_hash 重发恒 3004 重复。对「原发布者跑路、内容本身合规」的场景，只能 staff 手工 restore。建议：异主墓碑重发时给 staff 一条待办（半自动复活），而不是直接拒绝。

### P2-8 前端未接 batch/postpone/resume
后端 `/admin/reviews/batch|postpone|resume` 全部就绪（0288 批次产物），web 只接了 decide/deny-reasons/resubmit。日均积压时审核员仍需逐条点。补 UI 接线即可，后端无需动。

## 三、实测确认健康的部分（防重复排查）

| 动线 | 结果 |
|---|---|
| decide 状态守卫 | 重复裁决、postpone 后 decide 均被 `approval_status=0` 守卫拦住，无 TOCTOU |
| 自审拦截 | 单条（拒绝理由「不能审核自己发布的种子」）与批量（skipped 列表逐条说明）都工作 |
| 拒因校验 | 伪造 deny_reason_id=999 被拦；approve 带拒因被拦；拒绝无理由被拦 |
| PM 通知 | 过审/被拒均落 `messages`（kind=review_approved/rejected），邮件尽力而为不阻塞 |
| 被拒禁发闸门 | deny_count 达阈值时发种被拦（阈值键问题见 P1-2，闸门本身工作） |
| 可见性 | 被拒种旁人 404、作者可见、下载 404；待审种同口径 |
| 编辑回退 | 作者编辑后回待审（实测**会**清拒因字段——此前怀疑残留，撤销） |
| announce 三态 | 过审 200+peers 正常；真被拒种（guard 刷新后）回 failure reason；非作者对待审种不下发 peers |
| 批量裁决 | ≤100 条/次、去重、逐条跳过自审、副作用/日志/通知齐全 |
