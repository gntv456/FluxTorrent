## 2. P0 级问题（必须优先处理）

### P0-1｜worker 把四个 O(全表) 任务挂在 60 秒周期上，规模化后必然自锁并拖垮数据库

**现象（实测）**
`apps/worker/src/jobs/run.rs:58` 定义 60 秒 tick；`run.rs:130-146` 的 tick 体内用 `JoinSet` 逐一轮流挂上并**等待全部完成**：

```rust
// run.rs:130-146
spawn_lock!(js, &db, "job:collect_milestones", collect_milestones, &shard);
spawn_lock!(js, &db, "job:hr_enforce",        hr_enforce,        &shard);
spawn_lock!(js, &db, "job:hr_punish",         hr_punish,         &shard);
spawn_lock!(js, &db, "job:class_auto_adjust", class_auto_adjust, &shard);
...
while let Some(res) = js.join_next().await { ... }   // 等全部跑完才结束本轮
```

这四个任务都是**随数据线性增长的全表扫描**。灌入 42 万 snatches 后，容器日志实测（`docker logs flux-worker`）：

| 任务 | 单次耗时（实测日志） | 关键计划 |
| :--- | ---: | :--- |
| `hr_enforce`（`INSERT INTO hr_snapshots`） | **38.6 s** | 并行 Seq Scan 全表 `snatches` + 全表 `torrents` + **279,852 次索引探测**；`shared hit=895,226`（≈**7 GB 缓冲访问/次**） |
| `collect_milestones`（`INSERT INTO seed_milestones`） | **9.9 s** | 全表 `snatches` CROSS JOIN 4 档位 |
| `class_auto_adjust`（`WITH stats AS ...`） | **1.4 s** | `EXPLAIN` 单独跑 629ms；每用户 **2 个相关子查询**扫 snatches，本轮 **4,136 次索引扫描**、840k 缓冲访问 |
| `hr_punish`（`UPDATE hr_snapshots ...`） | 秒级 | — |

**为什么这是 P0（而不只是「慢」）**
1. 日志时间戳显示这组任务已进入 **~45–58 秒一轮**（`15:17:21 → 15:18:05 → 15:18:51 → 15:19:49`），即单轮耗时已接近/超过 60s 周期。`tokio::time::interval` 默认 `MissedTickBehavior::Burst`——**超时后会立刻补跑下一轮**，worker 将退化成「永不停歇地扫表」。
2. 与实时计费链路**共享同一个 worker 进程的 select! 循环**：`consume_announce`（announce 计费消费）挂在同一 60s 分支上，会被这批扫表任务拖后（`run.rs:106-120`）。
3. 与 tracker **共享同一个 PostgreSQL**：实测 tracker 日志出现 `sqlx::pool::acquire ... aquired_after_secs=5.17 slow_acquire_threshold_secs=2.0`——连接被 worker 抢占了 5 秒。
4. 更讽刺的是：首次跑完后 `rows_affected=0`，后续每分钟**重扫全部 42 万行只为确认「没有新行要插」**。纯浪费。
5. **连删除也治不了它**：本轮清理数据（`DELETE` 42 万行）后，该任务**仍在继续报慢**（15:22–15:23 连续三条），因为死元组仍占着数据页、全表扫描照样读，要等 autovacuum 回收后才恢复。这反向证明该任务的成本完全由「表页数」而非「有效行数」决定。

**影响**：真实站点（百万级 snatches / 万级用户）上线后，worker 将长期占满 CPU 与 PG 连接，表现为「站点越活跃、后台越卡」，且**难以归因**（因为它不报错，只是慢）。

**建议改法（按性价比排序）**
1. **改增量游标**（治本，改动最小）：给 `snatches` 记录已处理位点，只扫新增。
   ```sql
   -- 加一列 + 部分索引，把「全表反连接」变成「索引区间扫描」
   ALTER TABLE snatches ADD COLUMN hr_checked_at timestamptz;
   CREATE INDEX CONCURRENTLY idx_snatches_completed ON snatches (completed_at) WHERE completed_at IS NOT NULL;
   CREATE INDEX CONCURRENTLY idx_snatches_seeding   ON snatches (user_id)     WHERE seeding;
   ```
   任务改为 `WHERE s.completed_at > $last_watermark ORDER BY s.completed_at` 分批（如每批 5,000 行）处理，水位写回 `job_state`。
2. **降频**：`hr_enforce` / `collect_milestones` 从 60s 周期改到 **5–10 分钟** tick（或复用已有的 `tick10`/`tick30`）。H&R 快照与做种里程碑**不需要分钟级实时性**。
3. **事件驱动**：`completed` 事件本就在 `consume_announce` 的事件流里（`worker/src/jobs/process_event.rs:174` 已处理 `completed_at`）——把 H&R 快照建立直接挂到事件处理里，彻底免掉巡检扫描。
4. **`class_auto_adjust` 去掉相关子查询**：改为
   ```sql
   SELECT u.id, u.class_id, u.uploaded,
          COALESCE(agg.dl,0), COALESCE(agg.sh,0)
   FROM users u LEFT JOIN LATERAL (
     SELECT count(*) FILTER (WHERE completed_at IS NOT NULL) AS dl,
            COALESCE(sum(seeded_seconds),0)/3600 AS sh
     FROM snatches s WHERE s.user_id = u.id
   ) agg ON true WHERE u.class_id < 90;
   ```
5. **防超时兜底**：把 interval 行为改为 `MissedTickBehavior::Skip`，并在 tick 体开头检查上一轮是否仍在跑（`run.rs` 已有 `with_lock` 超时 900s，但对全表任务的时长预估明显不足）。

### P0-2｜Tracker 全量 GC 挂在一个默认 404 的端点上，幽灵 swarm 永久驻留（可被单账号撑爆内存）

**现象（代码取证 + 实测）**
- 全量 GC `gc_all`（唯一会 `retain` 掉**空桶**的入口）只在 `/metrics` 处理器里被调用：`apps/tracker/src/http_track/metrics.rs:19-31`——而第 19-28 行在 token 校验失败时**先 return 404**，`gc_all` 在第 31 行才轮到。
- 默认 `ANN_METRICS_TOKEN` 未设置（`docker/.env` 无该键，仅 `.env.example:19` 注释）→ 实测 **`/metrics` 恒 404** → **`gc_all` 从未执行**。
- 单桶 GC `gc_swarm`（`apps/tracker/src/peers/table.rs:246-251`）只 `retain` 掉过期 peer，**不删除已空的 `Swarm` 条目**；只有 `event=stopped` 触发的 `remove()`（`tracker.rs:106-115`）才移除空桶。而「只被 announce 一次、随后再无人问津」的 info_hash 永远不会走到 `remove`。

**实测数据**
```
announce 前 flux-tracker 内存 = 13.07 MiB
用 3000 个互不相同的随机 info_hash 各 announce 一次后
announce 后 flux-tracker 内存 = 14.84 MiB   → +1.77 MiB ≈ 590 B/swarm
Redis 快照 flux:tracker:peers  619 B → 542,062 B（542 KB，仅 3,000 个幽灵 swarm）
```
容器内存上限 **1 GiB**（`docker-compose.yml` deploy limits）。按 590 B/swarm 外推：**约 170 万个幽灵 swarm 即 OOM**。而每用户限流是 1800 次/分钟（`apps/tracker/src/main.rs:65`）——**单账号最快约 16 小时即可造出 170 万个幽灵 swarm 打崩 tracker**（tracker 是单进程 SPOF）。

**建议改法**
1. `gc_swarm` 内 `retain` 后判空即 `remove_if`，与 `remove()` 同口径（一处小改，立刻止住空桶泄漏）。
2. 把 `gc_all` 从 HTTP 端点迁到**独立后台定时任务**（如每 60s 一次），不再依赖监控抓取触发。
3. 对「仅被 announce 过一次即消失」的 swarm 设更激进的孤立回收上限。

### P0-3｜NexusPHP 兼容层列表无翻页上限：`page=1000000` 触发 `LIMIT 50,000,000`

**现象（实测）**
```bash
# 用 root 的真实 API token（Authorization: Token fxo_...）
/compat/nexusphp/torrents.json?page=1&pagesize=50        → st=200  835 ms
/compat/nexusphp/torrents.json?page=100&pagesize=50      → st=200 1002 ms
/compat/nexusphp/torrents.json?page=1000000&pagesize=50  → st=200 1649 ms ← LIMIT 50,000,000，返回空
```
根因：`apps/api/src/compat_http/nexusphp.rs:93-94` 只做 `page.max(1)`、`pagesize.clamp(1,50)`，而 `limit` 传入的是 `page * pagesize`（`:116`），最终 `list_noclamp_as.rs:223` 直接 `LIMIT $8`。`page` 无上界，i64 极端值还会溢出回绕成负 LIMIT。

**影响**：任意持有 API token 的普通用户，一条请求即可让 PG 物化千万行、撑爆内存与临时文件。20,000 种子时已 1.65s；50 万种子时是秒级~十秒级的可控 DoS。

**建议改法**（与 torznab 已用的 `offset+limit<=1000` 口径对齐）
```rust
let page = q.page.unwrap_or(1).clamp(1, 1000);
let pagesize = q.pagesize.unwrap_or(30).clamp(1, 50);
let want = page.checked_mul(pagesize).ok_or(DomainError::Validation("翻页参数越界".into()))?;
if want > 1000 { return Err(DomainError::Validation("翻页过深".into())); }
```
更彻底：给 `list_torrents_noclamp` 增加 `max_limit` 参数，把安全阀放在数据层而非依赖调用方自觉。

> 与《第三方工具适配视角》的分工：该文从「工具兼容性」角度已指出兼容层鉴权/字段问题；本条是从**性能与 DoS 面**给出的独立发现，需一并修。

## 3. P1 级问题

### P1-1｜种子列表默认排序含 `now()`，永远无法走索引

`apps/api/src/torrents/list_noclamp_as.rs:45` 的置顶表达式内含 `now()`（`pos_state_until > now()`），使 ORDER BY 变为 STABLE 表达式，PG 拒绝建索引（迁移 `0151_torrent_page_indexes.sql:8-13` 自述）。

**实测**：`/torrents` 冷缓存 **1,330 ms**，暖缓存 7 ms。计划为 `Seq Scan on torrents (20,002 行) → top-N heapsort`，且**连 `idx_torrents_approval` 都用不上**。

**建议**：把置顶物化为列，默认排序改走索引。
```sql
ALTER TABLE torrents ADD COLUMN sticky_rank INT NOT NULL DEFAULT 0;
CREATE INDEX CONCURRENTLY idx_torrents_sticky_created ON torrents (sticky_rank DESC, created_at DESC, id DESC);
-- worker 周期任务仅对「置顶状态变更/到期」的集合 UPDATE sticky_rank
```
ORDER BY 与游标键同步改为 `(sticky_rank, id)`。

### P1-2｜公开排行榜每次请求全量聚合最大表，且无缓存

`apps/api/src/content_http/misc.rs:108-128` 六个榜单各自 `JOIN snatches GROUP BY u.id ORDER BY val DESC LIMIT 10`，聚合在排序前无法下推 LIMIT，必须扫全集；端点为公开、无鉴权、**无 Redis 缓存**、六个查询串行。

**实测**：`/top/boards` **301 ms**（42 万 snatches）；计划为并行 Seq Scan + HashAggregate。按线性外推，1,000 万 snatches ≈ 1.7 s/请求，并发即雪崩。

**建议**：① 立刻加上与首页同范式的 Redis 共享缓存（TTL 60s + 写失效）；② 用 worker 每 10 分钟预计算的快照表 / 物化视图（`REFRESH MATERIALIZED VIEW CONCURRENTLY`）。

### P1-3｜peer 快照「整档读写」：一次请求读全站 peer

- 写侧：tracker 每 60s 把**全站所有 peer** 序列化成一个 Redis 单键（`apps/tracker/src/main.rs:122-152`）。
- 读侧：`apps/api/src/torrent_http/peers.rs:124` 一次 `GET` 取回整档，再用 `serde_json::from_str::<Vec<...>>` **全量反序列化**后线性过滤目标 info_hash。

**实测**：3,000 个幽灵 swarm 时快照 **542 KB**；种子详情页 peer 面板每次请求 11–20 ms。代码注释自述「10 万 peer ≈ 20 MB」——即**每次打开种子详情页都要传输+解析 20 MB**，1,000 并发即 20 GB/s 级内存/网络放大。

**建议**：读侧改为按 swarm 分键（外置模式已有 `flux:swarm:{info_hash}`，见 `peers/external.rs:23`），API 用 `HGETALL` 只取目标 swarm；同时把 peer 快照模型抽到 tracker/api **共享 crate**（现为手写镜像，字段改名会静默失败、面板清空，`peers.rs:29-41`）。

### P1-4｜Redis `allkeys-lru` 承载计费流，但既不入备份又是匿名卷

**实测纠正**（避免误判）：并非「零持久化」——`dump.rdb` 确实在写（容器内 2,366 B，`CONFIG GET save` 仍为默认三档）。但风险形态依然严重：
```
appendonly   = no
maxmemory    = 256mb
maxmemory-policy = allkeys-lru      ← 内存压力下会驱逐 stream 条目
/data 挂载     = 匿名卷（docker-compose.yml 的 volumes 段只命名了 pgdata/attachments/prometheus/grafana，无 redis）
```
而 Redis 里放的是**计费事件流与死信**（`flux:announce` 消费者组、`flux:announce:dlq`，见 `worker/src/jobs/group.rs:30-44`），且流的 `XTRIM` 只在消费时执行（`announce_main.rs:168-172`）——**worker 一停，流无上限增长到 256 MB，`allkeys-lru` 开始驱逐「尚未计费」的事件**。`scripts/backup.sh:4-5` 更明确写「Redis 不备份：限流/缓存均可再生」——对 stream/DLQ 这个判断不成立。

**建议**
```yaml
redis:
  command: ["redis-server","--requirepass","${REDIS_PASSWORD}",
            "--maxmemory","512mb","--maxmemory-policy","noeviction",
            "--appendonly","yes","--appendfsync","everysec"]
  volumes: ["redisdata:/data"]
volumes:
  redisdata: { name: "${FLUX_REDIS_VOLUME:-docker_redisdata}" }
```
并把 `backup.sh` 补一条 `redis-cli --rdb`，同步修正「Redis 均可再生」的表述。

### P1-5｜可观测性：监控栈开箱即失效 + 健康检查无分级

1. **指标端点鉴权头不匹配**：`docker/monitoring/prometheus.yml:6-24` 用标准 `authorization: type: Bearer`，而 api/tracker 的 handler **只认自定义头 `x-metrics-token`**（`apps/api/src/v4_http/metrics.rs:63-71`、`apps/tracker/src/http_track/metrics.rs:19-27`）。→ 即使按 `docs/ops/monitoring.md` 配好 token，Prometheus 抓取仍全 404，`docker/monitoring/alerts.yml` 的告警全部不触发。**「有监控栈」是假象**。（`/api/v1/metrics` 实测 404 亦源于此 + token 未设。）
2. **健康检查无分级**：api `/api/v1/health` 直接返 `{"status":"up"}`，**不探 DB/Redis**（`apps/api/src/http/auth_infra.rs:16-19`），compose 却用它做健康判据；worker 健康检查被显式 `disable: true`；tracker 仅探端口。→ DB/Redis 挂了，api 仍报 healthy，LB 持续导流。
3. **依赖故障时登录限流 fail-open**：`throttle` 对 `incr` 用 `unwrap_or(0)`（`apps/api/src/http/auth_infra.rs:23-35`）、账户锁定同样（`auth_http/login.rs:39-49,77-85`）→ **Redis 故障期间密码爆破/撞库/验证码轰炸全部失守**。同仓游戏侧已修为 fail-close（`games_http/helpers.rs:119-144`），说明此处是遗漏而非有意。
4. **`ops_webhook.rs` 仅支持 Discord + Telegram**，无企业微信/钉钉/Slack（国内站告警落地困难）。

**建议**：① prometheus 改 `http_headers: { x-metrics-token: ... }` 或让 handler 兼容 Bearer（推荐后者）；② 新增 `/api/v1/ready`（`SELECT 1` + Redis `PING`，失败返 503）供 compose/LB 使用，`/health` 保留纯存活；③ 限流/锁定改 fail-close 或按 IP 走进程内降级计数；④ 补企业微信/钉钉 webhook。

## 5. 本轮实测「做得很好」的部分（避免误伤）

- **Tracker announce 性能与防伪造**：实测 p50 **4 ms**、p95 10 ms；100 并发 wall **104 ms**（约 960 req/s，受测试端线程数限制）；薄壳架构（内存 DashMap + 分桶索引）健康。前几轮的差额计费、IP 封禁、限流链顺序本轮复核仍正确。
- **worker 多实例互斥**：定时任务有 `pg_advisory_lock` + 分支内 await，消费走 Redis 消费者组，**多 worker 不会重复发奖**（前几轮已验，本轮复核代码仍成立）。唯一需留意 `XAUTOCLAIM` 空闲阈值 360s——单条处理超 6 分钟可能被重复投递，依赖 `process_event` 幂等键兜底。
- **降级设计（tracker 侧）**：Redis 故障时降级到进程内限流窗口而非裸放，并有 `flux_tracker_redis_fallback_total` 指标；DB 刷新失败保留旧缓存值。这是**正确的 fail-close/降级**，建议以 tracker 为准统一 api 登录侧口径。
- **前端主体质量高**：表单普遍有防重复提交；种子列表走游标分页且区分空/错态；游戏交互（转盘/九宫格/刮刮乐/猜大小）均为原生 `<button>` + `aria-label`/`aria-pressed`，**键盘可达**，非纯鼠标。
- **安全面**：工作区扫描未见新的越权/经济漏洞；`/compat` 与 Torznab 均 JOIN `users.status`，封禁即失效。
