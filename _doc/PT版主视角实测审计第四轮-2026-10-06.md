## 一、已修

### P0-A 列表首屏缓存把「查看者视角」的结果发给所有人【实测 → 已修】
`torrent_http/list.rs` 的 `is_first_screen` 白名单列了 30 多个「必须为空」的条件，
**唯独漏了 `bookmarked`、`approval`、`rating_min`**。而首屏缓存键
`cache:tlist:first:v1:{gen}` 对所有登录用户共用（TTL 45s）：
- `?bookmarked=1` 走的是 viewer 私有谓词（`torrents/viewer_preds.rs:37`）
  ⇒ 我先查收藏，45 秒内别人打开资源库首页拿到的是**我的收藏列表**；
- `?approval=2` 见下一条。
修法：判定抽成 `torrents::view_scope::shared_cache_safe()`（同时把 list.rs 从 359 行
降回 320 行，不再靠放宽基线），并把三个漏项补进白名单。

### P0-B `?approval=2` 把被拒与回收站种子给任意登录用户【实测 → 已修】
`torrents/list_noclamp_as.rs:99-106`：`Some(2) => vec![2, 3]`，
而 `torrent_http/list.rs:138` 是 `approval: q.approval` **无任何权限判定**
（同文件 `include_unapproved` 却正确地把了 `torrent.see_banned`）。
⇒ 任何人 `GET /torrents?approval=2` 就能看到被拒种子的标题/分类/大小/上传者，
以及被删进回收站的内容（版主处理过的敏感驳回同样在里头）。
修法：与 `include_unapproved` 同一闸门（抽成 `can_see_unapproved` 一处判定，两处复用）。

### P0-C 聚合详情又把 viewer 态发给了别人（**我自己的修被覆盖**）【实测 → 已重做】
第二轮我修过 `assemble()` 里 `let _ = uid;` 的问题（`purchased`/`is_owner` 是
`get_torrent_detail(db, id, auth.id)` 的 viewer 列，却整块写进跨用户缓存桶）。
本轮核对发现：**我提交时（07f3215）文件里又是 `let _ = uid;`** ——
并行会话的同名文件覆盖了我的 hunk，而我在 `git add` 后没回看自己的改动是否还在。
症状：B 打开付费种子看到「已购买 / 我发布」，付费墙与编辑入口被隐藏。
修法：按当前 uid 重算 `is_owner`/`purchased` 后再返回。**流程教训见文末。**

### P0-D bencode 解析器无深度与溢出防护：一个上传文件能打挂请求线程【实测 → 已修】
`bencode/parse.rs` 的 `l`/`d` 分支无深度上限，且 `let end = start + len;` 无回绕保护：
- 1 MiB 的 `llll…`（远低于 4 MiB 上传上限）递归下降直接爆栈；
  `Bencode` 树的递归 `Drop` 在**错误路径**上同样会溢出；
- `18446744073709551615:x` 在 release 下回绕成 `end < start` → 切片 panic。
修法：`MAX_DEPTH = 32`（真实 .torrent 最深 4~6 层）+ `checked_add`，
并加两个单测（深层嵌套、超长前缀）。

### P1-E 重建 `.torrent` 会产出重复的根级 `private` 键【实测 → 已修】
`torrent.rs` 的 `retain` 只清 announce/url-list/httpseeds/dht_nodes，
随后无条件 `pairs.push(("private", 1))`；原文件根级若已有 `private`
（我们自己的下载结果就是如此）⇒ 输出里出现两个 `private`，
libtorrent 严格模式 `bdecode` 直接拒读。而「删了重发 / 跨站复种」正是必经路径。
修法：`retain` 一并去掉旧 `private`；单测断言重建后 `private` 唯一且 info_hash 不变。

### P1-F 标签筛选的总数恒为 0（SQL prepare 失败被吞）【实测复现 → 本批已修】
`list_noclamp_as.rs` 把列表用的 `tag_pred`（内含 `$9`）原样插进计数 SQL，
而计数侧 `tag_ids` 绑在 `$8`、`$9` 是 `size_min` ⇒ `cannot cast type bigint to integer[]`，
`.unwrap_or(0)` 吞掉 ⇒ 页面显示「共 0 个」但列表有行，且 compat 接口
`has_more:false` 让后面的页永远取不到。
**修法（本批）**：谓词抽到 `torrents/tag_pred.rs` 并按槽位参数化（列表 $9 / 计数 $8）；
计数失败不再静默——`tracing::error!` 留痕后降级 0；闸门 J8 复验。

## 二、待办（按版主/站长的痛感排序）

### 读路径
- **P1** 幽灵 peer 不进计数：`sweep.rs` 清了 `snatches.seeding/leeching`
  却不刷 `torrents.seeders/leechers`，二者只在 announce 批次「本轮被触碰」时重算
  ⇒ 「仅活种」列表里躺着死种、首页在线做种数虚高、濒危/求种定向漏掉它们。
- **P1** 审核单个种子（`review.rs`/`review_side_effects.rs`）**不失效任何缓存**，
  只有批量路径 bump 代际 ⇒ 刚过审的种子 45s 内仍搜不到；站型包改分类名同理。
- **P1** `sort=comments` 对分类内**每一行**跑 `(SELECT count(*) FROM comments …)`
  （20k 种 ⇒ 每页 2 万次子查询）；默认排序含 `now()` 且无索引。
- **P1** 搜索联想 `ORDER BY similarity(name,$3)` 没用 KNN 操作符 ⇒ trgm 索引不生效，
  每次按键全表打分；外层排序无唯一 tiebreaker ⇒ 下拉框在相同优先级间抖动。
- **P1** 主题详情 ≈ 每层 6 个子查询 × 200 层 + 每次读 `views = views + 1`
  （热行锁、刷新与爬虫都算浏览量）；论坛主题列表硬顶 50 条无分页。
- **P1** compat 翻页是「取前 page×pagesize 行再在 Rust 里 skip」
  ⇒ 第 400 页 × 50 = 一次拉 2 万行（每行还带 3 个关联子查询）后丢掉。
- **P2** RSS/邀请/站点库搜索的 `LIKE` 未转义（用户输入 `%` 变通配）；
  最短长度按**字节**判定（中文两字即放行）；
  sections 过滤值与 kind 名是**字符串内插**而非绑定参数（二次注入面）。
- **P2** `pg_stat_statements` 开了但**没有任何读取方**；`/metrics` 直方图不带路由标签；
  读路径 SQL 错误一律 `unwrap_or` 成空值 ⇒ 慢与坏都表现为「数据不对」而不是信号。

### 种子文件与客户端层
- **P0** 非 UTF-8 的 `info.name`（GBK/CP936/Big5，中文老包极常见）被判空
  ⇒ `validate_for_upload` 硬拒，**会员传不上真实 PT 内容**；
  且校验提示「info.name 与表单名称至少要有一个」而它根本看不到表单名（调用点早于表单合并）。
- **P1** 多文件种子的 `info.name` 不进路径校验循环 ⇒ `name = "../../x"` 可过，
  客户端按 name 建目录即穿越；`piece length` 只判 `> 0`（1 GiB 也放行，
  libtorrent 拒非 2 的幂、Transmission 会整块进内存）。
- **P1** 剥除 off-tracker 键只匹配 `dht_nodes`，漏 `dht-nodes`、BitComet 的 `ws`
  与 info 级 webseed 字段。
- **P1** peer 桶按「announce 的哈希」分桶，raw 与规范化两种口径**互不可见**
  ⇒ 计费两边都认（`guard.rs`/`process_event.rs`），但 peer 互相看不到：
  会员看到「2 个做种者，我的客户端 0 连接」。
- **P1** peer_id 不与用户绑定、也不限制单 passkey 的 peer 数
  ⇒ 复用他人 peer_id 可遮蔽对方槽位；「不要多机同 key」写在指南里但无任何强制。
- **P1** 附件是「登录即可按 sha256 取」，且响应头 `Cache-Control: public, immutable`
  ⇒ 鉴权资源进中间缓存；`storage::get` 整文件读进内存（含 HEAD 请求按
  `video_max_mib` 预分配）。
- **P1** 字幕下载只按自增 id 取，不 join `torrents.approval_status`
  ⇒ 挂在待审/被拒/回收种上的字幕可被枚举；外链字幕不过大小/扩展名/去重。
- **P2** magnet 把 passkey 放进 `tr=` 且无 `no-store`；无 BEP53 `xs`；
  `pieces_hash` 是 SHA1(info.pieces) 而非 BEP45 pieces root，
  且没有「按 pieces_hash 查」的端点 ⇒ 跨站复种工具拿不到可用数据。
- **P2** 客户端指南与实现不符：宣称 Transmission 会因 private 自动关 DHT
  （而 private 现在在根级，不生效）、未写 announce 格式（tracker 只服务
  `/announce/{passkey}`，`/announce?passkey=` 是 404）。

## 四、进镜像前的双账号复验补记（同日）

按承诺，第四轮修复进镜像前先手工双账号对打两条隐私修复。结果：抓到
**第四轮 P0-A 的修复不完整**，外加一条同族新漏洞、一条老漏洞。

### 补-A `?bookmarked=1` 仍经扩展共享缓存串用户（v2 键）【实测 → 已补修】
第四轮把 `bookmarked` 从**首屏缓存**白名单拿掉，但漏看了同文件下方还有第二级
「扩展共享缓存」`cache:tlist:v2:{gen}:{hash}`——它的入缓存判定只有
`status.is_some() || only_mine`（`list.rs:272`），`bookmarked` 不在其中。
于是 `?bookmarked=1` 只是从 first 键挪到了 v2 键，**照样跨用户**：TTL 20s 内
B 请求同 URL 直接命中 A 的收藏列表。
实测（`_workbuddy/_repro_v2_bookmark_leak.py`，修复前镜像）：

    [书签] A(root) 看到 T1=True；B(无书签, uid 4148) 看到 T1=True -> LEAK

修法：三个 viewer 维度（status/mine/bookmarked）收进
`torrents::view_scope::viewer_scoped()` 一处定义，v2 路径统一调用；
补单测 `viewer_dims_are_never_shared`。

### 补-B `?approval=2` 越权在修复前镜像上直接可复现【实测】
同脚本：`[越权] B 看到被拒种 T2=True；A(root) 看到 T2=True -> LEAK`。
证实 P0-B 不是理论问题；闸门 J7c 现在常驻看住它。

### 补-C 首页「娱乐流水」把墓碑号当公开面展示【实测 → 已修】
`http/home.rs` 的 lucky_draw（`spark_ledger` game/vote 流水 Top15）JOIN users
**没有 `status < 2`**，而同类公开榜（`/top/boards` 六榜、娱乐屋周榜两榜）全都已带。
造一条墓碑号（uid=107）的 now() 流水即置顶：

    [home 流水] top15 用户=['deleted-107-6470d57e', 'root', ...] 含墓碑号=True -> LEAK

修法：加 `AND u.status < 2`，与其余公开面口径对齐（墓碑删除不清账本是设计口径，
展示层过滤才是正确位置）。

### 闸门增补与旧镜像基线
`e2e_surface_economy_invariants.py` 新增 J7a–J7d：书签跨用户 + approval 越权，
**各带阳性对照**（A/版主必须看得到，否则判探针失效而不是通过）。
修复前镜像实测 **12/14**，两条红恰好就是缺陷本身（J7b/J7c），其余 10 条与既有一致。

### 探针坑（已写进脚本注释）
列表类断言必须显式带 `&alive=0`：本地种子 `seeders` 全 0，而列表默认视图
隐式 `seeders > 0`，裸 URL 恒空——首轮探针「阳性对照失效」就是踩了这个。

### 修复后镜像复验（同日，新镜像）
读路径批次把闸门扩到 20 条（新增 J8 标签计数槽位/J9 附件缓存头/J10 字幕
审批门），新镜像 **20/20 全绿**——J7b/J7c 由红转绿即四轮两条修复的现场证据；
`_verify_download_torrent.py` 与 PT 经济（15/15）、H&R（7/7）闸门同批复验通过。
写 J8–J10 时自己踩了同一个坑：闸门的 `psql()` 返回**整串**（非行列表），
`row[0]` 只取到首字符——J9 拿 `/attachments/b` 打 400、J10 解包崩溃，J8 因
单数字 id 侥幸通过。三条探针已改为整串用法。教训：**探针失败先怀疑探针自己**，红要红在缺陷上
（阳性对照就是判据）。

## 五、tracker 服务自身审计【线报，未逐条复验】

`apps/tracker/src/`（HTTP 7070 + UDP 6969）只读审计产出，排除了计费面（那在 worker）。
按建议处置顺序：

1. **`left` 解析失败静默当 0**（`http_track/params.rs:30` `unwrap_or` +
   `announce.rs:48` 只拦缺失/负数）⇒ `left=abc` / 溢出值全变 `left=0`，
   直接判做种、拿 3720s TTL——ecd0ab5「left 必填/非负」的补齐没封死非数字/溢出分支。
2. **无影子 peer / 同 IP / 多 passkey 去重，无每用户-每 swarm 上限**
   （`peers/table.rs:85` 唯一键仅 (info_hash, peer_id)）⇒ 单账号可在
   `main.rs:65` 的 1800/min 内批量灌假做种并真实下发；同 peer_id 跨账号互相覆盖
   `user_id`，`event=stopped` 可无归属校验顶掉他人条目。
3. **scrape 三缺口**（`scrape.rs:31`）：漏 `suspended/download_enabled` 判定
   （announce 有）；IP 不走 TRUST_PROXY/XFF（挂 LB 后全体共享一个限速桶、
   ip_bans 失效）；不查白名单 ⇒ 被拒/删除种的残留 peer 最长 62min 可查。
4. **peer TTL 与下发 interval 失配**（`peers/table.rs:17`：LEECH 90s / SEED 3720s
   硬编码；`guard.rs:72` interval 站设置默认 1800s 可配到 86400）⇒ left>0 的
   peer 90s 就被清，`incomplete` 大概率失真；interval>3720s 时做种也会被清空。
5. **scrape 口径**：complete/incomplete 只有 tracker 内存瞬时口径（不查 DB），
   `downloaded` 恒 0（`peers/bencode.rs:99`），重启 warm-restore 不带白名单校验。
6. **external 存储模式口径分裂**（`peers/external.rs:114`：snapshot 不跳 port=0；
   scrape 读本机内存而 announce 读 Redis）⇒ 多副本下同 hash 数字不一致。
7. **无效 passkey 无负缓存**（`guard.rs:134` 仅命中才缓存，封号恒 None）⇒
   垃圾 passkey 洪水 1:1 打 PG（池仅 8 连接）。
8. **UDP/HTTP 边界不一致**（`udp/announce.rs:43` 不拒 `left<0`；numwant=0 被抬成 1；
   两侧放行负数 uploaded/downloaded）。

低度：自连过滤只按 peer_id（换 peer_id 后自己旧记录被发回）；
UDP connection_id 弱 PRNG（固定种子）且会话表满 10 万整体清空；
port=0 被接受并计数；`no_peer_id=1` 未实现。

**已核对无问题**：panic/500 路径的字节级解析全有长度守卫；封禁/挂起在 announce
侧已拦且 3s 内生效；passkey 不进日志；numwant clamp(0,200) + 响应 50 双保险。

## 六、下载重建把 info 字典「规范化」→ 非规范种 info_hash 分叉【实测复现 → 本批已修】

复验 P1-E（重复 `private` 键）时按承诺做了第四条断言：下载种重建后 info
区间的 SHA1 必须 == 库 `raw_info_hash`。结果 FAIL——`_workbuddy/_verify_download_torrent.py`
第 ④ 项：

    FAIL  info 区间哈希 == 库 raw_info_hash  [span=(175, 288)]
    （重建 7f3989e3… vs 库 raw f1dd9a3e…）

根因：`build_download_torrent` 末尾把整棵根字典交给 `encode()` 重编码，而
`encode()` 按 BEP3 排序**所有**字典键——包括 info。上传时键序非标准
（如 `12:piece length` 排在 `4:name` 之前的重打包/跨站复种产物）的种子，
重建后 info 字节序改变：下载种的 info_hash 与上传入库的 raw 口径分叉，
M05「info 字典不动」只对规范输入成立。后果与已知「双口径 peer 互不可见」
同源——下载种再回来做种按新哈希 announce，与站内已有 peer 分成两个 swarm。

修法：`encode_root_keep_info` 根字典键仍按 BEP3 排序，唯一例外是 `info`
值直接落 `raw_info_span` 定位到的原始字节（扫描失败退旧行为）；新增单测
`download_rebuild_preserves_non_canonical_info_bytes` 构造非规范键序输入，
断言 raw 哈希逐字节保留（原有单测全是规范输入，从未覆盖此路径）。
