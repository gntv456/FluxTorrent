## 1. 产品定位与设计原则

### 1.1 一句话定位

> 给审种队列配一个不知疲倦的实习审核员：能自动放行干净的种，能自动拒绝明显违规的种，拿不准的留给人工——**它的每一次裁决都走人工审核的同一条管线，留同样的痕，发同样的通知**。

### 1.2 六条设计原则

1. **裁决同尺**：自动裁决必须调用 `review_decide::decide_one`（人工单条裁决的服务层收口），信用分/streak/促销/通知/approved_at 全部同口径。禁止任何「自动通道自己 UPDATE torrents」的旁路。
2. **机器只做减法，不做加法**：自动审种只服务「本来要排人工队列」的种（approval_status=0）；任何免审通道（分类/streak/信用/等级/权限）命中时发布即通过，自动引擎不参与、不重复检查、不推翻。
3. **宁可暂缓，不可误拒**（fail-safe to human）：自动拒绝必须高置信；灰区一律 POSTPONED（暂缓）转人工，附机器意见。误拒一个好人比漏放一个坏种伤害更大——拒绝会扣信用分、累计 deny_count 触发禁发闸门（`upload.rs:150-172`）。
4. **先影子，后执法**：上线流程强制两阶段——影子期只记分不裁决 + 与人工裁决对照校准 → 校准达标才切执法。照抄 0391 反作弊规则集「影子+回测」方法论。
5. **规则全部键化，界面全部人话**：每个规则都是 site_settings 里一个开关+几个数字/下拉，meta 里配中文 label/hint/enumOptions。小白看到的是「开关 + 滑块 + 三选一」，不是正则表达式。
6. **机器裁决永久可撤销、可追责**：每次自动裁决在操作日志标注规则集版本与命中规则；站长可一键把某条规则降级为「仅提醒」；用户申诉通道复用现有 appeal 机制，撤销裁决走人工 decide 反向流程（天然存在：2→0 resubmit / 4→0 resume / 1→3 下架）。

### 1.3 审核流水线全景

```
发布 upload
  │
  ├─ 硬校验（现有，发布时同步拒绝，不进队列）
  │    bencode/站外源/重复/字段/Logcheck/被拒禁发
  ├─ 免审 5 维（现有，命中即 1 通过，本方案不动）
  │
  └─ approval_status=0 待审 ──┬──> 【新增】自动审种引擎（0.5~2 分钟内跑）
                               │      规则逐条评估 → 三种结果：
                               │        AUTO_PASS  → decide(approve, by=引擎)
                               │        AUTO_DENY  → decide(deny, 理由=自动规则+详情) → 邮件+站内信
                               │        灰区/POSTPONE → 暂缓 + 机器意见，人工兜底
               ┌───────────────┘
               ▼
         人工审核队列（现有，机器看过仍拿不准的 + 暂缓的）
               │
               ▼
         人机对照台账（新增表）→ 影子期校准 / 执法期监督
```

## 2. 规则体系设计（三层十五规则）

规则分三层，对应置信度从高到低：**硬规则**（违反必拒，接近确定性）→ **软规则**（评分制，多信号叠加）→ **深检规则**（需耗时分析，异步执行）。

> 阈值全部为缺省值，站长可在后台每一条微调；每条规则可独立设置 强制/仅提醒/关闭。

### 2.1 第一层：硬规则（命中即 AUTO_DENY，置信度 ≈ 确定）

| # | 规则 ID | 人话名 | 判定逻辑（缺省） | 自动动作 |
|---|---|---|---|---|
| H1 | `arule_title_garbled` | 标题乱码/夹码 | 标题含乱码特征（连续不可打印字符、`ï¿½` 替换符、全角字符占比>60%）或夹藏 base64/16 进制串（长度≥20 的 `[A-Za-z0-9+/=]{20,}` 且非文件名场景） | 拒绝 + 邮件 |
| H2 | `arule_descr_missing` | 必备要素缺失 | descr 去标签后低于该分类下限（缺省 80 字，按分类可配），或必备要素清单有缺项（IMDB/MediaInfo/截图/字幕组等，按站型/分类配置，见 §2.5） | 缺省暂缓 + 邮件（逐项列出缺什么） |
| H3 | `arule_ads_keywords` | 描述含广告/引流 | 命中广告词库（微信群/QQ 群/ telegram / t.me/ 加 V/ 收费/ 网盘链接/ 外站注册链接等，词库站长可增删，缺省 ~30 词） | 拒绝 + 邮件 |
| H4 | `arule_leak_marker` | 泄露站内信息 | descr/标题含 passkey（40 位 hex 且形似本站 passkey 段）、本站 tracker URL 明文、他人 passkey 等内网标识 | 拒绝 + 邮件 + 同步写 leak_events |
| H5 | `arule_dupe_check` | 疑似重复资源 | 与近 90 天已过审种子标题相似度 > 0.92（去水分词后 Jaccard）或 mediainfo 指纹（视频轨 fourcc+时长+码率桶）完全一致 | 拒绝（理由：疑似重复，附原种链接）+ 邮件 |
| H6 | `arule_title_format` | 标题不符合命名规范 | 命名规则引擎（§2.6）：按站长配置的模板校验标题要素；strict 档缺必备要素才可拒，规范偏差只暂缓并附「建议标题」 | 按档位（缺省 warn=暂缓） |

**H 规则安全阀**：每条可配 `action: deny/postpone`，缺省 H1/H3/H4=deny，H2/H5/H6=postpone（H2 可能误杀小体积资源说明、H5 相似度有误报面、H6 命名歧义多——先暂缓观察）。

### 2.2 第二层：软规则（信用评分制）

不打死任何种子，而是算一个「发布者可信度 + 内容完整度」综合分，映射三档动作：

| # | 规则 ID | 人话名 | 判定（缺省） | 分值 |
|---|---|---|---|---|
| S1 | `arule_publisher_trust` | 发布者信用 | 基础分 = min(50, publish_credits × 5) + streak × 2 + 注册天数/30（封顶 10） | 0~100 加权 |
| S2 | `arule_media_rich` | 元数据完整度 | 有 PTGen/TMDB 卡片 +15；有 mediainfo +10；有海报/截图 +10；有副标题 +5 | 0~40 加权 |
| S3 | `arule_history_quality` | 历史通过率 | 近 90 天人工通过率 ≥95% +20；有被拒史 −10/次（封顶 −30）；有 H&R 记录 −15 | −30~+20 |
| S4 | `arule_report_pattern` | 被举报模式 | 发布者近 30 天被举报且成立的次数 × −20 | 0~−60 |

综合分阈值（站长可调）：

| 分数段 | 动作 | 缺省阈值 |
|---|---|---|
| ≥ `auto_pass_score` | AUTO_PASS 自动通过 + 邮件 | 80 |
| < `auto_deny_score` | AUTO_DENY 自动拒绝 + 邮件 | 30（**一期默认不启用自动拒绝段**，落此段先暂缓；影子期数据校准后再开） |
| 中间段 | POSTPONE 暂缓 + 机器意见，人工审核 | — |

> 设计说明：软规则层刻意保守——自动通过可以大胆些（放行的代价是泄漏检测和人工下架兜底），自动拒绝必须有硬规则或深检级证据；分段可整体「仅暂缓不拒绝」，即站长把 auto_deny_score 调成 0 即关闭软规则自动拒绝。

### 2.5 站型适配层（不同站点审不同的东西）

一套规则内核 + 站型/分类映射，是「站长配出自己站的审核标准」的主轴。维度按 **站型（site_type，11 包）→ 分类（category）→ 规则** 三级下钻，下级未配则继承上级，站型层未配则用通用缺省——站长只需覆盖自己站关心的几条。

**站型预设的规则覆盖矩阵（出厂内置，均可再改）**：

| 站型 | 加严/启用的规则 | 放宽/关闭的规则 | 站型特有判定素材 |
|---|---|---|---|
| movie | H6 强制（年份/分辨率/组名三要素）；D5 对照 TMDB（0358 第五源） | H5 相似度门槛降到 0.88（同片多版本常态，更严防重） | tmdb year/runtime；resolution 词表 |
| tv/剧集 | H6 强制（S/E 话数）；D4 强制（文件数=话数跨度） | H2 字数下限 40（剧集话题度低） | season/episode_first/last（0321 话数维度） |
| anime | H6 强制（话数+字幕组）；D4 强制 | H2 下限 40；H3 词库追加「熟肉招商/汉化组收款」类 | bangumi 源（0320）；字幕组 multiselect |
| music | Logcheck 已有（0311 前置，不重建）；H6 强制（艺人/专辑/年份/介质）；D3 强制（无损音轨 magic number） | H2 下限 30（曲目列表即正文） | artists 实体（0327）；cue/log 文件在场 |
| sports | H6 强制（对阵+赛季+日期） | H5 关闭（同赛事多机位属常态，误报面大） | sport_matches 对阵比分（0330）；league 词表（0324） |
| documentary | H6（年份/主题词） | — | works_meta（0399） |
| education | H6（科目/学段/格式） | H4 保持强制 | 分类层级（0178） |
| ebook | H6（书名/作者/格式） | H2 关闭（书籍 descr 常为目录节选，天然短） | ebook 按需模板（0x 0233 记忆：d902623） |
| comic | H6（话数/汉化组） | H2 下限 30 | — |
| variety | H6（年份/期数） | H5 降到 0.90 | — |
| 通用缺省 | H1/H3/H4 开；H2 80 字；H5 0.92 | 软拒关 | — |

**规则三要素的站型/分类覆盖**：每条规则的「启用/动作/阈值」都可按站型或分类写覆盖项（存 JSONB 映射 `{"movie":{"arule_title_format":{"action":"deny"}}}`，编辑面见 §3.1 卡片 6）。分类层示例：音乐站的「无损」分类把 D3 动作设为 deny 并把 H2 下限调 30，同一站「MV」分类关掉 D3。

**分类白名单（D2 的庇护所）**：出厂按站型给常见「软件/工具/学习」分类预填白名单（如 education 的「开发工具」），站长可在卡片 6 增删自己站的庇护分类。

**发布者画像的站型切分**：S1/S3 的通过率与 streak 以「当前站型维度」统计（对齐 0328 订阅进度按站型维度的先例），避免用户在低风险站型养出的信用溢出到高风险站型。

### 2.6 命名规则引擎（H6，站长配自己站的命名法）

命名是 PT 站审种最主观、也最该配置化的一环。设计目标：**小白选模板，进阶站长拼模板，谁都不写正则**。

**三级严格度**（`arule_title_format_level` 下拉）：

| 档 | 人话 | 行为 |
|---|---|---|
| off | 不检查 | H6 完全关闭（站型矩阵缺省含 off 选项） |
| warn | 只提醒 | 不符合 → 暂缓 + 给人工看差异；**不自动拒**（任何站型都不会因命名被机器拒，命名歧义太多） |
| strict | 严格 | 缺**必备要素**（可自动拒）；要素齐但顺序/分隔不规范 → 仍只暂缓并附「建议标题」 |

**要素库（内置 14 种，站长勾选+排序+定分隔符）**：

| 要素 | 提取器（内置，非正则暴露） | 站型典型 |
|---|---|---|
| 中文名/原名 | PTGen/TMDB/bangumu 抓取对照，无源时取最长 CJK 段 | 全部 |
| 年份 | `(19|20)\d{2}` 上下文消歧 | movie/tv |
| 分辨率 | 词表 480p…2160p/4K/8K（可扩） | movie/tv/anime |
| 来源 | 词表 BluRay/WEB-DL/Remux/HDTV/DVDRip…（可扩） | movie/tv |
| 编码/压制组 | 词表 x264/x265/H.265/AVC + 组名 `-([A-Za-z0-9@]+)$` 尾段 | movie/tv |
| 季 Sxx | `S\d{1,2}` | tv |
| 话数 Exx / 跨度 | `E\d{1,3}` / `E?(\d+)\s*-\s*(\d+)` | tv/anime/comic |
| 字幕组 | 站内字幕组词表（multiselect 值域同源） | anime |
| 艺人 | artists 实体（0327）匹配 | music |
| 专辑 | 艺人后首段 | music |
| 介质/音质 | 词表 FLAC/MP3/320kbps/24bit… | music |
| 对阵 | sport_matches 主客队名（0330） | sports |
| 赛季/日期 | league 词表（0324）+ 日期模式 | sports |
| 版本/修订 | v2/Repack/Extended 词表 | movie/tv |

**模板语法（进阶）**：`{中文名}.{年份}.{来源}.{分辨率}.{编码}-{组名}`——占位符即上表要素，字面分隔符站长自定（`.`/空格/`[]`）。校验器做「模板 → 自动编译成内部匹配器」，**配置面永远只有模板串与下拉，不出现正则**。缺省模板按站型预置（movie 缺省即上例；tv `{中文名}.S{季}E{话}.{来源}.{分辨率}-{组名}`；music `{艺人} - {专辑} ({年份}) [FLAC/{音质}]`；sports `{联赛} {赛季} {主队} vs {客队} {日期} {来源}`）。

**「建议标题」生成**：命中要素不全或顺序不符时，引擎用已提取要素按模板**生成一份规范标题**放进拒绝/暂缓文案——作者可直接复制改正，这是把「命名规则」从惩罚工具变成纠错工具的关键一步。

**与站型实体的天然联动**：年份/话数/对阵/艺人等要素提取结果直接与 PTGen/TMDB/bangumi/artists/sport_matches 已有实体交叉验证（D5），命名引擎不用自建任何数据源。

### 2.3 第三层：深检规则（异步沙箱执行，600s 档）

复用现有条件：announce 已有探针身份随机化（0311 批）、leak_scan 已在跑。深检只对「灰区种子」执行，避免全量沙箱开销：

| # | 规则 ID | 人话名 | 判定 | 动作 |
|---|---|---|---|---|
| D1 | `arule_torrent_sandbox` | 沙箱试连 | 对灰区种发起模拟 announce（随机身份），验证 tracker 可答、peer 拓扑正常、无「秒做种」异常（单人 0 上传即完成） | 异常 → 暂缓 + 证据；正常 → 灰区加分 || D2 | `arule_malware_hint` | 可疑可执行文件 | 种内含 .exe/.scr/.bat/.apk/.sh 且无「打包工具/破解补丁」分类白名单庇护 | 暂缓（不自动拒，人工确认） |
| D3 | `arule_fake_media` | 伪媒体文件 | 声称视频但最大文件不是视频容器（mp4/mkv/avi 系 magic number 校验）、音频声称无损但非 flac/ape/wav | 拒绝 + 邮件（此条置信度高，因有 magic number 客观证据） |
| D4 | `arule_files_crosscheck` | 文件×命名交叉校验 | 视频文件数 vs 命名话数跨度（`[01-12]` 应恰 12 个视频）、字幕文件数 vs 视频数倍率、音乐音轨数 vs 曲目数 | 不符 → 暂缓 + 证据（客观差异，未必恶意） |
| D5 | `arule_meta_crosscheck` | 元数据一致性 | 标题年份/话数/对阵 vs PTGen·TMDB·bangumi·artists（0327）·sport_matches（0330）·works_meta（0399）已有实体 | 不符 → 暂缓 + 双方取值对照 |

深检结果回写裁决的路径：深检任务完成后调用同一 `decide_one`，与在线引擎无二致。

### 2.4 规则引擎执行顺序

```
种子进入待审（新发布 / 编辑回退 / resubmit / restore）
  → 0.5~2 分钟内 worker 取件（600s 档轮询 + 待审队列事件唤醒可选）
  → 第一步：免审复核（若已被人审/免审，跳过）
  → 第二步：H 规则逐条（短路：一票即出）
  → 第三步：软评分（S1-S4 加权）
  → 第四步：分数段映射动作；灰区且开启深检 → 入深检，暂缓等待
  → 深检完成 → 复评 → 终裁
  → 终裁统一走 review_decide::decide_one
  → 人机对照台账落一行
```

1. **零术语**：所有 label 用上面的「人话文案」，规则 ID 只出现在 hint/审计里。

## 5. 修改自动复审（现状已半成，补齐三点）

现状：普通作者编辑 → 回退待审（`interact.rs:89-91`）；resubmit → 0（带 10 分钟冷却）；restore → 0。**自动引擎消费的就是待审队列，因此「修改自动复审」天然成立，零新表零新端点。**补齐：

1. **复审上下文继承**：`torrent_operation_logs` 已记录每次回退原因；引擎取件时读取该种上一轮裁决（人机对照台账），若上一轮为自动拒绝且本次命中同一条规则 → 直接维持拒绝（不再重新评分，防止「改个标点重交刷自动通过」）；若命中不同规则 → 正常流程。**同规则维持**同样有 10 分钟编辑冷却配合（resubmit 冷却已存在，编辑回退路径补同款检查：mtime 10 分钟内多次编辑合并为一次复审取件）。
2. **staff 编辑保通过不受影响**：现有 staff/免审等级编辑保 1 的逻辑（`interact.rs:60-66`）不动——staff 改过的种不进待审，自然不会被机器碰。
3. **编辑差异摘要进裁决**：引擎对比 edit 前后 descr diff，命中「只改了无关紧要内容」模式（相似度 > 0.98 且上次是拒绝）→ 暂缓转人工并标注「疑似无实质修改重交」。

## 6. 影子模式与上线流程（强制两阶段）

照抄 0391 反作弊「影子+回测」方法论，这是防止上线即误杀的安全底座：

### 阶段一：影子期（强制 ≥ 7 天或 ≥ 200 个样本）

- 引擎照常跑全部规则，但**只写人机对照台账，不调用 decide**。
- 人工照常审。每个人审裁决与机器意见落 `auto_review_shadow_log`（0400 表）对照。
- 每日摘要输出四指标：
  - **一致率** = 机器与人工同判 / 总数（目标 ≥ 85% 才可切执法）
  - **误杀率** = 机器拒 / 人工过（目标 ≤ 2%）
  - **漏放率** = 机器过 / 人工拒（目标 ≤ 5%，且逐例附规则命中，人工确认是否规则缺陷）
  - **减负率** = 机器可裁决数 / 总待审数（价值指标，预期 40~70%）
- 校准动作直接改阈值/关规则，改完可对历史台账**回放**（replay：用新配置重算历史样本，秒级，无副作用）——复用 0391 backtest 思路。

### 阶段二：灰度执法期

- `auto_review_mode` 从影子切「半自动」（只自动通过）→ 观察 3 天误杀/申诉 → 切「全自动」。
- 执法期影子对照**不停**：人工处理暂缓件时的裁决继续与「机器如果全权决定会怎么判」对照，长期监督漂移。
- **熔断器**：任一自然日内「人工推翻自动裁决 ≥ 5 例或推翻率 ≥ 20%」→ 自动降级为半自动 + 管理组告警（站内信+邮件）。站长可在设置页手动恢复。
- **申诉联动**：自动裁决被申诉推翻计入该规则的「误杀台账」，单规则累计被推翻 ≥ 10 例自动降级为「仅暂缓」并告警。

### 回滚

一键回「关闭」预设：mode=off。已产生的自动裁决不回滚（它们都有留痕，可人工批量纠正：管理台加「按规则反查」筛选，一键将某规则近期自动拒绝的种子批量 resume 回待审）。

## 13. 遗漏补全之一：并发、人机协作边界与冷启动（v1.2 新增）

### 13.1 与人工审核的并发（防「抢审」）

引擎取件到终裁之间有人工介入的四种竞态，逐一封死：

| 情形 | 处理 |
|---|---|
| 引擎评估中人审已裁决 | 终裁前重读 `approval_status`：已 ≠0 → 放弃裁决，仅落「人机相遇」对照行（这正是影子对照的执法期样本来源）；已 =4 暂缓 → 同样放弃，人审优先 |
| 引擎裁决后人审翻案 | 人工 decide 走现有路径正常覆盖（状态机允许），audit_log 两条并存；该样本计入熔断指标 |
| 两 worker 实例同时取件 | 取件即 CAS（`UPDATE ... SET 引擎锁 WHERE approval_status=0 AND id=?` 抢占）+ advisory lock 双保险（复用 shard_lock 模式） |
| 人审批量接口与引擎同刻批量 | decide_one 是单行收口且幂等键明确，行级竞争由数据库裁决；败者按「已裁决」分支处理 |

**裁决同尺的补强**：引擎终裁前的 0.5~2 分钟窗口里作者可能又编辑了种子（mtime 变化）→ 引擎丢弃本次评估、等待下一轮取件重评（拿最新内容裁决，避免「审的是旧版、拒的是新版」）。

### 13.2 自动裁决的人机协作定位

- **暂缓不是驳回**：POSTPONED 的语义是「机器拿不准，请人定夺」，人工处理暂缓件的界面沿用现有审核队列 + 机器意见侧栏（命中规则/分数/建议标题/深检证据），**人不看机器意见直接改判也完全允许**。
- **人工可一键「关闭此规则对该种子的影响」**：处理暂缓件时若认为规则误报，除放行外可顺手把该规则降级（写入规则反馈，进 §6 降级台账统计），反馈闭环驱动校准。
- **机器意见对发布者不可见（暂缓态）**：暂缓只给人工看；发布者侧仍是「待审核」状态，避免「机器说你有问题」引发不必要的申诉噪音。只有终裁（自动拒/自动过）才对发布者可见。

### 13.3 冷启动问题（新站没有历史人工裁决数据）

影子期四指标需要「人工裁决样本」，新站/低流量站攒不够。三层解法：

1. **信任继承（可开关，缺省关）**：把「免审通道通过的种子」也产出影子快照行（机器只记录不裁决，免审照常通过），作为「机器过 vs 站长认可」的对照样本——免审本身就是站长信任的表达，样本免费且量大。
2. **回放历史**：若站已运营过，直接对历史已裁决种子批量回放（replay 的离线版），几分钟攒出上千样本。
3. **直出保守档**：样本 < 50 时设置页统计条显示「样本不足，建议从谨慎号预设开始」，auto_pass_score 自动抬高 10 分（软约束，站长可覆盖）。

### 13.4 时间与窗口边界

- 发布后 90 秒延迟取件（缺省）之外：**排队超时升级**——待审超过 `auto_review_escalate_hours`（缺省 24h，0=关）仍无人审且机器未裁决 → 自动暂缓 + 管理组提醒「队列积压」，而不是无限等待（影子模式下同样生效，作为队列健康观测）。
- 深检中（verdict=3）超过 30 分钟未回环 → 视为深检任务死亡，自动回退为暂缓 + 告警（防深检卡死种子生命周期）。
- 节假日/审核组不在线：无特殊逻辑——自动审种本来就是「人不在时兜底」的方案，daily_cap 是唯一的流量阀。

## 15. 遗漏补全之三：可观测性与运维手册（v1.2 新增）

### 15.1 指标与告警（进现有 worker 告警通道 staff_alert）

| 指标 | 采集点 | 告警阈值（缺省） |
|---|---|---|
| 待审队列深度 | 引擎每轮取件前 count | > 50 持续 3 轮（60s 档即 3 分钟）提醒审核组 |
| 引擎评估耗时 P95 | 引擎自记 | > 500ms 告警（预算 200ms） |
| 深检任务积压/死亡 | 深检表扫描 | 死亡 > 0、积压 > 20 |
| 自动裁决推翻率（日） | 台账 | ≥ 20% 触发熔断（§6）并告警 |
| 影子一致率周环比 | 台账 | 下跌 > 10 个百分点告警（规则漂移信号） |
| 邮件发送失败率 | mailer 尽力日志聚合 | 连续失败 > 10 封告警（现无重试，见 §16 开放问题 2） |

### 15.2 台账页（`/admin/auto-review`）信息架构

- 顶部四指标卡 + 趋势（近 7/30 天）：一致率/误杀/漏放/减负。
- 中部台账列表：时间/种子/发布者/verdict/命中规则（展开看证据 JSONB）/机器分 vs 人工结果/ruleset_ver；筛选器=规则×verdict×用户×时间。
- 侧栏「规则健康度」：每条规则的命中量、暂缓转化率、被人工推翻次数、被申诉推翻次数——单规则健康度红黄绿，红线=触发 §6 自动降级。
- 操作区：回放（选时间窗+配置版本）、按规则反查批量恢复、导出 CSV。

### 15.3 运维 runbook 三条

- **误杀应急**：设置页把对应规则改「仅暂缓」→ 台账按规则反查受影响种子 → 批量恢复回待审 → 人工快审。全程不需停引擎。
- **引擎故障**：worker 挂了不影响人工审核（引擎只是队列消费者）；恢复后按 mtime 顺序补吃积压，daily_cap 可临时调大。
- **配置错误回滚**：settings 历史页（现有 history.rs）可查每次 auto_review 组变更人与 diff；ruleset_ver 快照保证历史裁决解释不变。

## 18. 终审五补（v1.3 新增：全流程资深视角走查后的最后缺口）

以「一个种子从发布到葬礼、一个用户从第一次被自动拒到申诉翻案、一个站长从装站到三年后升级」三条完整生命线走查 v1.2，补最后五个缺口。

### 18.1 申诉闭环补全（用户生命线的断点）

v1.2 只写了「邮件含申诉入口」，但申诉成功后的回流没定义，会形成「人工申诉翻案 → 引擎又自动拒回去」的死循环：

- **申诉成功的回流**：申诉通过 → 种子回待审（现有 appeal 流）。引擎复审时读取「该规则被人工推翻」记录：**同一种子 + 同一条命中规则不再自动拒**（人工已表态），其余规则照常评估；台账标注「人工推翻规则生效」。
- **被自动拒绝后的重交引导**：拒绝邮件里的「修改后重新提交」直链带预填上下文（自动定位到 descr 编辑区/命名对照），降低二次被拒率——目标是让用户的第二次提交通过率 >80%（进管理摘要观测）。
- **申诉对规则健康度的权重**：申诉翻案比普通人工推翻权重高（×2 计入 §6 降级台账），因为申诉是用户主动证明误判。

### 18.2 外部源依赖降级（引擎不能被 TMDB 拖死）

H6 命名提取与 D5 元数据交叉强依赖 PTGen/TMDB/bangumi 等外部源（探查确认 PTGen 上游可配但存在 DNS 失败前科，2026-10-05 P0）。统一降级策略：

| 情形 | 行为 |
|---|---|
| 外部源超时/5xx/解析失败 | 该规则本次**转暂缓**（外部证据拿不到=不能证明也不能证伪），绝不因源不可用而拒或放 |
| 连续 N 轮（缺省 5）失败 | 该源标记降级 + staff_alert 告警「TMDB 持续不可用，D5 已批量转暂缓」；恢复探测成功后自动回归 |
| 站长未配任何外部源 | D5 自动关闭（配置面隐藏该项），H6 退化为纯词表模式（无对照，只查要素存在性） |
| 缓存 | 外部源查询结果缓存（缺省 24h，键=源+外部 ID），避免同一种子深检回环重复打上游 |

### 18.3 金标准回归集（规则的「测试金字塔」尖）

纯函数评估器（§9）的最大红利是可以建标注样本集，防止「改一条规则、三个月后另一条悄悄坏掉」：

- 仓库内置 `auto_review_corpus/`：≥60 例标注样本（标题/descr 片段/文件清单/期望命中/期望分数段），含对抗样本（乱码混正常、广告词拆字、相似但不重复的标题对、H5 边界相似度、严格档顺序偏差、音乐假无损）。
- CI 门禁：全规则对样本集回归，命中/分数与基线 diff → 红；改规则必须同步改样本并说明理由（对齐本仓 route_manifest/i18n 基线纪律）。
- 影子数据反哺：影子台账里人工与机器不一致的典型案例，经人工确认后脱敏加入样本集——规则集越用越准的飞轮。

### 18.4 站长手册章节（受众=完全不会终端的站长）

按本仓《站长手册无终端纪律》，新增 `docs/webmaster/auto-review.md`（随 sync.mjs 上 wiki），三路并行给步骤（面板双击/本地改传/nano）：

- 「三分钟开起来」：影子模式开箱 → 看七天摘要 → 切半自动 → 切全自动（每步一张截图位）。
- 「读懂四指标」：一致率/误杀/漏放/减负的人话解释 + 「指标不好该怎么办」决策树（误杀高→哪类规则降级；减负低→哪个阈值抬高）。
- 「我要改规则」：改一条命名模板/加一个广告词/套站型预设的点击路径。
- 「出事了怎么办」：误杀应急 runbook 的站长版（§15.3 的白话版）。
- 「常见问答」：机器会不会误杀好人？被拒用户收到什么？影子模式要一直开吗？关掉会怎样？

### 18.5 版本升级与数据安全（三年生命线）

- **出厂包升级安全**：0402 site_packs 带出厂版本号；系统升级带新预设包时，**站长改过的键永不覆盖**，配置页出现「有新预设可套用」横幅+差异摘要；套用新包后**自动回到影子模式一个校准窗**（缺省 3 天）——新预设 = 新规则行为，必须重新校准（对齐 §6 影子纪律）。
- **ruleset_ver 连续性**：升级不重置版本号；历史台账可永远回放。
- **卸载路径**：关停自动审种 = 预设「关闭」；表与台账保留（审计要求），`auto_review_log` 进现有 audit_retain 归档策略；不提供删表（留痕不可销毁，对齐 audit_log 防篡改纪律）。
- **多实例横向扩展**（G30 部署形态）：引擎取件 CAS+advisory lock 天然多实例安全；深检并发 ≤2 是**每实例**上限，总并发=实例数×2，daily_cap 全站口径（Redis 计数）。
