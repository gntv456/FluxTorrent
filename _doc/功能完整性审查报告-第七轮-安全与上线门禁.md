## 2. 发现并修复的缺陷（P1，本轮唯一代码改动）

**种子详情族 4 个端点未鉴权，站点内容对公网裸奔**（`apps/api/src/http.rs`）：

| 端点 | 修复前 | 修复后 |
|---|---|---|
| `GET /torrents/{id}/detail`（简介/热度/魔力答谢） | 200 匿名可读 | 401 |
| `GET /torrents/{id}/files`（文件清单） | 200 匿名可读 | 401 |
| `GET /torrents/{id}/thanks`（答谢名单） | 200 匿名可读 | 401 |
| `GET /torrents/{id}/comments`（评论） | 200 匿名可读 | 401 |

根因：actix handler 签名里没有 `req: HttpRequest`，也就没写 `require_auth()`——与同文件 `list`/`detail`（均鉴权）不一致，属漏写而非设计。PT 站种子元数据是站点准入资源（`list` 的注释「站点准入收口：资源元数据不对外」即此口径），这 4 个端点是**绕过该收口的旁路**。修复：四个 handler 补 `require_auth`。

## 3. 安全探测结论（62/62 PASS）

- **管理面鉴权**：20 个 `/admin/*` + `/staffpanel` 端点，无认证全部 401、普通用户全部 403，无一漏网（含 `/admin/settings/schema` 的 staff 可见不可写分级）。
- **越权**：普通用户改/删他人种子 403；管理面用户详情 404（路由不存在于其视野）；伪造 `X-Role/X-User-Id` 头无效（鉴权只信 JWT + 库内 class）。
- **JWT**：alg=none、坏签名、篡改 payload 提权（class_id→99）全部 401——签名密钥校验有效，且 class 以库为准（此前轮次已验证）。
- **SQL 注入**：6 组探针全部参数化（200/400，无 SQL 错误信息泄漏）。
- **登录爆破限流**：同用户名第 6 次起返回业务码 1015（HTTP 400 + RateLimited）。注意：**本站限流约定是业务码而非 HTTP 429**，客户端必须读 `code` 字段；QA 脚本已按此口径断言。

## 4. tracker 协议链路（7/7 PASS）

- 正常 announce：200 + bencode，**`interval=1800` / `min interval=900` 正确下发**（读自 `site_settings.announce_interval`）。
- 坏 passkey：bencode `failure reason: passkey 无效`（BT 客户端约定 200 + failure reason，非 HTTP 4xx——脚本首轮误判，已按协议口径修正断言）。
- scrape（BEP48 `/scrape/{passkey}`）：正常 200 返回 files 字典；坏 passkey 拒绝。
- info_hash 长度校验（10 字节 → 拒绝）、peer_id 长度校验均生效。
- **部署坑（已处置）**：本地栈 tracker 容器曾运行旧镜像（代码已改、镜像未重建），interval 实测缺失；`docker compose build tracker && up -d tracker` 后通过。上线 SOP 必须整栈重建，禁止只 up 不 build。
