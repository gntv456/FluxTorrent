0. 先把六个词定义清楚

没有指标的目标只是口号。下面这张表是本方案的总纲——每条动作最终都要能对回这里的某一格。

最强

能力覆盖面不输任何竞品：列表 3 视图、筛选维度对齐 UNIT3D、详情页有 peers / 磁力 / 书签 / 相似 / 聚合。

最精细

筛选粒度到字段级：促销多选、健康度四态、体积/时间/种子/下载/完成数区间、动态维度、chips 逐项可移除。

性能最好

排序查询走索引（EXPLAIN 无 Sort）、详情页 SQL ≤4 条、热门页命中缓存 >90%、列表 P95 <120ms。

最顺手

任何操作 <100ms 内有反馈，翻页不丢行，批量/快捷键/hover 预览可用，键盘可达。

体验最好

三态（加载/空/错误）齐备，移动端零横向溢出，图片不抖，首屏可交互。

维护方便

同一语义只有一份实现、关键谓词有单测、契约漂移自动拦截、改一行 Rust 不全量重编译。

第 0 步（必须先做）：建立性能基线。仓库当前没有慢查询日志、pg_stat_statements、EXPLAIN 脚本、压测脚本（审计 §5 全项「未找到」）。没有基线就无法证明「性能最好」，也无法在改造后证明没有退化——所以基线采集是本方案的第一件事，不是最后一件。

2. 阶段一 · 正确性与地基

目标：先把错的改对、把慢的根因拔掉。这一阶段不新增任何用户可见功能，但所有后续阶段都建在它上面。

P0 · 动作 1

补齐三个缺失索引（最高性价比）

成本 1 条迁移 · 收益：消除两次全表扫描

files(torrent_id)、thanks(torrent_id)，以及为排序准备的复合索引。受「迁移在事务内执行」约束（0142 注释），不能 CONCURRENTLY，因此分两步：先在低峰窗口建，或在迁移前用带外脚本预建。

验收：对 /torrents/{id}/files 与 /thanks 各做一次 EXPLAIN (ANALYZE)，计划里必须出现 Index Scan 而非 Seq Scan；前后耗时数字记入基线表。
P0 · 动作 2

修游标分页：keyset 与 ORDER BY 对齐

成本 1 处 SQL + 1 处游标编解码 · 收益：修正确性 bug

当前翻页只比 t.id，而排序键是「置顶 + 排序列 + id」。改法：游标携带 (sticky_rank, sort_value, id) 三元组，谓词改为字典序比较 (a,b,c) < ($1,$2,$3)；同时把 sticky_expr 从计算列改名为物化列 sticky_rank smallint（由置顶变更处与 worker 维护，到期回落），这样排序与索引才能真正对齐。

验收：写一组「全部种子按 seeders 排序，逐页抓取直到结束」的测试，断言累计抓取的 id 集合 == 一次性全量查询的 id 集合，且无重复、无遗漏。这条测试进 CI。
P0 · 动作 3

排序走索引 + count 降级

成本 1 条迁移 + 1 处 SQL · 收益：列表页最贵的两处开销

  • 为常用排序建复合索引：(sticky_rank DESC, seeders DESC, id DESC)、(sticky_rank DESC, size DESC, id DESC)、(sticky_rank DESC, created_at DESC, id DESC)、(sticky_rank DESC, times_completed DESC, id DESC)。
  • count(*) 三档降级：首页/无筛选 → 沿用缓存；带筛选 → 优先用估算（reltuples 或对采样集算）；仅当用户滑到末页或点「精确总数」时才做精确 count。
  • 把「列表缓存」从「只有纯净首屏」扩到 (filter_hash, sort, cursor) 维度，短 TTL（15–30s），写路径按 torrent:* 前缀失效。
验收：五种排序各跑 EXPLAIN (ANALYZE, BUFFERS)，计划中不得出现 Sort 节点（除 comments 排序）；列表 P95 与基线对比不劣化，目标 <120ms。
P0 · 动作 4

详情页合并为 BFF 聚合端点

成本 1 个 handler + 前端改一处 · 收益：10 次 RTT → 3 次

新增 GET /api/v1/torrents/{id}/aggregate，把详情页首屏需要的数据（种子主体 + 详情扩展 + 文件列表 + 感谢计数与首屏 + 评论首屏 + 分组 + NFO + 标签）在一次请求内并行折叠；字幕与下载记录保持独立（它们依赖模块开关与懒加载）。顺带消除 comments/thanks 计数在两处重复聚合的问题。

验收：详情页首屏 HTTP 请求数 ≤3（文档 + 聚合 + 静态资源）；nfo 不再串行；首屏 TTFB 数字进基线表。
P0 · 动作 5

促销口径收口成唯一来源

成本 1 个 SQL 片段模块 · 收益：消灭一类漂移 bug

把「促销命中 + 优先级排序」抽成唯一的 SQL 片段构造函数（一处定义 kind 优先级与 scope 展开），列表 SELECT、count、RSS、compat 层全部引用它；同时把列表里重复两遍的 promotion / promotion_ends_at 子查询合并为一次 LATERAL 取两列。

验收：全仓 grep 促销优先级 CASE p.kind 只应出现在一处；RSS 与网页对同一筛选集合返回的种子集合一致（加一条对照测试）。
P0 · 动作 6

修 chips 逐项移除 + 三态补齐 + 等待态

成本 3 处前端小改 · 收益：用户体感立刻变好

  • 多选参数（分类、sec_*、未来的促销多选）每个值生成独立 chip，移除时只删该值，串空则删 key（改 withParam 增加「删值」语义）。
  • 补三态：torrent-tags 不再静默 return null；torrent-subtitles 区分空与错误并给重试；列表接口失败不再降级成「无数据」而是显示错误态与重试。
  • 排序/翻页/筛选加 useTransition 或路由 pending，保证 <100ms 内有视觉反馈（骨架/进度条/链接态）。
验收：手工回归「选 3 个分类 → 逐一点掉 chip」应逐个减少；断网/500 时三个客户端组件都出现明确错误提示而非空白。
P0 · 动作 7

地基：基线 + 单测 + 契约门禁

成本 3 项工程配置 · 收益：让后面所有阶段可被验证

  • 观测基线：开启 pg_stat_statements 与慢查询日志（log_min_duration_statement），加一个 scripts/explain_torrent.sh 一键输出列表/详情关键查询的执行计划，产物入 _doc/性能基线.md。
  • 单测：为 extra_preds / 列表谓词 / 计数谓词写 Rust 单测（覆盖每个筛选维度单用 + 组合 + 边界），并把 web 的 vitest 接进 CI（build-test.yml 加一步）。
  • 契约：给 domain-types 加最小 drift 校验任务（对比 Rust 枚举/错误码/关键 DTO 字段名），并把 TorrentDetailRow 补进共享契约。
验收：CI 里能看到 4 项新门禁；任意改一个筛选谓词若破坏语义，单测必须红；后端改字段名而不改 TS，drift 任务必须红。

3. 阶段二 · 形态与体验

目标：把「有维度但不顺手」变成「顺手得像 UNIT3D」。这一阶段几乎全是前端形态改造 + 缓存层，后端查询不再动刀。

2.1 列表三视图：表格 / 卡片 / 海报墙

数据侧 t.poster 已经在列表查询里返回（list_noclamp_as.rs:175），所以这是纯前端与 URL 状态改造：新增 view 参数（table|card|poster），海报墙走非对称网格 + 懒加载 + 骨架占位。视图偏好记入用户设置。

2.2 筛选实时化：URL 状态 + 软导航

保持「所有筛选在 URL」这个已有优势，把提交式表单换成客户端组件 + router.replace（带 debounce），业务逻辑仍在 API 侧。不引入 Livewire 式全栈耦合。

2.3 每页条数可配 + 无限滚动可选

默认 20 / 上限 50 从硬编码移入 site_settings（运营可调），前端提供 20/50/100 选项。

2.4 详情页五个缺口：磁力 / peers / 书签 / 相似 / 截图

磁力：有 info_hash + passkey announce，成本最低，先做。
书签：bookmark_count 字段已在类型里，只差 UI 与列表筛选项。
peers 列表：实时 peer 只在 tracker 进程内存（apps/tracker/src/peers/table.rs），API 无桥接——需要新增「tracker 暴露 swarm 快照（Redis key 或内部 HTTP）→ API 查询」链路，属于新基建，放在本阶段末尾。
相似推荐：先用零新基建的口径（同分类 + 同标签 + 同 IMDb）上线，后续再评估向量/外部元数据。
截图：需要 screenshots 表 + 上传入口 + 画廊组件。

2.5 缓存层补全

详情页静态部分（简介/文件/MediaInfo/NFO/标签/分组）按 torrent:{id}:* 做 30s 缓存 + 写失效；字典类（site-profile / section-dict / tags-dict）用 unstable_cache 长 TTL；site_settings 加通用 TTL 缓存（参照 module_flags 的 30s 模式）。

2.6 图片与首屏

海报/封面接入 next/image（或至少补 width/height + decoding="async" + 首屏 priority），列表卡片图走固定比例容器防抖。

阶段产出定义：列表页支持三视图切换且偏好落库；任一筛选操作页面不整刷；详情页有磁力与书签；热门详情页缓存命中率 >90%（Prometheus 加一个 cache hit/miss 计数器）。

4. 阶段三 · 精细与生态

目标：把「能用」推到「最强最精细」，并把运维代价压下来。

  • 筛选粒度对齐竞品：促销改多选、健康度扩四态（含濒危/墓地口径）、补「我做种中 / 我下载中 / 未下载」、书签与心愿筛选项。
  • 列表行内的信息密度：促销倒计时 hover、用户自己的下载进度条、内部组/官种徽标（对齐 UNIT3D 与华语站 U2 的进度四态）。
  • 聚合层：从「同组版本」扩展到 Collection（策展合集）与 Series（系列），让「作品」真正成为一等公民。
  • 评论增强：点赞、排序、嵌套回复（当前是平铺）。
  • 批量与键盘：多选批量下载（先做「批量复制下载链接」低成本版）、快捷键（/ 聚焦搜索、j/k 移动、d 下载）、hover 预览卡片。
  • DOM 语义契约：给列表加稳定的语义类（table.torrents / data-torrent-id / pro_free），让油猴脚本生态零成本适配——这是竞品调研里被打分最高的一条隐性资产。
  • 构建提速：docker/api.Dockerfile 引入 cargo-chef 分层（依赖层与代码层分离），把「改一行 Rust」的镜像重建从全量重编译降到只编业务 crate。
  • 观测与压测：列表/详情加直方图指标（P50/P95/P99）、慢查询 Top N 面板、scripts/bench_torrent.py 并发压测脚本进 CI（只跑冒烟档）。
  • 运维堵漏：worker 健康检查（写一个 /healthz 或心跳 key）、迁移前 LF/checksum 预检、ADR 目录（_doc/adr/NNN-*.md）把本次关键取舍记录下来。
阶段产出定义：列表信息密度达到 UNIT3D 同级；详情页五大缺口全部补齐（peers 视新基建进度）；发布一版 ghcr 镜像用 cargo-chef 后，实测镜像构建时间显著下降并记入文档。

6. 不做清单（控范围）

「最强」的反面是范围失控。以下明确不做或延后，理由写清：

  • 不引入第二套运行时（不上 Livewire 式全栈耦合、不引入 SPA 框架）：理由见竞品调研——双轨并存是 NP 最大的技术债源。
  • 不引入外部搜索引擎（Meilisearch/ES）作为主搜：pg_trgm + GIN 在十万级够用，等到出现明确的搜索质量投诉再评估，且必须保留 pg_trgm 兜底。
  • 不做向量相似推荐作为第一步：先用零基建口径（同分类/标签/IMDb）验证用户是否真的用，再决定是否上重武器。
  • 不把计费逻辑移回同步路径：任何「实时性」优化都不得让 announce 重新直写 DB。
  • 不做 big-bang 重写：所有改造必须可在单次发布内回滚。
  • 不抄 hack 式插件生态：需要扩展点就做契约化模块，不走 XBTIT 那种「升级要重打补丁」的路。
