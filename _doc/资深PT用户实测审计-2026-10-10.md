# 资深 PT 用户实测审计（2026-10-10）

口径：以一个用了八年 PT 的站员的日常动线走全站——进保种区认领、被 H&R 后查后台、
发求种、应求、交字幕、建合集、订阅 RSS、心愿单——只问一件事：**这条链路的下一环有没有真的接上**。
环境：本地栈 `flux-api/flux-web/flux-worker/flux-tracker + postgres + redis`，
站长（class 99）与非管理成员双视角，接口层与渲染层各验一遍。


> 同日续批：娱乐屋与农场土地阶梯见 `_doc/资深PT用户实测审计-批五-娱乐屋与农场-2026-10-10.md`
> （大厅聚合 500 的 i64→int4 绑参、农场 e2e 一条过期断言、写闸 e2e 九条口径漂移 + 一条待定性的 EV 数字）。
## 一、已修（附现场证据）

### A1 后台 H&R 总览整页 500 —— 一行脏流水炸全表
- 现象：`GET /api/v1/admin/hr/records` → 500，api 日志 `error occurred while decoding column "uploaded": unexpected null`。
  现场 `hr_snapshots` 共 7 行，其中 1 行的 `snatches` 已不存在。
- 根因：H&R 义务存在 `hr_snapshots`，上传/下载量却是读时从 `snatches` 现取（LEFT JOIN），
  而 `HrRecordRow.uploaded/downloaded` 声明成非 Option 的 `i64`。快照存续期间流水可被清理
  （复活任务、账号清理、级联删），LEFT JOIN miss 即 NULL → 解码失败。
- 修法：两列改 `Option<i64>`；后台 `admin-hr.tsx` 对应两格在无流水时显示「—」，
  不再把 `null` 静默算成 0G（`null/1024**3` 在 JS 里是 0，比 500 更难发现）。

### A2 成员「我的种子·保种中」500
- 现象：`GET /api/v1/users/{id}/torrentlist` 在该成员认领了保种但没有下载流水时 500。
- 根因：`user_torrentlist.rs` 的 preserved 查询 `CASE WHEN $3 THEN s.seeding ELSE false END`——
  `ELSE` 只在**非本人/非管理**时兜底；本人或 staff 看（reveal=true）时读的是 LEFT JOIN
  后的 `s.seeding/s.leeching/s.uploaded`，无 snatch 行即 NULL，而 `SnatchRow` 三列都是非 Option。
- 关键：`POST /preserve/claim` 不要求先下载，「认领但无流水」是**正常动线可达**状态，
  不是异常数据。修法：三列各配 `COALESCE(..., false/0)`。

### A3 加入复活队伍 500（删号留下的孤儿队伍）
- 根因：`admin_http/user_del.rs:120` 删号会 `DELETE FROM resurrections WHERE user_id=$1`，
  但 `social_team` 行不动 → 队伍失去关联资源。`social_http/team.rs` 的 join 查询
  把 LEFT JOIN 出来的 `r.torrent_id` 按 `i64` 解码；同一份 JOIN 在 `team_members.rs`
  早已按 `Option<i64>` 读——两套规则里被改漏的是 join 这条。
- 修法：改 `Option<i64>`，孤儿队伍按「该队伍已结束」拒绝加入（与相邻状态分支同文案，不新增未译串）。

### A4 保种区筛选：「已移出」直接白屏，「延续中」选了等于没选
- 现象（渲染层实测）：`http://127.0.0.1:3000/preserve?status=expired` → **HTTP 500**；
  `status=grace` 返回的是**未过滤的全量在保**列表。
- 根因：`status=expired` 走独立早退分支，只回三列裸数组 `[[id,name,size]]`，
  而 `data-content.ts getPreserve()` 按 `{items,total,stats}` 解构 → `stats.preserving` 抛错；
  `grace` 档位后端只在注释里写过，SQL 里没有任何对应判定。
- 修法：四档统一走同一条查询、同一个信封；宽限证据取 worker 出种时挂的
  `promotions(source='preserve_grace')` 3 天窗口——
  in=在保全部 / active=保种中（已认领）/ grace=延续中（已移出且宽限未过）/ out=已移出（宽限已过）。
  列表与计数共用一份视图判定片段，避免两处各写一份再漂移。

### A5 保种区「只进不出」棘轮：移出后永远回不了区
- 根因：灌入作业 `worker/src/jobs/class_adj.rs` 的准入条件是
  `NOT EXISTS (SELECT 1 FROM seed_preserve WHERE torrent_id = t.id)`，
  而行是 `ON CONFLICT DO NOTHING`——一旦某颗种子进过保种区并被移出（`exited_at` 置位），
  这行永久存在，日后它掉回 0 做种也**再也进不了保种区**，`preserve_exit` 的
  「seeders > 阈值才移出」于是成了单向门：站龄越久，保种区越空洞。
- 修法：准入把「已移出的行」视同可重入，`ON CONFLICT DO UPDATE` 重开该行
  （清 `exited_at/exit_reason/claimed_by/claimed_at/last_settle_at`），在保未移出的行不受影响。

### A6 求字幕「在身 3 单上限」fail-open
- 根因：`subtitles_flow.rs` 数在身单的 SQL 里多写了一个转义引号
  （`FROM subtitle_requests \"`），Postgres 报 42601，而外面是 `.unwrap_or(0)`——
  错误被吞成「0 单在身」，上限**永不触发**，一个成员可以把求字幕全占住。
- 修法：去掉那个引号，并把它和相邻的弃单计数查询一起改成错误外抛：
  资金/名额类闸门宁可拒绝操作，也不能在 DB 抖一下时放行。

### A7 求种板两个计数器长期假 0
- 现象：表格里「评论数 / 应求数」两列恒为 0（接口直接写死 `"comments": 0, "bids": 0`）。
- 根因：`comments` 只挂 `torrent_id`，`offers` 表**没有 request_id**——求种与候选之间
  没有外键，这两个数在数据模型里根本不存在。假 0 会被读成「没人应求」，直接劝退应求的人。
- 修法：接口改回 `null`，界面渲染「—」；真正的「求种↔候选」关联见待拍板 P-1。

### A8 求种板标题链到不存在的详情页
- 现象（渲染层实测）：`http://127.0.0.1:3000/requests/1` → **HTTP 404**，
  而求种板与卡片的标题都是 `<a href="/requests/{id}">`；后端也没有单条求种接口。
- 修法：两处标题改纯文本，等详情页立项后再挂回去。

### A9 保种区分页基准不一致
- 根因：全站列表分页统一走 `dto::page_window`（1 基），唯独 `/preserve` 用
  `page * per` 且 `page` 缺省 0——客户端照惯例传 `page=1` 会翻到第二页（首页整页空白）。
- 修法：改 1 基，缺省即第一页。

### A10 公开资料页「种子列表」——凡有行必 500（P0）
- 现象：`GET /api/v1/users/{id}/torrentlist` 对**任何有内容的用户**都 500，
  api 日志 `no column found for name: approval_status`。uid=1（有上传记录）实测 500，
  而两个空列表用户返回 200——空结果集不解码，所以问题被「没人用」掩盖着。
- 根因：`http::SnatchRow` 带 `approval_status/deny_reason` 两个 Option 字段
  （注释写明「仅 kind=uploads 填充」），但只有 `/me/torrentlist` 的 uploads 查询真的投影；
  公开资料复用同一结构体的 6 条查询都不投影。sqlx 对 Option 字段只容忍 NULL，
  **不容忍「列不存在」**，一解码就报错。
- 修法：两个字段加 `#[sqlx(default)]`（缺列即取 Default=None），序列化侧的
  `skip_serializing_if` 保留，响应形状不变。

### A11 用户中心「活跃会话」整卡 500（P1）
- 现象：`GET /api/v1/me/sessions` → 500，日志
  `decoding column "ip": Rust type String (as SQL type TEXT) is not compatible with SQL type INET`。
  `apps/web/components/sessions-card.tsx` 正是这卡的读口。
- 根因：`login_events.ip` 是 `inet`，`me_sessions.rs` 直接把它投影给 `ip: String`。
  同一张表的其他三处读口（`me_history.rs` / `admin_http/records.rs` / `staff_http/ipcheck.rs`）
  一贯写 `host(ip) AS ip`——又是「两份规则里被改漏的那一份」。
- 修法：改 `host(ip) AS ip`（与同表其余读口同口径）。

### A12 种子导出整页 500（无主种子）+ 审核通知的假警告
- `GET /api/v1/admin/export/torrents` → 500，日志 `decoding column 2: unexpected null`。
  `export_ops.rs` 用元组 `(i64, String, i64, …)` 解 `t.owner_id`——该列可空
  （站方代发/系统导入的种子没有上传者），一行无主种子就让整页导出不出来。
  同文件的用户导出早就把 email 写成 `Option<String>`，只有种子这条漏了。
- 同一列在 `admin_http/review_notify.rs` 里也按非 Option 解，但它外面是
  `let Ok(Some(..)) = row else { warn; return }`：不炸页，却把「这种子无主」
  当成「取数失败」天天写警告，真出故障时反而被噪声淹掉。
  改成 `Option<i64>` + 分支：无主→静默跳过（本来就没有可通知的上传者），
  查询真错→才 warn。
- 顺手做了个交叉核对：把全站「元组解码」的读口与 `information_schema` 的可空列
  对了一遍，除这两处外没有第三处（脚本 `_tmp_nullscan.py` 的思路值得做成常驻
  门禁：非 Option 位置命中可空列即红，与既有的 i64→int4 绑参盲区同族）。

### 顺手验过、没发现问题的动线（记录以免重复排查）
- 2FA 全环：`setup → enable(需当前 OTP) → 无 OTP 登录被 2010 拒 → 错 OTP 被 2011 拒 →
  正确 OTP 登录 200 → 失败登录按 reason=2 落 login_events`，链路完整。
- RSS：`/rss/{passkey}` 200（26KB XML）、伪 passkey 400、`/rss/forum/{passkey}` 200。
- 心愿单：add → 列表可见 → remove 生效；上限 20 条、`ON CONFLICT (user_id, keyword)` 幂等。
- 合集：root 建 → 列表/详情读得到（但成员建不了，见 P-4）。
- 互动：thanks（含 spark_given 记账）、评论发布与读取、给自己评论点赞被正确拒绝；
  收藏是 `PUT /torrents/{id}/bookmark {on:bool}`。
- 种子评分：本站没有「用户评分」写口（`rating` 是外部元数据，`rating_min` 只筛它），
  不是断链，别按 UNIT3D 的 user-rating 找。

### B1 主收件箱把「已归档」的信也列出来（P2）
- 现象：新建自定义文件夹 → 收信 → 移动进文件夹 → 文件夹计数正确变 1，
  但 `/messages/inbox`（不带 `box_id`）仍返回这封信；界面上同一封信在
  「收件箱」和「AB夹」里各出现一次。
- 根因：`message.rs` 的 inbox 过滤写的是 `($2::int IS NULL OR m.folder = $2)`，
  而它自己的字段注释与 `message-center.tsx`（`folder=null` 即主收件箱）都是
  「缺省 = 主收件箱（folder IS NULL）」。缺省时条件整体短路成「不过滤」。
- 修法：改 `m.folder IS NOT DISTINCT FROM $2::int`——NULL 也参与等值判断，
  缺省即只看主收件箱，带 `box_id` 时照旧只看那个文件夹。

### B2 界面「拒绝好友申请」实际把对方变成好友（P1，语义反转）
- 现象：`friends-actions.tsx` 两个按钮都打 `POST /friends`：
  「接受」带一个后端根本不认的 `action:"accept"`，「拒绝」裸调用。
  后端 `friend_create` 的口径是「对方也申请过我 → 双向转正」，
  于是实测：B 申请 A → A 点「拒绝」→ 关系直接变 `friend`。
  而 A 点「接受」时那个多余的 `action` 字段被 serde 忽略，反而侥幸走通。
- 另一半：`POST /friends/action` 只认 `black / unblack`，
  所以任何用 `accept` 的写法都会 400「action 需为 black / unblack」。
- 修法：后端补 `accept`（校验确有 incoming pending，双向转正并按既有口径
  给对方发「好友申请已通过」系统信；无申请可处理时报「没有待处理的好友申请」）
  与 `reject`（只撤掉对方的 pending，不通知，NP 同口径）；
  界面两个按钮改打 `/friends/action` 的 `accept`/`reject`。
  两条新校验串已进 `validation_details.tsv` 三语表并收缩棘轮基线。

### B3 `users.notify_topic_reply` 是假开关（P2）
- 现象：论坛回帖通知走 `notify_user()`，它无条件 `INSERT INTO messages`；
  而个人设置页里「有人回复我时通知我」这项改了也没用——全站只有
  设置读写处引用过这个列（grep 仅此一处），没有任何消费方。
- 修法：`post_write.rs` 加 `reply_pref_wanted()` 闸门，楼主通知与楼中楼
  被回复通知都先读接收方偏好；读不到（用户已注销等）按站点缺省 true 处理，
  宁可多发也不静默吞通知。

### B4 顺带验过、没问题的
- `accept_pm` 三态（yes/friends/no）确实在发信路径被消费，好友判定正确；
- 回复引用（`Re:` 前缀 + 「原信」引用）与转发（`Fw:`）都按
  `(receiver_id = 我 OR sender_id = 我)` 取原信，指不到别人的信——无越权读取；
- push：vapid 公钥可读，`p256dh` 会真校验长度（假订阅被拒），
  未订阅时 `/push/test` 明确报「尚未订阅推送」；
- `/messages/move` 校验文件夹归属（不是自己的文件夹报「目标文件夹不存在」）。

### B6 `/friends` 返回元组数组，两个消费端一起读到空（P1）
- 现象：`friend_list` 用 `Vec<(String, String)>` 解码，JSON 就成了
  `[["bob","incoming"], …]`；而 `packages/domain-types` 里声明的
  `FriendItem` 与 `friends-actions.tsx` 的 `FriendRow` 都是 `{username, list}`。
- 后果（实测）：
  · `/friends` 页面 `friends.filter(f => f.list === "friend")` 恒为空 →
    好友页永远是空的，黑名单同理；
  · 「收到的好友申请」那段根本不渲染（`r.list` 恒 undefined）→
    即使后端有了 accept/reject，用户也点不到；
  · 这正是 B2「拒绝按钮打错接口」能长期潜伏的原因——那段 UI 从来没人看见过。
- 修法：`friend_list` 改回具名结构体（`FriendRow{username,list}`）序列化，
  与 domain-types 的声明对齐。
- 顺带记下门禁盲区：`check_type_drift.mjs` 只比对**有具名 struct** 的读口，
  元组返回没有比对锚点，所以这条一路绿灯。要么给守卫加「返回元组的
  query_as 一律要求具名 struct」，要么在 TS 侧按 path 反查形状——先记着。

## 二、批三实测：钱与物的账（结论：本轮没发现缺陷，但记下口径与两处旁路）

以真实新号走一遍：商店购买、银行定期/活期、签到、任务、勋章佩戴、装扮、券、资金池。
逐条与库内对账：

- 商店：单价 1000 扣得准（`spark_ledger` 一条 `shop/-1000` + `shop_orders` 一行）；
  **同一 `idempotency_key` 重放不再扣款**（`replayed:true`、余额不变），
  换新键可连买第二单——0207b 的语义成立；`/shop/buy` 缺键直接 400，
  两个 web 调用点（`buy-button.tsx`、`dressup/_inner.tsx`）都真的带键。
- 银行：定期 50000/30 天扣本金、预估利息 123 与 `fixed_rates` 一致；
  提前支取按 `penalty_bp=50bp` 罚 250、实付 49750，回到余额后总额自洽；
  活期存入 1000 记账 `bank_demand_in`，取出超余额被 400 拒。
- 签到：首次 200（含 `streak/base/gacha_ticket`），同日重复被「今天已经签到过啦」拒。
- 券 / 资金池：用不存在的券被拒；`/magic-pool` 捐献入账 `pool_donate`，
  `/pool/honor` 读得到捐赠榜（模块开关处已接）。
- 勋章：`/medals` 14 枚、`max_worn=3` 读得到；佩戴未拥有勋章返回 `cleared`
  （即清空佩戴）——语义是「不拥有就不戴」，没有报错但也谈不上反馈，记一笔。

结论：这条线上**没找到会算错钱的缺陷**，两处旁路（P-9/P-10）与一处弱反馈记在待拍板里。

## 三、批四实测：论坛权限门与关注链（结论：门是硬的，闸门常驻）

以低阶成员（class 1）+ 站长双视角，把板块门槛 `minclassread` 抬到 5 后逐个读侧验：
`/forums`、`/forums/boards`、直读板块（403）、`/forums/feed` 关注流、`/forums/search`、
`/rss/forum/{passkey}` ——**六处都不漏标题**；受限板块内的真 poll 主题投票拿 403
（权限判定在业务查询之前，不会用 404/403 的差别泄露主题类型）。
版主治理：普通用户 `manage` 与删他人主题一律 403、且不落库；站长锁帖后回帖被
「主题已锁定」拒，解锁后恢复；`locked/sticky/digest` 三个标记都真落库。
关注链：关注用户 → 对方发新主题 → 关注者收到站内信；关注主题 → 他人回帖 → 收到通知；
自关注被拒、关注不存在的目标 404、`/follows/mine` 三个维度都读得到。

顺带排除两个假象（都读代码定案，没留下改动）：

## 七、批七实测：种子生命周期链（结论：挖出一条 P0，全站种子编辑从来没有成功过）

沿「发种 → 改资料 → 删进回收站 → 恢复 → 被拒 → 重提 → 过审」这条线逐环走，
每一环都在接口回吐与库两处各验一次，否定式断言都配正控。

### C1 `PUT /torrents/{id}` 100% 500（P0，种子编辑整条断）

- 现象：任何用户改任何字段（只改正文也算）都回 `code=1000 内部错误`；
  api 日志一句 `syntax error at or near "//"`。
- 根因：`apps/api/src/torrents/interact.rs` 的 `edit_torrent` 里那段
  `r#"UPDATE torrents SET …"#` 中，有人把 Rust 风格的 `//` 注释粘进了
  **SQL 字符串内部**。Postgres 不认 `//` 是注释（它是整除运算符），
  整条 UPDATE 直接解析失败。Rust 侧看不出来：注释在串内，编译与
  `cargo check` 全绿——这类 bug 只有真打一次才知道。
- 修法：注释提到 Rust 侧；顺带在源码里写明「串内注释只能用 `--` 并另起一行」。
- 复验：改前 `PUT` 一律 500；改后同一请求 200，正文落库、其余五件套
  （名字/短标/IMDb/封面/MediaInfo）与标签、维度一根没掉；
  正控是同一条 PUT 改得动短标（证明写通道真的活着，不是「本来就那样」）。
- 新门：`scripts/sql_comment_guard.py`（已进 CI）扫 `.rs` 字符串字面量里的
  `//`。口径按「零误报」设计——只认原始串与首词是 SQL 关键字的常规串，
  因为字符串配对正则会「从上一个串的收尾引号配到下一个串的开头条引号」，
  把中间正常的 Rust 注释误判成串内注释（首版就误报 6 处，收到 0 处才信）。
  全站现存 0 处。

### C2 发种表单的 IMDb 栏填了等于没填（P1，字段两处落点只认一处）

- `UploadForm.imdb` 只写进 `media_info.imdb`，而详情页、编辑回填、审核台、
  `?imdb=` 同片并集读的都是 `torrents.imdb_id` **列**；该列在上传时只从
  正文/种名里正则提取。库里 `media_info ? 'imdb'` 的行数为 0，
  列也全空——即两个落点实际都没吃到用户手填的那一栏。
- 佐证：存量 e2e 里写着「直接给两个种子写 imdb_id（模拟发布链路提取）」，
  即测试早就绕开了这条链。
- 修法：上传时按 ①表单栏 ②正文 ③种名 的优先级走**同一条**正则
  （`extract_imdb`，整条 IMDb 链接也吃得下），并在表单栏非空却解析不出编号时
  直接报错，不再静默收下。

### C3 编辑口对非法 IMDb 静默丢弃（P1，假成功）

- 旧逻辑：非空但不合 `TT+7~8` 形态 → 回落 `None`，而 `None` 的语义是
  「这个字段不动」，接口回 200。用户手滑填了 `abc`，页面提示保存成功，
  刷新后原值还在——三重误导。
- 修法：三态明确化：未填 = 不动；空串 = 清空（SQL 侧用
  `CASE … NULLIF($10,'')`，此前空串会写入 `''` 而不是 NULL）；
  非空必须解析得出编号，否则 `Validation`（校验详情已进 i18n 译文表）。
  发种口与编辑口共用同一把正则与同一句提示，防两处规则再漂。

### C4 要回收站却回一批过审种（P2，答非所问的读口）

  于是「伸手要回收站」拿到的是**已过审**列表；`9` 同理。
- 而 `POST /torrents/{id}/restore` 一直存在——有恢复动作却没有对应的读口，

## 批九：搜索 / 筛选 / 翻页 / 参数容错面（判据：语料矩阵 + 精确 id 集合）

### 两个真缺陷（commit 34fbc2c7）

1. **日历非法日期把高级搜索打成 500**：`norm_date` 只查 `YYYY-MM-DD` 形状，

建单时悬赏是**即时冻结**（从求种人余额划走）的。一旦第 2 步失败
（余额溢出、流水冲突、瞬断），第 1 步已经落库：请求变成「已完结」，
而入口守卫 `if status != 0` 又回「该求种已处理」把重试堵死。结果是
求种人的 300/500 魔力既不在他账上、也没到应种人手里，`spark_ledger`
里查无这笔 payout，后台没有任何补救入口。

实测（闸门 R3，`aa1010w`）：把应种人余额推到 `int64` 顶让入账必然溢出
→ 接口 500，但 `requests.status=1`、payout 流水 0 条、求种人零通知；
把余额恢复后重试，回 400「该求种已处理」。**钱确实丢了，不是理论风险。**

### 修法

- 状态更新与 `earn_spark_tx` 收进同一事务：发奖失败整体回滚，单子留在
  待应状态，障碍排除后可重试（闸门最后一条就是钉这个「不留死单」）；
- `Replayed` 视作冲突而非静默放过（同 kind 同键说明半途而废过）；
- 补上完结通知：旧实现发完钱就走，求种人只能自己回列表翻。按 0286 口径
  带 `kind='request_fulfilled'` + `params` 并过 `u_notice_enabled`，
  写入失败只 WARN 不阻断（完结已落库，因通知失败回 500 会让人重复应求）。

## P-35（新发现，未修）：个人主页把「后端出错」一律渲染成 404「用户不存在」

### P-35b（顺着失败的修复挖到的真根因，未修）：`ApiError` 把所有 HTTP 状态压成 code 1000

`apps/web/lib/api-client.ts:96-104`：

```ts
  if (!res.ok) { … throw new ApiError(1000, `服务异常（HTTP ${res.status}）`); }
  const body = await res.json();
  if (body.code !== 0) { … throw new ApiError(body.code, body.message, body.data); }
```

**HTTP 非 2xx 一律走第一条**：404 / 403 / 429 / 500 全都被压成
`code = 1000`，真实状态只活在 message 字符串里。信封码（NotFound=1004 等）
只有 2xx + 业务失败才会用到。所以：

- 前端**任何**「按错误类型分支」的代码都不可能判出「不存在」——
  这正是资料页 `catch { notFound(); }` 当初「看起来合理」的土壤；
- 我上一刀猜 `e.code === 1004` 必然不命中（实测：真不存在的 id 也变 500），
  不是手滑，是被这个契约误导——**根因在此，不在那一行 catch**。

正确修法（下批，两处一起）：
1. `ApiError` 增加 `status`（`!res.ok` 时 `new ApiError(1000, msg, undefined, res.status)`，
   并把 `code` 与 HTTP 语义分开；`body.code` 那条也带上 `res.status`）；
2. 资料页改为 `e.status === 404 ? notFound() : <错误边界>`，
   验收必须**两条同时过**：限流(429)→非 404、真不存在→仍 404。

## P-49（已修 cc3c0b7，活验见 AR）：超时回池的 SQL 取不到认领人，代行弃单的记账与通知 100% 静默失效

**根因**（`apps/worker/src/jobs/subtitle_flow.rs`）：

```sql
UPDATE subtitle_requests SET status = 0, claimed_by = NULL, ...
 WHERE status = 3 AND deadline_at < now() RETURNING id, claimed_by
```

Postgres 的 `RETURNING` 给的是**更新后**的行，`claimed_by` 已被自己置
NULL ⇒ Rust 侧 `if let Some(uid) = claimer` 永不成立，**审计与站内信双双
不写**，而回池本身成功（所以看数据像"正常工作"）。

**实测（AR 闸门 S5 抓到）**：把单推到「已认领 + deadline 已过」→ sweep 真的
回池（status 0/null），但 `audit_log` 里 `subreq.abandon` **全库 0 条**、
认领人也收不到「字幕认领已超时」。
对照实验（同一张临时表）：裸 `UPDATE…RETURNING` 取回 NULL，
`WITH cand AS (SELECT …), upd AS (UPDATE … FROM cand RETURNING c.旧值)`
取回 42 —— 确认是取值时机问题而非业务分支问题。

**为什么要紧**：F3 的「30 天内弃单 ≥3 暂停认领」只数 `subreq.abandon`。
worker 这条注释写明「超时回池等价于系统代行弃单——必须落审计，否则禁令
只数主动弃单，故意拖到超时的霸单人绕过计数」，而它实际上一次都没落过：
**绕过禁令的正是这条补丁想堵的那条路**。

**修法**：改 CTE 快照（先取 `claimed_by` 再更新），与 `ipcheck.rs` 里
traffic_ledger 的既有写法一致。全仓扫同类「UPDATE 里被 SET 改过又
RETURNING」的语句共 4 处候选：本条是真病灶；其余三处
（adapter `strikes` 取新值、hr `pardoned` 只当存在性判断、passkey 轮换取新值）
都是有意为之，不动。

## P-51（已修 4b782ad7 + 7b0bd4fc，`api:aa1011p` 活验）：protected 版块被 /forums/search 击穿

论坛「受保护版块」的口径是：帖子页把 2 楼起的正文替换成 `……`，只放行
staff（class≥90）/楼主本人/发帖人本人/本版版主。`community_http/forums.rs`
的搜索却直接 `(SELECT left(p2.body_text, 90) FROM posts p2 WHERE
p2.topic_id = t.id AND p2.body_text ILIKE $1 ORDER BY p2.id LIMIT 1)`
取任意楼层——同一批正文换了个出口就原样发出去了。

实测（一次性探针 `scripts/_as_probe_forum_readpath.py`，跑完即删）：

    详情：http=200 二楼 body='……' hidden=None
    搜索(私密关键词)：http=200 命中=1 snippet='二楼私密回复 ASPROT44343-SECRET'
    AS1 结论：protected 被搜索击穿 = True

改法：把「此读者能否看该版非一楼正文」抽成一个自带闭合的布尔式
`priv_floor`（staff / 楼主 / 本版版主 / 非 protected 版），匹配子查询与
片段子查询都套上 `({priv_floor} OR p.id = (SELECT min(pp.id) ...))`，
非特权读者在 protected 版块只匹配、只出一楼（一楼本就是公开正文）。

**这一刀自己捅了自己一刀**：`priv_floor` 少写一个右括号，两处各欠一层，
`cargo check` 全过（它只看 Rust 语法），Postgres 却报
`syntax error at or near "ORDER"`，`/forums/search` 整条 500。发现方式不是
人眼，是闸门里四条**正控**集体变红——负控那时全绿。教训写进 AS 的门面：

- 拼接 SQL 的改动，先把拼出来的字符串打出来 EXPLAIN 一遍再构建（本次
  12 行的临时脚本省下 12 分钟构建与一轮部署）；
- 权限类负判据绝不能是「返回空」：500 时 `data` 也是空。现在 `search()`
  非 200 或非列表直接 `SystemExit`，并补「可见时三出口都送得出」的地基。

## P-53（已修 4b782ad7，`api:aa1011p` 活验）：403 的探测照样涨热度

## P-56（已修 74e56ac5 迁移 0346，`api:aa1011q` 活验）：bilibili 模板取错捕获组

0345 把正则修好的那一刻，下一层缺陷才显形——`fillTemplate` 生成的 src 是

## P-57（已修 4e637f4a + 迁移 0347）：同一份文件跨用户上传必 500——sha 唯一索引与「按人权限行」互斥

0100 建表时按「同文件全站只存一份」下了 `attachments_sha_key UNIQUE (sha256)`；
0294（安全审计 P1-2）把可见性做进行里的 `visibility`，并把去重判据改成
「同人已有行才复用；他人已有行且本次要 private 时插独立行，物理文件仍按
sha 共享」。这条新语义要求同 sha 能有多行，而那条唯一索引从没被 DROP
（live `\d attachments` 复核仍在）⇒「插独立行」这条路永远撞约束。

实测（两个账号，同一份字节，两种顺序）：

    成员 shared → 200；站长同字节 private → **500**，库里该 sha 仍 1 行
    成员 private → 200；站长同字节 shared → **500**，库里仍 1 行

即 PT 站最常见的形态——两个人传同一张截图/同一张封面海报，只要有一方要走
私有，后来者直接失败。

- 索引换成 `UNIQUE (sha256, user_id)`：同人重复上传仍然去重（响应里的
  `deduplicated` 语义不变），跨用户各一行。
- 放开多行后逐个数过「按 sha 取单行」的地方：`fetch_optional` 遇多行会直接
  报错，GET/HEAD 的 mime/size、视频上传的「是否已有行」、字幕下载的
  mime/size 四处补 `ORDER BY id LIMIT 1`；`subtitles.rs` 的归属校验本就带
  `user_id`、`preview.rs` 本就 `LIMIT 1`，不动。
- 读取可见性 `visibility_denied` 从「取任意他人行」改成**聚合**判据
  （staff ∥ 自己有行 ∥ 存在 shared 行）。旧写法在同一 sha 两行时取到哪条
  全凭数据库心情：同一张图可能对某些人 404、对某些人全站可读。

## P-60（已修 4e637f4a）：HEAD 为了保住 Content-Length 整块分配文件字节

## 撤回的一条怀疑：Range 越界不返回 416

缺陷；AT 把当前行为钉成断言并写明「别重复立案」，省得下一轮再翻一遍。

## P-66（已修，两轮才修对）：passkey 整串躺在日志里，而 exclude 的通配写法根本不生效

私有站 passkey 走**路径**形态（`/api/v1/rss/{passkey}`、
`/api/v1/rss/forum/{passkey}`、tracker `/announce/{passkey}`）。第一轮审计
发现 `%r` 会把 `?passkey=` 写进 access log，于是换成 `%m %U`（不含 query）
并加 `.exclude("/api/v1/rss")`。但 passkey 在**路径**里，`%U` 挡不住，
所以注释接着写「整个 RSS 前缀不落 access log」——这一句是错的：

- actix `Logger::exclude` 是 **HashSet 精确匹配**（actix-web-4.15.0
  `src/middleware/logger.rs:322`：`exclude.contains(req.path())`），
  **没有通配语义**；
- 我第一版的修法 `.exclude("/api/v1/rss*")` 同样无效——本批实测部署后
  logger 行照旧带整串 passkey（`"m /api/v1/rss/ukkygjngp58fhi…" 400`）；
- 还有第二条通道：`request_id` 中间件的「请求开始」行记的是 `req.path()`，
  完全不看 Logger 的排除表。

passkey 是长期凭据（下种、订阅 RSS、替该账号 announce），日志的读者 =
运维 / 日志聚合 / 任何能 `docker logs` 的人，等于把全体订阅者的凭据发出去。

终版：`exclude_regex("^/api/v1/rss")` 挡 access log，
`request_id::log_safe_path` 按**形态**脱敏（≥32 字符且全字母数字的路径段
一律 `***`）挡第二条通道——不按端点名写白名单，未来任何「凭据进路径」的
出口自动安全。整块口径搬进 `access_log.rs`（main.rs 越 300 行门禁，顺手拆）。

tracker 侧一并核了：announce 返回 200 时其日志无请求行，这一路不落凭据。

## P-67（已修）：8 处自写计数在 Redis 故障时 fail-open，「拿不到计数」被当成「没超限」

`incr(...).unwrap_or(0)` 的分布（`grep '\.incr('` 全仓）：
`auth_http/login.rs` 的 acctlock 读写与成功清零、`compat_http/
download_keys.rs` 三闸（签发 10/凭证 20/IP 30）、`compat_http/nexusphp.rs`

收成 fail-close（注释写明「unwrap_or(0) 让计数恒 0 ⇒ 限流永不触发」），
这些出口却各写各的。最坏的一处是登录：Redis 抖动时**账号锁定判定形同虚设**，
而低慢定向爆破正是它管的。

收口到 `http/throttle.rs` 三个原语：

- `rate_window(state, key, max, window)` —— 纯限流出口；窗口写进**键名**
  （`rl:<key>:<窗口序号>`），TTL 只为回收存在（P-65 那课的教训）。
  用在 npdl / dlkey 三闸 / openup / appeal，并把 `limit_passkey` 本体也换过去

- `counter_peek` / `counter_bump` —— acctlock 与开放 API Token 桶：前者语义是

  喂 `TokenCtx.used`，fail-open 时连「剩余配额」一起谎报；
- `counter_clear` —— 成功登录的清计数：失败只 warn，不能为一个清理动作把
  已经成功的登录打成 5xx。

代价写在代码注释里：Redis 抖动期这些出口会 5xx（开放 API 整片、RSS 等），
与 ZT81 的既有拍板一致——宁拒服务，不静默放开防护。

开放 API 200、登录锁定读侧 200），2 条是闸门自己的错——

1. 断言 `path=/api/v1/rss/***` 找不到：tracing 会给字段名与 `=` 上 ANSI 颜色，
   原始流里 `path=<值>` 根本不连续。改：读日志先剥 ANSI 码；
2. 「投毒键已清」用 `EXISTS` 判：S3b 的正控会合法地重新创建这些计数键，
   于是自己把自己的键判成残留。改：值必须是「不存在或纯数字」。

## P-69（已修 5e01eafd）：游戏额度桶只在 n==1 时补 TTL → 一次失败就是永久 429

`games_http::check_rate_scoped` 的写法是「INCR 成功 → 若 n==1 才 EXPIRE，
EXPIRE 失败就报 500」。这条命令一旦失败（连接抖动/被抢占），键就永不过期，
计数一路累加 ⇒ 该用户在 instant/farm/pet 这一档上**永久 429**，而且此后
n 恒 >1，再也没有补 TTL 的机会。

修法照 `tracker::rate_over` 的既有写法：INCR 后查 `PTTL`，
`< 0`（无 TTL 或键不存在）就补一次 EXPIRE；补失败只 warn，由下一次调用自愈，
不打回本次请求。固定小时窗不变（不是每次续期，避免又犯 P-65 的滑动窗）。

**顺带订正我自己写进文档的一条记账**：上一段「同族还没收」里我把
`tracker::rate_over` 也列进去了——读了代码才确认它早就做对了（pttl 补 TTL
+ Redis 报错时回落进程内本地计数并打指标）。那是我拿子代理的概括当成
已核实事实写下的。规矩对「说它有洞」和「说已有」是同一句：**当场给行号**。

## P-70（我自己在 P-67 里引入的，已修 0a0611c3）：把「读不到」当成「读出错」

`counter_peek` 第一版是 `c.get(key).await.map_err(rl_err)?` 直接解 `i64`。
Redis 对**不存在的键**返回 nil，redis-rs 把 nil 解成 i64 是类型错误 ⇒
「从没失败过的账号」登录全部 500。部署 `aa1011x` 后闸门在第一步
`login()` 就撞死，日志写得很直白：

    限流服务不可用: Response was of incompatible type - TypeError
    （response was nil）

修法：`let v: Option<i64> = c.get(key).await.map_err(rl_err)?; Ok(v.unwrap_or(0))`
——没键 = 0，命令真报错才 fail-close。AU 的 S3 现在有左右两条断言把这个度
钉住：投毒（值非数字）→ 500，键干净 → 200。

教训：**fail-open 改 fail-close 时，「读不到」与「读出错」是两件事**。
一把 `?` 推过去看着安全，实际是把可用性换成了假的安全感；而且这类错
只在「一切正常」的路径上显形，所以正控（干净键必须 200）必须和负控同批。

## P-71（我自己在 P-67 里引入的第二条，已修）：把限流桶写成了空闲超时窗

`require_token` 的开放 API 桶在 P-67 改 fail-close 时选了 `counter_bump`
（INCR + 每次 EXPIRE 60）。这条键**不**进窗口，于是窗口含义从「每 60 秒
清零」变成「距最后一次调用 60 秒后清零」——正常轮询的客户端（Prowlarr、
cross-seed 每 30s 一次）计数永不复位，累计到 `rate_per_min` 之后被**永久
429**，而它完全没做错任何事。这不是理论：P-65 我已经因为「每次 EXPIRE」
被闸门自己退避重试续命过一次，改完 `rate_window` 却漏了这一处还在用旧语义。

修法：`rate_window` 改为返回窗口内第几次（开放 API 要往响应头报 used/剩余，
本来就该由它给数），`require_token` 换过去；`counter_bump` 的文档注释钉上
「别拿它做限流」。顺带 `x-ratelimit-reset` 从恒 60 改成「距分钟边界几秒」
——窗口进了键名，复位时刻就是边界，恒 60 会让退让的客户端白等。

## P-72（实测，已修）：限流键名双前缀，文档口径与实际差一层

`rate_window` 自己加 `rl:` 前缀，七处调用点又自带一次 ⇒ 线上真实键是

    rl:rl:npdl:fab7f4eedbf9be05:29862691
    rl:rl:npdl-ip:172.20.0.1:29862691

（`curl` 打一次 download.php 后 `redis-cli --scan` 直接抓到，不是推的）。
危害不在功能——限流照样生效——而在**读数接口**：审计文档、运维脚本、
闸门都按 `rl:<scope>:<id>` 写，于是 `--scan --pattern "rl:npdl:*"` 一条
数不到，AU 往 `rl:npdl:…` 投毒也打不中，「fail-close 生效」的判据会在
键名错位时**假绿**（我这批的 S3 就是这么红得莫名其妙）。修法：前缀归
`rate_window` 独占，调用方只传业务段；`throttle.rs` 的文档写死这条契约，
AU 新增 S5 直接断言「不存在 `rl:rl:*`」+「npdl 桶形状是
`rl:npdl:<16hex>:<窗口>` 且 TTL ∈ (0,120]」。

## P-73（实测，已修）：四条匿名计数还在 fail-open + 孤键

`shoutbox`(10s/人)、`captcha`(30/min/IP)、`ban-log`(5/min/用户名)、
`password/forgot`(3/h/邮箱) 还是 P-67 那一族的原样：`incr(...).unwrap_or(0)`
+ `if n == 1 { expire }`。收口时漏掉它们是因为我按「有 429 语义的出口」
清点，而这几条写在 handler 里、没走 helper。按危害排：

- `pwdforgot`：Redis 抖动 ⇒ 重置邮件不限速（铸流水 + 垃圾信）；EXPIRE 一
  失败 ⇒ 那个邮箱此后**永远**申请不到找回密码，只能人工删键——账号恢复
  通道的永久拒绝；
- `captcha`：计数维度是**出口 IP**，运营商 CGNAT 后成千用户共用一个 IP，
  孤键一留就是整片拿不到验证码，连带注册；
- `ban-log`：被禁的人查自己封禁记录（申诉流程要用）永久 429；
- `shoutbox`：冷却静默失效 + 该用户永久发不了言。

四条统一换 `rate_window`（fail-close + 窗口进键名，额度与窗口都不变）。
`rate_window` 的窗按对齐边界复位，`pwdforgot` 从「首请求起 1 小时」变成
「整点小时」，跨窗最坏 2×3——这是所有固定窗口的通性，与申诉档同口径。

AU 新增 S7 把「孤键 ≠ 永久拒绝」钉住：`SET rl:banlog:<u> 999`（无 TTL，
正是 EXPIRE 失败后的现场）→ 断言一次调用后不是 429、且新计数落在带窗口
的桶上；反控连打 7 次必须出现 429（限流本身没被拆）。修前这两条一红一绿
得恰好反了。

## P-74（实测，已修）：`%m` 不是 actix 的格式符，access log 整列方法静默消失

P-66 把 `%r` 换成 `%m %U` 挡 query 里的凭据——但 actix 4.15 的 specifier
表（logger.rs:525-536）只有 `% a t r s b U T D`、`%{x}i/o/e`、`%{x}xi/xo`，
**没有 `%m`**；未认识的走 `_ => FormatText::Str(...)`，于是 `%m` 被原样印成
字面量。线上每行：

    172.20.0.1 "m /api/v1/auth/login" 500 102 "-" "curl/8.19.0" 0.001105

不报错、不警告、不缺行——只有方法这一列没了。谁 POST 发种、谁 PUT 改设置，
在日志里与 GET 无法区分（排障与审计都靠这一列）。改 `%{method}xi` +
`custom_request_replace("method", |req| req.method().to_string())`。

这条给判据立了个新规矩：**日志格式要在渲染出来的那一行上双向断言**。
S1 原来只问「passkey 在不在日志里」，泄漏挡住了就算绿；现在同一段既断言
「不含 passkey」也断言「含 GET」，并把 `"m /api"` 这种字面量残留列成反控。
只看一个方向，同一个格式串能把「泄漏」和「丢字段」两种错藏在一起。

# 批三十一（2026-10-12）：passkey（无密码登录）整条线是半死的，而且能接管账号

新闸门 `scripts/pt_audit_av_passkey_ceremony.py`：Python 侧自己造 P-256 密钥
与 authData，把注册（begin→finish）与登录（begin→finish）两段仪式真走完。
在此之前没有任何闸门碰过 passkey，而它是登录页上一个能点、能绑、能显示
「绑定成功」的按钮。

## P-75（P0，实测已修）：绑定接口能覆盖别人的凭证 = 账号接管

`/auth/passkeys/finish` 的写入是

    INSERT INTO user_passkeys … ON CONFLICT (cred_id)
    DO UPDATE SET public_key = $4, sign_count = $5

而 `cred_id` 上的是**全局唯一**约束（`user_passkeys_cred_id_key`），
DO UPDATE 又不带 user_id 条件。于是任何登录用户（版主、普通会员、甚至
自己注册的小号）把 body 里的 `cred_id` 填成**别人的**凭证 ID，就把受害者的
公钥换成自己的；`user_id` 列仍是受害者的，所以之后走一遍正常的登录仪式
（用攻击者自己的私钥签名）即可拿到**受害者身份的 JWT**。
受害者的凭证 ID 从哪来？匿名端点 `/auth/passkey-login/begin` 按用户名直接
回吐 `cred_ids` 列表。

现场（跑在 aa1012a 上）：攻击者绑定返回 `200 {"bound":true}`，受害者库里
的公钥从 `043460dd…` 变成 `04a5aa42…`。不是推演。

根子在于服务端把 client 自报的 `(cred_id, public_key, auth_data)` 三元组
当可信输入：既不校验公钥与 authData 内凭证的一致性，也不校验 cred_id 归属。
本批取最小修法（不动协议面）：撞别人行就 403 + 审计 `passkey_takeover_attempt`
+ warn 日志；`ON CONFLICT` 补 `WHERE user_passkeys.user_id = EXCLUDED.user_id`
作双保险；cred_id 长度校验；每人最多 5 把；finish 上 10 次/分/人。

## P-78（实测已修）：passkey 登录全量 500——这条功能从没通过

`SELECT … COALESCE(u.class_id, 0) …` 那列是 `integer`(INT4)，元组按 `i64` 解
⇒ sqlx 每次报 `mismatched types; Rust type i64 (as SQL type INT8) is not
compatible with SQL type INT4` ⇒ `/auth/passkey-login/finish` **100% 500**。
配合 P-75 读这条更可怕：接管链路的最后一步其实是断的，所以「攻击者登不进」
这条断言在 aa1012a 上是**假过**（它靠 500 通过，而不是靠拒绝通过）。
修 P-78 就是把 P-75 的口子真正打开的那一刀，两批必须一起验。
判据现在写成：拒必须是 400/401 的凭证拒，`!= 200` 这种宽松断言一律不许。

## P-81（实测已修）：验签用错了方法——浏览器形态的签名一律被拒

`Signature::from_slice` 只吃**定宽 64 字节 r‖s**（ecdsa-0.16.9/src/lib.rs:224-230），
而 ASN.1 DER 是另一个方法 `from_der`（同文件 232-236；`der` feature 由 p256
已打开，`cargo tree -i ecdsa` 可查，不是 feature 没开的问题）。CTAP2/WebAuthn
规定 `sig` 就是 DER ⇒ 任何认证器交回来的签名都在这里被判「签名格式错误」。

同一把私钥、同一份签名的两种编码，跑在 aa1012c 上的实测：

    DER 72 字节      → 400 参数校验失败: 签名格式错误
    raw r‖s 64 字节  → 200 + 本人 JWT

所以 P-78 修完之后，passkey 登录对**脚本**通了、对**浏览器**仍然是死的。
这条只有在按浏览器形态（DER）签的闸门里才会显形——AV 就是。
AV 另加 S1b 负控：raw 形态必须被拒，「两种都收」等于口径没定，也防止后来人
把 `from_der` 改回 `from_slice` 还能过。

## P-82（实测已修）：公钥入口只认 SEC1——浏览器交的是 SPKI，一绑就错

`/auth/passkeys/finish` 用 `p256::EncodedPoint::from_bytes` 解公钥，
那个函数吃的是 **SEC1 未压缩点**（`0x04‖X‖Y`，65 字节）。而浏览器
`AuthenticatorAttestationResponse.getPublicKey()` 按 WebAuthn L2 返回的是
**DER SubjectPublicKeyInfo**（MDN 同口径），前端 `passkeys-card.tsx` 正是用它
取公钥 ⇒ 真实浏览器每次绑定都回「公钥格式错误」。
前端注释还写着「服务端兼容裸 COSE 公钥」——两头都不对：浏览器给的不是 COSE，
服务端也不收 COSE。

至此 passkey 在浏览器侧死了三次，位置各不相同：
**注册**（P-82 公钥格式）、**登录前置查询**（P-78 INT4 当 i64 ⇒ 500）、
**登录验签**（P-81 只吃 raw r‖s 不吃 DER）。三个都修完，这条功能才第一次
真的可用。修法：入口归一（SPKI → `VerifyingKey::from_public_key_der` → 存
SEC1；SEC1 原样收；COSE 明确拒并指名），库里形状不变所以登录侧零改动。

闸门 AV 相应改成**按真实客户端形状跑**：注册用 SPKI、签名用 DER；
S1c 断言 COSE 被明确拒且不留库行、SEC1 也能绑能登。诚实边界：
没有真在浏览器里点过（虚拟认证器需要 CDP 的 WebAuthn 域，browser-use
这套工具没暴露），用的是浏览器实际提交的字节形状，等价性在编码层而非
驱动层。

  15 分钟；当场 `DEL acctlock:root` 解开并复验能正常登录。以后这类「故意打
