# 资深 PT 用户实测审计（2026-10-10）

口径：以一个用了八年 PT 的站员的日常动线走全站——进保种区认领、被 H&R 后查后台、
发求种、应求、交字幕、建合集、订阅 RSS、心愿单——只问一件事：**这条链路的下一环有没有真的接上**。
环境：本地栈 `flux-api/flux-web/flux-worker/flux-tracker + postgres + redis`，
站长（class 99）与非管理成员双视角，接口层与渲染层各验一遍。


> 同日续批：娱乐屋与农场土地阶梯见 `_doc/资深PT用户实测审计-批五-娱乐屋与农场-2026-10-10.md`
> （大厅聚合 500 的 i64→int4 绑参、农场 e2e 一条过期断言、写闸 e2e 九条口径漂移 + 一条待定性的 EV 数字）。
## 一、已修（附现场证据）

### A1 后台 H&R 总览整页 500 —— 一行脏流水炸全表
- 现象：`GET /api/v1/admin/hr/records` → 500，api 日志 `error occurred while decoding column "uploaded": unexpected null`。
  现场 `hr_snapshots` 共 7 行，其中 1 行的 `snatches` 已不存在。
- 根因：H&R 义务存在 `hr_snapshots`，上传/下载量却是读时从 `snatches` 现取（LEFT JOIN），
  而 `HrRecordRow.uploaded/downloaded` 声明成非 Option 的 `i64`。快照存续期间流水可被清理
  （复活任务、账号清理、级联删），LEFT JOIN miss 即 NULL → 解码失败。
- 修法：两列改 `Option<i64>`；后台 `admin-hr.tsx` 对应两格在无流水时显示「—」，
  不再把 `null` 静默算成 0G（`null/1024**3` 在 JS 里是 0，比 500 更难发现）。

### A2 成员「我的种子·保种中」500
- 现象：`GET /api/v1/users/{id}/torrentlist` 在该成员认领了保种但没有下载流水时 500。
- 根因：`user_torrentlist.rs` 的 preserved 查询 `CASE WHEN $3 THEN s.seeding ELSE false END`——
  `ELSE` 只在**非本人/非管理**时兜底；本人或 staff 看（reveal=true）时读的是 LEFT JOIN
  后的 `s.seeding/s.leeching/s.uploaded`，无 snatch 行即 NULL，而 `SnatchRow` 三列都是非 Option。
- 关键：`POST /preserve/claim` 不要求先下载，「认领但无流水」是**正常动线可达**状态，
  不是异常数据。修法：三列各配 `COALESCE(..., false/0)`。

### A3 加入复活队伍 500（删号留下的孤儿队伍）
- 根因：`admin_http/user_del.rs:120` 删号会 `DELETE FROM resurrections WHERE user_id=$1`，
  但 `social_team` 行不动 → 队伍失去关联资源。`social_http/team.rs` 的 join 查询
  把 LEFT JOIN 出来的 `r.torrent_id` 按 `i64` 解码；同一份 JOIN 在 `team_members.rs`
  早已按 `Option<i64>` 读——两套规则里被改漏的是 join 这条。
- 修法：改 `Option<i64>`，孤儿队伍按「该队伍已结束」拒绝加入（与相邻状态分支同文案，不新增未译串）。

### A4 保种区筛选：「已移出」直接白屏，「延续中」选了等于没选
- 现象（渲染层实测）：`http://127.0.0.1:3000/preserve?status=expired` → **HTTP 500**；
  `status=grace` 返回的是**未过滤的全量在保**列表。
- 根因：`status=expired` 走独立早退分支，只回三列裸数组 `[[id,name,size]]`，
  而 `data-content.ts getPreserve()` 按 `{items,total,stats}` 解构 → `stats.preserving` 抛错；
  `grace` 档位后端只在注释里写过，SQL 里没有任何对应判定。
- 修法：四档统一走同一条查询、同一个信封；宽限证据取 worker 出种时挂的
  `promotions(source='preserve_grace')` 3 天窗口——
  in=在保全部 / active=保种中（已认领）/ grace=延续中（已移出且宽限未过）/ out=已移出（宽限已过）。
  列表与计数共用一份视图判定片段，避免两处各写一份再漂移。

### A5 保种区「只进不出」棘轮：移出后永远回不了区
- 根因：灌入作业 `worker/src/jobs/class_adj.rs` 的准入条件是
  `NOT EXISTS (SELECT 1 FROM seed_preserve WHERE torrent_id = t.id)`，
  而行是 `ON CONFLICT DO NOTHING`——一旦某颗种子进过保种区并被移出（`exited_at` 置位），
  这行永久存在，日后它掉回 0 做种也**再也进不了保种区**，`preserve_exit` 的
  「seeders > 阈值才移出」于是成了单向门：站龄越久，保种区越空洞。
- 修法：准入把「已移出的行」视同可重入，`ON CONFLICT DO UPDATE` 重开该行
  （清 `exited_at/exit_reason/claimed_by/claimed_at/last_settle_at`），在保未移出的行不受影响。

### A6 求字幕「在身 3 单上限」fail-open
- 根因：`subtitles_flow.rs` 数在身单的 SQL 里多写了一个转义引号
  （`FROM subtitle_requests \"`），Postgres 报 42601，而外面是 `.unwrap_or(0)`——
  错误被吞成「0 单在身」，上限**永不触发**，一个成员可以把求字幕全占住。
- 修法：去掉那个引号，并把它和相邻的弃单计数查询一起改成错误外抛：
  资金/名额类闸门宁可拒绝操作，也不能在 DB 抖一下时放行。

### A7 求种板两个计数器长期假 0
- 现象：表格里「评论数 / 应求数」两列恒为 0（接口直接写死 `"comments": 0, "bids": 0`）。
- 根因：`comments` 只挂 `torrent_id`，`offers` 表**没有 request_id**——求种与候选之间
  没有外键，这两个数在数据模型里根本不存在。假 0 会被读成「没人应求」，直接劝退应求的人。
- 修法：接口改回 `null`，界面渲染「—」；真正的「求种↔候选」关联见待拍板 P-1。

### A8 求种板标题链到不存在的详情页
- 现象（渲染层实测）：`http://127.0.0.1:3000/requests/1` → **HTTP 404**，
  而求种板与卡片的标题都是 `<a href="/requests/{id}">`；后端也没有单条求种接口。
- 修法：两处标题改纯文本，等详情页立项后再挂回去。

### A9 保种区分页基准不一致
- 根因：全站列表分页统一走 `dto::page_window`（1 基），唯独 `/preserve` 用
  `page * per` 且 `page` 缺省 0——客户端照惯例传 `page=1` 会翻到第二页（首页整页空白）。
- 修法：改 1 基，缺省即第一页。

### A10 公开资料页「种子列表」——凡有行必 500（P0）
- 现象：`GET /api/v1/users/{id}/torrentlist` 对**任何有内容的用户**都 500，
  api 日志 `no column found for name: approval_status`。uid=1（有上传记录）实测 500，
  而两个空列表用户返回 200——空结果集不解码，所以问题被「没人用」掩盖着。
- 根因：`http::SnatchRow` 带 `approval_status/deny_reason` 两个 Option 字段
  （注释写明「仅 kind=uploads 填充」），但只有 `/me/torrentlist` 的 uploads 查询真的投影；
  公开资料复用同一结构体的 6 条查询都不投影。sqlx 对 Option 字段只容忍 NULL，
  **不容忍「列不存在」**，一解码就报错。
- 修法：两个字段加 `#[sqlx(default)]`（缺列即取 Default=None），序列化侧的
  `skip_serializing_if` 保留，响应形状不变。

### A11 用户中心「活跃会话」整卡 500（P1）
- 现象：`GET /api/v1/me/sessions` → 500，日志
  `decoding column "ip": Rust type String (as SQL type TEXT) is not compatible with SQL type INET`。
  `apps/web/components/sessions-card.tsx` 正是这卡的读口。
- 根因：`login_events.ip` 是 `inet`，`me_sessions.rs` 直接把它投影给 `ip: String`。
  同一张表的其他三处读口（`me_history.rs` / `admin_http/records.rs` / `staff_http/ipcheck.rs`）
  一贯写 `host(ip) AS ip`——又是「两份规则里被改漏的那一份」。
- 修法：改 `host(ip) AS ip`（与同表其余读口同口径）。

### A12 种子导出整页 500（无主种子）+ 审核通知的假警告
- `GET /api/v1/admin/export/torrents` → 500，日志 `decoding column 2: unexpected null`。
  `export_ops.rs` 用元组 `(i64, String, i64, …)` 解 `t.owner_id`——该列可空
  （站方代发/系统导入的种子没有上传者），一行无主种子就让整页导出不出来。
  同文件的用户导出早就把 email 写成 `Option<String>`，只有种子这条漏了。
- 同一列在 `admin_http/review_notify.rs` 里也按非 Option 解，但它外面是
  `let Ok(Some(..)) = row else { warn; return }`：不炸页，却把「这种子无主」
  当成「取数失败」天天写警告，真出故障时反而被噪声淹掉。
  改成 `Option<i64>` + 分支：无主→静默跳过（本来就没有可通知的上传者），
  查询真错→才 warn。
- 顺手做了个交叉核对：把全站「元组解码」的读口与 `information_schema` 的可空列
  对了一遍，除这两处外没有第三处（脚本 `_tmp_nullscan.py` 的思路值得做成常驻
  门禁：非 Option 位置命中可空列即红，与既有的 i64→int4 绑参盲区同族）。

### 顺手验过、没发现问题的动线（记录以免重复排查）
- 2FA 全环：`setup → enable(需当前 OTP) → 无 OTP 登录被 2010 拒 → 错 OTP 被 2011 拒 →
  正确 OTP 登录 200 → 失败登录按 reason=2 落 login_events`，链路完整。
- RSS：`/rss/{passkey}` 200（26KB XML）、伪 passkey 400、`/rss/forum/{passkey}` 200。
- 心愿单：add → 列表可见 → remove 生效；上限 20 条、`ON CONFLICT (user_id, keyword)` 幂等。
- 合集：root 建 → 列表/详情读得到（但成员建不了，见 P-4）。
- 互动：thanks（含 spark_given 记账）、评论发布与读取、给自己评论点赞被正确拒绝；
  收藏是 `PUT /torrents/{id}/bookmark {on:bool}`。
- 种子评分：本站没有「用户评分」写口（`rating` 是外部元数据，`rating_min` 只筛它），
  不是断链，别按 UNIT3D 的 user-rating 找。

### B1 主收件箱把「已归档」的信也列出来（P2）
- 现象：新建自定义文件夹 → 收信 → 移动进文件夹 → 文件夹计数正确变 1，
  但 `/messages/inbox`（不带 `box_id`）仍返回这封信；界面上同一封信在
  「收件箱」和「AB夹」里各出现一次。
- 根因：`message.rs` 的 inbox 过滤写的是 `($2::int IS NULL OR m.folder = $2)`，
  而它自己的字段注释与 `message-center.tsx`（`folder=null` 即主收件箱）都是
  「缺省 = 主收件箱（folder IS NULL）」。缺省时条件整体短路成「不过滤」。
- 修法：改 `m.folder IS NOT DISTINCT FROM $2::int`——NULL 也参与等值判断，
  缺省即只看主收件箱，带 `box_id` 时照旧只看那个文件夹。

### B2 界面「拒绝好友申请」实际把对方变成好友（P1，语义反转）
- 现象：`friends-actions.tsx` 两个按钮都打 `POST /friends`：
  「接受」带一个后端根本不认的 `action:"accept"`，「拒绝」裸调用。
  后端 `friend_create` 的口径是「对方也申请过我 → 双向转正」，
  于是实测：B 申请 A → A 点「拒绝」→ 关系直接变 `friend`。
  而 A 点「接受」时那个多余的 `action` 字段被 serde 忽略，反而侥幸走通。
- 另一半：`POST /friends/action` 只认 `black / unblack`，
  所以任何用 `accept` 的写法都会 400「action 需为 black / unblack」。
- 修法：后端补 `accept`（校验确有 incoming pending，双向转正并按既有口径
  给对方发「好友申请已通过」系统信；无申请可处理时报「没有待处理的好友申请」）
  与 `reject`（只撤掉对方的 pending，不通知，NP 同口径）；
  界面两个按钮改打 `/friends/action` 的 `accept`/`reject`。
  两条新校验串已进 `validation_details.tsv` 三语表并收缩棘轮基线。

### B3 `users.notify_topic_reply` 是假开关（P2）
- 现象：论坛回帖通知走 `notify_user()`，它无条件 `INSERT INTO messages`；
  而个人设置页里「有人回复我时通知我」这项改了也没用——全站只有
  设置读写处引用过这个列（grep 仅此一处），没有任何消费方。
- 修法：`post_write.rs` 加 `reply_pref_wanted()` 闸门，楼主通知与楼中楼
  被回复通知都先读接收方偏好；读不到（用户已注销等）按站点缺省 true 处理，
  宁可多发也不静默吞通知。

### B4 顺带验过、没问题的
- `accept_pm` 三态（yes/friends/no）确实在发信路径被消费，好友判定正确；
- 回复引用（`Re:` 前缀 + 「原信」引用）与转发（`Fw:`）都按
  `(receiver_id = 我 OR sender_id = 我)` 取原信，指不到别人的信——无越权读取；
- push：vapid 公钥可读，`p256dh` 会真校验长度（假订阅被拒），
  未订阅时 `/push/test` 明确报「尚未订阅推送」；
- `/messages/move` 校验文件夹归属（不是自己的文件夹报「目标文件夹不存在」）。

### B6 `/friends` 返回元组数组，两个消费端一起读到空（P1）
- 现象：`friend_list` 用 `Vec<(String, String)>` 解码，JSON 就成了
  `[["bob","incoming"], …]`；而 `packages/domain-types` 里声明的
  `FriendItem` 与 `friends-actions.tsx` 的 `FriendRow` 都是 `{username, list}`。
- 后果（实测）：
  · `/friends` 页面 `friends.filter(f => f.list === "friend")` 恒为空 →
    好友页永远是空的，黑名单同理；
  · 「收到的好友申请」那段根本不渲染（`r.list` 恒 undefined）→
    即使后端有了 accept/reject，用户也点不到；
  · 这正是 B2「拒绝按钮打错接口」能长期潜伏的原因——那段 UI 从来没人看见过。
- 修法：`friend_list` 改回具名结构体（`FriendRow{username,list}`）序列化，
  与 domain-types 的声明对齐。
- 顺带记下门禁盲区：`check_type_drift.mjs` 只比对**有具名 struct** 的读口，
  元组返回没有比对锚点，所以这条一路绿灯。要么给守卫加「返回元组的
  query_as 一律要求具名 struct」，要么在 TS 侧按 path 反查形状——先记着。

## 二、批三实测：钱与物的账（结论：本轮没发现缺陷，但记下口径与两处旁路）

以真实新号走一遍：商店购买、银行定期/活期、签到、任务、勋章佩戴、装扮、券、资金池。
逐条与库内对账：

- 商店：单价 1000 扣得准（`spark_ledger` 一条 `shop/-1000` + `shop_orders` 一行）；
  **同一 `idempotency_key` 重放不再扣款**（`replayed:true`、余额不变），
  换新键可连买第二单——0207b 的语义成立；`/shop/buy` 缺键直接 400，
  两个 web 调用点（`buy-button.tsx`、`dressup/_inner.tsx`）都真的带键。
- 银行：定期 50000/30 天扣本金、预估利息 123 与 `fixed_rates` 一致；
  提前支取按 `penalty_bp=50bp` 罚 250、实付 49750，回到余额后总额自洽；
  活期存入 1000 记账 `bank_demand_in`，取出超余额被 400 拒。
- 签到：首次 200（含 `streak/base/gacha_ticket`），同日重复被「今天已经签到过啦」拒。
- 券 / 资金池：用不存在的券被拒；`/magic-pool` 捐献入账 `pool_donate`，
  `/pool/honor` 读得到捐赠榜（模块开关处已接）。
- 勋章：`/medals` 14 枚、`max_worn=3` 读得到；佩戴未拥有勋章返回 `cleared`
  （即清空佩戴）——语义是「不拥有就不戴」，没有报错但也谈不上反馈，记一笔。

结论：这条线上**没找到会算错钱的缺陷**，两处旁路（P-9/P-10）与一处弱反馈记在待拍板里。

## 三、批四实测：论坛权限门与关注链（结论：门是硬的，闸门常驻）

以低阶成员（class 1）+ 站长双视角，把板块门槛 `minclassread` 抬到 5 后逐个读侧验：
`/forums`、`/forums/boards`、直读板块（403）、`/forums/feed` 关注流、`/forums/search`、
`/rss/forum/{passkey}` ——**六处都不漏标题**；受限板块内的真 poll 主题投票拿 403
（权限判定在业务查询之前，不会用 404/403 的差别泄露主题类型）。
版主治理：普通用户 `manage` 与删他人主题一律 403、且不落库；站长锁帖后回帖被
「主题已锁定」拒，解锁后恢复；`locked/sticky/digest` 三个标记都真落库。
关注链：关注用户 → 对方发新主题 → 关注者收到站内信；关注主题 → 他人回帖 → 收到通知；
自关注被拒、关注不存在的目标 404、`/follows/mine` 三个维度都读得到。

顺带排除两个假象（都读代码定案，没留下改动）：

## 七、批七实测：种子生命周期链（结论：挖出一条 P0，全站种子编辑从来没有成功过）

沿「发种 → 改资料 → 删进回收站 → 恢复 → 被拒 → 重提 → 过审」这条线逐环走，
每一环都在接口回吐与库两处各验一次，否定式断言都配正控。

### C1 `PUT /torrents/{id}` 100% 500（P0，种子编辑整条断）

- 现象：任何用户改任何字段（只改正文也算）都回 `code=1000 内部错误`；
  api 日志一句 `syntax error at or near "//"`。
- 根因：`apps/api/src/torrents/interact.rs` 的 `edit_torrent` 里那段
  `r#"UPDATE torrents SET …"#` 中，有人把 Rust 风格的 `//` 注释粘进了
  **SQL 字符串内部**。Postgres 不认 `//` 是注释（它是整除运算符），
  整条 UPDATE 直接解析失败。Rust 侧看不出来：注释在串内，编译与
  `cargo check` 全绿——这类 bug 只有真打一次才知道。
- 修法：注释提到 Rust 侧；顺带在源码里写明「串内注释只能用 `--` 并另起一行」。
- 复验：改前 `PUT` 一律 500；改后同一请求 200，正文落库、其余五件套
  （名字/短标/IMDb/封面/MediaInfo）与标签、维度一根没掉；
  正控是同一条 PUT 改得动短标（证明写通道真的活着，不是「本来就那样」）。
- 新门：`scripts/sql_comment_guard.py`（已进 CI）扫 `.rs` 字符串字面量里的
  `//`。口径按「零误报」设计——只认原始串与首词是 SQL 关键字的常规串，
  因为字符串配对正则会「从上一个串的收尾引号配到下一个串的开头条引号」，
  把中间正常的 Rust 注释误判成串内注释（首版就误报 6 处，收到 0 处才信）。
  全站现存 0 处。

### C2 发种表单的 IMDb 栏填了等于没填（P1，字段两处落点只认一处）

- `UploadForm.imdb` 只写进 `media_info.imdb`，而详情页、编辑回填、审核台、
  `?imdb=` 同片并集读的都是 `torrents.imdb_id` **列**；该列在上传时只从
  正文/种名里正则提取。库里 `media_info ? 'imdb'` 的行数为 0，
  列也全空——即两个落点实际都没吃到用户手填的那一栏。
- 佐证：存量 e2e 里写着「直接给两个种子写 imdb_id（模拟发布链路提取）」，
  即测试早就绕开了这条链。
- 修法：上传时按 ①表单栏 ②正文 ③种名 的优先级走**同一条**正则
  （`extract_imdb`，整条 IMDb 链接也吃得下），并在表单栏非空却解析不出编号时
  直接报错，不再静默收下。

### C3 编辑口对非法 IMDb 静默丢弃（P1，假成功）

- 旧逻辑：非空但不合 `TT+7~8` 形态 → 回落 `None`，而 `None` 的语义是
  「这个字段不动」，接口回 200。用户手滑填了 `abc`，页面提示保存成功，
  刷新后原值还在——三重误导。
- 修法：三态明确化：未填 = 不动；空串 = 清空（SQL 侧用
  `CASE … NULLIF($10,'')`，此前空串会写入 `''` 而不是 NULL）；
  非空必须解析得出编号，否则 `Validation`（校验详情已进 i18n 译文表）。
  发种口与编辑口共用同一把正则与同一句提示，防两处规则再漂。

### C4 要回收站却回一批过审种（P2，答非所问的读口）

  于是「伸手要回收站」拿到的是**已过审**列表；`9` 同理。
- 而 `POST /torrents/{id}/restore` 一直存在——有恢复动作却没有对应的读口，

## 批九：搜索 / 筛选 / 翻页 / 参数容错面（判据：语料矩阵 + 精确 id 集合）

### 两个真缺陷（commit 34fbc2c7）

1. **日历非法日期把高级搜索打成 500**：`norm_date` 只查 `YYYY-MM-DD` 形状，

建单时悬赏是**即时冻结**（从求种人余额划走）的。一旦第 2 步失败
（余额溢出、流水冲突、瞬断），第 1 步已经落库：请求变成「已完结」，
而入口守卫 `if status != 0` 又回「该求种已处理」把重试堵死。结果是
求种人的 300/500 魔力既不在他账上、也没到应种人手里，`spark_ledger`
里查无这笔 payout，后台没有任何补救入口。

实测（闸门 R3，`aa1010w`）：把应种人余额推到 `int64` 顶让入账必然溢出
→ 接口 500，但 `requests.status=1`、payout 流水 0 条、求种人零通知；
把余额恢复后重试，回 400「该求种已处理」。**钱确实丢了，不是理论风险。**

### 修法

- 状态更新与 `earn_spark_tx` 收进同一事务：发奖失败整体回滚，单子留在
  待应状态，障碍排除后可重试（闸门最后一条就是钉这个「不留死单」）；
- `Replayed` 视作冲突而非静默放过（同 kind 同键说明半途而废过）；
- 补上完结通知：旧实现发完钱就走，求种人只能自己回列表翻。按 0286 口径
  带 `kind='request_fulfilled'` + `params` 并过 `u_notice_enabled`，
  写入失败只 WARN 不阻断（完结已落库，因通知失败回 500 会让人重复应求）。

## P-35（新发现，未修）：个人主页把「后端出错」一律渲染成 404「用户不存在」

`apps/web/app/(main)/users/[id]/page.tsx:48-54`：

```ts
  try {
    data = await api.get<ProfileData>(`/api/v1/users/${...}`);
  } catch {
    notFound();
  }
```

`catch` 不分成因。后端 429 限流、5xx、瞬断、鉴权失败——全都落进
`notFound()`，成员看到的是「该用户不存在」。

实测证据（同一次抓取里）：`/users/4411` 连抓四次 200，随后
`?tab=completed / incomplete / preserved / posts / comments` 与
**`/users/1`（root，在册活跃账号）全部 404** —— 同一个页面、同一条数据
路径，一秒内既能 200 又能 404，只可能是把暂时性失败当成了不存在。
排行榜/搜索里点进一个真实存在的人却「不存在」，还会把真实故障（限流、
接口 500）伪装成业务语义，排查时误导到人身上。

修法（web，两处，约 10 行，下一批与 P-32b/P-34 一并做）：
`ApiError` 目前只有业务 `code`（`api-client.ts:62-71`），**没有 HTTP status**
（本次核查：request() 作用域内未出现 status 字段）——先给 `ApiError` 带上
`status`，页面侧只对 `status === 404`（后端 NotFound 的业务码是
`1004`）走 `notFound()`，其余失败渲染可重试错误态（复用
`dict.common.retry`）。这样「不存在」与「现在读不到」在界面上分得开。

**同批排除**：`/users/1` 对未登录/非本人是否该 404 属职务档隐私口径
（page.tsx:54 之前另有 id 合法性判断），不在本条缺陷范围内——本条只针对
「把非 404 的失败也报成 404」。
