## 熊猫站（pandapt.net）好友买卖功能深度调研

**产出**：`_doc/熊猫站好友买卖功能深度研究.md`（完整玩法/数值/架构/借鉴建议）

### 结论速览
- 不是小游戏，是**挂在 NexusPHP 上的重型经营养成子系统**：10 个页面、45 个后端 action、Lv.1→100 经营等级线。
- 四层结构：交易层（身价买卖/挖角/追回/赎身/放生/包养）+ 养成层（五维/天赋/关系 5 阶/心情/15 种工作）+ 经营层（事务所委托 + 每日放映）+ 收集层（250 部电影海报 + 三种拍卖模式）。
- 真实意图：**给站内过剩魔力值造可回收泄洪阀**（槽位 12 万起/维护费/研修 3 万/抽水 8%），同时用日课拉高 DAU。
- 技术：服务端渲染壳 + 内联 `const bootstrap={...}` + Vue 2.7.16 + Element UI；**单入口 `ajax.php`**，`action=xxx&params[k]=v` → `{ret,msg,data,rid}`。
- 关键设计：**全部数值配置服务端下发**，前端只有校验常量；提交带 `request_uuid` 幂等。
- 实测数据（2026-09-17 16:29）：市场挂牌 911 人，抽样 87% 已有主人，身价集中在初始 10,000；被查账号经营等级全是 Lv.1（等级线刚上线 2026-08-18，**经验产出与需求严重不匹配**，后期功能实际不可达）。
- 运营状态：页面提示"海报图鉴维护中，当前委托不会掉落海报"。

### 对 FluxTorrent 的最重要借鉴
1. **数值配置必须进库+后台可改**，别硬编码进 Rust 常量（否则调平衡要重新编译发版）—— 熊猫这点做对了。
2. 交易类接口**必须幂等**（唯一索引 / request_uuid）。
3. 主题与机制解耦：熊猫把"电影海报"硬编码在页面里；FluxTorrent 应做成 `theme = movie|music|book|education|generic` 配置，机制不变只换素材表。
4. 文案层有合规风险（"佣人/娇宠/暖床"），正规场景必须重做措辞。

### 方法论沉淀（可复用）
- **会话复用**：PT 站全站需登录，直接抓只会拿到登录页。让用户从浏览器 F12 提供 `c_secure_*` cookie（NexusPHP 会话凭据），即可用 Python 复用登录态。
- **不要试图读浏览器 cookie 库**：Edge 运行时会独占锁定 `AppData\Local\Microsoft\Edge\User Data\Default\Network\Cookies`，Bash 沙箱与 PowerShell 两个通道都复制不出来（WinError 32 / Errno 13）。直接找用户要 cookie 最快。
- **NexusPHP 逆向套路**：抓页面 HTML → 抽内联 `<script>` → 找 `fetch('ajax.php')` 与 `post('xxx')` → 得到 action 全集 → 直调只读 action 拿结构化 JSON（比解析 HTML 高效得多）。
- **安全约定**：调用第三方站点接口时，脚本内置只读 action 白名单（`ALLOWED` 集合），http 层直接拒绝写操作，避免误触真实账号资产。

## 社交经营玩法改造方案：《片场》

**产出**：`_doc/社交经营玩法设计方案-片场.md`（诊断 + 主方案 + 2 个备选 + MVP 路径）

### 核心诊断（熊猫版为什么不好玩）
三个根上的问题，不是数值问题：
1. **参与被动 → 负向社交**：87% 的人是"被买"的，被买者获得羞辱感而非乐趣；靠社交压力驱动留存，长期伤社群。
2. **日课无决策**：15 种工作 / 4 种互动 / 3 个放映游戏，没有一个需要取舍，算完就结束。
3. **与站点真实行为脱节 → 零和抽税**：游戏产出跟做种/发布毫无关系，玩家互转魔力值、系统抽 8%。关掉它对站点做种数据毫无影响。市场因此是死的（身价全在初始值附近）。

### 三条转换原则
被动占有 → 自愿结盟；点一下就收益 → 有代价的抉择；孤立小游戏 → **真实站点行为是唯一产出引擎**。

### 主方案要点
- **《片场》**：玩家自愿报名进组，5 个岗位（摄影/剪辑/配乐/美术/导演）分别对应真实行为（上传量 / 发布 / 社区 / 冷门保种 / 管理），岗位互斥产生真实取舍。
- **真实行为驱动**：片场进度由 tracker 的真实数据推动 → 玩这个游戏 = 在站点做贡献 → 天然反刷、天然反哺站点。这是熊猫做不到、FluxTorrent 做得到的（数据在自己手里）。
- **谈判机制**：报名要报价，出品人可还价/拒绝；报价过高没人要、过低自己亏。这是熊猫完全缺失的博弈层。
- **赛季制（4 周一轮）**：换主题换规则，季末重置但荣誉沉淀为徽章；新人同起跑线，解决"线性永久成长"。
- **信誉分替代身价**：不可交易，只有违约会掉；从"被挖角焦虑"变成"想被好导演选中"。
- **正和经济**：产出由系统按真实贡献**发行**（而非玩家互转），把"通胀治理"从加税变成按贡献发行。

### 备选
- **A《艺人工会》**：保留买卖框架，只改"自愿挂牌 + 合约有期限 + 被买者拿分成"，可复用熊猫 80% 后端，改造量最小。
- **B《片酬竞拍》**：交易对象改成"本周产能分成权"，保留竞价刺激、去掉人身占有。

### 落地节奏（重要）
**MVP 先做 2 周验证**：只做摄影+美术两个岗位、4 人 1 周 1 轮、产出只给魔力+徽章、不做谈判。**埋点验证唯一假设：参与玩家的做种时长/上传量相比未参与玩家是否显著提升**。为负或持平就止损回备选 A。

### 其他
- 主题可参数化：`theme = film | music | book | education | generic`（片场/乐队/编辑部/课题组/项目组），机制不变只换素材表。
- 顺带解决合规：自愿协作的"剧组"设定文案干净，可直接用于教育站等正规场景；熊猫那种措辞上不了台面。

## 深化方案：协作玩法引擎与站型适配

**产出**：`_doc/协作玩法引擎与站型适配-深化方案.md`
**触发问题（用户提出）**："剧组片场是不是只适合影视类的站？" —— 问得准，v1 只用"换皮"两个字带过，不够。

### 核心回答
**机制通用，影视只在叙事层。** 拆三层：
- L3 素材层（图标/色板/产出物贴图）← 影视专属
- L2 叙事层（片场/剧组/摄影/成片/票房）← 影视专属
- **L1 引擎层（组队/档期/岗位互斥/真实行为采集/分账/赛季/信誉）← 与站型完全无关**

真问题：隐喻自带基因，硬套会显廉价 → 正确做法不是换名，而是**机制提成引擎（写一次）+ 叙事降成主题包（每站型一套）**。

### 原创分析工具：玩法对象是"人"还是"资源"
| 代际 | 对象 | 代表 | 评价 |
|---|---|---|---|
| 一代 | 人（被支配的资产） | 熊猫《好友买卖》 | 负向社交 |
| 二代 | 人（平等协作者） | 《片场》 | 正向，但依赖"愿意组队"的社群氛围 |
| 三代 | **资源（人作为伙伴）** | 抢救断种等 | **最干净 + 直接产出站点价值** |

**判断标尺：一个玩法越依赖"主题包装"才能成立，说明它离站点原生越远。**

### PT 原生玩法三件套（不需任何主题包装，全站型通用）
1. **《抢救断种》Rescue**（最推荐）：扫"做种数<N 且发布>M 天"的资源 → 组队认领 → 恢复健康做种 → 资源永久标记"20XX 年被 XX 拯救"。对象是资源、零社交压迫、陌生人也能协作、天然反刷。
2. **《接力保种》Relay**：长期保种任务切 N 棒，认领一棒、到点交接；压力来自"别拖累队友"（平等、正向），与熊猫"主人压榨佣人"（上下、负向）性质完全不同。
3. **《拓荒首发》Frontier**：冷门分类首发竞争，首个达标者获"拓荒者"标记，用荣誉引导内容多样性。

主线用主题包（发挥站型特色），日常用三件套（全站通用）；三件套可独立上线。

### 机制深化（让"有抉择"变硬）
- **岗位专精**：同一岗位连续做有专精加成，换岗衰减一半 → 产生"专精 vs 多面手"定位抉择
- **岗位羁绊**：摄影+剪辑=商业片（高魔力低稀有）、美术+配乐=文艺片（低魔力高稀有）、三岗齐备=大制作 → **"招募谁"变成真策略**（熊猫完全没有这层）
- **团队规模权衡**：小队稳定低风险 / 大队高产出高协调成本
- **赛季规则变形**（不是换皮）：科幻季加特效岗、恐怖季产出×1.5但违约惩罚翻倍、纪录片季冷门保种权重×2、经典季取消个性化
- **师徒**：老带新，师傅得荣誉不给数值（防刷）
- **信誉只影响准入资格，不剥夺已得**（避免挫败感）

### 通用程序约束（FluxTorrent 特有）
- **总开关默认关闭**（通用程序装上就跑出个"好友买卖"会让不想做社区运营的站长尴尬）
- 模块独立开关；《抢救断种》建议默认开启（成本低、直接反哺站点）
- 降级路径：不影响主体功能、不参与不亏、可一键下线且保留历史数据、可灰度
- 数值全配置化进库

### 路线图重要调整
**P0 从"片场"改为"抢救断种"**：不需主题包装、依赖最少（不要信誉和赛季）、产出可量化、验证的是最底层假设——"游戏能不能驱动真实行为"。这个不成立，后面的协作经营/谈判/赛季全都不用做。片场降到 P1，且以主题包形式实现。

### 站型→主题包决策表（选型标准）
> **主题必须从站点的真实资源里长出来，不能从"哪个游戏好玩"里选。**
影视→片场；音乐→乐队；教育→课题组；电子书→编辑部；游戏→汉化组；综合站→**按板块挂载多主题包，引擎层进度互通**（这是相对熊猫的结构性优势，熊猫把海报硬编码在页面里）。

## 实施深化：可信行为体系与经济模型（v3）

**产出**：`_doc/协作玩法实施深化-可信行为与经济模型.md`
**动机**：v2 留了个命门没答——**产出锚定真实行为，那行为能伪造怎么办？** 熊猫的零和系统天然免疫（产出不挂钩行为），我们的正和系统一旦被刷就崩盘。这是地基，必须正面解决。

### 核心结论：复用站点已有反作弊，不另建一套
- **游戏只消费站点"已被反作弊过滤过"的行为数据**，不新增采集通道
- 作弊代价必须是**封号**（威慑力），而不是"少赚游戏币"（毫无威慑）
- 被标作弊 → 游戏进度冻结 + 未结算贡献作废

### 行为可信分级（权重与伪造成本正相关）
长期做种 1.2 / 冷门保种 1.5 / 有效上传 0.8 / 发布 0.6 / 社区 0.2 / **纯发帖 0（不给产出，只给人气分）**。
把权重压在站点真正稀缺的行为上，直接消灭灌水动机。

### 最脆弱一环：自产自销刷"冷门保种"（必须三条同时生效）
1. 资源需**发布满 30 天**才计入
2. 该资源须曾有 **≥3 个不同外部做种者**（证明不是自娱自乐）
3. **发布者本人保自己的种不算**（本分不是贡献）
叠加后刷分成本远高于正常做种。

### 延迟结算（给反作弊留观察窗）
`pending`（计入预估不发钱）→ 7 天观察窗 → `verified`（进可结算池）→ 赛季 `settled` 发行；期间被标作弊 → `voided` 清零。
先例：PT 站的 H&R 本来就是延迟考核，玩家接受度没问题。副产品：顺带解决"赛季末冲量"。

### 贡献地板（不产出，但不禁止参与）
分享率 ≥ 1.0 / 无 H&R 欠账 / 非作弊标记。低于地板仍可玩可看可拿荣誉，只是没有魔力值收益。

### 经济模型：次线性发行 + 反向定标
- 否决"按量线性发钱"（必然通胀，等于重走熊猫建抽水出口的老路）
- 否决"固定池按份额分"（零和感，内卷劝退）
- **采用**：`全站发行 = k × (全站有效贡献)^0.75`，个人按份额分 → 自己多做赚更多（正反馈），全站都多做则人均略降（控通胀），没人玩则趋近 0（不凭空印钱）
- **反向定标（关键）**：先定通胀目标反推池子上限 → `(目标年通胀率 × 全站魔力值总量 − 站点原有年产出) / 赛季数`。**游戏从"通胀源头"变成"通胀调节器"**，这是熊猫做不到的
- 稀缺贡献用凸函数（log 加成），抢救类用定额高额奖励（因为保种 1TB 边际价值递减，救活一个濒危资源边际价值极高）

### 数据模型核心
`social_season / social_contract / social_member / social_contribution / social_reputation / social_issuance` + 资源层 `rescue_target / rescue_team / rescue_honor` + 主题层 `social_theme`。
三个关键点：contribution 的 **pending→verified→voided 状态机**是防伪载体；`source_ref` 可溯源；`social_theme` 让加主题 = **插一行数据而不是改代码**。

### 接口对比洞察
熊猫 45 个 action 里一大半在处理"玩家互转的结算与反套利"（追回资格/包养窗口/批次逐项提示）。我们所有产出都是**系统单向发行**，没有双方对账、余额不足、部分成功那一坨边缘情况，**action 数量未必更少但复杂度低得多**。

### 观测与预案
- **北极星指标（唯一）**：参与玩家的「周有效做种时长」与「冷门保种数」相比未参与玩家的差值。其他都是辅助。
- 灰度 10% 开启 + 10% 对照 + 80% 现状，观察 4 周。差值持平说明只是"零和搬家"，为负**立即止损**。
- 三条降级（全部是配置项，不需重新部署）：没人玩→只留《抢救断种》；被刷→只留荣誉不发币；通胀→收紧系数 k。
- 护栏指标：发行量/全站总量、自产自销比例、参与者作弊率、违约率、作废率。

### 实施顺序（重要）
`G 埋点 → A 贡献采集 → B 状态机 → E 抢救断种 → C 发行账本 → D 引擎玩法 → F 主题包`
- **G 先上**：没有对照数据，后面全是拍脑袋
- **A→B 先于 C**：先有可信行为数据，再谈发钱
- **E 排在 C 之前**：抢救断种不依赖发行体系，能更早验证核心假设

## 落地深化：冷启动、玩家旅程与数值标定（v5）

**产出**：`_doc/协作玩法落地深化-冷启动与数值标定.md`
**动机**：v4 解决"不被玩坏"，但没解决"**跑不起来**"——尤其是冷启动这个社交玩法的头号杀手。

### 头号洞察：熊猫的"不好玩"和"87% 参与率"是同一件事的两面
熊猫**不需要冷启动**，因为它不要求同意就把新人分配出去（账号 `gntv` 的 `trade_type = seed_init`「初始归属给 whlwhlwhl」）。**它用强制拉入换来了 87% 覆盖率。**
我们选择自愿（正确），就失去了这个杠杆，必须自建冷启动。经典死法：第一批契约没人发起 → 招募页空 → 新玩家看到就走 → 死亡螺旋。

### 冷启动五条解法（按优先级）
1. **先做不需要组队的玩法**（抢救断种单人可认领）
2. **系统托底队友**（人数不足时 NPC 补位，保证流程跑得完，产出打折）
3. **梯度解锁社交**（单人→双人→小队→联赛，别一上来就组队）
4. **种子用户**（定向邀请做种榜前 N，跑出前 10 个示范契约）
5. **空列表永不展示**（没条目时显示"X 天后开放"倒计时）

**这重新解释了实施顺序：E（抢救断种）不只为"依赖少"，它是整个玩法的冷启动入口。**

### 自我批评：我的方案里也有社交压力
v2 批熊猫"用社交压力驱动"，但契约机制同样有压力。**分界线：压力必须来自自愿加入、可预见、可选择、可退出的关系。**
- 负向：损失由他人决定、无法拒绝（被买、被挖、被放生）
- 正向：收益依赖协作，但自愿、知道队友是谁、能选能退

**四条防护**：只在自愿关系施压；惩罚只针对"逃跑"不针对"尽力"；**独狼模式**（单人玩法收益略低但零社交压力）；压力可见可控（进度透明）。
**重要修正：取消团队连坐。** 连坐会让新人不敢加入（"我拖累别人怎么办"）。失败只影响收益，不体现在羞辱。

### 28 天玩家旅程暴露的三个洞
1. **D1~D7 空窗**：认领完没事干 → 需每日微任务（查看濒危清单、投票加急）
2. **D14 首笔收益**：太少 = 直接流失 → 数值标定是生死线
3. **D28 归零**：必须用荣誉页承接，让"归零"读起来像"归档"而非"清零"

### 数值标定（把 k 填上）
- 通胀硬顶：`(目标年通胀率 × 全站魔力值总量 − 站点原有年产出) / 赛季数`，示例 167 万/赛季
- 测算：中度玩家（周做种 200h、冷门保种 5 个）赛季约 2~3 万魔力，占其做种收益约 25%
- **硬约束：游戏收益 ≤ 做种收益的 30%**。超过就会"为了玩游戏而做种"，行为扭曲、本末倒置。这是最重要的数值纪律。
- k 不是常量，每赛季按上赛季数据重算

### 其他
- 赛季衔接：结算期设 24 小时只读期；荣誉传承 = 拯救记录永久 / 信誉保留 70% / 专精重置
- 异常：成员被封则契约不失败（进度按比例下调）；资源被删则目标作废不扣分
- 实施计划 P0~P5，**门禁：P1 单人玩法"≥5% 活跃用户完成过抢救"不达标就不进 P2**
- generic 主题包已给出可直接入库的 JSON 样例（守护者/分享者/发布者/联络人/统筹）

## 契约机制修补与 P0 实现细节（v7）

**产出**：`_doc/契约机制修补与P0实现细节.md`

### 关键勘误：v6 的贡献反查方案不成立
v6 写"契约期内 seeding 流水自动归属契约"——**错**。核对 `jobs.rs` 的落库语句：
```sql
INSERT INTO spark_ledger (id, user_id, amount, kind, idempotency_key) VALUES (...)
```
**没有 ref_type / ref_id**。因为 `seeding_reward` 是**每用户每小时聚合一条**（覆盖当时所有做种），本来就不对应单个种子 → 无法反查某个种子的贡献；即使按时间窗过滤也会把无关种子算进来。

**正确方案：从 `snatches` 表算增量**（`(user_id, torrent_id)` 粒度，有 `seeded_seconds` / `uploaded`）：
- 加入契约时记基线 `seed_seconds_begin` / `uploaded_begin`
- 结算时算 delta
- **和现有 `seed_preserve` 的基线/delta 做法完全一致**，运维直觉统一
- 精度到单资源，根治"挂无关种子刷契约贡献"

### 10 个设计漏洞（本轮补齐）
1. **契约贡献范围**：只算契约目标资源（防挂无关种子）
2. **信誉互评可互刷** → **事实驱动 90%（不可伪造）+ 好评 ≤10%**，每季 5 次配额
3. **赛季末发起契约必失败** → 赛季结束前 7 天禁发起新契约
4. **一资源多契约** → 部分唯一索引 `WHERE status IN (0,1)`
5. **资格校验时机** → 加入时就校验（不是结算时才发现不合格）
6. **NPC 托底队友取消** → 改成"**允许 1 人契约**"，人数是加成不是门槛（比 NPC 简单得多，也符合冷启动思路）
7. **资源被非成员自然救活** → 算契约成功，但荣誉文案要诚实（"推动资源恢复健康"而非"我拯救了它"）
8. **结算事务一致性** → 跨表结算必须显式单事务
9. **幂等键** `social:rescue:{contract_id}` / `social:season:{season_id}:{uid}`
10. **目标被删** → 契约进入独立状态 `5=作废`，不扣信誉

### 核对结果（上轮标记的不确定项）
- `site_settings(name TEXT PRIMARY KEY, value TEXT, updated_at)` ✓ 上轮推测正确，`ON CONFLICT (name)` 可用
- `seed_preserve` 后续加了 `seed_time_begin` / `uploaded_begin` / `last_settle_at`（0042）

### P0 实现要点
- **不建清单表**：濒危是动态状态，实时查 `torrents` 即可（口径抄 `seeding_reward` 的濒危判定 `seeders<=1 AND times_completed>=3`）
- 「抢救目标」= 3 个做种（脱离危险）；「健康」= 7 个（复用 `preserve_exit` 口径）——两者不同，文案要区分
- **P0 的真实目的不是功能，是拿数据**：埋点 `rescue_claim_intent_click / rescue_list_view`，**>15% 才进 P1，<5% 要重想钩子**
- P0 全部是新增代码，不改现有逻辑 → 风险极低

### 开放问题（诚实列出）
seeders=0 的资源如何处理 / 跨站资源 / 多分类分组 / 赛季长度与站点规模的关系 / 信誉初始值 1000 待校准

## 组队结算 job 与单人隔离（v11）

### 动手前发现的冲突（必须先隔离）
现有 `resurrection_settle`（`jobs.rs:920`）判据是「**领取者本人**做到 required_hours 且仍在做种」，
全额 5000 给 `r.user_id`。而组队任务的 `r.user_id` **就是队长** → 队长会被**双发**
（单人结算一次 + 组队分账一次），队员被绕开。
**处置**：给 `resurrection_settle` 加 `AND r.team_id IS NULL`（1 行，向后完全兼容）。

### 新增 job：`social_team_settle`
挂在 hourly tick，紧跟单人结算之后（`with_lock(&db, "job:social_team_settle", ...)`）。
- **判据**：团队增量合计 ≥ `required_hours × 3600`，且至少一名成员仍在做种
  （采纳「团队总和」而非「每人各自达标」——组队语义是「资源被保种足够久」，好处是**分摊**而非拔高总量）
- **分账**：按 `delta` 占比；整数除法余数落排序末位，总额守恒（实测 5000 → 2777 + 2223）
- **落点**：`spark_ledger`（`kind='social_team_reward'`，幂等键 `social:team:{team_id}:{uid}`）
  + `users.spark_balance` + `social_team_member` 回填（`contributed_sec`/`settled_amount`/`join_status=4`）
  + `rescue_honor` + 站内信

### 可靠性：比现有实现更稳
现有 `resurrection_settle` 用「CAS 置 done 后发奖」——若发奖中途崩溃，`status` 已是 done，
下轮 `WHERE status='open'` 不再匹配 → **奖励永久丢失**（注释说的"幂等键可补发"只覆盖同轮重试）。
本 job 改为：**以 `settled_at IS NULL` 作「未处理」标记**，发奖/写荣誉/置标记**同一事务**
→ 崩溃则整体回滚，下轮重新处理 ✓

### 测试结果（全通过）
造数：队伍 2 人、团队增量 900000s（阈值 864000s）、均在做种 → `docker restart flux-worker` 触发首轮 tick：
- `resurrections.status=done`；`social_team` `status=2` + `settled_at` 已置
- 分账 user2 500000s→**2777**、user3 400000s→**2223**（合计恰好 5000）
- 流水 2 条 / 荣誉 1 条（`uids={2,3}`、`total_sec=900000`）/ 站内信 2 条
- **幂等复测**：再重启一次 worker，流水仍 2 条、总额仍 5000 → **无重复发放** ✓
- 清理与余额回滚干净

### 踩的坑（脚本层，非后端）
`psql -c` 执行 INSERT/UPDATE/DELETE 时**结果在第一行、命令标签（`INSERT 0 1`）在最后**。
一度用 `stdout.strip()` 取全段 → `team_id` 变成 `"3\nINSERT 0 1"` → 后续 SQL 全错位却**不报错**，
表现为"数据莫名其妙没写进去"。**取第一个非空行。**

## 契约失败流转与信誉体系（v12）

### 调研发现（两个）
1. **`resurrections.status` 的 `expired` 是"声明了但没实现"**——全仓库没有任何代码把它置为 expired，
   和 `social_reputation` 一样属于建表时预留、逻辑从未落地。
2. **我 0102 建 `social_team` 时漏了 `deadline_at`**——没有期限就无法判定超时。

### 处置：新增 0103 迁移，而不是改 0102
0102 已执行且 `_sqlx_migrations` 有记录。**sqlx 校验迁移文件 checksum**，改已执行的迁移会直接启动失败
（`migration 102 was previously applied but has been modified`）。
0103 补：`deadline_at` 列（回填 `created_at + 14 days`）+ 部分索引 + 6 个信誉参数配置项。

### 设计口径（三条）
- **不连坐**：失败只记一次事实（信誉 −5）+ 通知，不罚款/不追责/不公开点名
  —— 连坐会让新人不敢加入，而新人恰恰最需要参与
- **区分「逃跑」与「尽力」**：完成 +20 / 到期未达标 −5 / 中途退出 −15
  —— 否则等于逼人在快失败时提前跑掉
- **信誉只影响准入资格，不剥夺已得收益**；区间 [0, 2000]，初始 1000
- 失败文案刻意平实，强调「已产生的做种时长仍计入做种收益，不受影响」

### 实现
- 新接口 `POST /social/team/leave`（队长不能退出；退出后不再参与结算）
- 新 job `social_team_expire`（**排在成功结算之后**——恰好卡在期限内达标的应算成功；
  事务内用 `status IN (0,1) AND settled_at IS NULL` 做 CAS 与结算互斥）
- `social_team_settle` 补上完成信誉 +20

### 一个有意为之的设计点
**worker job 不检查 `module_social` 开关**（只有 API 检查）——模块关闭时，已存在的契约必须能收尾，
否则那些队伍永远悬在"进行中"、成员拿不到奖励与信誉。与 `resurrection_settle` 现有行为一致。

### 端到端测试（三场景全通过）
| 场景 | 关键结果 |
|---|---|
| 超时失败 | `status=3` / `fail_reason=deadline_exceeded` / `resurrection=expired` / 信誉 `995,0,0,1` ✓ |
| 中途退出 | 队长退出 400 / 队员退出 200（−15）/ `join_status` 2=1,3=3 / 重复退出 400 ✓ |
| 成功结算 | `status=2` / 分账 **2777+2223** / `fulfilled_count=1` ✓ |

**信誉串联验证**：`1000 −5(失败) −15(退出) +20(完成)` 完全对得上（user2: 995→1015；user3: 995→980→1000）。
环境完全恢复：`module_social=no`、teams/members/resurrections/reputation/honor 全部归零。

### 踩的坑（全是脚本层）
1. **`team_id` 传成字符串**（psql 返回 str）→ `invalid type: string "7", expected i64`，要 `int()`
2. **三个场景共用一个种子** → `resurrections.torrent_id` 唯一约束导致第二/三场景插入失败
3. **`rescue_honor` 漏清理** —— 它的 `team_id` 是 `ON DELETE SET NULL`（刻意的，为让荣誉留存），
   删队伍带不走荣誉行，必须显式清理

### 完成度
**契约生命周期已完整**：招募 → 进行 → 成功 / 失败 / 退出，四条路径都有落点。
剩余：前端队伍页面（后端齐全但玩家看不到入口）、赛季结算 job、埋点（等上线）。

### 两个方法论发现（本轮最重要的收获）
1. **客户端组件不能用 curl 的 SSR HTML 验证**：标了 `"use client"` 的组件数据靠浏览器
   `useEffect` fetch，SSR 只输出 loading 态 → curl 抓到的 HTML **没有列表数据**，别误判成 bug。
   要用 playwright 看**渲染出的元素计数**（`page.locator('table.nexus-table').count()`），别用字符串匹配。
2. **登录态要设三处，最容易漏 localStorage**：

   | 位置 | 键 | 作用 |
   |---|---|---|
   | cookie | `flux.session` | middleware 存在性判断 |
   | cookie | `flux.token` | RSC（服务端组件）取数 |
   | **localStorage** | `flux.token` | **客户端组件 fetch 读它**（`api-client.ts:68`） |

   只设 cookie → 客户端 fetch 401 → 被 `api-client.ts:105` 重定向到
   `/login?next=…&expired=1`（表现为「明明登录了却被踢到登录页」）。
   **`expired=1` 不是 middleware 加的**（它只加 `next`），是 api-client 收到 401 后加的 —— 这本身就是线索。
   排查时**别怀疑 middleware**（它只检查 `flux.session` 是否存在，4 行逻辑）。

**这个 bug 只有真的把页面渲染出来看才会发现** —— tsc、API 测试、SSR HTML 全部通过。

## 新人考核调研（v15）

### 问题
新人入站后的考核进度在哪里看？同类项目怎么实现？

### 答案：入口在 `/me/exams`
- **路径**：顶栏「更多 ▾」→ **成长荣誉** → **我的考核**

- 派发条件：`u.class_id >= t.target_class AND u.created_at > now() - $exam_onboard_days 天`
  （`exam_onboard_days` 默认 **30**）；认领时快照 `base_uploaded` / `base_seed_seconds` / `base_uploads`
- 指标：`tasks.metric` JSONB —— `upload_delta` / `download_delta` / `seed_seconds_delta` /
  `seed_points_delta` / `uploads` / `subtitles`；`tier` 非空时切**累计口径**（基线视为 0）
- 当前新人考核：任务 id=28「新人转正考核」，`{"seed_seconds_delta": 432000}`（做种 120 小时），
  奖励 2000；实测已有 13+ 名用户被派发

### 同类项目：NexusPHP 自带完整 Exam 模块（本地 `.np-research/np/`）
- **三表**：`exams`（含 `filters` / `indexes` / `is_discovered` / `priority`）、`exam_users`、
  `exam_progress`（**按种子粒度记明细**，有 `torrent_id`）
- **四定时命令**：`ExamAssign` / `ExamAssignCronjob` / `ExamUpdateProgress` / `ExamCheckoutCronjob`
- **后台**：Filament `ExamResource` + `ExamUserResource`（**含 `avoid` / `recover` / `bulkAvoid`**）
- **指标定义**：`indexes` 数组，每项含 `index`（来自 `Exam::$indexes` 枚举）+ `require_value`

### 可借鉴 3 点 / 我们更好 2 点
| 借鉴 | 说明 |
|---|---|
| **豁免 / 恢复** | `avoid` / `recover` / `bulkAvoid` —— 管理组免除或恢复某人考核，**实用性最高**（我们现在只能改库） |

## 考核豁免/恢复（v17，0105）

### 设计：独立标记列，不动 status 枚举
`task_claims.status` 状态机是 0→1/2，`task_settle` 只扫 status=0。
用 status=3 会打断状态机（恢复时还得迁移回 0）→ 改用**独立标记列**：
`exempted_at TIMESTAMPTZ` + `exempted_by BIGINT REFERENCES users(id) ON DELETE SET NULL`（迁移 0105）。
豁免 = 置标记；恢复 = 清空；结算扫描加 `AND exempted_at IS NULL`（task_jobs.rs task_settle）。
**恢复后原记录自然回到结算流**——基线没动，增量口径不受豁免期影响。
部分索引 `idx_task_claims_open ON task_claims (status) WHERE status = 0 AND exempted_at IS NULL`。

### 接口与前端
- `POST /admin/exam-users/{claim_id}/exempt`（仅 `status=0` 且未豁免；CAS `AND exempted_at IS NULL` 防重；记录操作人）
