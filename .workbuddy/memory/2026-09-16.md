### 实测结论
1. **全新建站（测试A）**：ghcr v0.1.0 api 镜像对空库启动 → 94 个迁移全过（镜像只含 0094 及以前，0095-0100 是未提交的工作区文件）→ healthy，health 端点 `{"status":"up"}`。冷启动含迁移约 25s。
2. **版本偏差行为（测试B-1）**：旧镜像 api 对已 apply 更多迁移（100>94）的库启动 → sqlx 立即报错 `migration 95 was previously applied but is missing in the resolved migrations`，crash-loop，**fail-fast 不做静默降级**。这是 sqlx 默认行为，防止旧代码跑新库；但也意味着**一旦在生产先跑了含新迁移的代码（哪怕只一次 api 启动），回滚到旧镜像就永久起不来**，只能恢复 DB 备份。
3. **checksum 修改（测试B-1b）**：篡改已 apply 迁移的 checksum → `migration 90 was previously applied but has been modified` 拒绝启动；恢复 checksum 后正常启动。同号改文件 = 炸。
4. **旧 worker 对新库（测试B-2）**：worker 不跑迁移，0095-0100 恰好全是加可空列/新表 → 意外兼容正常干活。**这是运气不是设计**——0098 snatch_agent_progress 若为 NOT NULL 列就会翻车。

## v0.1.1/v0.1.2 发版与 checksum 行尾事故（接上节）

- **v0.1.1**（0142e51）：工作区 50 文件全提交（0095-0100 六迁移+UDP tracker+附件图床等），消除生产镜像分叉。
- **v0.1.1 实测翻车**：对生产快照库启动报 6 个迁移 `modified`（28/54/57/58/59/61）。
- **根因**：本机 `core.autocrlf=true`，这 6 个文件本地是 CRLF 被 apply 入库（CRLF checksum）；
  git blob 与 CI 是 LF → 官方镜像 LF checksum ≠ 库内 CRLF checksum。其余 94 个本地 LF 无恙。
  **sqlx checksum 字节级敏感，行尾也算**。
- **修复（v0.1.2, 5f931bf+56629e7）**：
  1. `.gitattributes` 锁 `*.sql/*.Dockerfile/*.sh/*.toml/*.yml = eol=lf`；
  2. `scripts/align_migration_checksums.sql` 存量库一次性对齐（值取自 v0.1.1 空库重放权威值，幂等）；
  3. 运维手册 §5.1 补存量站切官方镜像的前置步骤 + 回滚纪律（旧镜像+DB 备份配套）。
- **v0.1.2 验证全通**：生产快照库（对齐后）+ api/worker/tracker 0.1.2 全栈 → healthy、
  worker job 无 ERROR、tracker announce 正常。测试环境已清，生产未动。
- **教训入规**：迁移文件永不修改（含行尾）；新迁移建文件后立即 `git add` 固化行尾；
  Windows 开发机 `git config core.autocrlf input` 或依赖 .gitattributes。
