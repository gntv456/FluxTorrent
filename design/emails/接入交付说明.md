## 3. MIME 结构摘要（本机捕获，69 封）

捕获方式：`python design/emails/smtp_sink.py 2526` 起本地捕获器（只绑 `127.0.0.1`，不转发），
`cargo test -p flux-api --bin flux-api probe_multipart_into_local_sink -- --ignored` 走生产同款
`SmtpConfig → build_smtp → deliver → message` 路径发送 3 语 × 正常/恶意 样本。

| 检查项 | 结果 |
|---|---|
| 邮件总数 | 69（3 语 × 2 输入 × 11 封 + 6 封 generic_notice） |
| `Content-Type` | 69/69 `multipart/alternative` |
| part 顺序 | 69/69 `text/plain` → `text/html` |
| 传输编码 | text = **base64**，html = **quoted-printable**（捕获器不宣告 8BITMIME，走线上同款编码） |
| 字符集 | 两 part 均 `utf-8`，解码无 `U+FFFD` |
| 主题 | RFC 2047 编码，逐封解码正确；无 CR/LF，无 `Bcc:/Cc:/X-` 注入 |
| 链接 | 每封 HTML 4 条 `href`、纯文本 4 条 URL，**相对链接 0** |
| From | `山海驿站 <noreply@local.test>`（显示名 = 站点名） |

示例（invite，zh-CN）：

```
Content-Type: multipart/alternative; boundary=...
Subject: =?utf-8?b?...?=
From: =?utf-8?b?5bGx5rW36amd56uZ?= <noreply@local.test>   ← 山海驿站
--boundary
Content-Type: text/plain; charset=utf-8
Content-Transfer-Encoding: base64
--boundary
Content-Type: text/html; charset=utf-8
Content-Transfer-Encoding: quoted-printable
```

报告：[email-mime-report.json](_shots/email-mime-report.json)；原始邮件：`design/emails/_smtp_capture/*.eml`。

## 4. 转义 / 绝对链接实测证据

恶意输入：`<script>alert(1)</script> & "x"` + 追加 `CRLF Bcc: evil@x.test`，用于用户名、种子名、驳回理由、邀请人、群发正文与主题覆盖。

**HTML part（已转义）**

```html
&lt;script&gt;alert(1)&lt;/script&gt; &amp; &quot;x&quot;
```

**text/plain part（原样保留，换行保留）**

```
<script>alert(1)</script> & "x"
Bcc: evil@x.test
```

- HTML 中不再出现可执行的 `<script>` 标签；纯文本不做 HTML 转义（`&`、引号、尖括号按原字符呈现）。
- 主题行中的 CRLF 被压成空格 → `... "x" Bcc: evil@x.test` 仍在同一行，`header_injection=false`（69/69）。
- 链接：全部 `https://flux.example.site/...` 绝对地址；`relative_links=0`、纯文本相对 URL 0。
  invite 的 4 条：`{base}/register?invite=…`、`{base}/rules`、`{base}/contactstaff`、以及正文 CTA。

## 6. 纯文本交付（追加 1）

### 6.1 生成方式

11 份 `design/emails/plain/<name>.txt` 由 `mailtpl::render_text` **同一实现**输出，UTF-8 / LF / 无 BOM；
不是从 HTML 摘文字。每份固定结构：`Subject:` → 一句「为什么收到」→ 关键信息 → 完整 URL → 安全兜底 → 页脚。

折行规则：**72 列**（要求 68–72），优先空格断行；URL 整行不折，URL-only 行放宽到 **≤120 列**
（64 hex token 的验证链接物理上无法 78 列内断行），在校验 JSON 中按 `urlOnlyLines=2` 单独计数。

### 6.2 11 封 × 13 项通过表

`exists / noBom / lfOnly / subjectFirst / hasWhy / hasContact / placeholders / noHtml / noMarkdown / noEmoji / urlsAbsolute / lineWidth / endsWithNewline`

| 文件 | 13 项 | URL-only 行 |
|---|---|---|
| invite | 全 ✓ | 2 |
| password-reset | 全 ✓ | 2 |
| email-verify | 全 ✓ | 2 |
| review-approved | 全 ✓ | 2 |
| review-rejected | 全 ✓ | 2 |
| application-approved | 全 ✓ | 2 |
| application-rejected | 全 ✓ | 2 |
| appeal-accepted | 全 ✓ | 2 |
| appeal-rejected | 全 ✓ | 2 |
| account-status | 全 ✓ | 2 |
| hr-warning | 全 ✓ | 2 |

`allPass=true`，`files=11`，无 HTML 标签残留、无未替换异常占位符、无 Markdown 符号、无 emoji。
校验：[plain-verify.json](_shots/plain-verify.json)；脚本 `design/emails/check_plain.mjs`。

### 6.3 抽查 3 封逐句对照（纯文本 vs HTML）

**① invite**：纯文本 24 行；HTML 同样的 5 组内容（标题 / 为什么收到 / 邀请人·有效期·邀请码 / 注册步骤 / CTA+兜底 / 安全 / 页脚）。
差异：纯文本去掉了装饰带、印章标签、按钮文案与「复制链接」说明的重复层级；信息条目顺序与数值完全一致。
结论：**内容等价、纯文本更短**。

**② review-rejected**：纯文本含「审核结论：未通过」+ 理由占位、种子 ID / 标题、修改建议 3 条、`{base}/upload`、安全段、页脚。
HTML 的结论块 + 信息块 + 清单与之一一对应；HTML 多一个主按钮（文案「重新提交」），纯文本用同一行的完整 URL 替代。
结论：**等价**，纯文本无按钮视觉层级。

**③ hr-warning**：纯文本含预警结论、种子 ID / 标题 / 已做种 / 要求 / 截止时间、`{base}/me`、安全段、页脚；与 HTML 信息块逐项相同。
差异：HTML 的结论块有语义色（琥珀）与印章标签，纯文本用「预警：做种时长不足」一行表达；数值与截止时间完全一致。
结论：**等价**，纯文本去掉颜色语义，靠文字标签补足。

## 9. 未完成项（如实列出）

1. **真机收件箱未验证**：没有可用的真实收件地址，本轮只做本地 SMTP 捕获 + MIME/渲染核查；送达率、垃圾箱、SPF/DKIM/DMARC 均未验证。
2. **Reply-To 未设置**：`site_settings` 无职员联系邮箱键（`SITEEMAIL` 已删除，`/contactstaff` 是站内工单），不臆造地址。
3. **i18n**：使用既有 `users.site_language`（`en/chs/cht` → `En/ZhCn/ZhTw`，未知值回落 zh-CN）。
   匿名收件人（被邀请者、入站申请人尚未注册）无语言偏好 → **固定 zh-CN**，属遗留项；未加字段、未加迁移。
4. **From 显示名**：`accountname` 是 SMTP 认证账号（邮箱），不能当站点名；本轮显示名取 `site_name`。
5. **outbox 存储**：`mail_outbox` 仍只有 `subject/body` 两列，HTML 以 `\u{1}FLUXMAIL2 <json>` 前缀塞进 `body`；
   旧行无前缀按纯文本投递，坏 JSON 回退纯文本（不丢信），但这是临时约定，后续建议加列时再迁移。
6. **空数据降级**：驳回理由/申诉说明为空时，文案为「未填写具体理由」，不编造；种子标题空按语言显示「（标题不可用）」。
7. **URL 行宽例外**：email-verify 的 64 hex token 链接在纯文本中超过 78 列，按「URL-only ≤120 列」处理。
8. **反色对比度为模拟值**：`invert(1) hue-rotate(180deg)` 是近似，非 Android Force Dark / Outlook 高对比的真实算法。
