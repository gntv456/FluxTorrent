# FluxTorrent 站点通知邮件设计说明

> 本轮只出样图与设计说明，**没有改动任何生产代码，没有发送任何真实邮件，也没有接入 SMTP**。
> 样图位于 `design/emails/`，索引页 `design/emails/index.html` 可直接双击打开；验证截图位于 `design/_shots/`。

> **当前有效版本：第 12 节「统一母版规范」。** 第 1–11 节保留为过程记录；
> 其中第 10 节（潮汐风）与第 11 节（两封山海经）描述的方案**已被第 12 节取代**，不再代表现状。

---

## 0. 结论先行

- 站点现有 **16 类邮件触发点**，其中 **15 类都是 `text/plain` 裸文本**，只有邀请函是 `multipart/alternative`（HTML + 纯文本）。所有邮件正文均为 Rust 代码里硬编码的中文，**没有邮件 i18n**。
- 本轮交付 **11 封独立 HTML 样图 + 1 个索引页**，覆盖邀请、找回密码、邮箱激活、种子审核（通过/拒绝）、入站申请（通过/拒绝）、申诉（成立/未通过）、账号状态、H&R 预警。
- 设计使用 **600px 表格布局 + 全内联样式 + 系统字体栈**，不依赖外部 CSS/JS/Web 字体、不使用 flex/grid、不使用背景图片、不放追踪像素。
- 视觉全部取自 `apps/web/app/styles/base.css` 的品牌令牌。**没有自编十六进制色值**。其中主按钮刻意使用 `--text-strong` 深海军蓝而不是 `--sky-deep`，因为后者在白底上的对比度只有约 3.6:1，不满足邮件正文 4.5:1 的可达性要求。
- 浏览器真实渲染验证：**40 组检查，0 横向溢出**；600px 下最大 `scrollWidth` 恰为 600，375px 下恰为 375；暗色模式实测 H1 14.50:1、正文 10.63:1、按钮 7.33:1；图片屏蔽态 4 封抽查均为 `visibleImgs=0` 且正文文字完整保留。
- **未被真实邮件客户端验证**：Gmail / Outlook / Apple Mail 的真实渲染、Outlook.com 强制反色、QQ/网易邮箱的图片代理均未实测，属于基于 CSS 支持面的静态推断（详见第 6 节）。

### 1.3 发信配置

| 项 | 现状 | 结论 |
|---|---|---|
| SMTP 来源 | `site_settings` 的 `smtp_host / smtp_port / smtp_from / accountname / accountpassword / encryption`，缺省回退环境变量 `SMTP_URL / SMTP_FROM` | 后台配置优先 |
| 端口/加密 | `ssl` → 465（默认）、`tls` → 587、`none` → 明文 | 已支持三种 |
| 发件人 | `smtp_from` 原样 `parse()` 成 `Mailbox` | **没有 display name**；`From` 直接是地址 |
| 回复地址 | 无 | **没有 `Reply-To`**；用户回复邮件会回到发件邮箱，但不一定进工单 |
| 站点基址 | `PUBLIC_SITE_URL` → `PUBLIC_WEB_URL` → `PUBLIC_API_URL` | 已统一收口到 `mailer::site_base()` |
| 退订 | 无 | 事务邮件本不需要；但群发邮件**没有退订入口**，存在合规与投诉风险 |
| 隐私链接 | 无 | 站点目前没有 `/privacy` 页面，页脚不应凭空放一个死链 |
| 追踪像素 | 无 | 本轮也不引入 |
| 邮件 i18n | 无 | 正文中文硬编码；仅站名、审核主题模板可由后台覆盖 |

## 2. 设计决策

### 2.1 为什么这样排版

1. **600px 单列 + 卡片**：邮件客户端最稳的宽度；不尝试双列，避免 Outlook 下塌成堆叠。
2. **首屏三件事**：每封邮件在 H1 上下先回答「为什么收到」「需要我做什么」「关键结论/数字」，图片屏蔽时也一样。
3. **信息块代替表格正文**：有效期、编号、邀请码、做种时长放在浅底信息块里，标签 12px、值 14px，便于扫读；不使用图片承载。
4. **状态色块**：通过/拒绝/待激活/封禁用 `success/danger/warning-soft` 三组令牌，结论在第一屏就能分辨；不只靠颜色，色块内始终有文字（通过/未通过/封禁）。
5. **单一主 CTA**：每封只有一个实心按钮，文案 2–6 字、动词开头；按钮下方永远有可复制的兜底链接。
6. **安全兜底独立成块**：找回密码、邮箱激活、邀请、封禁这类高风险场景，用警告色浅底块说明「不是你本人操作怎么办」「链接过期怎么办」「联系谁」。
7. **页脚克制**：事务邮件只写「必要通知，不提供退订」+ 站点域名 + 站规 + 联系管理组；不放假隐私链接、不放假退订链接。

### 2.2 为什么这样写文案

- **不用「尊敬的用户」**：直接用「你好 阿澈」「你的朋友 老王」；邀请函用邀请人姓名建立信任。
- **先结论后解释**：种子拒绝的第一句就是「这次没有通过审核」，原因单独成块；申诉结果第一句就是「申诉成立 / 未通过，原处理维持」。
- **拒绝必须可操作**：拒因具体到「标题缺分辨率与片源、简介缺 MediaInfo」，并给 3 条修改建议与申诉入口，不写「不符合规范」。
- **找回密码不展示任何账号信息**：不写用户名、不写邮箱，只写「有人（希望是你）申请了重置」；这能降低转发/误发导致的信息泄露。
- **过期有第二条路**：找回密码给「回忘记密码页重新申请」，邮箱激活给「邮箱验证页重发」，邀请给「有效期与名额」，申请给「重新申请」。
- **数字/单号用等宽感排版**：`font-variant-numeric: tabular-nums` + `letter-spacing: .04em`，不加载真等宽字体，Outlook 不支持时自然退化为普通数字。
- **英文与繁中不是直译**：英文用 `Accept invite`、`Set new password`、`View torrent` 这类动作短语；繁中用「電子郵件」「帳號」「申訴」等台湾用语（详见第 4 节）。

### 2.3 可达性与反垃圾

- 图片只有 logo，`alt` 为站点名，旁边始终有文字站名；状态与关键数字全部是文本。
- 正文对比度：`--text-body` 对白底约 8.1:1；`--text-faint` 对白底约 5.34:1；按钮白字对 `--text-strong` 约 13.9:1；结论色块均在 4.5:1 以上（见第 6 节实测/计算）。
- 每封只有一个主 CTA；链接文字是「接受邀请」「设置新密码」「查看种子」等，不使用「点击这里」。
- 不使用短链、不堆大写、不连续感叹号、不放 GIF/动画、不放追踪像素。
- 每封都有 preheader，且与正文第一句不重复。
- 主题行控制在 40 个中文字符以内（见第 3 节逐封长度）。

### 2.4 暗色模式与强制反色

- 邮件正文的底色/文字色全部内联；`<head>` 中的 `<style>` 只做 `prefers-color-scheme: dark` 覆盖，并用 `!important` 压过内联样式。
- 暗色值：页面 `#0b1220`、卡片 `#141d2c`、描边 `#2a3a52`、H1 `#e8eef7`、正文 `#c3cede`、次级 `#9aa9bf`、按钮底 `#2fa8ff`、按钮字 `#06121f`、链接 `#8ecbff`。
- **Outlook Windows 桌面版不读 `<style>`，也不做暗色**：它会保持浅色卡片，这是可接受的降级。
- **Outlook.com / 部分客户端强制反色**：不尝试用背景图或固定色块对抗反色；基础版式是「浅底 + 深字」，反色后成为「深底 + 浅字」，文字仍然可读。此点为静态推断，未在 Outlook.com 实测。
- 索引页额外提供 `#fx-dark` 强制暗色预览，仅用于设计评审；生产邮件不包含这段 `#fx-*` 预览 CSS。

### 2.5 图片屏蔽态

- 唯一图片是页头 logo；屏蔽后隐藏 `img`，右侧文字「FluxTorrent / 一句话简介」仍在。
- 没有用图片承载状态、金额、编号、验证码或按钮；因此图片屏蔽不影响任何操作。
- 索引页用 `#fx-noimg` 预览；验证时同时用 Playwright 中断 `logo-mark.png` 请求，双重确认。

### 2.6 纯文本备选

- 每封都给出独立的 `text/plain` 文案（见第 3 节），不是从 HTML  stripping 出来的。
- 纯文本顺序：为什么收到 → 关键信息 → 链接 → 安全兜底 → 页脚。
- 纯文本不使用 Markdown 语法，避免部分客户端显示原始符号；用空行和短横线分段。

## 3. 每封邮件要点与文案

> 样图内为示例数据（如「老王」「阿澈」「#1024」），生产模板应替换为第 5 节的占位符。
> 主题行长度按中文字符计；备选主题行同样控制在 40 字以内。

### 3.1 邀请函 `invite.html`

- **主题行**：`老王 邀请你加入 FluxTorrent`（15 字）
- **备选**：`你的 FluxTorrent 邀请，3 天内有效`（18 字）
- **预览文本**：`老王 给你留了一个邀请名额，3 天内有效，仅可使用一次。`
- **结构**：品牌区 → 「邀请」标签 → H1（邀请人 + 站名）→ 一句话说明站点 → 信息块（邀请人 / 有效期 / 名额）→ 主 CTA → 兜底链接 + 邀请码 → 安全提示 → 页脚
- **主 CTA**：`接受邀请`（4 字）
- **次 CTA/兜底**：完整注册链接 + 邀请码文本
- **安全兜底**：不认识邀请人 → 直接删除；打开链接不会创建账号、不会收费
- **纯文本**：

```text
老王 邀请你加入 FluxTorrent

你的朋友 老王 给你留了一个邀请名额。FluxTorrent 是一个热爱分享的资源社区，注册后即可开始浏览与下载。

邀请人：老王
有效期：3 天（72 小时）
名额：仅限 1 人，一次性使用

接受邀请：
https://fluxtorrent.ptang.top/register?invite=7f3a9c2e5b8d1f4a6c0e9b7d3a5f2c8e

邀请码：7f3a9c2e5b8d1f4a6c0e9b7d3a5f2c8e（注册时也可手动填写）

如果你不认识 老王，直接删除这封邮件即可。仅仅打开链接不会创建账号，也不会向你收取任何费用。

本邮件由 FluxTorrent 会员通过站内邀请功能发出。
fluxtorrent.ptang.top · 站规 · 联系管理组
```

### 3.2 找回密码 `password-reset.html`

- **主题行**：`FluxTorrent 密码重置链接（30 分钟内有效）`（26 字）

### 未验证 / 需要真实客户端回归的点

1. **Outlook Windows（Word 引擎）**：圆角、`max-width`、`<style>`、`font-variant-numeric`、长 token 换行均为静态推断，未在真机 Outlook 打开。
2. **Gmail 网页/移动端**：`<style>` 暗色媒体查询、图片屏蔽代理、375px 下的 padding 折叠未实测。
3. **Apple Mail**：`prefers-color-scheme` 暗色与圆角表现未实测。
4. **Outlook.com 强制反色**：未实测；基础版式按「反色后仍可读」设计，但没有 `[data-ogsc]` 定制。
5. **QQ 邮箱 / 网易邮箱**：国内客户端对 `<style>` 与图片的处理未实测；本轮只保证「无图片也能读」。
6. **真实 SMTP 投递**：未发送任何真实邮件；SPF/DKIM/DMARC、发件人声誉、退信处理未验证。

## 8. 接入清单（最小后端改动）

> 本轮**不出生产模板文件**。以下是把样图变成真实邮件所需的最小清单，按优先级排列。

### P0：不改就无法发送 HTML

## 10. 底图 / 纹理层补充（第二轮）

> 用户反馈：样图整体白底、缺氛围。本轮为 11 封邮件补一层**纯 CSS 生成**的装饰底图，并新增一个 375px 图片屏蔽预览与一列降级对照。未改动生产代码，未新增图片资产。

### 10.1 选型：为什么不用真图片底

先盘点了站点现有底图资产（`apps/web/public/backgrounds/`）：

| 资产 | 体积 | 为什么不适合进邮件 |
|---|---|---|
| `site-tide.svg` | 8.4 KB | Gmail 及多数客户端不渲染 SVG 作为邮件图片，`<img src="*.svg">` 会被剥离或显示为空 |
| `login-page-tide.svg` / `login-intro-tide.svg` | 9.3 / 9.2 KB | 同上；且是登录页插画，含界面元素，放进邮件像截图 |
| `login-page-tide-photo.jpg` / `login-intro-tide-photo.jpg` | 129.9 / 126.4 KB | 一张就吃掉 150 KB 预算的绝大部分，且需再压 |
| `site-tide-photo.jpg` | 332.9 KB | 直接超出单封体积目标 |

真实图片底还需要三套并行实现：Gmail/Apple 用 `background-image`、Outlook 桌面用 VML `v:background`/`v:fill`、其余客户端退化纯色——维护成本与出错面都大，而且图片被屏蔽时最需要"底图还在"的场景恰好落空。

因此选择 **CSS 渐变 + 重复渐变**：零请求、零体积、图片屏蔽不影响、天然满足"底图不承载信息"。

### 10.2 分级与实现

| 级别 | 邮件 | 高度 | 构成 | Outlook 退化 |
|---|---|---|---|---|
| A 潮汐色带 | 邀请、找回密码、邮箱激活 | 88px | 深海军蓝 → 天蓝 → 浅青的三段 `linear-gradient` + 11% 白色斜纹 + 顶部椭圆光晕 + 3px `#0d1b3e` 底边 | `bgcolor="#1c3f74"` 纯色带 |
| B 轻纹理 | 种子通过/拒绝、申请通过/拒绝、申诉成立/未通过 | 56px | 结论色（薄荷 `#167c63` / 暖红 `#d60000`）8% 斜纹 + 同色淡渐变到白 + 3px 结论色底边 | `bgcolor="#e7f7f1"` / `#ffe9e2` |
| C 警示底纹 | 账号状态、H&R 预警 | 64px | 琥珀 `#936800` / 玫瑰 `#d60000` 8% 斜纹 + 淡渐变到白 + 3px 警示色底边 | `bgcolor="#fff4d6"` / `#ffe4dc` |
| 页面底 | 全部 | — | `#f5faff` + 5.5% 深蓝点阵（`radial-gradient` 平铺 12px） | 纯色 `#f5faff` |

实现要点（以 A 级为例，其余同级只换色值）：

```html
<td class="fx-scene" height="88" aria-hidden="true" bgcolor="#1c3f74"
    style="height:88px;background-color:#1c3f74;background-image:
      repeating-linear-gradient(115deg, rgba(255,255,255,.11) 0 2px, rgba(255,255,255,0) 2px 14px),
      radial-gradient(320px 160px at 16% 0%, rgba(255,255,255,.42) 0%, rgba(255,255,255,0) 70%),
      linear-gradient(180deg, #0d1b3e 0%, #1c3f74 45%, #2f86c8 72%, #bfe6f7 100%);
    border-radius:16px 16px 0 0;border-bottom:3px solid #0d1b3e;font-size:0;line-height:0;">&nbsp;</td>
```

- 三层背景在同一 `background-image` 里按"上层在前"声明：斜纹压渐变、光晕在最上，只发一次 CSS 声明，Gmail 支持多背景。
- `bgcolor` 属性与 `background-color` 双写，Outlook 桌面丢弃 `background-image` 后仍是一块与色带同色系的纯色。
- 色带内**没有任何文字**，只有 `&nbsp;`，并标 `aria-hidden="true"`，屏幕阅读器与搜索引擎都不会把它当内容。
- 结构分隔仍用 `border-bottom`（实线，Outlook 也支持），没有让底图兼职分隔线。
- 色带底部与卡片白色之间用浅色收尾（`#bfe6f7` / `#ffffff` / `#fffaf0`），避免出现硬边。

### 11.3 白底回退：深色品牌区 + 浅色正文区

**这是本轮的硬约束**：玄墨底 + 宣纸字一旦被客户端剥掉背景色，就会变成"白底白字"。采用的解决方式不是给文字加描边，而是**从结构上让文字永远不落在深色上**：

1. 96px 玄墨装饰带内**零文字**：只有一个 `&nbsp;`，并标 `aria-hidden="true"`；品牌名、标题、正文、CTA 全部在下方宣纸卡面。
2. 卡面 `bgcolor="#faf6ec"` 与页面 `bgcolor="#f7f3e8"` 双写属性 + 内联样式；即使 `background-color` 被剥，`bgcolor` 仍给出浅底。
3. 主 CTA 改成**金底玄字**（`#d3a13f` 底 + `#241a05` 字），而不是深底浅字：即便金底被剥、白纸露出来，深字仍然清晰（实测 17.14:1）。
4. 有效期标签同样金底深字，剥底后退化为"白底深字"，信息不丢。
5. 朱砂小印改为**纸面底 + 朱砂描边 + 朱砂印字**（`#f7f3e8` / `#a82e1c` / `#b8431f`）。之前是朱砂实底 + 宣纸字，在极端剥底时会变成浅字落在白纸上；现在两种状态都可见。

|---|---|---|
| 96px 装饰带 | `#0a0f0d` | 纯玄墨色块，竹简竖纹与金晕消失，底边 `1px solid #8a6a1c` 仍在 |

### 11.8 本轮局限

- 未在 Gmail / Apple Mail / Outlook 真机跑；上述客户端结论为静态推断，只有本机 Chrome 是实测。
- 强制反色用 `filter: invert(1) hue-rotate(180deg)` 模拟，不是各客户端真实的强制反色算法；深色装饰带在反色后会变浅，这是模拟下的预期结果，且带内无文字。
- "剥背景"是脚本遍历内联样式删除声明，与某些客户端（如 Gmail 的 CSS 清理器）行为接近但不完全等同；`bgcolor` 在真实客户端的保留率未逐家实测。
- `#fx-noimg` / `#fx-dark` 是设计预览开关，不属于生产模板逻辑；生产模板的暗色只依赖 `prefers-color-scheme`。
- 未测 320px、系统 `forced-colors` 高对比模式、以及图片半加载状态。

### 12.3 尺寸档位（层级靠尺寸，不靠换色）

| 档位 | 装饰带 | 邮件 | 为什么是这一档 |

### 12.4 语义色使用边界

允许出现的**只有三处**：

1. 装饰带底边线（1px，落在玄墨上）；
2. 印章式结论标签（34×34 描边印 + 信息块内的描边小标签，都是纸面底 + 彩色描边 + 彩色字）；
3. 主 CTA（本轮**不启用**：按钮统一金底玄字，避免"按钮颜色=结论"造成含义漂移）。

正文、标题、结论块一律墨色层级（`#232d27` / `#3a453e` / `#55605a`）。语义色不写句子。

| 语义 | 含义 | 底边线（玄墨上） | 印章 / 标签（纸面上） | 用在哪几封 |
|---|---|---|---|---|
| 金 | 无结论，纯品牌 | `#d3a13f` | `#a82e1c` 朱砂印 | 邀请、找回密码 |
| 石青 | 待办 / 需继续动作 | `#5cb3c7` | `#23606f` | 邮箱激活 |
| 石绿 | 通过 / 成立 | `#3fae8f` | `#1f6e59` | 种子通过、申请通过、申诉成立 |
| 朱砂 | 未通过 / 驳回 / 封禁 | `#d0442a` | `#a82e1c` | 种子拒绝、申请拒绝、申诉驳回、账号封禁 |
| 琥珀 | 预警 / 待处理 | `#b07f1e` | `#6b5527` | H&amp;R 预警 |

#### 每个颜色决策的依据（都是实测，不是"看着差不多"）

| 位置 | 最终取值 | 被淘汰的候选与原因 |
|---|---|---|
| 石绿文字 | `#1f6e59` 5.67 / 5.18 | `#2c7a64` 在纸面 4.78 勉强过，落到信息块 `#f1ecdd` 只有 **4.36 → 12px 标签不达标** |
| 石青文字 | `#23606f` 6.54 / 5.98 | `#2e7a8c` 纸面 4.55、落到 `#f1ecdd` **4.16 → 不达标** |
| 朱砂文字 | `#a82e1c` 6.33 / 5.79 | `#c1512f` 纸面 **4.34 → 不达标**；`#b8431f` 5.04 达标，但剥背景落到 `#f1ecdd` 只剩 4.61，余量太薄 |
| 琥珀文字 | `#6b5527` 6.59 / 6.02 | `#b07f1e` 纸面只有 **3.30 → 只能做玄墨上的 1px 线，绝不能做文字** |
| 12px 辅助标签 | `#55605a` 6.07 / 5.54 | 上一轮用的 `#6a746d` 实测 **4.49:1**，刚好差 0.01 不达标；本轮 11 封全部换成 `--text-muted` |
| 金线标签字 | `#6b4a1a` 7.43 / 6.79 | `#8a6a1c` 纸面 4.68 达标但余量仅 0.18；`#b07f1e` 3.30 不可用 |
| 第一印象底边线 | `#d3a13f` | 曾用 `#8a6a1c`（3.83:1），在玄墨上几乎看不出"这条线存在"，第一印象档需要更明确的金线 |
| 警示底边线 | `#b07f1e` | 与金线 `#d3a13f` 区分：琥珀更深、更闷，5.4:1 在玄墨上仍清楚；这样"警示"和"第一印象"不会撞色 |

**为什么「通过」用石绿、不用石青？** 石青在本套体系里只有一个含义：**还没完成、需要收件人继续动作**（邮箱激活、待补充材料）。审核通过、申请通过、申诉成立都是**终局且正向**的结果，如果再出现石青，收件人会以为"还差一步"，去找一个并不存在的操作。反过来，邮箱激活如果用石绿，就等于告诉对方"已经完成"，而实际上账号还没激活。**语义色必须一一对应一个动作状态，不能只按"好看"分配。**

**为什么拒绝类不把朱砂写进正文？** 上一轮 9 封把结论做成彩色文字 / 彩色标签，散落在标题、横幅与按钮上。结果是：红色文字在剥背景 / 强制反色下最难控制，且会让整封邮件看起来像警告。本轮把朱砂收进 1px 线与 34px 印章，正文全部墨色——**结论靠「未通过 · 待修改」这个描边标签表达，不靠满屏红字**。

### 12.6 白底回退与降级矩阵

硬矛盾还是那个：玄墨底 + 宣纸字一旦被剥背景，就变成白底白字。解法不是给文字描边，而是**让文字永远不落在深色上**：

1. 装饰带内**零文字**（只有一个 `&nbsp;`，标 `aria-hidden="true"`），品牌名、标题、正文、CTA 全部在下方纸面；
2. 页面 `bgcolor="#f7f3e8"`、卡面 `bgcolor="#faf6ec"`、信息块 `bgcolor="#f1ecdd"`、结论 / 安全块 `bgcolor="#f2edde"`——属性 + 内联样式双写；
3. CTA 是**金底玄字**，不是深底浅字：金底被剥后白纸露出来，深字反而更清楚（17.14:1）；
4. 印章是**纸面底 + 彩色描边 + 彩色字**，不是彩色实底 + 浅字；
5. 结论标签同理（`background-color:#faf6ec` + 描边），剥背景后退到信息块的 `bgcolor`，仍是 5.79:1。

| 状态 | 触发方式 | 实际发生 | 兜底 | 实测 / 推断 |
|---|---|---|---|---|
| 图片屏蔽 | `#fx-noimg`（`img{display:none}`） | logo 消失，品牌行保留 40px 占位，品牌名退到文字位；**正文、信息块、按钮、装饰带全部完整** | 无图依赖 | **实测**：`visibleImgs=0`，11 封布局高度不变 |
| 暗色客户端 | `emulateMedia({colorScheme:'dark'})` | **钉住纸色、不换肤**：页面 / 卡面 / 正文与浅色一致 | `@media (prefers-color-scheme: dark)` 用 `!important` 把纸色钉回 | **实测**：与浅色同值 |
| 强制反色 | `invert(1) hue-rotate(180deg)` | 纸面变深、墨字变浅，比例基本保持；装饰带变浅，带内无文字所以无影响 | 深色↔浅色成对 | **实测**：最低 4.86（CTA） |
| 剥 `background*`（留 `bgcolor`） | 正则删除所有内联背景声明 | 纸纹、竹简纹、金晕消失，色块由 `bgcolor` 接管；装饰带变成纯 `#0a0f0d` | 5 处 `bgcolor` | **实测**：最低 5.18 |
| 再剥 `bgcolor` | 连属性一起删 | **白底深字**，对比反而最高；装饰带退化为 96/56/64px 空白区 + 1px 底边线 | 无（这是极限态） | **实测**：最低 6.12 |
| Outlook 桌面（无 `background-image`） | 不支持渐变 / 多背景 | 装饰带纯玄墨色块，底边 1px 语义线仍在；圆角退化为直角 | `bgcolor` | **推断**（无真机） |
| Gmail 102KB 截断 | 单封体积 | 最大 10.9KB，不会被截 | 无 | **实测体积** |
| 320px 视口 | — | 未测 | 375 已验证 0 溢出 | **未测** |

> 关于"再剥 bgcolor 后装饰带变成空白区"：这是接受的降级。装饰带的功能是**节奏与品牌停顿**，不是信息载体；一旦背景被完全剥离，我们宁可让它变成一块干净的留白，也不要塞一张兜底图片（那会引入新的图片依赖，违背本轮"不新增图片资产"的边界）。

**暗色模式为什么不换肤？** 上一轮是"玄墨页面 + 宣纸卡面"。但那样一来，如果客户端**同时**做两件事（系统暗色 + 剥背景），页面会变白、页脚浅字 `#b7c0ad` 落在白底上只有 2.2:1——这是一个无法用实测兜住的组合。本轮把暗色钉回纸色，四种状态因此共用同一份实测值，也少了一套需要回归的皮肤。

### 13.2 纯文本规范

`design/emails/plain/<name>.txt` 与实际发送的 `text/plain` part **同源**（都由
`mailtpl::render_text` 生成），不是从 HTML 摘出来的文字；落盘用于逐句对照。

| 规则 | 取值 |
|---|---|
| 首行 | `Subject: ...`，便于与 HTML 主题行对照 |
| 第二段 | 一句「为什么收到这封邮件」 |
