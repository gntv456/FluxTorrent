# FluxTorrent 深度链路审计报告（2026-10-20）

> 视角：以「资深 PT 用户」身份在真实运行栈上逐条走功能链，查功能是否成立、
> 链路是否通；发现即修，修复即复跑验证。

## 0. 审计环境与方法

| 项 | 值 |
| --- | --- |
| 栈 | Postgres 16 + Redis 7 + flux-api(8080) + flux-worker + flux-web(3000) + flux-tracker(7070/6969) |
| 路由基线 | `docs/api/route-manifest.json` 共 819 条（社区域 92 条） |
| 前端覆盖 | 110 个覆盖层页面 |
| 账本口径 | `users.uploaded/downloaded` 只是快照，权威是 `traffic_ledger` + `balance_baseline`；魔力权威是 `spark_ledger` |
| 闸门 | 3 套 e2e 不变量套件 + 160 组经济/账本/功能闸门 + 13 个 node 守卫 + 读口巡检 + 前端巡检 |

方法：真实 HTTP 链路（非 mock）→ 库侧交叉核对 → 定位到代码 → 修 → 重跑同一条判据。

### P0-5 六条迁移按 CRLF 记账 → 干净检出/CI/官方镜像起不来

- **现象**：288/376/388/389/390/391 六条迁移，库里记的是**本地 CRLF 工作区字节**
  的 sha384，而仓库 canonical 形态是 LF（`.gitattributes` 有 `*.sql text eol=lf`，
  但它只管 checkout/commit，管不住编辑器「另存为 CRLF」）。
  于是本机构建恰好能起（工作区还是 CRLF），**干净检出的镜像起不来**——
  与 2026-09-16 那次同型事故（当时是 28/54/57/58/59/61）一模一样。
- **修复**：工作区六条归一 LF；`scripts/align_migration_checksums.sql` 补六条，
  按 **canonical LF 字节**重记校验和（内容逐行核对过：忽略行尾完全一致，
  重记不丢语义）。
- **预防**：审计脚本新增 **WORKTREE-NOT-LF** 判据（工作区字节 ≠ canonical LF 即红）；
  并修掉审计脚本自己的 CRLF 变体算法（原先 `b.replace(b"\n", b"\r\n")`
  遇到本来含 CRLF 的 blob 会算出 CRCRLF，把「行尾不同」误报成 CONTENT-MISMATCH）。
- **验证**：`python3 scripts/audit_migration_checksums.py` → **403/403 全对上，OK**
  （「干净检出/CI 构建可启」）。

### P1-6 psql 从 stdin 读 SQL 时**出错也返回 0** → 闸门假绿/假红的一整类

- **机制**：`psql` 用 `-c` 时出错返回 1；用 **stdin**（`-f -` / `input=`）时
  出错只把 ERROR 打到 stderr，**退出码仍是 0**。于是「只取 stdout、失败不抛」
  的闸门拿到的是**空串**而不是报错。
- **本轮实测被咬到**：隔离复现 H&R 阶梯限下时，探针 INSERT 写错了列名
  （`block_invoke` vs 真列 `block_invite`），psql 退出码 0、INSERT 静默没落库，
  复现得出「阶梯限下在位也会恢复下载权限」的**错误结论**，
  差点把 P-445 的正确设计当成缺陷改掉。
- **修复**：
  - `scripts/pt_audit_lib.py` 增 `psql_stdin()` 统一封装
    （`-v ON_ERROR_STOP=1` + rc≠0 或 stderr 含 ERROR 即抛）；
  - 25 个「只 print 不抛」的脚本改成 **raise**；
  - `pt_ci_api_sql_prepares.py` / `pt_ci_worker_sql_prepares.py`：argv 加
    ON_ERROR_STOP，且外层脚本失败要能归因（否则一条 PREPARE_FAIL 都没有 = **假绿**）；
  - 新增闸门 `scripts/psql_stdin_guard.py`（已接进 `scripts/ci_local.sh`）：
    psql stdin 形态的脚本必须「失败有信号」，否则红。
- **验证**：`python3 scripts/psql_stdin_guard.py` → OK（全部脚本都改到位）。

### P1-1 考核处罚闸门自己留悬空流水（HL1 判红）

- **现象**：`scripts/pt_audit_hl_ledger_fk.py` HL1 红——火花账本悬空 user_id

### P1-2 表面经济闸门 4 条恒红——闸门在测空气

- **现象**：`scripts/e2e_surface_economy_invariants.py` 长期 16/20，
  红的四条是：J3 RSS 命中该匿名种、J3b 条目里不出现上传者账号名、

- **根因（三个独立问题叠在一起）**：

  2. **RSS 取数窗口**：`/rss/{passkey}` 默认 50 条且按 `t.id` 倒序，
     探针种是装站时留的老种子，排在 50 条窗外 → 必然「命中 0 条」；
  3. **闸门硬删 users 行**：与产品「墓碑化」纪律冲突（180 处外键），
     还会再制造悬空流水。
- **修复**（只改闸门，不动产品口径）：
  - 脚本改为**自己现场注册**一个普通会员探针：走邀请码 + 自研算术验证码，

  - RSS 取数加 `showrows=200`（参数上限 200）把老种子纳入窗口；
  - 探针退场改走**产品自己的删号口**：先 `POST /admin/users/status` 封禁，
    再 `DELETE /admin/users/{id}` —— 服务端做墓碑化（status=3 +

    与产品纪律一致，不再出现悬空流水。
- **验证**：**20/20 通过**；探针退场后库里是墓碑态
  （`deleted-6874-xxxx` / status=3），HL1 仍绿，邀请码无残留。
- **推广**：同样的「写死 39 号」地雷在另外两套 e2e 里也有

  也不再有「硬删 users 行」的违规动作。

补测注册链路时确认的三条产品口径（不是缺陷，但容易误解，写在这里免得再踩）：

1. `captcha_provider=none` 的意思是「不用第三方验证码」，**不是「不用验证码」**——
   自研算术题（`GET /auth/captcha` 拿题 → 带 `captcha_id` + `captcha_answer` 注册）
   仍然是必填闸门，缺题或答错一律拒。
2. 管理员「增发邀请码」（`POST /admin/users/adjust` 的 `invite_grant`）是
   **直发有效邀请**（30 天有效），既不加 `quota_extra` 也不占邀请人周配额；
   `quota_extra` 走的是「发放道具项」那条口（`user_grant_item`）。
3. 同网络环境 24 小时最多注册 2 个号（`reg_ip_limit=2` / `reg_ip_window_hours=24`）。
   这条让「注册类闸门」天然不可重复跑，新增的闸门做法是：开跑前把限额临时放宽、
   收尾时原样还原，并把自己在 `reg_ip_signups` 里的占位行清掉。
