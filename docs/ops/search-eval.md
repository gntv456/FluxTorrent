# 搜索方案评估（E9）

> 结论先行：**当前 PG pg_trgm 方案继续用，不立项外置搜索引擎**。触发升级的
> 条件与路径见文末。本文是 E9 的评估归档，数字口径来自
> [性能基线](../../_doc/性能基线-2026-09-27.md)（dev 库，同环境前后对比用）。

## 现状能力（全部已上线）

| 能力 | 实现 | 备注 |
|---|---|---|
| 全字段模糊搜索 | ILIKE + pg_trgm GIN（中文友好） | 标题/副题/简介/文件名四域，search_area 分流 |
| 精确模式 | search_mode=2 等值 | NP 口径 |
| 同义词/别名 | E9：site_terms 联动（替换词→规范词 OR 扩展） | 上限 5 条，字符白名单防注入 |
| 排除词/发布者 | exclude/owner 独立参数 | 与关键字同转义 |
| 组合筛选 | 分类多选/维度/标签 all|any/促销/存活/审核态 | B3 批统一谓词 |
| 排序 | 六键 colhead + keyset 游标翻页 | 深翻页不衰减 |

## 为什么不现在上 meilisearch/ES

1. **量级未到**：dev 基线搜索 p95 <20ms；PT 站种子量典型 1-50 万，pg_trgm
   GIN 在这个量级 p95 通常 <100ms（本仓 tlist 缓存再兜一层）；
2. **一致性成本**：外置索引要维护「种子审核/软删/促销变更→重索引」管道，
   失败即搜索结果与列表不一致——这类分裂比慢更伤信任；
3. **运维面**：多一个有状态服务（内存/升级/备份），compose 栈复杂度 +1；
4. **竞品参照**：UNIT3D 用 Meilisearch 但 5 万+结果性能问题 2026-09 才修；
   NexusPHP 把 ES/Meili 做成可选件而非默认——默认形态两家都是 DB 搜索。

## 升级触发条件（满足其一再立项）

- 真实库（≥10 万种子）搜索 p95 > 500ms，且 tlist 缓存命中率无法再优化；
- 需要相关性排序（按相似度而非时间/做种数排序）成为产品诉求；
- 需要跨实体联合搜索（种子+论坛+用户一框出结果）。

## 升级路径（届时执行）

1. 先加 `search_provider` settings 键（none/meilisearch），代码留 trait 位；
2. 写侧：种子过审/编辑/下架事件 → 索引队列（复用 Redis Stream 基建）；
3. 读侧：`/torrents` 的 search 谓词按 provider 分流，DB 恒为兜底；
4. 带量基准：`scripts/perf_baseline.py` 灌 10 万种子前后对比归档。

## 同义词扩展的性能注记（E9 实现细节）

`site_terms` 规则每请求惰性查询（LIMIT 200，主键表点查级）；命中后至多
扩展 5 个 LIKE 模式、每模式 2-3 列 OR——在 trgm GIN 上是可下推的多键 OR。
若未来 terms 规模大到该查询可见，把启用规则物化进 Redis 缓存即可（低频变更）。
