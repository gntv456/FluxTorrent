# Wiki 建设方案（站内帮助中心 + 对外文档站）

> 面向站长：你想把已有的 51 篇文档变成一个 wiki 站点，读者是**站内用户**（帮助中心）和**外部站长/开发者**（文档站）两拨，内容既要能用 Git 管、又能后台编辑。
> 本文是**可执行方案**：架构、数据流、分期落地步骤都写清楚，每步都有取舍。核实日期 2026-10-03。

## TL;DR（赶时间看这版）

> **2026-10-04 更新：阶段 1、2、3 全部落地。** 站内帮助中心 `/help`（后台可编辑）+ 对外文档站 [wiki.ptang.top/ft](https://wiki.ptang.top/ft/)（docs-hub 多项目中枢，Git 权威，push 即发布）。只剩可选的阶段 4（草稿流）按需再做。

- **不新建 wiki 引擎**。用现成的 Next.js 站 + 现有基础设施做，成本从"几周"降到"一两天"。
- **分两个独立站**：
  - **站内帮助中心**（`/help`）：给注册用户看，**读数据库**，站长在后台可视化编辑。✅ **已上线**
  - **对外文档站**（独立子域如 `docs.你的域名.com`）：给站长/开发者看，**读 Git 里的 md**，改 md 提交即发布。
- **关键取舍**：两个站的**内容源不同**（站内=DB 可编辑，对外=Git 文件），这样两边各自用最顺手的维护方式，**不做 md↔DB 双向同步**（那是维护地狱）。

## 阶段 1 已落地：站内帮助中心怎么用

**已经在你的站上了**，访问 `https://你的域名/help` 即可看到 7 篇用户指南。

**站长的日常操作**（全部在后台，**不需要碰代码、不需要 Git**）：

1. 进后台「自定义页面」面板（管理员工具里那一项）。
2. 列表里 slug 以 `help-` 开头的就是帮助文档。改标题、正文、排序、上下线都在这里。
3. 想让某一篇出现在 `/help` 目录里 → **「帮助分组」填 `guide`**（留空就是普通页面，不进目录）。
4. 「组内排序」决定目录里的先后（1、2、3…）。
5. 单篇正文地址是 `/p/help-01-join` 这种。

> ⚠️ **一个必须知道的坑**：这个面板的保存是**全量覆盖**。如果你在别的页面（不是 `help-` 开头）上操作，不会影响帮助文档；但**编辑帮助文档本身时，「帮助分组」和「组内排序」两个框必须一起保存**——面板已经帮你带上了，正常保存即可。

**想把仓库里的 `docs/user/*.md` 重新灌一遍**（比如改了源文件）：

```bash
python scripts/import_user_docs.py --base http://127.0.0.1:8080
```

- **幂等**：按 slug 更新，不会重复建页；**不会**把你手动下线的页偷偷上线。
- ⚠️ 它会**覆盖** title/body/doc_sort——即**仓库是源、DB 是被覆盖方**。所以：**日常小修改直接在后台改（别跑脚本）；只有真要从仓库批量同步时才跑脚本。** 两种方式别混着来，否则会互相覆盖。

**已知边界（第一版没做的）**：

- 没有目录内搜索（站内全局搜索能间接命中，但 `/help` 页面本身没有独立搜索框）。
- 没有「草稿 → 发布」状态流转（草稿需求做方案二时再加）。
- 帮助文档没有独立权限（跟自定义页面一样，站长/管理员可编辑）。

## 二、两条路的取舍（为什么这么设计）

| 维度     | 站内帮助中心                     | 对外文档站                                 |
| :------- | :------------------------------- | :----------------------------------------- |
| 读者     | 你的注册用户                     | 别的站长 / 开发者 / 想二开的人             |
| 内容源   | **数据库**（后台编辑，即时生效） | **Git md 文件**（提交即发布，有版本历史）  |
| 更新方式 | 后台可视化编辑器                 | 改 md → `git push`                         |
| 权限     | 站长/管理员（登录态内）          | 公开                                       |
| 搜索     | 站内搜索（pg_trgm）              | 站点自带搜索（Nextra 内置）                |
| 部署位置 | 主站 `/help`                     | 独立子域或路径                             |
| 好处     | 随时改、用户即时看到、不用懂 Git | 版本化、可 PR、离线可读、GitHub 上直接可看 |
| 代价     | 无版本历史（除非自己加）         | 改完要会 Git                               |

> **为什么不把两边做成一份数据？** md 和 DB 双向同步要处理冲突、格式转换、删除传播，是典型的维护灾难。分开做，两个读者群各自用最顺手的维护方式，**互不牵制**。

## 三、方案 A：站内帮助中心（优先做，半天上线）

### 目标

把 `docs/user/` 七篇（用户指南）变成站内多页帮助，用户在 `/help` 看，站长在后台编辑。

### 数据模型（新增迁移 0274）

`custom_pages` 只能存单页、不分章节、不适合成套文档。**两个做法选一个**：

**做法 1（推荐，最省事）：复用 custom_pages + 目录页**

- 每篇文档 = 一个 `custom_pages` 记录（body 存渲染好的 HTML）。
- 章节导航 = 一个"索引页"，body 里手写链接列表，或用菜单系统（`menu_items` 已有树形 CRUD）挂导航。
- 零新表，直接给现有 `custom_pages` 加字段（如 `doc_group`、`doc_sort`）做分组排序。
- 工作量：迁移 + 导入脚本 + 一个前台 `/help/[slug]` 路由。**半天**。

**做法 2（重）：新建 `doc_pages` 表**

- 字段：`id / slug / title / body_md 或 body_html / group / sort / visible / updated_at`。
- 支持从 md 导入、后台编辑、以后可加"草稿/发布"状态。
- 工作量：迁移 + API + 后台管理页 + 前台路由。**1–2 天**。
- 什么时候值得：如果你想让帮助内容有**草稿→审核→发布**流程，或想存 markdown 源文。

> **我的建议**：**先做做法 1**（半天验证需求）。如果验证下来"后台编辑/发布流程"是真需求，再升级到做法 2（表结构兼容，只需把 custom_pages 迁到 doc_pages）。

### 落地步骤（做法 1）

1. **迁移 0274**：给 `custom_pages` 加 `doc_group TEXT`、`doc_sort INT`（默认 0），并把 `docs/user/` 七篇的 slug 预置进去。
2. **导入脚本** `scripts/import_user_docs.py`：读 `docs/user/*.md` → 转 HTML（用项目里已有的 markdown 渲染管线，前端若已有 md→html 就复用）→ 灌进 `custom_pages`。**idempotent**（重复跑按 slug upsert）。
3. **前台路由** `apps/web/app/(main)/help/`：
   - `page.tsx` = 目录页（列出所有帮助文档，按 group 分组）。
   - `[slug]/page.tsx` = 单篇正文（复用 `/p/[slug]` 的渲染逻辑，或直接复用组件）。
4. **搜索**：把 `doc_*` 页纳入站内搜索索引（pg_trgm 已在，照现有 FAQ 的做法挂进去）。
5. **后台管理**：在 admin 端加"帮助中心"管理（列表 + 编辑），复用 custom_pages 现有管理能力（若无则加）。
6. **导航**：菜单系统加"帮助"项指向 `/help`。

### 验收

- `/help` 能列出 7 篇；
- 点任一篇，正文完整、样式跟站内一致（走同一套 CSS 令牌，深色自动跟随）；
- 站长在后台改一篇，前台刷新即见；
- 站内搜索能搜到帮助内容。

## 四、方案 B：对外文档站（叠加，1 天）

### 目标

`docs/` 四册（webmaster/user/customize/ops）→ 一个带搜索/侧边栏/暗色主题的静态站，公开访问，GitHub 上也能直接读。

### 技术选型

- **Nextra 4**（Next.js 官方文档框架，和你现有 Next 技术栈同源）——推荐。
- 或 **VitePress**（Vue 生态，文档站体验最成熟）。
- 两者都自带：侧边栏、搜索（本地/Algolia）、暗色模式、静态导出。

> **建议 Nextra**：你主站就是 Next.js，Nextra 可复用设计令牌、React 组件，风格和主站统一；VitePress 更独立但风格要重调。

### 落地步骤

1. **新建 `apps/docs/`**（或独立仓库，二选一）：
   - 同仓库：目录隔离，CI 单独构建，产物挂 `docs.你的域名.com`。
   - 独立仓库：文档可独立发版，但版本同步要手动。**推荐同仓库**（改文档和改代码一起提 PR）。
2. **接现有 md**：`content_dir` 指向仓库的 `docs/`，或复制一份过去（推荐**指向**或软链，避免两份内容不同步）。
3. **配主题**：复用 TIDE/baozi 的暗色令牌（CSS 变量），让文档站和主站观感一致。
4. **部署三选一**：
   - **GitHub Pages / Cloudflare Pages**：零运维，push 即发布，**最省事**。
   - **加进现有 compose**：新容器跑 `next export` 产物 + Nginx，域名反代。适合要自控的。
   - **Nginx 直接托管静态导出**：最轻。
   > **建议先 Cloudflare Pages/GitHub Pages**，零成本验证；跑通了再决定要不要进 compose。
5. **加"编辑此页"链接**：每页底部放一个 GitHub 编辑按钮，直达对应 md 的 edit URL（读者贡献门槛最低）。

### 验收

- `docs.你的域名.com` 能打开，4 册目录清晰；
- 搜索能用（搜"announce"、"备份"能命中）；
- 暗色/亮色切换正常；
- 顶部有"这是文档站，主站在 xxx"的回站链接。

## 五、两站关系与一致性

- **不要互相同步内容**。`docs/user/` 是"用户指南"进站内帮助中心；对外文档站可以**也放** user 册（`/user`），但**由 Git 单一维护**，对外站从 Git 读、站内站从 DB 读——这是**两个副本**。
- **怎么办**：接受"user 册有 Git 副本 + DB 副本"的事实，但**只在一处编辑**：
  - 建议：**user 册的"权威版"是 Git md**；导入脚本负责同步到 DB（可挂 CI 定期跑或手动跑）。站长在后台改属于"临时覆盖/小修"，下次导入会被 Git 版覆盖（**要在后台编辑时提示"此页由仓库维护，下次导入会被覆盖"**）。
  - 或者：**user 册的权威版是 DB**；对外文档站不含 user 册（只放 webmaster/customize/ops 三册）。**这个最省事**，强烈推荐。

> **最终建议**：
>
> - 对外文档站 = `docs/{webmaster,customize,ops}` 三册，**纯 Git 维护**。
> - 站内帮助中心 = `docs/user/` 一册，**DB 权威**，站长后台编辑。
> - 两边不重叠、各自维护，零同步成本。

### 阶段 3 交付形态（与原计划的差异）

没有在 `apps/docs/` 自建 Nextra——升级成了**独立多项目文档中枢** [docs-hub](https://github.com/gntv456/docs-hub)（VitePress + GitHub Pages Actions，自定义域 `wiki.ptang.top`）：

- 本仓三册（webmaster/customize/ops）+ 总览共 **44 页**全量收录在 `/ft/` 前缀下，与本仓其他四个项目的文档合站；
- **内容不手写**：docs-hub 仓的 `scripts/sync.mjs` 从本仓 `docs/` 同步（本仓仍是唯一权威）。本仓文档改完 → docs-hub 跑 `node scripts/sync.mjs && npm run docs:build` → push 即发布；
- 决策不变的部分照旧：user 册不进对外站（DB 权威在站内）；push 即发布零运维。

> **日常更新口诀**：改本仓 `docs/` → commit push → 到 `D:\docs-hub`（或克隆处）`git pull` 不需要（sync 直读本地盘）→ `node scripts/sync.mjs && npm run docs:build` → commit push，Pages 1 分钟内自动上线。
>
> 已知坑（2026-10-04 实战）：md 正文/围栏里出现 `{{...}}`（如 `docker inspect --format '{{.State.Error}}'`）会被 Vue 当 JS 表达式炸构建——sync.mjs 已内置转义（正文包 `v-pre`、行内代码插零宽空格），再遇到同类报错先查 sync 是否跑过。

## 七、已拍板的决策（2026-10-03）

1. **user 指南不两边放** ✅ —— 对外站只放 webmaster/customize/ops 三册，user 册只在站内（DB 权威）。**零同步成本**。
2. **对外站托管用 Cloudflare Pages / GitHub Pages** ✅ —— 零运维，`git push` 即发布。
3. **站内帮助中心用做法 1** ✅ —— 复用 `custom_pages` + 0274 迁移，不新建表。草稿流留到有真实需求时再升级。
