# FluxTorrent 契约与架构成熟化策划案（FRAME-PLAN-01）

> 成文：2026-10-13 · 文档编号 FRAME-PLAN-01 · 姊妹篇：`docs/design/design-system-plan.md`（DS-PLAN-01 v3）
> 目标一句话：**把「725 条路由配 3.7% 契约覆盖、设计意图存在于对话里」的后端，建成契约驱动、分层清晰、可长期演进的自部署 PT 引擎**——对标报告 §3 判定的"差距最大的一项"，目标是从 3.7% 走到 100% 机器可读，并且让契约反过来约束与驱动开发。
>
> 定位：DS-PLAN-01 管"看得见的现代"（UI/性能），本方案管"看不见的顶级"（契约/框架/逻辑）。两案共享 §10 流程规范与门禁哲学（只许向好）。

---

## 0. 设计意图

### 0.1 三条意图（每条带反面边界）

**意图一：契约是单一真源，代码与文档从契约生成，不是相反。**
现状：`/api/v1/openapi.json` 手写 serde_json 27 条（spec.rs 13 + spec_np.rs 14），门禁 check_type_drift 只能防 8 条手写契约的正则对拍；其余 698 条路由的类型真相散在 handler 签名与 TS 手写类型里。同类站 14 天写出 312 个带生命周期标记的操作，我们 344 个迁移攒出的体量反而没有机器可读清单。
*不做什么：不搞"一次性全量 utoipa 化"——725 条路由的大爆炸迁移必然烂尾。分域推进（§3），每域完成即进门禁。

**意图二：错误码即契约。**
我们的数字错误码体系（21 变体→20 码，TS 侧 25 常量）是比对方字符串码更强的资产——可枚举、可门禁对拍、可分段。要做的是把"错误码 ↔ 触发条件 ↔ 用户文案"三元组变成机器可查的注册表，让 `check_type_drift` 从"防 8 条"扩到"全量对拍"。
*不做什么：不改信封形态（`{code,message,data,request_id}` 已上线且稳定）；不追求 REST 纯度（NP 兼容层保持原口径）。

**意图三：架构分层有宪法，不靠自觉。**
24 个 `*_http/` 域包是健康的地域划分，但层间依赖无约束（handler 直写 SQL 与业务逻辑混居是常态）。本方案给出分层规则并交给 cargo workspace 结构 + 门禁强制。
*不做什么：不推倒重来重写 handler——按"触碰即迁移"纪律渐进抽离，同 DS-PLAN 的存量哲学。

### 0.2 非目标

- 不换框架（actix-web 4 保持）；不换数据库；不改既有 API 路径与信封（兼容层契约不动）；
- 不做 GraphQL（REST+OpenAPI 已够，多范式是维护负担）；
- 微服务化不做——G30 多机部署方案已定，单体多实例是既定架构。

## 2. 目标架构（分层宪法）

```
┌─ H 路由层 *_http/        只做：参数解析、鉴权调用、信封包装。禁止 SQL、禁止业务判断
├─ S 服务层 src/services/   用例编排：一个用例一个函数（跨表事务、副作用调度）。禁止 HTTP 词汇
├─ D 领域层 src/domain/     纯逻辑：判定/公式/状态机（已有 seeding 公式在 DB 函数的先例，应用层同思路）
├─ R 仓储层 src/repo/       SQL 唯一居住地（已有 repo/ 底子，扩容）
└─ C 契约层 openapi_http/ + domain-types   机器可读真源，H 层从中生成/对拍
```

宪法条款（进 CONTRIBUTING + cargo 层面用 workspace 成员隔离 + 门禁 grep 强制）：
1. H 不 import sqlx（除 repo）；2. S 不 import actix；3. D 不 import 两者；4. 所有新端点先在契约层登记（schema+错误码+分页口径）再写 handler——"契约先行"从纪律变成流程顺序。

**H 禁 SQL 存量棘轮的登记与收缩（2026-10-14 补记）**

`scripts/layer_baseline.json` 现登记 **367 个 H 层文件 / 2279 处 sqlx 引用**——
这是 §0.1「分层宪法对存量是方向不是现状」的量化底数。本次处置一例：

| 文件 | 变更 | 理由 |
|---|---|---|
| `admin_p3_http/jixiao_reads.rs` | 登记 **=4** | 批六十六按 300 行门禁从 `jixiao_ops.rs` 拆出的**读口**；4 处 `sqlx::query_as/query_scalar` 属**存量搬迁**（非新增），该文件头注释已自述拆分缘由 |
| `admin_p3_http/jixiao_ops.rs` | **8 → 4** | 母文件被拆走 4 处，计数按实收缩 |

一条 sqlx 引用都没变多（8 = 4 + 4），拆分时**漏跑 `--update`** 才让门禁报
「新文件零容忍」。**新增 H 层文件仍零容忍**——不在基线者直接拦，不进基线。

## 3. 契约工程五步（分域推进，每域独立 PR 线）

| 步 | 内容 | 完成判据 |
|---|---|---|
| ① 域清单生成器 | 写 `scripts/route_manifest.mjs`：从 mount 函数静态提取全部路由→方法→handler 名，产出 JSON 清单（不依赖 utoipa 先拿到"路由真相"） | 725 条全量清单入库，与 cargo check 联动防漂移 |
| ② 错误码注册表 | errors.rs 加 `#[derive(IntoStaticStr)]`+触发条件注释 → 脚本导出 `docs/api/error-codes.md` + TS 常量自动生成（替换手写 25 常量） | check_type_drift 从 8 条扩到全量错误码对拍 |
| ③ utoipa 域试点 | 选 compat 层（8 条 NP 路由+已有手写 spec 的 14 条）做首个 utoipa 化域：handler 加 `#[utoipa::path]`，spec.rs 手写版改为生成物 | 兼容层契约 100% 生成，spec.rs 删除手写路径 |
| ④ 分域推进顺序 | 开放 API（tokens/download_keys/rss tokens，~15 条）→ 认证与 me 域（~30 条）→ 种子读写域（~60 条）→ 其余域按流量 | 每域完成即扩门禁：该域路由必须在 openapi.json 出现 |
| ⑤ 消费端闭环 | 前端类型从 OpenAPI 生成（openapi-typescript）替换手写 TS 接口，按域替换不搞全量 | 前端手写接口类型归零（分域） |

不追求 同类站 的 `defined`（已定未实现）标记——那是 roadmap 工具不是契约工具；我们的路线是"实现的必须是契约，契约必须可实现"。

## 4. 逻辑层治理（消灭"双入口纪律"）

review.rs 与 review_batch.rs 需要人工同步计数逻辑（0288 纪律）、H&R 赦免三口合并（批四十三 P-165）——这类"同一用例多处实现"是 bug 之源。治理：

1. **用例函数化**：每个写用例在 services/ 有唯一入口（`review_decide`、`hr_pardon` 已在批次中自然形成），路由层只做参数适配；
2. **事务边界声明**：用例函数签名带 `tx` 或自管事务，禁止路由层裸开事务；
3. **副作用清单化**：过审副作用（自动促销/订阅推送）这类多副作用用例，副作用清单进函数文档注释，新增副作用必须改清单（防漏发）；
4. **状态机显式化**：种子 5 态、工单 4 态这类状态迁移，判定收进 domain/ 纯函数 + 单测矩阵（当前迁移条件散在 SQL WHERE 里，改规则要读三处）。

---

## 5. 推广项（已完成域的横向复制）

- **乐观并发**：设置域的 expected updated_at 模式推广到——HR 规则（torrent_batch 的 hr_policy 写入）、版主配置、促销 intent 审批（0356 已有 revision 基础）；
- **幂等头**：13 个端点已支持 Idempotency-Key 头兜底，写类新端点一律默认支持（流程 §10.3 PR 清单加一条）；
- **审计语义声明**：管理端写操作的审计 action 命名规约（`域.动作`）统一，为审计检索界面打地基。

## 7. 达标验收清单（"契约/框架/逻辑顶级"的可判定定义）

1. 路由清单 100% 机器可读且防漂移过 CI；
2. 错误码注册表自动生成文档与 TS 常量，drift 门禁全量覆盖；
3. compat 层 + 开放 API 域契约 100% utoipa 生成（手写 spec 归零），其余域覆盖率门禁只升不降、终态 ≥80%；
4. 分层宪法三条进门禁且红测有效（故意违规必被拦）；
5. review_decide / hr_pardon 型"双入口"归零（用例函数唯一化）；
6. 状态机迁移判定全部进 domain/ 纯函数且有迁移矩阵单测；
7. 乐观并发覆盖全部"先读后写"配置域；写类新端点默认幂等头；
8. 前端接口类型按域从 OpenAPI 生成（手写归零分域推进）；
9. 审计 action 命名规约统一且 lint 可查；
10. 冷启动课题立项有结论（迁移合并/基线快照二选一，允许结论是"维持现状+文档化"）。

### 7.10 冷启动课题结论（2026-10-13 立项评审，结论：A 维持现状+文档化）

实测数据（本地栈 flux-postgres / flux-api，359 个迁移全部应用）：

- 迁移体积：`apps/api/migrations` 共 359 个 SQL 文件、约 1.8 MB；
- `_sqlx_migrations.execution_time` 记录的**累计**执行时间约 10,696 s
  （~2.97 小时）——但这是**有数据库上增量回放**的口径：top 5 慢迁移
  （init 663 s、partitions 601 s、arcade fishing 208 s…）全是建表后
  backfill/索引构建，慢在数据量不在 DDL 数量；
- **空库冷启动**（新装场景）与此不同：本地栈 flux-api 容器健康重启的
  观测日志显示，迁移表已就位时启动到 listening 仅 ~0.06 s（`relation
  "_sqlx_migrations" already exists, skipping` → `listening on 0.0.0.0:8080`
  同秒内完成）。空库首装 359 个迁移的 DDL 段（建表/约束/索引）按
  install_e2e 装站闸门的既有实测为**数十秒量级**，且只发生在首次部署；
- 执行模型（main.rs 迁移段）：`sqlx::migrate::Migrator::new(dir).run()`
  一次性顺序跑全部未应用迁移，**非逐文件独立事务**——sqlx 的 run 对
  非事务性迁移（本仓 `.sql` 文件无 `-- no-transaction` 标记的默认路径）
  在单连接上按文件顺序执行并逐条记 checksum，失败即中止。
  `FLUX_BOOT_MIGRATIONS=0` 已提供多副本滚动启停的跳过开关。

三选项评估：

- **A 维持现状 + 文档化（推荐）**：冷启动数十秒仅首次部署/空库装站
  可感知，日常重启（迁移已应用）零成本；升级路径保持 sqlx 原生
  （checksum 对账、advisory lock、失败中止语义全继承）；359 个文件
  的 git 历史与 `audit_migration_checksums.py` 对账工具链无需任何
  改动。风险仅在于「新环境首装慢」，由 install_e2e 装站闸门覆盖
  验证。**本结论段即该选项的文档化部分。**
- **B 迁移合并成基线快照**：把 359 个文件 squash 成一个
  `0001_baseline.sql`。收益：首装 DDL 一次执行、文件数归一；
  风险：sqlx 的 `_sqlx_migrations` checksum 对账机制需整体重写
  （存量库的 359 行历史记录与单一 baseline 无法对上，要么清表重放
  ——生产库不可接受，要么双轨记账——对账工具 `audit_migration_
  checksums.py` 与 `align_migration_checksums*.sql` 三套脚本全部
  重做）；迁移文件的 git blame/评审链断裂。收益（省数十秒首装）
  远不抵风险。
- **C squash 只读归档（折中）**：旧迁移移入 `migrations/archive/`
  不再参与执行，新装走导出的 baseline 快照，存量库走原路径。
  问题：同一 schema 两个真值来源，恰是 FRAME 全程在消灭的形态
  （对照 §4 双入口、0159 标签双写）；且 baseline 快照需要一套
  「从活库导出并对拍」的维护纪律，否则每月漂移。

**结论：A。** 冷启动成本是首装一次性且被装站闸门覆盖的，B/C 的
复杂度都会落在「对账机制重写/双真值维护」这两个本方案明确对抗的
方向上。触发重评条件：若未来单次空库装站超过 5 分钟，或迁移数
翻倍导致 CI/装站闸门时长不可接受，再按本节三选项重新评审。
